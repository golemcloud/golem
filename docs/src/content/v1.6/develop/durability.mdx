# Control durability guarantees

Durable agents record host interactions in the oplog. Recovery replays completed calls from their
recorded outcomes and repairs an eligible incomplete call at its own `Start`. It does not rerun a
group of completed effects. Guests cannot disable recording or change the execution cursor.

Use [SDK sagas](/v1.6/develop/transactions) for workflows that need compensation. Use
[retry policies](/v1.6/develop/retries) for retryable host operations. A trap is permanent;
return an error for a transient condition and use a retry schedule. Throwing after an HTTP response
does not retry that completed request.

A Rust panic is permanent, including inside code that formerly used `atomically`. It no longer
retries the block or rewinds completed effects.

## Remote-write safety

Golem treats remote writes as eligible for re-execution. An incomplete call can therefore be
retried even when the peer might already have applied it. External exactly-once behavior requires
the peer to enforce an idempotency key; a header alone is not a guarantee.

There is no guest idempotence-mode switch. Make writes duplicate-safe at the peer before relying
on retries or crash recovery. A lost response does not prove the write failed. Retry predicates
must not use `is-idempotent`: the host no longer supplies that property.

## Custom durable operations

The low-level `golem:durability@1.6.0` interface is for SDK and library authors. Its live resource
groups raw observational host effects into one logical call with a typed request and response.
Finishing the resource records the result; replay returns that result without evaluating the
body. Dropping it unfinished does not trigger a retry. Recovery of an eligible incomplete custom
call reruns its whole body, so the library must make repeated attempts safe.

Use the SDK combinator rather than managing the resource manually. See
[custom durable invocations](/v1.6/develop/additional) for the lifecycle and SDK entry points.

**TypeScript, Effect, Scala, MoonBit, and Go: sequential execution only.** In these SDKs, a custom operation's execution scope remains installed while its body waits. Do not run unrelated guest work concurrently with it, including ordinary host calls or another custom operation. A sibling's effects can be attributed to the wrong operation, causing incorrect replay or invocation failure. The SDKs do not reliably detect this misuse.

Sequential and properly nested custom operations remain supported. An asynchronous body can await host operations when no unrelated guest work runs during those waits. For example, a library can perform a sequence of remote calls and persist one typed result. Complete one custom operation before starting the next; await each nested operation before continuing its parent.

Do not leave detached promises, fibers, futures, tasks, goroutines, or callbacks running after the body exits. This applies to failure and cancellation as well as success. Stop and join outstanding work before closing the operation. A fail-fast combinator such as `Promise.all` does not join surviving siblings on rejection, and joining at the end does not make concurrent custom scopes supported.

| SDK | Custom operation restriction |
| --- | --- |
| TypeScript | Use `durable` sequentially; do not overlap it with other promises or callbacks. |
| Effect | Use `Durability.wrap` and `wrapInfallible` sequentially; do not overlap them with other fibers or concurrent effects. |
| Scala | Use `DurabilityApi.durable` and `durableAsync` sequentially; do not overlap them with other futures or callbacks. |
| MoonBit | Use `@api.durable` and `durable_async` sequentially; do not overlap them with other tasks. |
| Go | Use `durability.Run` sequentially; its blocking body can yield to other goroutines, so a synchronous-looking call is not a concurrency safeguard. |

These restrictions concern custom durability in the five SDKs above, not ordinary built-in durable HTTP/RPC APIs or the Rust scope integration.

## Nonresumable handles

A live connection is not durable state. Nonresumable handles report typed loss after
reconstruction. Handle the loss by explicitly opening and initializing a new session. Do not
silently resend pending traffic: loss does not prove that an earlier write never reached the peer.
See [WebSockets](/v1.6/develop/websocket) for the supported reconstruction policies.

## Commit oplog

`oplog-commit` waits for replication before execution continues. It is a replication barrier,
not a transaction commit for external services, and it does not undo any effect.

## Operator recovery

External operators can [revert or fork an agent](/v1.6/cli/agents) at validated oplog cuts.
These are management operations, not guest-code retry primitives. They do not undo effects
already applied by an external service. Reconcile those effects before repeating business work.
