# Deployment

Golem Services are distributed as Docker images. They are available in [Golem Services Docker Hub](https://hub.docker.com/u/golemservices). Each Docker image is built for the following architectures:

- linux/amd64
- linux/arm64

The services are using the following storage backends:

- Relational Database (RDB) - [PostgreSQL](https://www.postgresql.org/) or SQLite (for running locally)
- [Redis](https://redis.io/)
- Blob storage - Shared File System or S3
- [etcd](https://etcd.io/) - optional, only for the shard manager's distributed mode

## User and Permissions

Every image runs its service as the user `golem`, uid and gid 65534, with the home directory `/home/golem`. The default configuration keeps local data below `/data`, which belongs to that user: SQLite databases in `/data` and file system blob storage in `/data/blob_storage`. The services need no Linux capability.

A path that a service writes must belong to uid 65534, or be writable by it:

- A new Docker named volume mounted at `/data` or `/data/blob_storage` takes the owner of that directory in the image, so it needs no change.
- A bind mount takes the owner of the host directory. Give the directory to the user before the first start, for example with `chown -R 65534:65534 <host directory>`.
- In Kubernetes, set `runAsUser`, `runAsGroup` and `fsGroup` to 65534 in the pod `securityContext`. The kubelet then makes a volume that supports ownership management, such as an `emptyDir` or a persistent volume, writable by group 65534. A `hostPath` volume keeps the owner of the host directory.

Run the services with no capabilities and without privilege escalation: `--cap-drop ALL --security-opt no-new-privileges` with Docker, `capabilities.drop: [ALL]` and `allowPrivilegeEscalation: false` in Kubernetes. Only `xfs-quotad`, a separate process that `ManagedXfs` agent filesystem storage needs, holds a capability, `CAP_SYS_ADMIN`. Its image, `golemservices/golem-xfs-quotad`, also runs as uid 65534; see [Run xfs-quotad](/v1.6/operate/filesystem_snapshots#run-xfs-quotad).

## Golem Services

The following sections provide a description of each service.

### Registry Service

[golem-registry-service](https://github.com/golemcloud/golem/tree/main/golem-registry-service) manages accounts, applications, environments, components, plugins, tools, policies, and related registry data in the relational database and blob storage.

See also: [configuration](https://github.com/golemcloud/golem/blob/main/golem-registry-service/config/registry-service.toml), [environment variables](https://github.com/golemcloud/golem/blob/main/golem-registry-service/config/registry-service.sample.env), [docker image](https://hub.docker.com/r/golemservices/registry-service)

### Worker Service

[golem-worker-service](https://github.com/golemcloud/golem/tree/main/golem-worker-service) provides APIs and [HTTP gateway](/v1.6/operate/architecture#the-gateway) functionality for agents and acts as a routing service for worker executors. It retrieves gateway definitions from the registry service, uses blob storage for initial agent files, and stores gateway sessions in Redis or SQLite.

See also: [configuration](https://github.com/golemcloud/golem/blob/main/golem-worker-service/config/worker-service.toml), [environment variables](https://github.com/golemcloud/golem/blob/main/golem-worker-service/config/worker-service.sample.env), [docker image](https://hub.docker.com/r/golemservices/golem-worker-service)

### Worker Executor

[golem-worker-executor](https://github.com/golemcloud/golem/tree/main/golem-worker-executor) is responsible for running the [agents](/v1.6/concepts/agents) that belong to assigned shards. The service keeps each agent's oplog in **indexed storage** - PostgreSQL, SQLite or Redis - and uses key-value and blob storage alongside it.

See also: [configuration](https://github.com/golemcloud/golem/blob/main/golem-worker-executor/config/worker-executor.toml), [environment variables](https://github.com/golemcloud/golem/blob/main/golem-worker-executor/config/worker-executor.sample.env), [docker image](https://hub.docker.com/r/golemservices/golem-worker-executor)

### Shard Manager

[golem-shard-manager](https://github.com/golemcloud/golem/tree/main/golem-shard-manager) maintains the worker executors' shard assignments. It runs in one of two modes, selected by the `persistence` configuration:

- **Local mode** (`persistence.type = "Postgres"` or `"Sqlite"`) stores the shard state and the quota state in one SQL database. There is no leader election, so **exactly one instance may run**.
- **Distributed mode** (`persistence.type = "Etcd"`) stores the shard state in etcd. Any number of replicas may run: one wins an etcd lease campaign and drives all topology decisions while the rest stand by. The quota state lives in etcd too, under `/golem/quota/`, and a newly elected leader restores it, so executors keep the quota leases they hold across a failover. Switching an existing deployment from local to distributed mode does not carry the quota state over: executors acquire their leases again, and capacity budgets start from their full limit.

Every worker executor holds a **lease** on its shard assignment and renews it with the shard manager. A lease lasts `shard_lease_duration` (1m by default) and an executor renews at a third of the time it has left, so roughly every 20s. The shard manager refuses to start with a lease shorter than 30s and warns about one shorter than 1m: the deadline it allows each renewal call never drops below 10s, so a shorter lease cannot fit the three renewal attempts a lease is meant to get. Each renewal carries the epoch of every shard the executor holds; a shard's epoch is its ownership generation, advanced only when the shard moves to another executor and never by a renewal. A renewal whose claim does not match the shard manager's view is renewed all the same, and the response carries the shard manager's set, which the executor adopts exactly as it would an assignment push: pushes deliver a change at once, and renewals guarantee it arrives within a third of the lease even if the push was lost. The shard manager records a shard's new owner before it tells anybody about it, so a rebalance whose write is refused changes nothing at all, and every delivery carries the revision of the state it was read from. An executor ignores a delivery older than one it has already applied, so a push and a renewal that cross on the network cannot leave the older set in place. Revisions are only comparable within one shard manager process, so every delivery also names the process that sent it: an executor follows the process that answered its latest registration or renewal and starts its revisions over when that changes - which is how a shard manager that failed over, or came back on a wiped or restored store, gets its sets applied although its revisions start lower - and it ignores a push from any other process, renewing at once to hear from the one in charge. An executor that stops renewing loses its lease, and the shard manager reclaims and redistributes those shards on its next pass, which runs at least every third of `shard_lease_duration` even in a cluster where nothing else is happening; a crashed or unreachable executor's shards are therefore re-homed within about one lease duration plus one pass. The lease reaches the executor as the time remaining on it rather than as an absolute time, so the two machines' clocks are never compared and skew between them can neither lengthen nor shorten it. The executor anchors that time to the moment it sent the request the lease answers, so time the reply spends in flight comes off its copy of the lease and is never added to it, and its copy lapses no later than the shard manager's. An assignment push carries the shard set and its revision only: it never extends a lease. The lease is the one place the two machines' clocks must agree on a rate rather than on a value: an executor whose clock runs slow relative to the shard manager's keeps admitting for that fraction of a lease past the shard manager reclaiming it, which is milliseconds under ordinary `ntp` or `chrony` discipline and seconds while such a daemon is slewing off a large offset, so an executor should not be started until its clock is synchronised. An executor whose own copy of the lease has expired stops **admitting** new work for its shards and reports that sharding is not ready, which a worker service retries after refreshing its routing table - invocations already running are not interrupted. A graceful stop - including the `SIGTERM` an orchestrator sends to stop a pod - deregisters the executor instead of waiting for its lease to expire, so its shards move on the next pass. A shard manager restart or failover restarts the lease of every executor it takes over, so a restart never evicts a healthy cluster. While every stored lease is still valid, which is the normal case after a crash, the new leader skips the startup health check and restarts all of them; an executor that is dead is removed by the periodic health check (`health_check.delay`, 10s by default) about 10s later. After a longer outage the new leader checks the executors first, for at most `initial_health_check_timeout`, and removes the ones that fail. An executor whose own copy of the lease lapsed during the outage resumes admitting work on its next successful renewal rather than on the push that follows the re-grant, and neither a re-grant nor a renewal ever moves an executor's deadline earlier, so a `shard_lease_duration` reduced across a restart takes effect only once the new length outruns the deadline each executor was last told.

The lease bounds how long a lost shard keeps being served, but it cannot stop an executor that has already lost one from finishing a write it had started. That is what **oplog fencing** is for. Each agent's oplog records the shard epoch allowed to write it, and every batch of entries is checked against that record atomically with the insert - in the same database transaction, or on Redis in the same script - so a refused write leaves nothing behind. An executor whose epoch is behind is turned away at the storage rather than discovering the problem later: that one agent stops there, and the worker service resumes it on the shard's new owner. The record only ever moves forward - an executor re-granted the shard at a higher epoch takes over, and one holding a stale epoch cannot claim it back - and an absent record fences an open oplog too, because the record is written before an oplog's first entry and removed before its last. That protection covers an oplog whose record exists. Deleting an agent removes its record and forgets the epoch with it: an executor that still has the oplog open is refused, but an oplog without a record - a new agent, a deleted agent created again, or one last written before this release - is claimed by whichever epoch opens it first, so for those only the lease stops an executor that has lost the shard. The archive layers that older oplog entries move into are fenced the same way, and so are ephemeral agents' oplogs, which are written straight into them. Blob storage has no conditional write, so an archive layer in blob storage keeps a list of its chunks in the indexed storage, fenced like the rest, and reads only the chunks listed there; archive chunks written to blob storage before this release are not listed, and are no longer read. Fencing covers the oplog and nothing else. An executor that has lost a shard can still write that agent's key-value records, its status and its blob payloads, none of which carry an epoch: a stale status blob can overwrite a newer one until the agent's next status change on its new owner, while the oplog - the only record replay reads - stays correct. Nor does the fence undo what has already left the machine: an outgoing call an agent made before its first refused write has happened, and the shard's new owner, having no record of it, makes it again, which is the same at-least-once exposure a crash between the call and its oplog entry already has. A call the executor has not started yet is refused once the fence has latched, so the window is the call in flight rather than every call after the shard moved.

Fencing is enforced by every indexed storage backend, for deleting an agent as much as for writing to it: a deletion that finds another executor has taken the agent over removes nothing, and fails with the answer that sends it to the new owner. A deletion under way when its shard moves may be finished by the shard's new owner instead. The shipped configuration defaults `indexed_storage` to a SQLite file of its own, which serves a single executor; executors that share shards need storage they can all reach, which means PostgreSQL or Redis, because a SQLite file is written by one process. Redis is only as durable as the last write the server kept: a failover that loses the most recent writes can lose a raised epoch with them, and the previous owner is then accepted again until the record is next raised, so prefer PostgreSQL or SQLite where that window matters. Redis Cluster is not supported. `KVStoreSqlite` and `KVStoreMultiSqlite` derive their location from the key-value storage, so they require `key_value_storage.type` to be `Sqlite` or `MultiSqlite` respectively; any other combination fails at startup.

A shard epoch only means something against the shard manager state that minted it. A state that is wiped, replaced or restored from a backup mints epochs below the ones the oplogs already record, and the storage refuses every write at those, so the affected agents stay unavailable until their records are cleared. To clear them, stop every executor, run `DELETE FROM indexed_key_epoch` on the indexed storage - for `MultiSqlite` and `KVStoreMultiSqlite`, on every `*-oplog-*.db` file under the root directory; on Redis, delete the keys matching `*oplog-epoch:*` instead - and start the executors again; each oplog records its owner's epoch when it is next opened. Run the delete only while no executor is running, because an oplog without a record accepts whichever executor opens it first.

Distributed mode talks to etcd over **plaintext HTTP** and without authentication. Every entry in `persistence.config.endpoints` must start with `http://`; a replica configured with anything else refuses to start. etcd therefore has to be reachable unauthenticated, either on a trusted network or through a TLS-terminating proxy running alongside the shard manager, with the endpoints pointing at that proxy.

Give `persistence.config.endpoints` a **single load-balanced address** - the Kubernetes Service in front of the etcd cluster - rather than a list of members. With a member list the client keeps a member that is down in its rotation: reads retry through it and recover, but writes do not, and a leadership campaign can spend tens of seconds landing on the dead member before it gets anywhere.

Every write to the shard state or the quota state is a new etcd revision, and etcd keeps every revision of a key until it is told to compact, so a leader that renewed leases forever would fill etcd's backend. The leader therefore **compacts** the history behind the state after each of its passes, keeping the newest `persistence.config.compaction_retention_revisions` revisions (1000 by default). Compaction is cluster-wide: it drops that much history for every key on the etcd cluster, not only the shard manager's. On a cluster shared with other applications set it to `0`, which disables it, and leave compaction to the cluster's operator or to etcd's own `--auto-compaction-mode`.

A quota lease change is stored as one etcd transaction: the resource, the lease, and one delete for each expired lease the change reclaims. The shard manager reclaims at most 120 expired leases per change, so a transaction holds up to **122 operations**, and the etcd cluster must accept at least that many. etcd's default `--max-txn-ops` of 128 does. On a cluster configured below 122, a change that reclaims many expired leases at once is refused, and so is every later change to that resource.

`persistence.config.request_timeout` must be at most half of `persistence.config.leader_lease_ttl`, and startup refuses the configuration otherwise. A lease is granted and its keepalive opened back to back, each bounded by the request timeout, so a larger value could let a lease expire before it was ever renewed.

**Failover** in distributed mode costs a graceful stop almost nothing: on SIGTERM or Ctrl-C a leader releases its lease and a standby takes over within milliseconds, and a standby stopped the same way leaves the election queue at once. The new leader still has to run its startup, so a graceful handover is fast for the election but not free. A leader that is killed or partitioned releases nothing, so it holds its lease until etcd expires it and a standby is elected between two thirds of `persistence.config.leader_lease_ttl` and the full value (10s by default) after that leader's last renewal. Then the new leader runs its startup. When every executor lease stored in etcd is still valid, which is the normal case after a crash, the startup skips the executor health check and the leader serves almost at once. After a longer outage it checks the executors for at most `initial_health_check_timeout` (3s by default). A broken etcd connection is not a failover: an etcd member restart or a raft leader change ends the keepalive stream and the leader reconnects it, so only etcd declaring the lease gone, or a full lease period with no acknowledged renewal, ends a leadership.

During that window no replica serves: the replicas answer `UNAVAILABLE`, and name the old leader until its lease expires. Clients keep asking and reach the new leader once its startup has completed. A worker service does not ride the window out on a warm routing table cache: the first executor-level error it hits discards the cached table, and the worker service then waits until a leader serves again. A worker executor that starts inside the window retries its registration for about 10s in total with the default `shard_manager.retries` and exits when that budget runs out, so raise `shard_manager.retries.max_attempts` on the executors if their startup has to survive a shard manager failover.

The worker executors and worker services wait out a failover by themselves, so no client setting needs tuning for it. A call that may be repeated keeps asking for about 15s once a replica has named a leader that cannot be reached, or a replica itself answers `UNAVAILABLE`, and the 15s count from the start of the call; if the `shard_manager.retries_on_unavailable` schedule takes longer than that in all, the call keeps asking for that long instead. This covers one lease TTL plus the startup with the default settings. While no replica names a ready leader, such a call therefore waits up to about 15s before it fails. A shard manager that cannot be reached at the configured address at all is not a failover, and `shard_manager.retries_on_unavailable` still decides how long the client keeps trying there, as it does for any other failure. A call that must not run twice is not repeated.

A registration is persisted before it is acknowledged, so an executor that receives a successful registration response holds a lease the next leader will find. A registration that could not be persisted - because the leader lost its lease part-way through the write, for instance - is answered with an error instead, and the executor retries it within its `shard_manager.retries` budget.

In distributed mode **every replica serves its gRPC port** (`grpc.port`) from startup, and only the leader runs calls. A standby answers each call with `UNAVAILABLE` and a `golem.shardmanager.v1.NotLeader` detail that holds the leader's host and port (`leader_host`, `leader_port`). It takes that from an in-memory view of the etcd election, so a call does not read etcd. The worker executors and worker services follow the detail: they connect to the leader directly and keep using it until a call to it fails, when they ask their configured address again. The leader publishes its address only once its own startup has completed, so a client is never sent to a leader that cannot serve yet. Other tools, such as `grpcurl` or your own scripts, must follow the `NotLeader` detail themselves.

A Deployment or StatefulSet `RollingUpdate`, health gates such as Helm `--wait`, Flux `wait: true` or Argo, and a PodDisruptionBudget work with these replicas. Use two different probes on the HTTP port (`http_port`):

- **Readiness:** `/readyz`. It answers 200 while the replica serves. For a leader that means while it believes it holds its lease. For a standby it means while etcd has answered it within one lease TTL. Otherwise it answers 503, and it also does so during the replica's startup. In distributed mode a replica is also not ready until it has reached its own advertised address once: a TCP connection to the advertised host and port and, when gRPC TLS is off, a gRPC health check. With gRPC TLS on, only the TCP connection is made. The replica tries again every second. While it fails, the log has a warning that names the address, so a wrong `grpc.advertised_host` or `grpc.advertised_port` shows up as a replica that never becomes ready. A setup in which a pod cannot reach its own externally advertised address, such as some NAT or port-mapping layouts, keeps the replica unready.
- **Liveness:** `/healthcheck`.

The gRPC health service reports the overall status `""` as SERVING on every replica. The service name `golem.shardmanager.v1.ShardManagerService` is SERVING only on the replica that serves. Routing by a leader label is not needed.

A `kubectl port-forward` to the Service can land on a standby. Its answer then names a pod IP that a laptop cannot reach. Port-forward to the serving pod instead, which is the one whose `/metrics` shows `shard_manager_is_serving 1`.

Each replica must set **`grpc.advertised_host`** (`GOLEM__GRPC__ADVERTISED_HOST`): the host that other processes reach its gRPC port at. On Kubernetes that is the pod IP, from the downward API; in Docker Compose, the replica's own service name. The shard manager takes a host, which may be a DNS name or an IP address, because in Docker Compose the service name is the natural address; the executors take `grpc.advertised_ip`, which is always an IP address. A replica in distributed mode refuses to start without it, or with `0.0.0.0` or `::`, and warns about a loopback address, which works only when every process runs on one host. Clients connect to the leader at its advertised host and port, so the executors and worker services must be able to reach every replica's pod, as they already must behind a Service.

The advertised port is `grpc.advertised_port` (`GOLEM__GRPC__ADVERTISED_PORT`). It is optional and defaults to the bound `grpc.port`. Set it when a port mapping or NAT puts the replica behind a different port. The value `0` is refused.

Each replica needs its **own** advertised address, such as its pod IP. Never use the Service name. A replica that finds another replica advertising its address watches the lease of that replica's key. A live replica keeps renewing its lease, which moves the end of the lease later; when the new replica has seen the end move later twice, it stops with an error. (A key left by an earlier process of the same pod is never renewed: its lease only runs down and the key disappears, so the replica waits it out and leads, even if the lease TTL was changed before the restart or an etcd leader change extended the lease once.)

With gRPC TLS enabled, a client that has no `shard_manager.tls.server_domain_name` checks the leader's certificate against its configured `shard_manager.host`, when that host is a DNS name. The shard managers' certificate must then name that host, for example the Service name. A configured `server_domain_name` takes precedence.

Two gauges tell the replicas apart. `shard_manager_is_serving` is 1 on the replica that takes calls; use it to find the leader that serves. To read the election itself, run `etcdctl elect -l /golem/shard-manager/leader`. It prints the leader's election value, a JSON document with its identity, its gRPC address, a `ready` flag and its build `version`. `shard_manager_is_leader` is 1 on the replica that holds the leadership lease - the sum across replicas should always be 1. The two differ while a new leader starts: `shard_manager_is_leader` is 1 from the moment the replica wins the election, because it holds the lease from then. `shard_manager_is_serving` becomes 1 only after the replica has restored its state and checked the executors (a short time after a crash, up to `initial_health_check_timeout` after a longer outage). Over HTTP a standby and a stuck replica look the same, and both gauges read 0 for a healthy standby and for a wedged one alike. `shard_manager_campaign_attempt_failures_total` is what tells those apart: rising means the replica cannot reach etcd and is retrying, flat means it is simply waiting for the leadership.

A Kubernetes layout for three replicas behind one ordinary Service:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: golem-shard-manager
spec:
  replicas: 3
  minReadySeconds: 20
  strategy:
    type: RollingUpdate
    rollingUpdate: { maxSurge: 1, maxUnavailable: 0 }
  selector:
    matchLabels: { app: golem-shard-manager }
  template:
    metadata:
      labels: { app: golem-shard-manager }
    spec:
      containers:
        - name: shard-manager
          image: golemservices/golem-shard-manager:<version>
          env:
            - name: GOLEM__GRPC__ADVERTISED_HOST
              valueFrom: { fieldRef: { fieldPath: status.podIP } }
            - name: GOLEM__GRPC__PORT
              value: "9092"
            - name: GOLEM__HTTP_PORT
              value: "8081"
            - name: GOLEM__PERSISTENCE__TYPE
              value: Etcd
            - name: GOLEM__PERSISTENCE__CONFIG__ENDPOINTS
              value: '["http://etcd-client.etcd.svc:2379"]'
          ports:
            - { name: grpc, containerPort: 9092 }
            - { name: http, containerPort: 8081 }
          livenessProbe:
            httpGet: { path: /healthcheck, port: http }
          readinessProbe:
            httpGet: { path: /readyz, port: http }
---
apiVersion: v1
kind: Service
metadata:
  name: golem-shard-manager
spec:
  selector: { app: golem-shard-manager }
  ports:
    - { name: grpc, port: 9092, targetPort: grpc }
---
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: golem-shard-manager
spec:
  maxUnavailable: 1
  unhealthyPodEvictionPolicy: AlwaysAllow
  selector:
    matchLabels: { app: golem-shard-manager }
```

Point the executors' and worker services' `shard_manager.host` (`GOLEM__SHARD_MANAGER__HOST`) at the Service name, and set their `shard_manager.port` (`GOLEM__SHARD_MANAGER__PORT`) to the Service's gRPC port, 9092 in this example. The host alone is not enough: the client's default port is 9002, which the Service does not expose. A rolling update that replaces the leader's pod sends it SIGTERM, and the leader releases its lease, so a standby takes over within milliseconds and serves once its startup completes. The replica identity falls back to `HOSTNAME`, which Kubernetes sets to the pod name, so the example needs no extra identity variable.

`minReadySeconds: 20` matters for rollouts. A new pod is Ready at once, because a standby is ready while etcd answers it. Without a pause, Kubernetes then stops the next old pod while a just-elected leader is still running its startup, and several startups can follow in a row. The replicas order the election queue by build version (see below), so the old leader hands over once, to a new replica, whatever order Kubernetes stops the old pods in.

`unhealthyPodEvictionPolicy: AlwaysAllow` in the PodDisruptionBudget matters during an etcd outage. Every replica is then unready, and a budget that counts unready pods would block every node drain.

A rolling update hands the leadership over once, to a new replica, without any setting. Each replica writes its build version into its election entry, and an old standby moves to the end of the election queue when a replica of a newer version queues behind it. Versions compare by semantic-version precedence. A development build compares as a pre-release of the next release: a build after the tag `1.6.0-rc2` is newer than `1.6.0-rc2` and older than `1.6.0`. A replica of an older release that writes no version, or a version text that is no semantic version, never causes a move and never moves, and the queue then keeps its order. A rollback, which queues an older version behind newer ones, moves nothing.

The same layout for three replicas in Docker Compose. The replicas share one network alias, and each one advertises its own service name:

```yaml
services:
  golem-shard-manager-1: &shard-manager
    image: golemservices/golem-shard-manager:<version>
    environment: &shard-manager-env
      GOLEM__GRPC__PORT: 9092
      GOLEM__HTTP_PORT: 8081
      GOLEM__PERSISTENCE__TYPE: Etcd
      GOLEM__PERSISTENCE__CONFIG__ENDPOINTS: '["http://etcd:2379"]'
      GOLEM__GRPC__ADVERTISED_HOST: golem-shard-manager-1
    networks:
      default:
        aliases: [golem-shard-manager]
  golem-shard-manager-2:
    <<: *shard-manager
    environment:
      <<: *shard-manager-env
      GOLEM__GRPC__ADVERTISED_HOST: golem-shard-manager-2
  golem-shard-manager-3:
    <<: *shard-manager
    environment:
      <<: *shard-manager-env
      GOLEM__GRPC__ADVERTISED_HOST: golem-shard-manager-3
```

The worker executors and worker services set `GOLEM__SHARD_MANAGER__HOST: golem-shard-manager` and `GOLEM__SHARD_MANAGER__PORT: 9092`. The complete example, with etcd and the other services, is in [docker-examples/distributed-etcd](https://github.com/golemcloud/golem/tree/main/docker-examples/distributed-etcd).

**Upgrade note.** Replicas of a version before this change write an election value that this version cannot read. A standby of this version then names no leader, and clients retry until the old replicas are gone. Roll all shard manager replicas before you rely on redirects.

### Component Compilation Service

[golem-component-compilation-service](https://github.com/golemcloud/golem/tree/main/golem-component-compilation-service) is a sidecar service responsible for compiling components. The service uses Blob storage as data storage.

See also: [configuration](https://github.com/golemcloud/golem/blob/main/golem-component-compilation-service/config/component-compilation-service.toml), [environment variables](https://github.com/golemcloud/golem/blob/main/golem-component-compilation-service/config/component-compilation-service.sample.env), [docker image](https://hub.docker.com/r/golemservices/golem-component-compilation-service)

### Golem Router

[golem-router](https://github.com/golemcloud/golem/tree/main/golem-router) is an [Nginx](https://nginx.org/) proxy for Golem APIs.

See also: [configuration](https://github.com/golemcloud/golem/blob/main/golem-router/golem-services.conf.template), [docker image](https://hub.docker.com/r/golemservices/golem-router)
