# Deployment

Golem Services are distributed as Docker images. They are available in [Golem Services Docker Hub](https://hub.docker.com/u/golemservices). Each Docker image is built for the following architectures:

- linux/amd64
- linux/arm64

The services are using the following storage backends:

- Relational Database (RDB) - [PostgreSQL](https://www.postgresql.org/) or SQLite (for running locally)
- [Redis](https://redis.io/)
- Blob storage - Shared File System or S3
- [etcd](https://etcd.io/) - optional, only for the shard manager's distributed mode

## User and Permissions

Every image runs its service as the user `golem`, uid and gid 65534, with the home directory `/home/golem`. The default configuration keeps local data below `/data`, which belongs to that user: SQLite databases in `/data` and file system blob storage in `/data/blob_storage`. The `golemservices/golem` image keeps its data in `/var/lib/golem`, which also belongs to that user. The services need no Linux capability.

A path that a service writes must belong to uid 65534, or be writable by it:

- A new Docker named volume mounted at `/data`, `/data/blob_storage` or `/var/lib/golem` takes the owner of that directory in the image, so it needs no change.
- A bind mount takes the owner of the host directory. Give the directory to the user before the first start, for example with `chown -R 65534:65534 <host directory>`.
- In Kubernetes, set `runAsUser`, `runAsGroup` and `fsGroup` to 65534 in the pod `securityContext`. The kubelet then makes a volume that supports ownership management, such as an `emptyDir` or a persistent volume, writable by group 65534. A `hostPath` volume keeps the owner of the host directory.

Run the services with no capabilities and without privilege escalation: `--cap-drop ALL --security-opt no-new-privileges` with Docker, `capabilities.drop: [ALL]` and `allowPrivilegeEscalation: false` in Kubernetes. Only `xfs-quotad`, a separate process that `ManagedXfs` agent filesystem storage needs, holds a capability, `CAP_SYS_ADMIN`. Its image, `golemservices/golem-xfs-quotad`, also runs as uid 65534; see [Run xfs-quotad](/next/operate/filesystem_snapshots#run-xfs-quotad).

## Golem Services

The following sections provide a description of each service.

### Golem

The [golem](https://github.com/golemcloud/golem/tree/main/cli/golem) executable runs every service in one process with `golem server run`. The `golemservices/golem` image runs it, and serves the management API, the HTTP APIs and MCP on one port, `9881`. Configure it with a TOML file passed as `--config`, or with `GOLEM__<SECTION>__<FIELD>` environment variables; see the [configuration](https://github.com/golemcloud/golem/blob/main/cli/golem/config/golem-server.toml) and the [environment variables](https://github.com/golemcloud/golem/blob/main/cli/golem/config/golem-server.sample.env). The image sets these variables:

| Variable | Value in the image |
|----------|--------------------|
| `GOLEM__DATA_DIR` | `/var/lib/golem`, a volume |
| `GOLEM__ROUTER__ADDRESS` | `::`, which accepts IPv6 and IPv4 |
| `GOLEM__ROUTER__PORT` | `9881` |

Set `GOLEM__ROUTER__MANAGEMENT_HOST` to the host name of the management API. Requests for that host reach the management API, requests for every other host reach the HTTP API and MCP deployments, and no environment can register the host as a domain. Behind a reverse proxy, add the proxy's address to `GOLEM__WORKER_SERVICE__ROUTE_RESOLVER__TRUSTED_INGRESS_ADDRESSES`, so the router takes the host from `X-Forwarded-Host`.

The router listens on all interfaces, so the server refuses to start until the admin token (`GOLEM__REGISTRY_SERVICE__INITIAL_ACCOUNTS__ROOT__TOKEN`), the webhook keys (`GOLEM__WORKER_SERVICE__WEBHOOK_CALLBACK_HANDLER__HMAC_KEY` and `GOLEM__WORKER_EXECUTOR__AGENT_WEBHOOKS_SERVICE__HMAC_KEY`, the same value) and the invocation session token key (`GOLEM__WORKER_SERVICE__INVOCATION_SESSION_TOKENS__ACTIVE_KEY__KEY`) have secret values. The error lists the settings that still have their public default values.

At every start, the registry service provisions the built-in plugins and tools. It reads each of them from its cache, `builtin-artifacts` in the data directory, and downloads from the [golem-builtins](https://github.com/golemcloud/golem-builtins/releases) releases on GitHub each one that the cache does not have or that does not match its checksum. The downloads take about a minute. Without outgoing HTTPS connections to GitHub, a start that must download fails. Keep `/var/lib/golem` on a persistent volume, so that only the first start downloads. Without a persistent volume, for example in a container without a volume or in a task without storage, every start downloads again.

The image arguments are the arguments of `golem`; the default is `server run`. With `GOLEM_LITESTREAM=true`, [Litestream](https://litestream.io/) replicates the SQLite databases of the data directory. Use it where the volume itself can be lost, for example an ephemeral disk or a disk of one host. In this mode the worker executor keeps its key-value storage and its indexed storage in one SQLite database each, `key-value-storage.db` and `indexed-storage.db`, instead of one database per agent. The server then has a fixed set of databases: these two, `registry.db`, `shard_manager.db`, `scheduler.db` and `gateway-sessions.db`. No database file is ever deleted: deleting an agent deletes rows, and Litestream replicates that like any other write. Before the server starts, the image restores each of these databases that the data directory does not have from the replica. Turn Litestream on only for a new data directory: in this mode the server does not read the databases per agent in `kv-store`, which it writes without Litestream.

| Variable | Description |
|----------|-------------|
| `GOLEM_LITESTREAM` | `true` to replicate the databases with Litestream; `false` by default |
| `GOLEM_LITESTREAM_REPLICA_URL` | Replica of the data directory: `s3://<bucket>/<path>` or `file:///<path>`. The replica of `<name>.db` is `<path>/<name>.db`. The query, such as `?endpoint=http%3A%2F%2Fminio%3A9000&region=us-east-1`, applies to every database, and Litestream reads it |
| `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` | Credentials of the S3 replica; `LITESTREAM_ACCESS_KEY_ID` and `LITESTREAM_SECRET_ACCESS_KEY` work too |

Litestream takes the data directory from `GOLEM__DATA_DIR`, so do not set `data_dir` in the `--config` file, and it sets the key-value storage and the indexed storage of the worker executor, so do not set them either. Litestream replicates only the SQLite databases: keep the blobs in S3, for example in one bucket with `namespace_prefixes = true`. Litestream does not replicate the cache of the built-in plugins and tools, so a restore to a new volume downloads them again. Exactly one server may write to a replica.

See also: [docker image](https://hub.docker.com/r/golemservices/golem)

### Worker Service

[golem-worker-service](https://github.com/golemcloud/golem/tree/main/golem-worker-service) provides APIs and [HTTP gateway](/next/operate/architecture#the-gateway) functionality for agents and acts as a routing service for worker executors. It retrieves gateway definitions from the registry service, uses blob storage for initial agent files, and stores gateway sessions in Redis, SQLite, or PostgreSQL.

To use PostgreSQL for gateway sessions, set `gateway_session_storage.type = "Postgres"` in the worker service configuration. Under `gateway_session_storage.config`, set `host`, `port`, `database`, `username`, `password`, `max_connections`, `pending_login_expiration`, and `cleanup_interval`. The optional `schema` defaults to `golem_worker_service_session_store`, separate from other services' migration tables. For the single executable, nest these settings under `worker_service`; supply the password through `GOLEM__WORKER_SERVICE__GATEWAY_SESSION_STORAGE__CONFIG__PASSWORD` rather than checking it into a configuration file.

See also: [configuration](https://github.com/golemcloud/golem/blob/main/golem-worker-service/config/worker-service.toml), [environment variables](https://github.com/golemcloud/golem/blob/main/golem-worker-service/config/worker-service.sample.env), [docker image](https://hub.docker.com/r/golemservices/golem-worker-service)

#### Long-lived connections

Set every load balancer and proxy idle timeout longer than the keep-alive interval. Allow margin for network delay. Enable WebSocket upgrades and disable response buffering for SSE routes. A proxy with a fixed maximum connection lifetime can still close a connection that has traffic.

The worker service uses these settings in `config/worker-service.toml`:

```toml
[invocation_session]
keep_alive_interval = "30s"
max_pong_timeout = "0s"

[mcp]
sse_keep_alive_interval = "15s"

[durable_streams]
long_poll_timeout = "30s"
```

The invocation session WebSocket sends Pings at `keep_alive_interval`, which must be non-zero. The default `max_pong_timeout = "0s"` disables the Pong deadline, but Pings continue. Set a positive duration to require a Pong within that duration after a Ping is flushed to the socket.

The `golem-client` socket task reads and answers Pings while an invocation waits, even when the caller does not poll for output. When its bounded output buffers fill, it pauses socket reads and answers Pings when reading resumes. It does not send separate client Pings.

A positive Pong deadline is a strict responsiveness limit, not a reliable dead-peer test. Backpressure in either direction can delay Pong processing, including full server input queues or byte budgets and full client output buffers. Enable it only when neither endpoint can remain backpressured longer than the timeout. Otherwise keep the default `"0s"`.

MCP uses the RMCP transport's SSE comment keep-alive on open GET and POST streams. `sse_keep_alive_interval` must be non-zero. Durable stream SSE emits a `control` event after each read, including empty reads. An idle read waits for at most `long_poll_timeout`, with an executor cap of 30 seconds, so no separate SSE heartbeat is needed.

Environment variable equivalents are `GOLEM__INVOCATION_SESSION__KEEP_ALIVE_INTERVAL`, `GOLEM__INVOCATION_SESSION__MAX_PONG_TIMEOUT`, `GOLEM__MCP__SSE_KEEP_ALIVE_INTERVAL`, and `GOLEM__DURABLE_STREAMS__LONG_POLL_TIMEOUT`.

For `golem server run`, nest these sections under `worker_service`, for example `[worker_service.invocation_session]`. Add `WORKER_SERVICE` to the environment variable path, for example `GOLEM__WORKER_SERVICE__MCP__SSE_KEEP_ALIVE_INTERVAL`.

### Worker Executor

[golem-worker-executor](https://github.com/golemcloud/golem/tree/main/golem-worker-executor) is responsible for running the [agents](/next/concepts/agents) that belong to assigned shards. ### Shard Manager

[golem-shard-manager](https://github.com/golemcloud/golem/tree/main/golem-shard-manager) maintains the worker executors' shard assignments. It runs in one of two modes, selected by the `persistence` configuration:

- **Local mode** (`persistence.type = "Postgres"` or `"Sqlite"`) stores the shard state and the quota state in one SQL database. There is no leader election, so **exactly one instance may run**.
- **Distributed mode** (`persistence.type = "Etcd"`) stores the shard state in etcd. Any number of replicas may run: one wins an etcd lease campaign and drives all topology decisions while the rest stand by. The quota state lives in etcd too, under `/golem/quota/`, and a newly elected leader restores it, so executors keep the quota leases they hold across a failover. Switching an existing deployment from local to distributed mode does not carry the quota state over: executors acquire their leases again, and capacity budgets start from their full limit.

Every worker executor holds a **lease** on its shard assignment and renews it with the shard manager. A lease lasts `shard_lease_duration` (1m by default) and an executor renews at a third of the time it has left, so roughly every 20s. The shard manager refuses to start with a lease shorter than 30s and warns about one shorter than 1m: the deadline it allows each renewal call never drops below 10s, so a shorter lease cannot fit the three renewal attempts a lease is meant to get. Each renewal carries the epoch of every shard the executor holds; a shard's epoch is its ownership generation, advanced only when the shard moves to another executor and never by a renewal. A renewal whose claim does not match the shard manager's view is renewed all the same, and the response carries the shard manager's set, which the executor adopts exactly as it would an assignment push: pushes deliver a change at once, and renewals guarantee it arrives within a third of the lease even if the push was lost. The shard manager records a shard's new owner before it tells anybody about it, so a rebalance whose write is refused changes nothing at all, and every delivery carries the revision of the state it was read from. An executor ignores a delivery older than one it has already applied, so a push and a renewal that cross on the network cannot leave the older set in place. Revisions are only comparable within one shard manager process, so every delivery also names the process that sent it: an executor follows the process that answered its latest registration or renewal and starts its revisions over when that changes - which is how a shard manager that failed over, or came back on a wiped or restored store, gets its sets applied although its revisions start lower - and it ignores a push from any other process, renewing at once to hear from the one in charge. An executor that stops renewing loses its lease, and the shard manager reclaims and redistributes those shards on its next pass, which runs at least every third of `shard_lease_duration` even in a cluster where nothing else is happening; a crashed or unreachable executor's shards are therefore re-homed within about one lease duration plus one pass. The lease reaches the executor as the time remaining on it rather than as an absolute time, so the two machines' clocks are never compared and skew between them can neither lengthen nor shorten it. The executor anchors that time to the moment it sent the request the lease answers, so time the reply spends in flight comes off its copy of the lease and is never added to it, and its copy lapses no later than the shard manager's. An assignment push carries the shard set and its revision only: it never extends a lease. The lease is the one place the two machines' clocks must agree on a rate rather than on a value: an executor whose clock runs slow relative to the shard manager's keeps admitting for that fraction of a lease past the shard manager reclaiming it, which is milliseconds under ordinary `ntp` or `chrony` discipline and seconds while such a daemon is slewing off a large offset, so an executor should not be started until its clock is synchronised. An executor whose own copy of the lease has expired stops **admitting** new work for its shards and reports that sharding is not ready, which a worker service retries after refreshing its routing table - invocations already running are not interrupted. A graceful stop - including the `SIGTERM` an orchestrator sends to stop a pod - deregisters the executor instead of waiting for its lease to expire, so its shards move on the next pass. A shard manager restart or failover restarts the lease of every executor it keeps, so a restart never evicts a healthy cluster. While every stored lease is still valid, which is the normal case after a crash, the new leader skips the startup health check and restarts all of them; an executor that is dead is removed by the periodic health check, which waits `health_check.delay` (10s by default) and then checks with its own retries, about 11s for an executor that does not answer at all, so about 21s after the restart. After a longer outage the new leader checks the executors first, for at most `initial_health_check_timeout`, and removes the ones that fail; if the check runs out of time it still removes the ones that had already answered that they are unhealthy, keeps the ones it could not finish checking, and leaves those to the periodic check. An executor whose own copy of the lease lapsed during the outage resumes admitting work on its next successful renewal rather than on the push that follows the re-grant, and neither a re-grant nor a renewal ever moves an executor's deadline earlier, so a `shard_lease_duration` reduced across a restart takes effect only once the new length outruns the deadline each executor was last told.

The lease bounds how long a lost shard keeps being served, but it cannot stop an executor that has already lost one from finishing a write it had started. That is what **oplog fencing** is for. Each agent's oplog records the shard epoch allowed to write it, and every batch of entries is checked against that record atomically with the insert - in the same database transaction, or on Redis in the same script - so a refused write leaves nothing behind. An executor whose epoch is behind is turned away at the storage rather than discovering the problem later: that one agent stops there, and the worker service resumes it on the shard's new owner. The record only ever moves forward - an executor re-granted the shard at a higher epoch takes over, and one holding a stale epoch cannot claim it back - and an absent record fences an open oplog too, because the record is written before an oplog's first entry and removed before its last. That protection covers an oplog whose record exists. Deleting an agent removes its record and forgets the epoch with it: an executor that still has the oplog open is refused, but an oplog without a record - a new agent, a deleted agent created again, or one last written before this release - is claimed by whichever epoch opens it first, so for those only the lease stops an executor that has lost the shard. The archive layers that older oplog entries move into are fenced the same way, and so are ephemeral agents' oplogs, which are written straight into them. Blob storage has no conditional write, so an archive layer in blob storage keeps a list of its chunks in the indexed storage, fenced like the rest, and reads only the chunks listed there; archive chunks written to blob storage before this release are not listed, and are no longer read. Fencing covers the oplog and nothing else. An executor that has lost a shard can still write that agent's key-value records, its status and its blob payloads, none of which carry an epoch: a stale status blob can overwrite a newer one until the agent's next status change on its new owner, while the oplog - the only record replay reads - stays correct. Nor does the fence undo what has already left the machine: an outgoing call an agent made before its first refused write has happened, and the shard's new owner, having no record of it, makes it again, which is the same at-least-once exposure a crash between the call and its oplog entry already has. A call the executor has not started yet is refused once the fence has latched, so the window is the call in flight rather than every call after the shard moved.

Fencing is enforced by every indexed storage backend, for deleting an agent as much as for writing to it: a deletion that finds another executor has taken the agent over removes nothing, and fails with the answer that sends it to the new owner. A deletion under way when its shard moves may be finished by the shard's new owner instead. The shipped configuration defaults `indexed_storage` to a SQLite file of its own, which serves a single executor; executors that share shards need storage they can all reach, which means PostgreSQL or Redis, because a SQLite file is written by one process. Redis is only as durable as the last write the server kept: a failover that loses the most recent writes can lose a raised epoch with them, and the previous owner is then accepted again until the record is next raised, so prefer PostgreSQL or SQLite where that window matters. Redis Cluster is not supported. `KVStoreSqlite` and `KVStoreMultiSqlite` derive their location from the key-value storage, so they require `key_value_storage.type` to be `Sqlite` or `MultiSqlite` respectively; any other combination fails at startup.

A shard epoch only means something against the shard manager state that minted it. A state that is wiped, replaced or restored from a backup mints epochs below the ones the oplogs already record, and the storage refuses every write at those, so the affected agents stay unavailable until their records are cleared. To clear them, stop every executor, run `DELETE FROM indexed_key_epoch` on the indexed storage - for `MultiSqlite` and `KVStoreMultiSqlite`, on every `*-oplog-*.db` file under the root directory; on Redis, delete the keys matching `*oplog-epoch:*` instead - and start the executors again; each oplog records its owner's epoch when it is next opened. Run the delete only while no executor is running, because an oplog without a record accepts whichever executor opens it first.

Distributed mode talks to etcd over **plaintext HTTP** and without authentication. Every entry in `persistence.config.endpoints` must start with `http://`; a replica configured with anything else refuses to start. etcd therefore has to be reachable unauthenticated, either on a trusted network or through a TLS-terminating proxy running alongside the shard manager, with the endpoints pointing at that proxy.

Give `persistence.config.endpoints` a **single load-balanced address** - the Kubernetes Service in front of the etcd cluster - rather than a list of members. With a member list the client keeps a member that is down in its rotation: reads and writes that never reached etcd are sent again after a short delay, within the retry budget, and so are compactions; a write that reached etcd is never sent again, so a refusal stays final. The leader's ready mark is retried on any retriable failure, because it sets the same value again. Even so, a leadership campaign can spend tens of seconds landing on the dead member before it gets anywhere.

Every write to the shard state or the quota state is a new etcd revision, and etcd keeps every revision of a key until it is told to compact, so a leader that renewed leases forever would fill etcd's backend. The leader therefore **compacts** the history behind the state after each of its passes, keeping the newest `persistence.config.compaction_retention_revisions` revisions (1000 by default). Compaction is cluster-wide: it drops that much history for every key on the etcd cluster, not only the shard manager's. On a cluster shared with other applications set it to `0`, which disables it, and leave compaction to the cluster's operator or to etcd's own `--auto-compaction-mode`.

A quota lease change is stored as one etcd transaction: the resource, the lease, and one delete for each expired lease the change reclaims. The shard manager reclaims at most 120 expired leases per change, so a transaction holds up to **122 operations**, and the etcd cluster must accept at least that many. etcd's default `--max-txn-ops` of 128 does. On a cluster configured below 122, a change that reclaims many expired leases at once is refused, and so is every later change to that resource.

`persistence.config.request_timeout` must be at most half of `persistence.config.leader_lease_ttl`, and startup refuses the configuration otherwise. A lease is granted and its keepalive opened back to back, each bounded by the request timeout, so a larger value could let a lease expire before it was ever renewed.

**Failover** in distributed mode costs a graceful stop almost nothing: on SIGTERM or Ctrl-C a leader first refuses every call, on connections that clients already hold too, then releases its lease, and finally closes its connections, so that clients find the new leader; a standby takes over within milliseconds, and a standby stopped the same way leaves the election queue at once. The new leader still has to run its startup, so a graceful handover is fast for the election but not free. A leader that is killed or partitioned releases nothing, so it holds its lease until etcd expires it and a standby is elected between two thirds of `persistence.config.leader_lease_ttl` and the full value (10s by default) after that leader's last renewal. Then the new leader runs its startup. When every executor lease stored in etcd is still valid, which is the normal case after a crash, the startup skips the executor health check and the leader serves almost at once. After a longer outage it checks the executors for at most `initial_health_check_timeout` (3s by default). A broken etcd connection is not a failover: an etcd member restart or a raft leader change ends the keepalive stream and the leader reconnects it, so only etcd declaring the lease gone, or a full lease period with no acknowledged renewal, ends a leadership. A connection to etcd that goes silent without closing, such as one through a node that lost power, is found by an HTTP/2 probe, sent every 6s while the election's watch and lease keepalive are open, and is replaced within about 6s plus `persistence.config.request_timeout`. The first request after 6s of silence also probes its connection: a dead idle connection costs that one request, which waits out `request_timeout`, and the connection is replaced; a read is then retried on the new one, and a write fails with an unknown outcome, as any write in flight does. A standby that is cut off from etcd keeps naming the leader it last saw, and is not ready once etcd has been silent for a lease TTL.

During that window no replica serves: the replicas answer `UNAVAILABLE`, and name the old leader until its lease expires. Clients keep asking and reach the new leader once its startup has completed. A worker service does not ride the window out on a warm routing table cache: the first executor-level error it hits discards the cached table, and the worker service then waits until a leader serves again. A worker executor that starts inside the window waits it out too: its registration is a call that may be repeated, and the executor repeats it within its `shard_manager.retries`. With no ready leader at all, a registration fails only after each of those repeats has waited out the budget described below.

The worker executors and worker services wait out a failover by themselves, so no client setting needs tuning for it. A call that may be repeated keeps asking for about 15s once a replica has named a leader that cannot be reached, or a replica itself answers `UNAVAILABLE`, and the 15s count from the start of the call; if the `shard_manager.retries_on_unavailable` schedule takes longer than that in all, the call keeps asking for that long instead. This covers one lease TTL plus the startup with the default settings. While no replica names a ready leader, such a call therefore waits up to about 15s before it fails. A shard manager that cannot be reached at the configured address at all is not a failover, and `shard_manager.retries_on_unavailable` still decides how long the client keeps trying there. The 15s is fixed: with a longer `leader_lease_ttl` or `initial_health_check_timeout`, raise `shard_manager.retries_on_unavailable` on the clients, because a call waits for whichever is longer. A call that must not run twice is not repeated. To notice a replica whose node lost power in time, the clients probe their connections to a named leader and to the configured address every 2s and wait 5s for the answer, also while idle, whatever their keep-alive settings say, and they use one connection to the configured address that is not replaced for its age, whatever `connection_pool_size` and `max_connection_age` say; a sidecar proxy answers such probes itself, so behind one they find a dead proxy but not a dead replica.

A registration is persisted before it is acknowledged, so an executor that receives a successful registration response holds a lease the next leader will find. A registration that could not be persisted - because the leader lost its lease part-way through the write, for instance - is answered with an error instead, and the executor retries it within its `shard_manager.retries` budget.

In distributed mode **every replica serves its gRPC port** (`grpc.port`) from startup, and only the leader runs calls. A standby answers each call with `UNAVAILABLE` and a `golem.shardmanager.v1.NotLeader` detail that holds the leader's host and port (`leader_host`, `leader_port`). It takes that from an in-memory view of the etcd election, so a call does not read etcd. The worker executors and worker services follow the detail: they connect to the leader directly and keep using it until a call to it fails, when they ask their configured address again. The leader publishes its address only once its own startup has completed, so a client is never sent to a leader that cannot serve yet. Other tools, such as `grpcurl` or your own scripts, must follow the `NotLeader` detail themselves. A replica that refuses a call before it ran, because it is starting, stopping, no longer sure that it holds its lease, or knows no ready leader, adds the detail `type.googleapis.com/golem.shardmanager.v1.RefusedBeforeRunning` to the status. The detail has no message type in the proto and its value is empty, so a tool recognises it by that type URL alone. A call refused with that mark never ran, so a tool may send it to another replica whatever the call is, while an `UNAVAILABLE` without either detail may have run. A replica that has not reached its own advertised address is a standby and names the ready leader with `NotLeader`.

A Deployment or StatefulSet `RollingUpdate`, health gates such as Helm `--wait`, Flux `wait: true` or Argo, and a PodDisruptionBudget work with these replicas. Use two different probes on the HTTP port (`http_port`):

- **Readiness:** `/readyz`. It answers 200 while the replica serves. For a leader that serves, that means while it believes it holds its lease. A standby, and a just-elected leader that is still running its startup, are ready while etcd has answered them within one lease TTL. It answers 503 before the replica has connected to etcd, and in local mode until the startup has completed. In distributed mode a replica is also not ready until it has reached its own advertised address once: a TCP connection to the advertised host and port and, when gRPC TLS is off, a gRPC health check. With gRPC TLS on, only the TCP connection is made. The replica tries again every second. While it fails, the log has a warning that names the address, so a wrong `grpc.advertised_host` or `grpc.advertised_port` shows up as a replica that never becomes ready. A setup in which a pod cannot reach its own externally advertised address, such as some NAT or port-mapping layouts, keeps the replica unready. Without gRPC TLS the health check asks for an entry that only this process has, so an address that another process answers at, such as a Service name that reaches only other replicas, is refused the same way. The check passes as soon as one attempt reached this process, so it catches a typo or an address that reaches another replica, and nothing more: a name that resolves to several replicas including this one (a headless Service, the Compose alias) passes, and a ClusterIP name passes after a few attempts. A name that several replicas advertise is caught by the rule below, not by this check. A replica that has not reached its own address does not campaign: it neither queues for the leadership nor leads, and it sends callers on to the ready leader as any standby does. If every replica fails the check, no replica leads, and the warning in the log is the first sign.
- **Liveness:** `/healthcheck`.

The gRPC health service reports the overall status `""` as SERVING on every replica. The service name `golem.shardmanager.v1.ShardManagerService` is SERVING only on the replica that serves. Routing by a leader label is not needed.

A `kubectl port-forward` to the Service can land on a standby. Its answer then names a pod IP that a laptop cannot reach. Port-forward to the serving pod instead, which is the one whose `/metrics` shows `shard_manager_is_serving 1`.

Each replica must set **`grpc.advertised_host`** (`GOLEM__GRPC__ADVERTISED_HOST`): the host that other processes reach its gRPC port at. On Kubernetes that is the pod IP, from the downward API; in Docker Compose, the replica's own service name. The shard manager takes a host, which may be a DNS name or an IP address, because in Docker Compose the service name is the natural address; the executors take `grpc.advertised_ip`, which is always an IP address. A replica in distributed mode refuses to start without `grpc.advertised_host`, or with `0.0.0.0` or `::`, and warns about a loopback address, which works only when every process runs on one host. Clients connect to the leader at its advertised host and port, so the executors and worker services must be able to reach every replica's pod, as they already must behind a Service.

The advertised port is `grpc.advertised_port` (`GOLEM__GRPC__ADVERTISED_PORT`). It is optional and defaults to the bound `grpc.port`. Set it when a port mapping or NAT puts the replica behind a different port. The value `0` is refused. An advertised host that does not form a valid address with the port, such as one with a space, a `#`, a zone suffix (`fe80::1%eth0`) or a second colon outside an IPv6 literal, is refused at startup. An advertised IPv6 address needs an IPv6 bind address: set `GOLEM__BIND_ADDRESS: "::"`, because startup refuses an IPv6 advertised host when `bind_address` is IPv4.

Each replica needs its **own** advertised address, such as its pod IP. Never use the Service name. A replica that finds another replica advertising its address watches the lease of that replica's key. A live replica keeps renewing its lease, which moves the end of the lease later; when the new replica has seen the end move later twice without a change of etcd's raft leader in between, it stops with an error. (A key left by an earlier process of the same pod is never renewed: its lease only runs down and the key disappears, so the replica waits it out and leads, even if the lease TTL was changed before the restart or an etcd leader change extended the lease once.)

With gRPC TLS enabled, a client that has no `shard_manager.tls.server_domain_name` checks the leader's certificate against its configured `shard_manager.host`, when that host is a DNS name. The shard managers' certificate must then name that host, for example the Service name. A configured `server_domain_name` takes precedence.

Two gauges tell the replicas apart. `shard_manager_is_serving` is 1 on the replica that takes calls; use it to find the leader that serves. To read the election itself, run `etcdctl elect -l /golem/shard-manager/leader`. It prints the leader's election value, a JSON document with its identity, its gRPC address, a `ready` flag and its build `version`. `shard_manager_is_leader` is 1 on the replica that holds the leadership lease - the sum across replicas should always be 1. The two differ while a new leader starts: `shard_manager_is_leader` is 1 from the moment the replica wins the election, because it holds the lease from then. `shard_manager_is_serving` becomes 1 only after the replica has restored its state and checked the executors (a short time after a crash, up to `initial_health_check_timeout` after a longer outage). Over HTTP a standby and a stuck replica look the same, and both gauges read 0 for a healthy standby and for a wedged one alike. `shard_manager_campaign_attempt_failures_total` is what tells those apart: rising means the replica cannot reach etcd and is retrying, flat means it is simply waiting for the leadership.

A Kubernetes layout for three replicas behind one ordinary Service:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: golem-shard-manager
spec:
  replicas: 3
  minReadySeconds: 20
  strategy:
    type: RollingUpdate
    rollingUpdate: { maxSurge: 1, maxUnavailable: 0 }
  selector:
    matchLabels: { app: golem-shard-manager }
  template:
    metadata:
      labels: { app: golem-shard-manager }
    spec:
      containers:
        - name: shard-manager
          image: golemservices/golem-shard-manager:<version>
          env:
            - name: GOLEM__GRPC__ADVERTISED_HOST
              valueFrom: { fieldRef: { fieldPath: status.podIP } }
            - name: GOLEM__GRPC__PORT
              value: "9092"
            - name: GOLEM__HTTP_PORT
              value: "8081"
            - name: GOLEM__PERSISTENCE__TYPE
              value: Etcd
            - name: GOLEM__PERSISTENCE__CONFIG__ENDPOINTS
              value: '["http://etcd-client.etcd.svc:2379"]'
          ports:
            - { name: grpc, containerPort: 9092 }
            - { name: http, containerPort: 8081 }
          livenessProbe:
            httpGet: { path: /healthcheck, port: http }
          readinessProbe:
            httpGet: { path: /readyz, port: http }
---
apiVersion: v1
kind: Service
metadata:
  name: golem-shard-manager
spec:
  selector: { app: golem-shard-manager }
  ports:
    - { name: grpc, port: 9092, targetPort: grpc }
---
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: golem-shard-manager
spec:
  maxUnavailable: 1
  unhealthyPodEvictionPolicy: AlwaysAllow
  selector:
    matchLabels: { app: golem-shard-manager }
```

Point the executors' and worker services' `shard_manager.host` (`GOLEM__SHARD_MANAGER__HOST`) at the Service name, and set their `shard_manager.port` (`GOLEM__SHARD_MANAGER__PORT`) to the Service's gRPC port, 9092 in this example. The host alone is not enough: the client's default port is 9002, which the Service does not expose. A rolling update that replaces the leader's pod sends it SIGTERM, and the leader releases its lease, so a standby takes over within milliseconds and serves once its startup completes. The replica identity falls back to `HOSTNAME`, which Kubernetes sets to the pod name, so the example needs no extra identity variable.

`minReadySeconds: 20` matters for rollouts. A new pod is Ready at once, because a standby is ready while etcd answers it. Without a pause, Kubernetes then stops the next old pod while a just-elected leader is still running its startup, and several startups can follow in a row. The replicas order the election queue by build version (see below), so a rollout to a newer version hands the leadership over once, to a new replica, whatever order Kubernetes stops the old pods in. A rollout that keeps the version, such as a configuration change, and a rollback keep the queue's order, so `minReadySeconds` is what keeps a just-elected leader from being stopped in the middle of its startup.

`unhealthyPodEvictionPolicy: AlwaysAllow` in the PodDisruptionBudget (Kubernetes 1.27 or later) matters during an etcd outage. Every replica is then unready, and a budget that counts unready pods would block every node drain.

A rolling update to a newer version hands the leadership over once, to a new replica, without any setting. Each replica writes its build version into its election entry, and an old standby moves to the end of the election queue when a replica of a newer version queues behind it. Versions compare by semantic-version precedence, with the numbers in a release candidate and in a development build compared as numbers: `1.6.0-rc10` is newer than `1.6.0-rc9`. A development build compares as a pre-release of the release its last tag belongs to: `1.6.0-rc2-156-g…` is newer than `1.6.0-rc2-9-g…` and `1.6.0-rc2`, but older than a later tag `1.6.0-rc2.2` and than `1.6.0-rc3`, and `1.6.0-12-g…` is newer than every candidate and older than `1.6.0`. A replica of an older release that writes no version, or a version text that is no semantic version, never causes a move and never moves, and the queue then keeps its order. A rollback, which queues an older version behind newer ones, moves nothing, and neither does a rollout of the same version.

The same layout for three replicas in Docker Compose. The replicas share one network alias, and each one advertises its own service name:

```yaml
services:
  golem-shard-manager-1: &shard-manager
    image: golemservices/golem-shard-manager:<version>
    environment: &shard-manager-env
      GOLEM__GRPC__PORT: 9002
      GOLEM__HTTP_PORT: 8081
      GOLEM__PERSISTENCE__TYPE: Etcd
      GOLEM__PERSISTENCE__CONFIG__ENDPOINTS: '["http://etcd:2379"]'
      GOLEM__GRPC__ADVERTISED_HOST: golem-shard-manager-1
    networks:
      default:
        aliases: [golem-shard-manager]
  golem-shard-manager-2:
    <<: *shard-manager
    environment:
      <<: *shard-manager-env
      GOLEM__GRPC__ADVERTISED_HOST: golem-shard-manager-2
  golem-shard-manager-3:
    <<: *shard-manager
    environment:
      <<: *shard-manager-env
      GOLEM__GRPC__ADVERTISED_HOST: golem-shard-manager-3
```

The worker executors and worker services set `GOLEM__SHARD_MANAGER__HOST: golem-shard-manager` and `GOLEM__SHARD_MANAGER__PORT: 9002`. The complete example, with etcd and the other services, is in [docker-examples/distributed-etcd](https://github.com/golemcloud/golem/tree/main/docker-examples/distributed-etcd).

**Upgrade note.** Replicas of a version before this change write an election value that this version cannot read. A standby of this version then names no leader, and clients retry until the old replicas are gone. Roll all shard manager replicas before you rely on redirects.

### Component Compilation Service

[golem-component-compilation-service](https://github.com/golemcloud/golem/tree/main/golem-component-compilation-service) warms the compiled-component cache in Blob storage. It is an optional optimisation: if precompilation is skipped or fails, the executor compiles and caches the component on first use. Pending requests are held in memory and are lost on restart. The service compiles one component at a time because Wasmtime already parallelises compilation internally.

The service rejects an enqueue immediately when its request queue is full. The registry still completes the component upload. The registry's `component_compilation.config.enqueue_timeout` bounds the entire enqueue attempt, including connection establishment and retries; its default is `1s`. A timeout skips cache warming, not the component upload. A timed-out request might already have reached the compilation service and can still be compiled. Saturation is not retried inside the upload request.

| Compilation service setting | Default | Meaning |
| --- | --- | --- |
| `compile_worker.queue_capacity` | `100` | Maximum pending compilation requests, excluding the component being processed |
| `compile_worker.upload_queue_capacity` | `100` | Maximum compiled components waiting for upload, excluding the component being uploaded |

Both capacities must be positive. Their environment variables are `GOLEM__COMPILE_WORKER__QUEUE_CAPACITY` and `GOLEM__COMPILE_WORKER__UPLOAD_QUEUE_CAPACITY`. The registry timeout is `GOLEM__COMPONENT_COMPILATION__CONFIG__ENQUEUE_TIMEOUT`.

#### Choose queue capacities

The defaults are starting values, not measured recommendations for golem-dev or golem-prod. Measure each environment with its actual CPU and memory limits and Blob storage backend before selecting values:

1. Use representative small and large components and realistic deployment bursts. For cold-compilation measurements, confirm compiled-blob cache misses and disable or start with a cold Wasmtime filesystem cache (`engine.enable_fs_cache`). Fresh component revisions alone do not bypass the filesystem cache. Measure warm-cache workloads separately.
2. Observe `component_compilation_time_seconds` and the pending-request queue. Measure sustained successful compilations and artifact uploads per second over wall-clock time. Download time and upload backpressure affect throughput but are outside the histogram. Choose how much cache-warming delay is useful: validate the time from admission until the artifact is available against the expected first invocation. Use measured throughput and that delay to choose the request capacity. A larger queue does not increase compilation throughput.
3. Exercise slow Blob storage uploads. Observe `component_compilation_upload_queue_length` and process/pod peak memory with the proposed capacity. The upload queue retains compiled components, which can be much larger than request metadata. In addition to the queue, allow for one component being uploaded, one being processed or waiting for upload-queue space, compilation working memory, download buffers, artifact serialization buffers, Blob storage upload buffers, and runtime overhead. Leave headroom below the pod memory limit.
4. Run a burst that exceeds the request capacity. Confirm that `component_compilation_enqueue_total{outcome="rejected"}` increases in the registry and that uploads remain responsive. Exercise an unavailable or unresponsive compilation service and confirm the configured enqueue budget bounds the extra upload delay.
5. Record the component mix, resource limits, compilation durations, sustained throughput, time until artifacts are available, queue peaks, peak memory, enqueue outcomes, and upload latency with the chosen golem-dev and golem-prod settings in the deployment configuration review.

Use process or container memory measurements, such as the platform's working-set/RSS metrics. Do not interpret RSS differences between compilations as precise per-component allocation measurements: allocators, shared compiler threads, and retained artifacts affect them. The compilation-duration histogram measures successful Wasmtime component-build calls. It excludes request-queue wait, component download, compiled-blob cache hits, and artifact upload, but includes Wasmtime filesystem-cache loads when that cache is enabled. The queue gauges exclude in-flight work; a flat queue does not prove progress. Check compilation logs and duration samples as well.

See also: [configuration](https://github.com/golemcloud/golem/blob/main/golem-component-compilation-service/config/component-compilation-service.toml), [environment variables](https://github.com/golemcloud/golem/blob/main/golem-component-compilation-service/config/component-compilation-service.sample.env), [docker image](https://hub.docker.com/r/golemservices/golem-component-compilation-service)

### Golem Router

[golem-router](https://github.com/golemcloud/golem/tree/main/golem-router) is an [Envoy](https://www.envoyproxy.io/) proxy that serves the services on one port, routed by host. Requests for the management host reach the registry service and the management API of the worker service. Requests for every other host reach the custom request port of the worker service, which serves the HTTP API and MCP deployments by domain. Point every name at the router in DNS. The image runs Envoy as uid and gid 65534.

| Variable | Description | Default |
|----------|-------------|---------|
| `GOLEM_ROUTER_MANAGEMENT_HOST` | Host name of the management API | required |
| `GOLEM_ROUTER_REGISTRY_SERVICE_HOST`, `GOLEM_ROUTER_REGISTRY_SERVICE_PORT` | Registry service HTTP API | required, `8081` |
| `GOLEM_ROUTER_WORKER_SERVICE_HOST` | Host of the worker service | required |
| `GOLEM_ROUTER_WORKER_SERVICE_PORT` | Worker service HTTP API (`port`) | `9005` |
| `GOLEM_ROUTER_WORKER_SERVICE_CUSTOM_REQUEST_PORT` | Worker service `custom_request_port` | `9006` |
| `GOLEM_ROUTER_PORT` | Port the router listens on, IPv4 and IPv6 | `8080` |
| `GOLEM_ROUTER_TRUSTED_HOPS` | Number of proxies in front of the router whose `X-Forwarded-For` and `X-Forwarded-Proto` it trusts | `0` |
| `GOLEM_ROUTER_STREAM_IDLE_TIMEOUT` | Longest time without data on a request or a connection, in seconds | `3600s` |
| `GOLEM_ROUTER_DNS_REFRESH_RATE` | How often the router resolves the service host names again, in seconds | `10s` |
| `GOLEM_ROUTER_MAX_CONNECTIONS` | Largest number of open client connections | `50000` |
| `GOLEM_ROUTER_CONCURRENCY` | Number of Envoy worker threads (`--concurrency`) | `2` |
| `GOLEM_ROUTER_STATS_PORT` | Port that serves the Prometheus metrics of Envoy at `/stats/prometheus`, IPv4 and IPv6 | none |

The container arguments are added to the arguments of Envoy, for example `--log-level debug`. A `--concurrency` argument replaces `GOLEM_ROUTER_CONCURRENCY`.

Envoy starts one worker thread for each CPU of the host, not for each CPU of the container limit, and each worker thread opens its own connections to the services. Set `GOLEM_ROUTER_CONCURRENCY` to the CPU limit of the container.

With `GOLEM_ROUTER_STATS_PORT`, the router serves `/stats/prometheus` on that port and answers every other path with 404. The Envoy admin interface listens on `127.0.0.1:19000` in the container and is not reachable from outside it. Do not publish the metrics port to the internet; scrape it from inside the deployment.

The router sends HTTP/2 without TLS to the services, so a request that the client cancels is also cancelled in the service. It sends the WebSockets of the management API, `/connect` and the invocation session (`/v1/agents/invoke-agent-session`), to the worker service over HTTP/1.1. HTTP API deployments do not serve WebSockets, so the router answers a WebSocket upgrade for any other host with 403. When a host name resolves to several replicas, the router sends a request to the replica with the fewest open requests. A request has no time limit, so invocations that wait for a result, server-sent events, MCP sessions and websockets stay open for as long as they send data; `GOLEM_ROUTER_STREAM_IDLE_TIMEOUT` ends a silent one. The router does not limit the size of a request body; the services apply their own limits. It accepts header names with an underscore and keeps an encoded slash in the path. It resolves the service host names again every `GOLEM_ROUTER_DNS_REFRESH_RATE`, so it follows a service that restarts with a new address, and it starts before the services are resolvable. The router answers `/metrics` on the management host with 404, so the metrics of the services do not reach the clients; scrape the services directly.

The router keeps the original `Host` header, with its port, and sets `X-Forwarded-Host` to the same value. It appends the address of the client to `X-Forwarded-For`, and sets `X-Forwarded-Proto` to its own scheme, `http`. Where TLS ends at a proxy in front of the router, set `GOLEM_ROUTER_TRUSTED_HOPS` to `1`, so that the router keeps the `X-Forwarded-Proto` of that proxy.

The worker service accepts `X-Forwarded-Host` and `X-Forwarded-Proto` only from the addresses in `route_resolver.trusted_ingress_addresses` (`GOLEM__ROUTE_RESOLVER__TRUSTED_INGRESS_ADDRESSES`). Add the address of the router to it, so that the worker service takes the scheme from the router, for example `https` where TLS ends in front of the router. Reserve the management host in the registry service with `domain_registration.reserved_domains` (`GOLEM__DOMAIN_REGISTRATION__RESERVED_DOMAINS`), so that no environment can register it.

See also: [configuration](https://github.com/golemcloud/golem/blob/main/golem-router/docker/golem-router-entrypoint.sh), [docker image](https://hub.docker.com/r/golemservices/golem-router)

## Request Limits

Every path into an agent has the same payload limit of 32 MiB: the gRPC message from the worker service to the worker executor, the invocation session WebSocket message, and the REST and MCP request body.

| Setting | Service | Default | Description |
|---------|---------|---------|-------------|
| `body_limits.api` | worker service, registry service | `33554432` (32 MiB) | Largest REST request body. A larger body gets `413 Payload Too Large` |
| `body_limits.mcp` | worker service | `33554432` (32 MiB) | Largest MCP request body |
| `body_limits.upload` | registry service | `2147483648` (2 GiB) | Largest `multipart/form-data` request body: component and plugin uploads with their initial file archives, and initial agent file uploads |
| `http_server.http2_max_header_list_size` | worker service, registry service | `65536` (64 KiB) | Largest HTTP/2 header list. A larger header list gets `431 Request Header Fields Too Large` |
| `http_server.http2_initial_stream_window_size` | worker service, registry service | `1048576` (1 MiB) | HTTP/2 flow-control window of each request stream |
| `http_server.http2_initial_connection_window_size` | worker service, registry service | `1048576` (1 MiB) | HTTP/2 flow-control window of each connection |
| `http_server.http2_adaptive_window` | worker service, registry service | `false` | Sizes the HTTP/2 windows from the measured bandwidth-delay product, instead of the initial window sizes |
| `http_server.http2_max_pending_accept_reset_streams` | worker service, registry service | `20` | Streams that the client may reset before the server accepts them, before the server closes the connection (rapid reset protection). Behind a proxy that resets the streams of many clients on a few connections, such as Envoy, a low value closes connections with good requests on them when requests time out. Set it higher there |
| `http_server.http2_max_local_error_reset_streams` | worker service, registry service | `1024` | Streams that the server may reset because of errors, before it closes the connection |
| `invocation_session.websocket.max_message_size`, `max_frame_size` | worker service | `33554432` (32 MiB) | Largest WebSocket message and frame of the invocation session. A larger message or frame closes the session with close code 1009 |
| `invocation_session.websocket.max_write_buffer_size` | worker service | `67108864` (64 MiB) | Outbound bytes that may wait for the client |
| `connect_websocket.*` | worker service | same as `invocation_session.websocket` | The same limits for the agent event stream (`connect`) |

A request that declares a larger `Content-Length` gets 413 before the service reads its body. A request without `Content-Length` gets 413 when its body passes the limit.

The invocation session and the agent event stream (`connect`) answer a message or frame above their limit with close code 1009. They do not read the payload of a frame whose header declares a larger size.

The HTTP/2 header list limit is above the 60 KiB that Envoy accepts by default, so a gateway in front of Golem decides first. The HTTP/2 settings apply to every HTTP port of the service: for the worker service, `port`, `custom_request_port` and `mcp_port`.

For environment variables, add the path to `GOLEM__`, for example `GOLEM__BODY_LIMITS__API`. For `golem server run`, nest the settings under `worker_service` or `registry_service`, for example `GOLEM__WORKER_SERVICE__BODY_LIMITS__MCP`. The HTTP/2 settings of the `golem server run` listener are `router.http_server`, for example `GOLEM__ROUTER__HTTP_SERVER__HTTP2_MAX_HEADER_LIST_SIZE`.

## Network Addresses

Every service binds all of its listeners to `bind_address` (`GOLEM__BIND_ADDRESS`). The default `0.0.0.0` accepts IPv4 connections only. Set it to `::` on a network that needs IPv6, such as a Fly.io private network or an IPv6-only Railway environment: the service then accepts both IPv6 and IPv4 connections, whatever the operating system's default for IPv6 sockets is. On a host whose kernel has no IPv6 support, binding `::` fails, and the service stops at startup with the address in the error.

The shard manager identifies a worker executor by the address it reaches it at, and by default takes that address from the source IP of the executor's registration. Where the network translates source addresses, that IP is not one the shard manager and the worker services can dial. Set `grpc.advertised_ip` (`GOLEM__GRPC__ADVERTISED_IP`) on each executor to the IP address it is reachable at - on Fly.io, the machine's `FLY_PRIVATE_IP` - and the shard manager uses it for the shard lease and for the quota leases of that executor. Every executor needs an address of its own: two executors that advertise the same address replace each other's registration. An advertised IP address must be of a family the executor's `bind_address` accepts - an advertised IPv6 address needs an IPv6 `bind_address`, usually `::` - and an address that names no single host - unspecified, multicast, broadcast or IPv6 link-local - is refused at startup.
