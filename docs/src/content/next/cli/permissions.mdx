# Golem CLI Permissions

## API tokens

API tokens allow accessing the Golem APIs from external services. The `golem api-token` command allows managing the tokens of the current account.
To manage them programmatically, check [the token API](/next/rest-api/token).

### Listing existing tokens

The following command lists all the tokens associated with your account:

```shell copy
golem api-token list
```

### Creating a new token

To create a new token, use the following command:

```shell copy
golem api-token new
```

The command prints the new token's ID, expiration date and **secret**. The secret is only shown once, so make sure to save it.

Optionally, an expiration date can be specified with `--expires-at` in RFC 3339 format (for example `2027-01-01T00:00:00Z`). If not specified, the default expiration date is `2100-01-01T00:00:00Z`.

### Deleting a token

Each token has a **token ID**. Use the `api-token delete` command to remove a token using its identifier:

```shell copy
golem api-token delete 08bc0eac-5c51-40a5-8bc6-5c8928efb475
```

## Sharing permissions with other accounts

Applications, environments, components and agents belong to an **account**. The details of the current account can be queried with:

```shell copy
golem account get
```

Permissions can be shared with other accounts using **permission shares**, managed by the `golem account permission-share` command. A permission share has a **name**, a **target account** (identified by email) and a set of **permission grants**:

```shell copy
golem account permission-share new target@example.com staging-access \
  --lower-positive 'environment(my-account/my-app) @ target@example.com : view : staging' \
  --lower-positive 'component(my-account/my-app/staging) @ target@example.com : view : *'
```

Each grant has the form `<class>(<owner>) @ <recipient> : <verb> : <resource>`, for example the first grant above allows `target@example.com` to **view** the `staging` environment of the `my-app` application owned by `my-account`. Grants passed with `--lower-positive` add permissions, while grants passed with `--lower-negative` exclude permissions from the share. Both flags can be specified multiple times.

Existing permission shares can be listed, inspected, updated and deleted:

```shell copy
# Shares owned by the current account
golem account permission-share list
# Shares received by the current account
golem account permission-share list --received

golem account permission-share get <PERMISSION_SHARE_ID>
golem account permission-share get-by-name staging-access
golem account permission-share update <PERMISSION_SHARE_ID> --lower-positive '...'
golem account permission-share delete <PERMISSION_SHARE_ID>
```

<Callout>
  `permission-share update` replaces the positive (or negative) grants of the share with the ones
  provided in the command. Grant kinds not specified in the command are kept.
</Callout>

## Permission cards

Granted permissions are represented by **cards**. Cards are owned by an account (for example the account's root card, cards created for permission shares and environment defaults, and the initial cards of agents), or are held in an agent's runtime wallet. Cards can be inspected and revoked with the `golem card` command:

```shell copy
# Cards owned by the current account
golem card list
# Only some kinds of cards
golem card list --include-environment-defaults --include-agent-initials
# Cards in an agent's wallet
golem card list --agent 'CounterAgent("my-counter")'

golem card get <CARD_ID>
```

A card can be revoked using `card revoke`. Revoking a card also revokes **all of its descendants**, so this is a destructive operation and asks for confirmation:

```shell copy
golem card revoke <CARD_ID>
```
