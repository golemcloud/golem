# Metrics

## Overview

Every Golem service exposes **Prometheus metrics** on its HTTP interface. The metrics are available at the `/metrics` endpoint for scraping.

Beside the service-specific metrics each service exports a single **counter** called `version_info` in which the labels hold service-specific information.
The currently available labels are:

| Label     | Description                |
| --------- | -------------------------- |
| `version` | The version of the service |

The shard lease metrics take their label values from a fixed set and never from an agent, project or environment identifier. A label value is exported at 0 before its first event, so a query reads 0 instead of no data. To find a single agent, use the logs at the site of the refusal.

### Component Service

Component service exposes the following Prometheus metrics:

| Metric                     | Type      | Labels                                                                                                     | Description                                                                     |
| -------------------------- | --------- | ---------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| `poem_request_count`       | counter   | `http.request.method`, `url.full`, `[http.path_pattern]`, `http.response.status_code`, `exception.message` | Counts every request on the HTTP interface                                      |
| `poem_errors_count`        | counter   | `http.request.method`, `url.full`, `[http.path_pattern]`, `http.response.status_code`, `exception.message` | Counts failed requests on the HTTP interface                                    |
| `poem_request_duration_ms` | histogram | `http.request.method`, `url.full`, `[http.path_pattern]`, `http.response.status_code`, `exception.message` | Measures the duration of handling requests on the HTTP interface                |
| `api_success_seconds`      | histogram | `api`, `api_type`                                                                                          | Measures the duration of successfully serving API requests (both HTTP and gRPC) |
| `api_failure_seconds`      | histogram | `api`, `api_type`, `error`                                                                                 | Measures the duration of failed API requests (both HTTP and gRPC)               |
| `grpc_api_active_streams`  | gauge     |                                                                                                            | Number of open incoming gRPC streams                                            |

The registry service also exports `component_compilation_enqueue_total`, a counter with the fixed `outcome` labels `accepted`, `rejected`, `failed`, and `timeout`. `accepted` means the compilation service admitted the request, not that compilation finished. `rejected` means its compilation queue was full. `failed` includes transport errors, application errors, and malformed responses. `timeout` means the registry exhausted its overall enqueue budget. These outcomes do not fail the component upload. The counter does not count uploads made with precompilation disabled.

#### Agent Filesystems

These metrics are for the XFS volume of the agent filesystems. An executor exports them at 0 from the start when it uses an XFS storage mode. The project metrics are only for `ManagedXfs`. For the usage of the volume, use the volume metrics of your platform, for example `kubelet_volume_stats_available_bytes` on Kubernetes.

| Metric | Type | Labels | Description |
| --- | --- | --- | --- |
| `filesystem_pressure_recovery_seconds` | histogram | `outcome` | Time of a recovery of free space after a write failed for space. The recovery unloads idle agents until the free space reaches the target. `outcome` is `recovered`, `target_not_reached` (no idle agent was left to unload), `deadline`, `observation_failed` (the free space could not be read), `cleanup_failed` (the cleanup of an unloaded agent filesystem failed), `not_under_pressure` (the volume had enough space, so the failure has another cause) or `unavailable` (the executor is shutting down). |
| `filesystem_pressure_unload_attempts_total` | counter | `outcome` | Each unload of an idle agent that a recovery of free space tried. `outcome` is `unloaded`, `ineligible` (the agent got new work or is being deleted before the unload ran; the recovery goes on with the next agent), `cleanup_failed` (the agent stopped, but the cleanup of its filesystem failed), `task_failed` (the unload task panicked or was cancelled) or `deadline` (the recovery deadline passed before the unload finished). Many `ineligible` attempts with `target_not_reached` recoveries mean that the candidates woke up, not that none were idle. |
| `filesystem_storage_refusals_total` | counter | `cause` | Agent filesystem calls that failed because no space was left. `cause` is `agent_quota` (the agent used up its own quota, which is normal) or `physical_capacity` (the volume is full, and a recovery did not free enough). |
| `filesystem_project_cleanup_failures_total` | counter | `operation` | Failed cleanups of managed XFS projects. The project stays reserved, and its space stays used, until a later cleanup succeeds. `operation` is `delete` (the delete of an agent filesystem), `drop` (the fallback cleanup of an agent filesystem that was dropped without a delete) or `stale` (the cleanup of a project left over at the path of a new agent filesystem). |
| `filesystem_project_stale_reclaims_total` | counter | | Managed XFS projects that a new agent filesystem found left over at its path, for example after a crash, and cleaned. A rate that keeps going up shows that cleanups fail. |

### OTLP Plugin

The [OTLP plugin](/next/develop/observability#setting-up-the-otlp-plugin) exports durable stream summaries separately from the service's Prometheus endpoint:

| Metric | Type | Labels | Description |
| --- | --- | --- | --- |
| `golem.durable_stream.event_count` | counter | `event`, `outcome` | Durable stream summary events. `event` distinguishes registration, aggregated items, stream end/cancellation, and session result/finish/cancellation/expiry. Terminal summaries may include `outcome` (`success` or `error`). |

Item counts are aggregated into the metric value. The plugin does not create one span or label value per streamed item and does not export item payloads through this summary.

`session-cancellation` counts cancellation-related journal records (request, consumer intent, and application), not unique logical cancellations. One cancellation can produce several records. A session result and its eventual stream or session terminal are separate events; an early result is not stream completion.

Collector delivery is best effort even though source lifecycle state advances when a batch is accepted.
