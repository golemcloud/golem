# Persistence

## Introduction

The Golem Worker Executor uses a set of storage layers for persisting agent state and everything related to the execution of agents. This page gives an overview of what is stored where, as well as some pointers for extending Golem OSS with new storage implementations.

## Storage types

The worker executor requires four types of storage backends:

- A **blob storage** for storing and retrieving arbitrary sized binary blobs
- A **key-value storage** with some extra requirements for set/sorted-set-like operations
- An **indexed storage** for an append-only, indexable store for agent's operation log (oplog)
- A **scheduler storage** for durable scheduled actions

Currently Golem provides the following implementations, configurable through the worker executor's config file:

| Storage type | Implementations |
| --- | --- |
| Blob storage | S3, file system, SQLite, in-memory |
| Key-value storage | Redis, PostgreSQL, SQLite, multi-SQLite, namespace-routed, in-memory |
| Indexed storage | Redis, PostgreSQL, SQLite, multi-SQLite, in-memory |
| Scheduler storage | PostgreSQL, SQLite, in-memory |

## Blob storage on S3

With S3, the blob storage keeps each kind of blob in the bucket that one setting of the `[blob_storage.config]` section names:

| Setting | Blobs |
| --- | --- |
| `compilation_cache_bucket` | The compiled components of the compilation cache |
| `custom_data_bucket` | The blobs that agents write through the WASI Blob Store API |
| `oplog_payload_bucket` | The large payloads of oplog entries, seal records and deletion records |
| `compressed_oplog_buckets` | The compressed oplog of the archive layers in the blob storage, one bucket for each layer |
| `initial_agent_files_bucket` | The initial files of agents |
| `components_bucket` | The original component Wasm files of the registry service |
| `filesystem_snapshots_bucket` | The [filesystem snapshots](/next/operate/filesystem_snapshots) of agents |

The key of each object starts with `object_prefix`, when it is set. All services that share the blob storage must use the same endpoint, buckets, `object_prefix` and `namespace_prefixes`. The services do not create buckets.

### One bucket for all blobs

By default (`namespace_prefixes = false`), the bucket keeps the blobs of one kind apart from the blobs of other kinds. So each bucket setting, and each entry of `compressed_oplog_buckets`, must name a different bucket: the keys of two kinds can be the same, and so can the keys of two archive layers. Every service refuses to start when two of these settings name the same bucket, and the error names both settings.

Set `namespace_prefixes = true` to use one bucket for all blobs, for example on a platform that gives one S3-compatible bucket. Then each key starts with a segment for the kind of the blob, after `object_prefix`, and the key of the compressed oplog also holds its layer. No key of one kind is below the prefix of another kind, so all bucket settings can name the same bucket. These settings of the `[blob_storage.config]` section put all blobs into the bucket `golem`. The other S3 settings, such as `region`, `object_prefix` and `retries`, stay as they are:

```toml
[blob_storage]
type = "S3"

[blob_storage.config]
namespace_prefixes = true
compilation_cache_bucket = "golem"
custom_data_bucket = "golem"
oplog_payload_bucket = "golem"
compressed_oplog_buckets = ["golem"]
initial_agent_files_bucket = "golem"
components_bucket = "golem"
filesystem_snapshots_bucket = "golem"
```

`compressed_oplog_buckets` must still have one entry for each archive layer in the blob storage (`blob_storage_layers` in the `[oplog]` section).

With `namespace_prefixes = true`, the keys have these prefixes:

| Blobs | Key prefix |
| --- | --- |
| Compilation cache | `<object_prefix>/compilation_cache/<Wasm hash>/` |
| WASI Blob Store data | `<object_prefix>/custom_data/<environment id>/` |
| Oplog payloads | `<object_prefix>/oplog_payload/<agent mode>/<environment id>/<agent>/` |
| Compressed oplog | `<object_prefix>/compressed_oplog/<agent mode>/<environment id>/<type tag>/<layer>/` |
| Seal and deletion records | `<object_prefix>/seal_records/<agent mode>/<environment id>/<type tag>/seals/<agent id>/` |
| Initial agent files | `<object_prefix>/initial_agent_files/<environment id>/` |
| Component uploads | `<object_prefix>/component_uploads/<account id>/` |
| Filesystem snapshots | `<object_prefix>/filesystem_snapshots/<environment id>/<agent>/<incarnation id>/` |

Without `object_prefix`, each prefix starts at the segment of its kind. `<agent mode>` is `durable` or `ephemeral`, and `<layer>` is the index of the archive layer in the blob storage, from 0. `<agent>` is the agent part of the location of [filesystem snapshots](/next/operate/filesystem_snapshots/recovery#where-the-snapshots-are). The same segments make the directories of the file system blob storage below its `root`.

`<type tag>` is the environment-local type ID, written as eight lowercase hexadecimal digits. Seal and deletion records use the same `seal_records/` prefix even with `namespace_prefixes = false`, in `oplog_payload_bucket`.

Component upload keys end in `<sha256>-<uuid>`. With `namespace_prefixes = false`, the key is `<object_prefix>/component_uploads/<account id>/<sha256>-<uuid>` in `components_bucket`, with `<object_prefix>/` omitted when it is not configured.

To give a service access to one kind of blob only, use a policy on its key prefix. For example, without `object_prefix`, grant the object permissions on `arn:aws:s3:::golem/initial_agent_files/*`, and grant `s3:ListBucket` on `arn:aws:s3:::golem` with the condition that `s3:prefix` starts with `initial_agent_files/`. The services list objects to read and delete directories.

<Callout type="warning">
  The two layouts give different keys to the same blob. Golem does not move the objects when `namespace_prefixes` changes, and it does not read the keys of the other layout. Choose the setting before the first start of a deployment and do not change it later.
</Callout>

## Compilation cache

The Golem **registry service** stores original component Wasm files in its configured blob storage, which supports S3, local filesystem, SQLite, and in-memory backends. It exposes them through its [download API](/next/rest-api/component) for the worker executor. The Wasm files must be **compiled** to native code before execution, which is time-consuming. To reduce agent startup time, these compiled binaries are cached in the worker executor's **blob storage**.

If the registry database and its blob storage both use SQLite, configure separate database files. An upload can repair a missing Wasm file while the registry holds a write transaction. If both stores use the same file, that transaction blocks the repair write.

The **component compilation service** is a special, horizontally scalable component of the Golem system which shares this storage with worker executors and is capable of precompiling components before they are being used by any of the executors.

The compilation cache uses the Wasm content hash and the Wasmtime artifact fingerprint. Environments with identical Wasm share the same compiled artifact. After all services use the new keys, you can remove old filesystem entries at `compilation_cache/<environment id>/<component id>/<revision>/<fingerprint>.cwasm`. For S3, prepend the configured object prefix. If S3 namespace prefixes were disabled, the old path inside the compilation cache bucket omitted `compilation_cache/`. For SQLite, remove rows whose namespace starts with `compilation_cache-`, and keep the new `compilation_cache` namespace. Do not delete the original component Wasm.

## Oplog

Running agents continuously persist operations into the agent's **oplog**. The oplog is append-only (persisted entries are never modified) and it is indexable (during the recovery of an agent it is read from the earliest entry to the latest one).
The oplog is stored in multiple configurable layers. The default configuration is the following:

- The **primary oplog layer** uses the **indexed storage**. This is the one where running agent's entries are appended to
- There is a **secondary layer** that is also persisted to the **indexed storage**, but on this level each entry holds a compressed set of oplog entries.
- A **tertiary layer** holds even larger chunks of compressed oplog entries and stores them in the **blob storage**.

Oplogs are moved toward lower layers to prevent the primary indexed storage from filling up. With the default layers, idle agents' oplog entries eventually reach blob storage. On supported storage, Golem then seals the agent and removes its indexed rows, including its creation marker and epoch fences.

In addition to the above, there are oplog entries holding user-defined data (such as invocation parameters). As these user-defined payloads can have an arbitrary size, the worker executor has to protect its storage layer against putting too large entries into the primary oplog. For this reason large payloads are written to the **blob storage** and the corresponding oplog entry only stores a reference to them. Payloads below a configurable limit are stored inline in the oplog entry.

### Configuration

The `[oplog]` section of the worker executor configuration allows customizing the above described behavior.

The default configuration is the following:

```toml
[oplog]
archive_interval = "1day"
blob_storage_layers = 1
entry_count_limit = 1024
indexed_storage_layers = 2
max_operations_before_commit = 128
max_payload_size = 65536
skew_margin = "30s"
seal_put_timeout = "10s"
server_commit_bound = "5m"
shard_lease_max_ttl = "60s"
```

These options have the following meaning:

| Option                         | Description                                                                                             |
| ------------------------------ | ------------------------------------------------------------------------------------------------------- |
| `archive_interval`             | The delay between scheduled archival steps that move oplog sections down one layer                      |
| `blob_storage_layers`          | The number of archive layers using the **blob storage**                                                 |
| `indexed_storage_layers`       | The total number of layers (one primary + archives) using the **indexed storage**                       |
| `entry_count_limit`            | The number of oplog entries triggering the archivation of a chunk to the lower oplog layer              |
| `max_operations_before_commit` | The number of non-critical oplog entries that can be buffered before committed to the oplog             |
| `max_payload_size`             | The maximum size of user-defined payloads that can be stored inline in an oplog entry                   |
| `skew_margin` | The clock-skew allowance subtracted from the shard lease deadline |
| `seal_put_timeout` | The client timeout for a single conditional seal-record PUT; it does not bound server commit time |
| `server_commit_bound` | The assumed maximum time for the blob server to commit a received request, or never commit it |
| `shard_lease_max_ttl` | The ceiling applied to received shard lease TTLs; configure it at least as large as the shard manager's `shard_lease_duration` |

### Sealed agents and PostgreSQL footprint

While any indexed data row of an agent exists, indexed storage remains its authority. Blob chunks have an indexed manifest, and writes retain their shard epoch fence. An epoch row alone is a fence, not data presence.

Seal runs only after full archival, with no latched fence, when the resident generation is idle and can be evicted. Suspended agents can seal without being resumed. A start waiting for a permit or replaying cannot seal. The owner writes a conditional seal record containing the manifests, metadata, status, completed promises and rejected periodic snapshot indexes. It removes derived KV caches and the moved promise copies, then atomically releases every indexed data and epoch row of the agent.

A sealed agent is read from its record and chunks. Metadata, listing, oplog inspection and search do not restore rows or refresh KV caches. Activating a durable agent schedules archival and restores its manifests, marker and fences in one transaction before opening it. The first invocation-result lookup can rebuild its index from the archive. An ephemeral agent is not activated again: response and duplicate reads stay frozen and write nothing. Deletion that must record a stream cascade is the sole exception; it unseals either mode without starting the guest, and claims deletion before releasing the lifecycle guards. Deletion without stream history stays on the frozen fast path.

With PostgreSQL for indexed, KV and scheduler storage, sealed agents with no pending obligations add no rows to `index_storage`, `indexed_key_epoch`, `kv_storage`, `set_storage`, `sorted_set_storage` or `scheduled_actions`. Pending promises and timers of durable agents remain until resolved. They are bounded by outstanding waits, not archived history. Pending promises of retired ephemeral agents move into the record; an external completion creates one KV completion row that remains until deletion.

Seal requires an atomic whole-agent release (PostgreSQL, SQLite or in-memory indexed storage), a durable scheduler (PostgreSQL or SQLite), a final blob archive layer and an expiring shard lease. Redis and multi-SQLite skip seal and keep their indexed footprint. Configurations without a blob archive layer also keep it.

### Blob-store requirements and deletion GC

Seal records require ordered paged listings with modification timestamps and conditional create (`If-None-Match: *`). S3 general-purpose buckets, and compatible stores that implement both operations correctly, can be used. S3 directory buckets are unsupported because their listings are unordered. GCS through its S3 interface and Garage are unsupported because they do not provide the required conditional writes. Golem does not detect these stores for you.

The deployment must bound clock skew by `skew_margin` and ensure that a request received by the blob server commits within `server_commit_bound`, or never commits. The client timeout alone does not establish this bound. A seal record carries a fixed lease-derived deadline in its key. Readers admit it only when its listed modification time plus the timestamp resolution is at most that deadline. Unseal checks its deadline against the database clock.

Deletion writes a tombstone before removing indexed state and retains an epoch fence against old owners. A durable `CollectTombstone` action collects the tombstone, its old seal records, incarnation-scoped chunks and fence after:

`T_gc = tombstone.last_modified + shard_lease_max_ttl + seal_put_timeout + server_commit_bound + 2 × skew_margin`

The defaults give about seven minutes. GC checks PostgreSQL identity and a fresh listing before removing anything: a failed deletion that left the same incarnation alive loses only its tombstone. GC leaves a recreated incarnation intact. After successful GC, the deleted agent has no seal keys, indexed rows or GC schedule row. Scan paths never schedule GC.

A process crash after the tombstone write but before indexed deletion does not retry the delete automatically. The user must delete again. Until deletion finishes or GC discards the tombstone of that failed deletion, a marked agent can be absent from both listing stages.

## Agent metadata

The **oplog** is the primary source of truth for agent state, but the **key-value store** also caches aggregated agent metadata for performance. This metadata records the oplog index from which it was calculated, and Golem can refresh it by processing newer entries. Full archival clears the cached status, checkpoint, invocation-result index and mode hint. Seal also removes the derived stream-session index. Sealed metadata reads use the record's snapshot without writing these caches; activation can rebuild them from the history.

## Filesystem snapshots

When [filesystem snapshots](/next/operate/filesystem_snapshots) are enabled, the worker executor keeps copies of the files of durable agents that take snapshots in the **blob storage**. With S3, it uses the bucket that `filesystem_snapshots_bucket` names. Each incarnation of an agent has its own location. See [Where the snapshots are](/next/operate/filesystem_snapshots/recovery#where-the-snapshots-are).

## Promises and schedules

The worker executor stores **promise information** in its **key-value storage** until seal moves completed promises into the seal record. Readers use KV first, then the record of the same incarnation, including for duplicate completion and cross-agent polls. Pending durable promises remain in KV; pending ephemeral promises move too. Scheduled actions, including promise completion used to wake agents after long sleeps, use the separate **scheduler storage**. A sealed agent has no `ArchiveOplog` row.

## WASI Blob store and Key Value store

Golem implements (partially) the [WASI Blob Store](https://github.com/WebAssembly/wasi-blobstore) and [WASI Key-Value Store](https://github.com/WebAssembly/wasi-keyvalue) proposals. These interfaces allow agents to store blobs and key-value data in the worker executor's configured **blob storage** and **key-value storage** layers.

### Custom blob storage quotas

An account's blob storage quota applies only to data that agents write through the WASI Blob Store API. Internal blobs such as oplog payloads, compilation caches, initial agent files, components, and snapshots do not consume this quota.

Worker executors enforce the quota from their last known account balance and send net byte changes to the registry service. Concurrent executors can each spend the same stale remaining balance before their next usage update, so a distributed deployment can temporarily exceed the configured limit. S3 deployments correct accounting drift by comparing the recorded total with the physical objects. Reconciliation runs in the background when a resource-limit read or usage update observes that the reconciliation interval has elapsed; it is not a periodic timer. Consequently, an idle account is corrected only after its next such activity, and a delta that overlaps a sweep can require the next successful sweep to converge.

For reconciliation to be accurate, registry services and worker executors must use the same S3 endpoint, `custom_data_bucket`, `object_prefix`, and `namespace_prefixes`. With `namespace_prefixes = false`, the services refuse to start when `custom_data_bucket` names the bucket of another setting, even when filesystem snapshots are disabled, because the keys of the two namespaces can otherwise be the same. This check keeps the blobs of other namespaces, such as filesystem snapshots, out of the account's blob storage quota. With `namespace_prefixes = true`, the keys of the custom data have their own prefix, so the custom-data bucket can be the bucket of all blobs (see [One bucket for all blobs](#one-bucket-for-all-blobs)).

Blob mutations and usage reporting are not atomic. An executor crash can lose usage changes that have not reached the registry. Automatic physical reconciliation is enabled only for S3. Filesystem and SQLite deployments enforce quotas using incrementally reported usage, but crash-induced accounting drift can persist indefinitely, including undercounting that permits further writes beyond the configured limit.
