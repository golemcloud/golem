# Build with your coding agent

Your coding agent can write, build, and deploy a Golem application. Give it the project's instructions and skills, agree on the application's boundaries, and review the resulting identities, authority, waits, and public endpoints.

## Your coding agent and your Golem agents

Two kinds of agent take part in this workflow. Keep them separate in prompts and in review.

|                    | Your coding agent                         | Agents on Golem                                                                 |
| ------------------ | ----------------------------------------- | ------------------------------------------------------------------------------- |
| What it is         | The assistant in your editor or terminal  | Instances of the agent types defined in your application                        |
| What it does       | Edits code, runs `golem` commands         | Holds durable state, calls tools and other agents, waits, serves HTTP and MCP   |
| What constrains it | Your assistant's own permission settings  | [Cards](/next/concepts/cards), tool bindings, and middleware enforced by Golem |

Your coding agent writes the agent types; Golem runs the agents. The permissions you grant your coding agent have no effect on a deployed agent, whose authority comes only from its cards.

## Use the project's instructions and skills

`golem new` writes guidance for coding agents into the application directory:

| Path              | Contents                                                                                                                       |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `AGENTS.md`       | A Golem-managed guide for the project's language: structure, agent fundamentals, build and deploy commands, and a skills index |
| `.agents/skills/` | Common CLI and manifest skills, plus skills for the project's SDK                                                              |
| `.claude/skills/` | The same skills for Claude Code, through a `.claude` symbolic link to `.agents`, or a copy on Windows or when `.claude` exists  |

Project skills cover:

- **Define and connect:** agent types, `golem.yaml`, agent calls, promises, and webhooks.
- **Run and expose:** tools, middleware, HTTP endpoints, MCP servers, secrets, retries, and transactions.
- **Operate:** logs, oplog queries, simulated crashes, and updates.

The same catalog is published as the [How-To Guides](/next/how-to-guides). No project skill writes an `initialCard`; use [Authority: cards](/next/concepts/cards) and the [cards reference](/next/develop/cards).

`golem build` updates the Golem-managed section of `AGENTS.md` and the project skills when they differ from the CLI version. Some assistants load skills only at startup: after `golem new`, tell yours to reload its skills, or restart it.

## Optional bootstrap skills before a project exists

Before scaffolding a project, install the `golem` binary as described in the [Quickstart](/next/quickstart). Optional bootstrap skills help your coding agent create a project or configure Golem Cloud. Installing them requires Node.js and npm:

```shell copy
npx skills add golemcloud/skills
```

- `golem-new-project` scaffolds an application with `golem new`, including template selection and non-interactive flags.
- `golem-cloud-account-setup` creates a Golem Cloud profile, authenticates, manages API tokens, and prepares an application for cloud deployment.

The skills use the open agent skills format. Without Node.js, run `golem new` yourself; it still writes the project instructions and skills.

## Give it a goal and constraints

A useful brief states what the application must do and which decisions your coding agent must bring to you. Adapt this plain-text brief:

```text copy
Build a Golem application that <goal>.

Before writing code, read https://learn.golem.cloud/next/concepts and the
project's AGENTS.md. Treat these docs and project instructions as
authoritative; do not use older Golem APIs from memory. Use the project
skills in .agents/skills/ and the
<TypeScript | Effect | Rust | Scala | MoonBit | Go> SDK.

Propose, and wait for my confirmation on:
- each agent type and the constructor parameters that identify an agent
- the effects each agent may perform: tools, outbound HTTP, secrets, files
- every point where an agent waits for a person or an external event
- every HTTP endpoint, MCP server, or file an outsider can reach

Then build with `golem build --yes`, deploy to the local server with
`golem deploy --yes`, and verify the behavior by invoking agents. Simulate
a crash during a multi-step task and show the result.

Before deploying anywhere other than the local server, explain the
authority each agent will have and how its cards limit it.
```

Non-interactive `golem` commands accept the global `--format json` flag, so your coding agent reads results instead of parsing text. Each result carries a `$type` field; `golem output-schema --type <TYPE>` prints its JSON Schema. This complete command lists agents as JSON:

```shell copy
golem --format json agent list
```

`golem repl`, `golem ssh`, `golem completion`, and `golem server run` ignore `--format`. In a non-interactive shell, commands that ask for confirmation fail unless given `--yes`.

## Inspect its work

Review the decisions in the build, not only whether it runs:

- **Is each agent's identity right?** Constructor parameters decide which calls share state; one agent per user behaves differently from one per conversation. See [Agents](/next/concepts/agents).
- **What may each agent access?** Read its cards, tool bindings, and secrets. The default card is broad; deployment beyond your machine needs explicit authority. See [Authority: cards](/next/concepts/cards) and [Tools](/next/concepts/tools).
- **What happens while an agent waits?** Check which promise or webhook it awaits, who completes it, and what happens if nobody does. See [Agents working together](/next/concepts/agents-working-together).
- **What is publicly exposed?** List the HTTP endpoints with their authentication and CORS settings, and any MCP server. See [Artifacts](/next/concepts/artifacts).
- **Which failures were tested?** Ask for a simulated crash, a local server restart, and the oplog of an affected agent. See [Durable by default](/next/concepts/durable-by-default) and [Living with agents](/next/concepts/living-with-agents).
