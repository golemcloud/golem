# Make Secure HTTP APIs

Golem API gateway has built-in authentication support to identify users using the OpenID protocol.
When authentication is enabled on a mount or endpoint, Golem signs the user in before any agent code runs. Agent constructors and methods then read the signed-in user from the invocation context: `ctx.caller`.

## Setup Security for your API routes in Golem

### Register an app with an Identity Provider and get a client-id and client-secret.

Golem supports the following OIDC provider types: **google**, **facebook**, **microsoft**, **gitlab**, and **custom** (any OIDC-compliant provider via `--custom-issuer-url`).

For Google, here is the direct link to register your app with [Google Identity Provider](https://console.cloud.google.com/apis/credentials).
Make sure your app with a redirect URL and get the client-id and client secret.

The redirect URI must have the same origin as the HTTP API deployment that uses the security scheme. When using a locally executed Golem instance during development, the default deployment domain is `<app>.localhost:9006`, so the redirect URI can be `http://<app>.localhost:9006/auth/callback`. HTTP redirect URIs are accepted only for `localhost`, `*.localhost` and loopback IP addresses. Otherwise it should be `https://mydomain.com/auth/callback`, where `mydomain.com` is the domain in which you will be deploying your API in Golem.

The `/auth/callback` part is just an example and it can be anything, as far as it doesn't collide with any other existing routes.

We call these details "Api Security Scheme" in Golem API Gateway. Next step is to register this scheme in Golem.

### Register API Security Scheme with your app's client-id and client-secret with Golem

Make sure you name your security scheme uniquely, and provide the client-id, client-secret and redirect-url as given below.

#### Google example

```shell copy
golem api security-scheme create \
  --provider-type google \
  --client-id REPLACE_WITH_GOOGLE_CLIENT_ID \
  --client-secret REPLACE_WITH_GOOGLE_CLIENT_SECRET \
  --redirect-url http://localhost:9006/auth/callback \
  --scope openid --scope email --scope profile \
  my-security
```

#### Custom OIDC provider

For any OIDC-compliant provider not in the built-in list, use `--provider-type custom` with `--custom-provider-name` and `--custom-issuer-url`:

```shell copy
golem api security-scheme create my-custom-oidc \
  --provider-type custom \
  --custom-provider-name "my-provider" \
  --custom-issuer-url "https://auth.example.com" \
  --client-id "YOUR_CLIENT_ID" \
  --client-secret "YOUR_CLIENT_SECRET" \
  --redirect-url "https://app.example.com/auth/callback" \
  --scope openid
```

By now, you are having a security scheme registered with `golem` which enables authentication for your agents.

### Enable authentication in your agent code

Once the security scheme is registered, enable authentication using the `auth` option on your agent's mount or on individual endpoints.
A handler reads who is calling from its invocation context. `ctx.caller.original` is the principal that started the chain of calls; for a request from a signed-in browser user, it is a `user` principal with the user's claims. `ctx.caller.immediate` is the principal that made this call. A user's claims never leave the invocation context: they are not part of the HTTP request binding, and callers do not send them.

```typescript
import { z } from 'zod';
import { defineAgent, method, http } from '@golemcloud/golem-ts-sdk';

const Profile = z.object({ email: z.string().optional(), name: z.string().optional() });
type Profile = z.infer<typeof Profile>;

export const SecureAgent = defineAgent({
  name: 'SecureAgent',
  id: { name: z.string() },
  http: http.mount('/secure/{name}', { auth: true }), // all endpoints require authentication
  methods: {
    getProfile: method({ input: {}, returns: Profile, http: http.get('/profile') }),
  },
});

export const SecureAgentImpl = SecureAgent.implement({
  init: () => ({}),
  methods: {
    getProfile(_input, ctx): Profile {
      const caller = ctx.caller.original;
      if (caller.kind !== 'user') {
        throw new Error('Expected a signed-in user');
      }
      const { email, name } = caller.claims;
      return {
        email: typeof email === 'string' ? email : undefined,
        name: typeof name === 'string' ? name : undefined,
      };
    },
  },
});
```

Every method handler receives the invocation context as its second argument, and `init` receives it as its `ctx`.

```rust
use golem_rust::agentic::{InvocationContext, Principal};
use golem_rust::{agent_definition, agent_implementation, endpoint, Schema};

#[derive(Schema)]
pub struct Profile {
    pub email: Option<String>,
    pub name: Option<String>,
}

#[agent_definition(mount = "/secure/{name}", auth = true)]
pub trait SecureAgent {
    fn new(name: String) -> Self;

    #[endpoint(get = "/profile")]
    fn get_profile(&self, ctx: InvocationContext) -> Profile;
}

struct SecureAgentImpl {
    _name: String,
}

#[agent_implementation]
impl SecureAgent for SecureAgentImpl {
    fn new(name: String) -> Self {
        Self { _name: name }
    }

    fn get_profile(&self, ctx: InvocationContext) -> Profile {
        let Principal::User(user) = ctx.caller().original() else {
            panic!("expected a signed-in user");
        };
        let claims = user.claims().unwrap_or_default();
        Profile {
            email: claims["email"].as_str().map(String::from),
            name: claims["name"].as_str().map(String::from),
        }
    }
}
```

An `InvocationContext` parameter can appear in `new` and in any method. The SDK supplies it; it is not part of the method's input.

```scala
import golem.{BaseAgent, InvocationContext, Principal}
import golem.runtime.annotations.{agentDefinition, agentImplementation, endpoint}

import scala.concurrent.Future

@agentDefinition(mount = "/secure/{name}", auth = true)
trait SecureAgent extends BaseAgent {
  class Id(val name: String)

  @endpoint(method = "GET", path = "/whoami")
  def whoAmI(context: InvocationContext): Future[String]
}

@agentImplementation()
final class SecureAgentImpl(private val name: String) extends SecureAgent {
  override def whoAmI(context: InvocationContext): Future[String] =
    context.caller.original match {
      case user: Principal.User => Future.successful(user.subject)
      case other                => Future.failed(new IllegalStateException(s"expected a signed-in user, got $other"))
    }
}
```

A `Principal` or a `Caller` cannot be a method parameter, a result or part of a value type: the build fails with a message that points to `ctx.caller`. A principal kept in the agent's state fails when the SDK serializes that state, for example for a snapshot: at build time where the SDK can see it, otherwise at run time. To remember who called, store `ctx.caller.original.ref`, a `PrincipalRef`: an issuer and a subject that grant nothing by themselves. Compare it later with `equals`.

## Authenticate a Separate Frontend with PKCE

Cookie login is convenient when the browser accesses the protected API directly. For a public frontend hosted on another origin, configure the security scheme to use the OAuth 2.0 authorization code flow with PKCE:

### Configure the gateway and agent

Run this command from your development machine or deployment environment. It registers the security scheme with Golem; it is not frontend or agent code. Keep the upstream client secret out of the browser application.

```shell copy
golem api security-scheme create my-security \
  --provider-type custom \
  --custom-provider-name "my-provider" \
  --custom-issuer-url "https://auth.example.com" \
  --client-id "YOUR_UPSTREAM_CLIENT_ID" \
  --client-secret "YOUR_UPSTREAM_CLIENT_SECRET" \
  --redirect-url "https://api.example.com/oidc/callback" \
  --scope openid,email,profile \
  --login-mode authorization-code-pkce \
  --frontend-redirect-uri "https://frontend.example.com/auth/callback" \
  --frontend-origin "https://frontend.example.com"
```

The upstream `--redirect-url` is a gateway callback URL that you register with the identity provider. Each `--frontend-redirect-uri` is an exact URI where Golem may return the frontend after login. Each `--frontend-origin` is allowed to call the generated token endpoint through CORS. Production URIs must use HTTPS; loopback HTTP URIs (`localhost`, `*.localhost`, `127.0.0.1` and `[::1]`) are accepted for local development.

The security scheme's frontend origins apply only to its generated authorization and token endpoints. In your **agent code**, enable authentication and allow `https://frontend.example.com` through [CORS on the protected application routes](/next/invoke/making-custom-apis#cors). Use the example for your agent's SDK; this configuration is separate from the browser code below.

Golem exposes the following endpoints on the API deployment's origin. The gateway implements them; do not add agent methods or frontend routes for them. Replace `<security-scheme-id>` with the ID of the registered security scheme:

```text
/.golem/oidc/<security-scheme-id>/authorize
/.golem/oidc/<security-scheme-id>/token
```

### Start login in the browser frontend

The next two snippets are **browser-side TypeScript**, independent of the SDK used to write your agent. They are not agent implementations. Adapt them to your frontend framework and run them in the same browser tab, where `sessionStorage` retains the verifier across the login redirects.

Put this first fragment in an async login-button handler or a browser module that starts login. Replace `SECURITY_SCHEME_ID`, the API origin, and the frontend callback URI with the values from your security scheme. It generates a fresh verifier, derives its S256 challenge, stores the verifier under a random state value, and navigates to the gateway's authorization endpoint:

```typescript copy
const bytes = crypto.getRandomValues(new Uint8Array(32))
const base64url = (value: ArrayBuffer | Uint8Array) =>
  btoa(String.fromCharCode(...new Uint8Array(value)))
    .replaceAll("+", "-")
    .replaceAll("/", "_")
    .replaceAll("=", "")

const verifier = base64url(bytes)
const challenge = base64url(
  await crypto.subtle.digest("SHA-256", new TextEncoder().encode(verifier)),
)
const state = crypto.randomUUID()
sessionStorage.setItem(`pkce:${state}`, verifier)

const authorize = new URL(
  "/.golem/oidc/SECURITY_SCHEME_ID/authorize",
  "https://api.example.com",
)
authorize.search = new URLSearchParams({
  response_type: "code",
  redirect_uri: "https://frontend.example.com/auth/callback",
  state,
  code_challenge: challenge,
  code_challenge_method: "S256",
}).toString()
location.assign(authorize)
```

### Handle the callback in the browser frontend

Your frontend must serve `https://frontend.example.com/auth/callback`. After login, Golem redirects the browser there with `code` and the original `state`. Run this second fragment in that page's async initialization code. Its `state` and `verifier` variables are local to the callback; the stored verifier connects it to the login fragment.

Before exchanging the code, handle an authorization error and reject a missing code, a missing state, or a state with no matching verifier in `sessionStorage`. The fragment below shows the successful path only: the TypeScript `!` assertions do not perform those checks. Remove the stored verifier once it is consumed, then exchange the code at the gateway's token endpoint:

```typescript copy
const callback = new URL(location.href)
const state = callback.searchParams.get("state")!
const verifier = sessionStorage.getItem(`pkce:${state}`)!
sessionStorage.removeItem(`pkce:${state}`)

const response = await fetch(
  "https://api.example.com/.golem/oidc/SECURITY_SCHEME_ID/token",
  {
    method: "POST",
    headers: { "content-type": "application/x-www-form-urlencoded" },
    body: new URLSearchParams({
      grant_type: "authorization_code",
      code: callback.searchParams.get("code")!,
      code_verifier: verifier,
      redirect_uri: "https://frontend.example.com/auth/callback",
    }),
  },
)
const { access_token, expires_in } = await response.json()
```

Check `response.ok` before using the token response; the fragment omits error handling. `access_token` is the opaque Golem token and `expires_in` is its lifetime in seconds. Keep the token in frontend memory and send it—not an upstream provider token—to protected routes as `Authorization: Bearer <access_token>`. Never put it in a URL.

Authorization codes expire after 60 seconds and are consumed by the first exchange attempt. Bearer tokens expire after one hour. There are no refresh tokens; start authorization again after expiry or any failed exchange. PKCE mode does not establish a cookie session.

### Redirects and Cookies

Internally, there are a couple of redirects that's going on when you access the protected endpoint.
The first redirect is to the identity provider's login page as explained below, and internally this is followed by the identity provider hitting the redirect URL (
which is exposed on your behalf by Golem API gateway) with all the details of the user.
This is followed by another redirect to the original URL that you tried to access, and this time the session-id, tokens/secrets set in a secure Cookie, which your
browser will resend. Once the browser sends the cookie, Golem API gateway will validate the cookie and allow you to access the protected endpoint.

We will be adding more support for various clients and use-cases in future releases based on the user feedback.

### Unexposed CallBack Endpoint

Note that the callback endpoint is exposed automatically based on the re-direct url specified in the API security scheme. Users cannot customise or add
these call back endpoints manually. This is to avoid any security issues that may arise due to misconfiguration of the callback endpoint.

### Troubleshooting

Most of the errors in this use-case are originated from a wrong security scheme configuration. For example, a wrong `redirect-url`
can result in odd errors that is difficult to spot, as this is originated from the providers and not Golem.

Make sure the scope is correct and includes email. Trying to access the email claim while the scope doesn't have it in the security scheme,
will result in errors.

### Known Issues

Using multiple security schemes (with the names foo-security-scheme, and bar-security-scheme ) with the same redirect-url is not supported and leads to an internal error.

```sh
Selected profile: local

error: API Security Scheme Service - Error: 500 Internal Server Error, InternalError: Internal repository error (unique
     key violation)
```
