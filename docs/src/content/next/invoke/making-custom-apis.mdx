# Make Custom HTTP APIs for your Golem App

Golem's [Gateway](/next/concepts/worker-gateway) service not only exposes the [low-level REST API for invocations](/next/invoke/http)
but also provides a way to expose agent methods as HTTP APIs.

In Golem 1.5, HTTP endpoints are defined **directly in agent code** using language-native decorators and macros — no YAML route definitions or scripting languages needed.

For raw streaming request/response handling, framework-owned routing, or static and
live file mappings, see [HTTP routers and file serving](/next/invoke/http-routers).
Complete code-first endpoints take precedence over those mounted fallback behaviors.

## Mount Points

Every agent that wants to expose HTTP endpoints must first define a **mount point** — the base URL prefix under which all its endpoints are available. The mount path can contain placeholders like `{name}` that map to the agent's constructor parameters.

<Tabs items={["TypeScript", "Effect TypeScript", "Rust", "Scala", "MoonBit"]} storageKey="nextra-tabs-language-sdk">
<Tabs.Tab>
```typescript
export const Tasks = defineAgent({
  name: 'Tasks',
  id: { name: z.string() },
  http: http.mount('/task-agents/{name}'),
  methods: {
    // ...
  },
});
```
</Tabs.Tab>
<Tabs.Tab>
```typescript
export const Tasks = defineAgent({
  name: "Tasks",
  mode: "durable",
  id: { name: Schema.String },
  http: Http.mount("/task-agents/{name}"),
  methods: {
    // ...
  },
})
```
</Tabs.Tab>
<Tabs.Tab>
```rust
#[agent_definition(mount = "/task-agents/{name}")]

    fn new(name: String) -> Self;
    // ...
}
```
</Tabs.Tab>
<Tabs.Tab>
```scala

```
</Tabs.Tab>
<Tabs.Tab>

If there are multiple agent constructor parameters, they all have to be mapped in the mount path.

## Endpoints

Once the mount is defined, individual agent methods can be exposed as HTTP **endpoints**. Each endpoint specifies an HTTP method and a path suffix relative to the mount point. Path placeholders are mapped to method parameters. Parameters not mapped through the path or headers are taken from the request body.

<Tabs items={["TypeScript", "Effect TypeScript", "Rust", "Scala", "MoonBit"]} storageKey="nextra-tabs-language-sdk">
<Tabs.Tab>
```typescript
createTask: method({
  input: { request: CreateTaskRequest },
  returns: Task,
  http: http.post('/tasks'),
}),

getTasks: method({ input: {}, returns: z.array(Task), http: http.get('/tasks') }),

completeTask: method({
  input: { id: z.number() },
  returns: Task.nullable(),
  http: http.post('/tasks/{id}/complete'),
}),
```
</Tabs.Tab>
<Tabs.Tab>
```typescript

  input: { request: CreateTaskRequest },
  success: Task,
  http: [Http.post("/tasks")],

```
</Tabs.Tab>

### Response Conventions

Return types control the HTTP response:

| Return type | HTTP response |
|-------------|---------------|
| A value (e.g. `Task`) | `200 OK` with JSON body |
| `Option<T>` / `T \| null` | `Some`/non-null → `200`; `None`/`null` → `404 Not Found` |
| `Result<T, E>` | `Ok` → `200`; `Err` → `400 Bad Request` with JSON error |
| `void` / `()` | `204 No Content` |

## CORS

CORS can be configured at the **mount level** (applies to all endpoints) and optionally overridden per **endpoint**:

<Tabs items={["TypeScript", "Effect TypeScript", "Rust", "Scala", "MoonBit"]} storageKey="nextra-tabs-language-sdk">
<Tabs.Tab>
```typescript

  name: 'MyAgent',
  id: { name: z.string() },
  http: http.mount('/api/{name}', { cors: ['https://app.example.com'] }),
  methods: {
    // All endpoints inherit the mount-level CORS setting

    // This endpoint adds additional allowed origins

});
```

  id: { name: z.string() },

    // ...

## Customizing Durable Stream Routes

An endpoint with stream inputs or outputs is exposed as a [Durable Streams](/next/invoke/durable-streams) URL family. By default, each URL uses the canonical method parameter name (and `$result` for a direct stream result), JSON streams use `application/json`, byte streams use `application/octet-stream`, external writes and both deletion operations are enabled, and the worker-service defaults control admission.

Route metadata can customize that HTTP surface without changing the agent method or the durable stream itself:

| Customization | Effect |
| --- | --- |
| Slot `name` | Replaces the canonical slot name in the public URL and OpenAPI document. The canonical name remains the source selector in metadata and is not also accepted as a URL alias. |
| Slot `contentType` | Replaces `application/octet-stream` for a direct `stream<u8>` slot. Ordinary reads and metadata, append negotiation, and OpenAPI use the custom MIME type; SSE remains `text/event-stream` with base64 data. |
| `allowExternalWrites: false` | Removes `POST` from writable input slots. |
| `allowStreamDelete: false` | Removes `DELETE` from stream URLs. |
| `allowInvocationDelete: false` | Removes `DELETE` from invocation-session URLs. |
| Reader limit | Caps concurrent admitted live readers (long-poll and SSE) per stream for this route. |
| Append limit | Caps admitted append requests per second per stream for this route. |

Disabled operations return `405 Method Not Allowed` with an `Allow` header that lists only the enabled methods. Admission exhaustion returns `429 Too Many Requests` with `Retry-After: 1`. Limits are maintained independently for each deployed route and worker-service node; they do not replace executor protocol limits or form a cluster-wide quota.

<Callout type="info">
  These options preserve the official Durable Streams wire protocol: they choose
  URL names, an opaque byte-stream media type, optional protocol operations, and
  stricter gateway admission. Custom media types are supported only for direct
  byte streams (`stream<u8>`) and must be concrete non-text, non-JSON types
  without parameters or wildcards. JSON-shaped streams remain
  `application/json`. Native `text/plain` for `stream<string>` is not supported;
  use the JSON representation so byte sub-offset forks cannot split a UTF-8
  value.
</Callout>

Only `$result` has an implicit canonical name. Other slot selectors must identify an existing top-level input or output slot. Public names must be unique across the route, and canonical selectors must remain valid and unique even when a public name is supplied.

The same route customization looks like this in each SDK:

## Deployments

To make the code-first routes accessible, a deployment section is needed in the application manifest (`golem.yaml`). This maps agents to domains per environment:

```yaml
httpApi:
  deployments:
    local:
    - subdomain: app-name  # resolves to app-name.localhost:9006 by default
      agents:
        Tasks: {}
```

You can specify which agents to deploy to which (sub)domains, organized by environment (e.g. `local`, `staging`, `prod`).

## Deploying the API

Once the deployment is configured in `golem.yaml`, deploy with:

```shell
golem deploy
```

## OpenAPI Specification

Golem automatically generates an OpenAPI specification from the code-first route definitions. Each deployment exposes `openapi.yaml` and `openapi.json` endpoints:

```shell
curl http://app-name.localhost:9006/openapi.yaml
```

This returns an OpenAPI 3.1 specification describing the deployed endpoints, including path parameters and request/response schemas. Download this deployment-specific document when generating an HTTP client; the Golem management API specification does not describe your agents' routes.

Methods with stream parameters or results appear as Durable Streams URL families:

- `PUT {base}` creates a server-assigned session and returns its URL in `Location`.
- `PUT`, `GET`, `HEAD`, and `DELETE` on `{base}/invocations/{session}` create, inspect, or cooperatively cancel a session.
- Each stream has a concrete path under `{base}/invocations/{session}/streams/`. Input streams support `POST` for appending; output streams do not. `DELETE` cancels and tombstones an individual stream.

The document includes the schema and direction of every slot, with `x-golem-route-mode: durable-streams` and `x-golem-stream-slot` metadata. Without a public name override, the direct result slot is spelled `%24result` in the OpenAPI path. JSON reads return arrays of the element type; byte streams use their configured media type. Reads also support long-poll and SSE through the `live` query parameter. SSE returns `text/event-stream`, so clients need an SSE parser rather than a JSON response parser; byte-stream SSE data is base64 encoded and declares `Stream-SSE-Data-Encoding: base64`.

Non-stream arguments belong to session creation and retain their path, query, header, or body bindings. Create the session before appending when the method requires body or header arguments. Append operations document producer retry headers and `Stream-Closed` for atomic closure. JSON array bodies are batches; an array-valued message needs an outer batch array. Empty append bodies are valid only when closing the stream.
