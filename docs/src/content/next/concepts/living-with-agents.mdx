# Living with agents

A durable agent outlives the process that runs it and the deployment that created it. Its identity and oplog persist while it runs, while it is suspended, when it is rebuilt after a failure, and when it moves to new code. Operating a Golem application means managing that history.

## Deploy code; update existing agents deliberately

`golem deploy` uploads components and applies HTTP and MCP deployments. It does not start agents, which are created on first use, and it does not change existing agents: each stays on its component revision until you update it.

| Update mode | How state moves | Use it when |
|---|---|---|
| Automatic (`auto`) | Golem replays the agent's oplog against the new code. If the new code diverges from the recorded history, the update fails and the agent keeps running on its old revision. | The change is compatible with what existing agents already recorded. |
| Manual (`manual`) | The old revision saves the state as a snapshot; the new revision loads it. You implement both functions. | The change alters state layout or control flow. |

Update affected agents during a deploy, or one agent at a time:

```shell
golem deploy --yes --update-agents auto
golem agent update 'OrderAgent("order-42")' auto --await
```

Inspect failed updates in the oplog or with `golem agent get`. [Updating agents](/next/develop/updating#failure-codes) explains the failure codes and recovery actions. `--redeploy-agents` and `--reset` delete agent state instead of moving it.

## Inspect, interrupt, revert, and fork

`golem agent get` shows an agent's status, pending invocations, and update history; `golem agent stream` follows its output and logs. `golem agent oplog` prints the journal, and `--query` searches it with Lucene syntax by entry kind, method or tool name, idempotency key, or request and response values:

```shell
golem agent oplog 'OrderAgent("order-42")' --query 'update'
```

`golem agent interrupt` stops a running agent and `golem agent resume` continues it. `golem agent simulate-crash` makes an agent recover through the same path as a real failure.

**Revert** removes recent oplog history, either the last N invocations or every entry after an index, and returns the agent's state to that point. It changes the agent, not the outside world: a charged payment stays charged. Reverting to an index inside an invocation lets the agent perform the removed steps again. Undo external effects with a saga's compensations or application logic.

**Fork** creates a second agent from an existing history. In code, `fork()` splits an agent at the current point into an agent with the same base identity and a new phantom ID; both continue. The REST API forks an agent from a chosen oplog index. A fork explores an alternative or divides work; it is not compensation.

There is no replay debugger: inspection is the oplog, through the CLI and REST API, with revert, fork, and `simulate-crash`.

## Observe execution

The oplog is each agent's audit record, with nothing to configure: invocations, durable host calls, tool calls, card events, updates, and errors, in order.

The built-in `golem-otlp-exporter` plugin, added to a component in `golem.yaml`, exports to an OpenTelemetry collector: traces with W3C trace context propagated in and out, logs, and per-agent metrics such as invocation count, duration, fuel, and memory. Custom spans survive across invocations and crashes. The exporter is an oplog processor plugin: Golem delivers each oplog entry to it exactly once, and the oplog stays the authoritative record.

## Pay for work and retained state, not a waiting process

An agent waiting on a sleep, promise, webhook, or slow agent call is **suspended** after a short threshold: Golem unloads it from memory and rebuilds it from its oplog when the wait ends.

Usage is measured as compute (fuel), allocated memory over time, and storage. A suspended agent allocates no memory and uses no compute, but its oplog, files, and snapshots stay in storage and still count. `golem agent delete` removes an agent's state. Self-hosted deployments meter nothing by default; per-agent memory and disk caps stay enforced.

## Set application budgets

| | User-defined quotas | Platform limits |
|---|---|---|
| Protects | Your budgets: model tokens, API calls, connections | The platform |
| Defined by | You, per environment in `resourceDefaults` or with `golem resource` | The operator's plan (`golem account limits show`) |
| Shapes | Any named resource, as a rate, capacity, or concurrency pool | Memory and disk per agent, monthly compute, resource counts |
| When exceeded | Your choice: `reject` fails the request, `throttle` suspends the agent until capacity returns, `terminate` stops the agent | Creation rejected, growth capped, or durable agents suspended |

Golem cannot know what a model call will cost, so model budgets need the harness: before each call it reserves an estimate from a quota token, then commits actual usage (`withReservation` in the TypeScript SDK). A runaway loop stops at the cap, and an agent can split its budget among child agents.

## Scale by adding agents

An agent runs one invocation at a time, so throughput comes from more agents. Golem partitions agents into shards across executor nodes, and a gateway routes each call to the executor that owns the shard. When executors join or leave, shards move and agents are rebuilt from their oplogs. Ownership is fenced: oplog writes carry the shard's epoch, so an executor that has lost a shard cannot write to its agents. Agents on a failed executor are unavailable until another rebuilds them. See [Architecture](/next/operate/architecture).
