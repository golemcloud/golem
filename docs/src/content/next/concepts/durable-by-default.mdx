# Durable by default

A durable agent recovers its memory, files, and in-progress work after crashes, restarts, and moves between nodes. Durable is the default agent mode; [Agents](/next/concepts/agents) covers the alternatives.

## The oplog records durable host calls

Every durable agent has an **oplog**: an append-only journal of its execution. Golem records nondeterministic inputs and interactions such as clock reads, random numbers, HTTP requests including model calls, calls to other agents, tool calls, and the order in which concurrent calls complete. Invocations, updates, and snapshots go in the same journal.

Golem supplies this recording at the WebAssembly host boundary, with no step annotations, activity wrappers, or determinism rules in application code. Each agent is single-threaded. Re-running its code against recorded inputs reconstructs its state, so a plain `this.count += 1` is durable.

## Recovery reconstructs memory, files, and execution

When an agent's process is lost, Golem starts a fresh instance of its code, on any node, and re-runs it against the oplog. Recorded results satisfy completed durable host calls. Computation and local file operations run again: Golem restores the initial files or the filesystem snapshot selected for recovery, then replay rebuilds subsequent changes. This reconstructs the agent's variables, call stack, and files so it can continue from its recorded progress.

Suspension, eviction, rebalancing, restart, and crash all rebuild an agent through this same path. A node that has lost ownership of an agent cannot write to its oplog, so two copies never run against the same history.

An `OrderAgent` charges a payment over HTTP, then reserves stock in an `InventoryAgent`. The node crashes while the reservation call is in progress.

During recovery, the payment response comes from the oplog and no request is sent. The reservation call is re-sent with the same key, and `InventoryAgent` returns the result of the reservation it already ran. Had the crash come after the payment request left but before its response was recorded, Golem would re-send it with the same `idempotency-key` header, and a payment provider that honors the header would charge once.

Model calls follow the same rule. If the node fails after the model responds in the excerpt below, recovery reads the response from the oplog instead of requesting it again. An agent loop that fails at step 7 of 12 resumes at step 7.

```typescript
// Excerpt: part of a ReportAgent method body
const response = await fetch("https://api.model-provider.example/v1/chat", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ messages: this.messages }),
});
const draft = (await response.json()).message;
this.messages.push(draft);

const review = await ReviewerAgent.client.get({ team: "finance" }).review({ draft: draft.content });
```

## Execution guarantees

Once Golem accepts an invocation, infrastructure failures do not lose it. Golem recovers the same invocation across crashes, restarts, and updates, continuing from its recorded history.

| Interaction | Guarantee |
|---|---|
| Agent invocation | Executes exactly once per idempotency key. A repeat with the same key returns the recorded result. |
| Agent-to-agent call | Agent-to-agent calls execute exactly once. Every retry and replay carries the same key, and the target agent runs the call once. |
| Tool call | Every tool call executes exactly once. Replay re-runs the component-tool body to reconstruct local state, using recorded results for its completed durable host calls. An interrupted call continues under its original invocation identity. |
| Model call | Completed model calls are recovered from the oplog rather than requested again. |
| Outgoing HTTP request | Golem automatically attaches an `idempotency-key` header, stable across retries and recovery. A completed request is answered from the oplog. A request in flight at the failure is re-sent with the same key, and services that honor the header process it once. |
| Your own code | Computation and local file operations re-run to reconstruct memory and files. Completed durable host calls use their recorded results, including clock and random values. |
| Atomic region, on retry | The whole region re-executes from its start and re-sends its completed requests with the same idempotency keys. |

Golem derives the `idempotency-key` header from the request's oplog position, so you keep no deduplication tables. If you set the `idempotency-key` header yourself, your value replaces Golem's. To put a durable key in a request body, call `generateIdempotencyKey()`. HTTP is the boundary of Golem's control: a request without a recorded response may already have reached the service, so the service's handling of the key decides whether it runs twice.

## Retries and waits

Golem retries transient failures, such as network errors and interrupted executions. It also retries HTTP 5xx responses when a retry policy matches on status code. Permanent errors, permission failures, and deterministic traps outside atomic regions are not retried. When retries are exhausted, the agent is marked failed.

Retry policies are named, prioritized, and composable; the highest-priority matching policy applies, over a server-configured default. Declare policies per environment in `golem.yaml` under `retryPolicyDefaults`, change them live with `golem retry-policy create|update|delete`, or scope one to a block of code with `withRetryPolicy`.

Waiting agents are suspended and rebuilt through the same recovery path. [Agents working together](/next/concepts/agents-working-together) explains durable waits.

<Callout type="info">
Recovery does not fix bugs: code that fails deterministically fails again. Agents on a failed node are unavailable until another node rebuilds them.
</Callout>

## Snapshots, updates, and explicit transactions

**Snapshots** shorten recovery. An agent type can snapshot its state on a policy, such as every N invocations; recovery loads the latest usable snapshot and replays only later entries. Snapshots are optional; the oplog is the durability mechanism.

**Updates** respect recorded history. An automatic update replays the agent's oplog with the new code; if the new code diverges from that history, the update fails and the agent keeps running on its old revision. A manual update moves state through the old revision's snapshot save and the new revision's load.

**Explicit transactions** group effects, which are otherwise retried one at a time. An atomic region (`atomically`) re-executes from its start if a crash or retryable error interrupts it. For business failures that need undo, such as a declined payment after a reservation, `compensable` steps inside `fallibleSaga` or `infallibleSaga` run compensations in reverse order.
