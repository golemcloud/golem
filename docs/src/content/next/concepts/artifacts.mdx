# Artifacts

An artifact is something an agent delivers to people: a front-end to click, a report to download, or live progress to watch. One `golem deploy` ships agents, their tools, and the front-end whose buttons call them. The agents act only with the [cards](/next/concepts/cards) they hold.

Golem serves live files directly from the agent's filesystem and provides resumable streams. The application does not need to copy those files to a separate host or implement its own stream-resumption buffer.

## Methods become HTTP endpoints

An agent type can declare a mount path, and its methods can declare endpoints under it. Every constructor parameter appears in the mount path, so the URL names the agent: `POST /reports/acme/q3` reaches `ReportAgent("acme", "q3")`.

```typescript
// Excerpt: constructor and HTTP declarations inside ReportAgent's defineAgent call
id: { tenant: z.string(), quarter: z.string() },
http: http.mount("/reports/{tenant}/{quarter}"),
methods: {
  create: method({
    input: {},
    returns: z.string(),
    http: http.post("/"),
  }),
},
```

The first request for a name creates that agent; later requests reach the same agent. Only mounts that opt into phantom agents get a fresh instance per request. Path, query, and header parameters bind to typed inputs, return values map to status codes, and each deployment publishes an OpenAPI 3.1 document at `/openapi.yaml`.

## Routers, static files, and live files

An **HTTP router** handles requests that do not fit a typed method, such as streaming uploads or an existing HTTP framework. A router is an ephemeral agent type with an empty constructor and one literal mount. Its handler takes a standard Fetch `Request` and returns a `Response`, so a Fetch-compatible framework can supply it:

```typescript
export const EchoRouter = defineHttpRouter("EchoRouter")
  .mount("/echo")
  .implement((request) => new Response(request.body));
```

A router calls ordinary agents through their clients. A client disconnect cancels the router invocation without rolling back effects already performed.

| | Static deployment files | Live agent files |
|---|---|---|
| Source | A router's read-only initial files, versioned with the deployment | A durable agent's current filesystem |
| Declared with | `.static(route, path)` on the router | `exposeFiles` on the agent's mount |
| Work per request | None: streamed from shared storage, no agent created | Loads the agent if needed and reads the file; no method runs |
| Caching | Strong `ETag`, revalidated, `304` on a match | `Cache-Control: no-store` |
| Typical content | A front-end's HTML, CSS, and JavaScript | A report the agent just wrote |

A live-file read waits for the agent's running invocation, so it never returns a half-written file. When a typed method endpoint and a router match the same path, the method endpoint handles the request; for `GET` and `HEAD`, a router tries its files before its handler. One router can serve a single-page app at `/` while typed endpoints answer its API calls on the same origin.

## Read-only responses can bypass execution

A [read-only method](/next/concepts/agents#each-agent-runs-one-invocation-at-a-time) can return a cached result without entering the agent's queue or loading its WebAssembly instance. By default, the cache lasts until the next state-changing invocation. A cache hit writes nothing to the oplog.

On a `GET` endpoint, the response carries `Cache-Control` and an `ETag`. A matching `If-None-Match` gets `304 Not Modified` without executing the method or loading the agent.

## Streams that survive reconnects

A method with a stream input or result, mounted on an HTTP route, is exposed as a **Durable Streams** URL family. Durable Streams is an open HTTP protocol for resumable streams: the invocation lives in a server-side session, not in one HTTP request, so a browser tab that reloads continues from the last offset it read. Unmodified Durable Streams clients work against these URLs.

Bridge libraries and the CLI stream over a separate WebSocket session protocol, not Durable Streams; see [Agents working together](/next/concepts/agents-working-together).

## Login, subdomains, and other clients

A `subdomain` entry in an `httpApi` deployment in `golem.yaml` gives the application an address: `my-app.localhost:9006` locally and `my-app.apps.golem.cloud` on Golem Cloud.

With `auth: true` on a mount and a security scheme attached to the agent in the deployment, Golem authenticates each request before it reads a file or activates an agent. A single-page app on another origin logs users in with the OAuth2 authorization code flow with PKCE and receives a short-lived Golem bearer token.

<Callout type="warning">
Authentication identifies the caller; it does not authorize access to every report. In a method handling `/reports/acme/q3`, application code must check `this.getPrincipal()` against the application's access rules for `acme` before returning data or performing work.
</Callout>

Every client reaches the same agent identity, state, and oplog:

| Client | Route to the agent |
|---|---|
| Browser, HTTP client | Endpoints, routers, and files listed in an `httpApi` deployment |
| MCP client | Agents listed in an `mcp` deployment (`my-app.localhost:9007/mcp` locally) |
| Developer | `golem agent invoke`, `golem repl` |
| Your application | Generated bridge libraries |
| Other services | REST API: `POST /v1/agents/invoke-agent` |
| Other agents | Typed method calls |
