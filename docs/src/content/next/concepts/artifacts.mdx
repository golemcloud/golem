# Artifacts

Agents produce things that people use: an API, a web front-end, a report to download, live progress to watch. Golem calls these **artifacts** and serves them from the agents that produce them, so an application needs no separate web server, file host, or streaming service.

For example, a `ReportAgent` writes its front-end into its own filesystem and serves it as live files. The front-end's buttons call the agent's HTTP endpoints, progress streams back to the page while the agent works, and the finished report, a file the agent wrote, is served from the agent's filesystem. The front-end, the API, the stream, and the file all come from the agent, and the agent is durable.

## HTTP endpoints for agent methods

An agent type can declare an HTTP mount path, and its methods can declare endpoints under it. The mount path contains every constructor parameter, so the URL identifies the agent. With this declaration, `POST /counters/alice/increment` calls `increment` on `CounterAgent("alice")`:

Path, query, and header parameters map to method inputs, and return values map to responses. Each deployment publishes an OpenAPI document for its endpoints. A deployment can claim a subdomain, such as `my-app.localhost:9006` locally or `my-app.apps.golem.cloud` on Golem Cloud.

## HTTP routers

When an application needs full control over HTTP, for example to serve an existing web framework or handle streaming uploads, it can define an **HTTP router**. A router's handler receives a standard Fetch `Request` and returns a `Response`:

```typescript

  .mount("/echo")
  .implement((request) => new Response(request.body));
```

```moonbit
#derive.http_handler
pub fn EchoRouter::serve(_self : Self, request : @http.HttpRequest) -> @http.HttpResponse {
  let input = request.body
  {
    status: 200,
    headers: [],
    body: @schema.AgentStream::produce(
      async fn(writer) {
        defer input.drop()
        for ;; {
          match input.read() {
            None => return
            Some(chunk) =>
              if writer.write_one(chunk) is @schema.PeerDropped { return }
          }
        }
      },
      on_unstarted_drop=() => input.drop(),
    ),
  }
}
```

A router calls agents through their clients, so one router can serve a single-page app while typed endpoints answer its API calls on the same origin.

## Interactive apps

A web app on Golem is interactive, not static output: its JavaScript runs in the browser and calls the agents' HTTP endpoints, which expose durable agent code with the agent's state and permissions. An agent can generate an app at runtime: it writes HTML and JavaScript into its own filesystem, serves them as live files, and the page calls the agent's endpoints. What Golem does not run is a long-lived server process, such as a development server, inside a tool.

## Live files

A durable agent serves files from its own current filesystem, such as a page it generated or a report it just wrote. Serving a live file does not run a method, and live files are never cached. A live file is never served half-written: the read waits until the agent's current method call finishes.

Content that no agent produces, such as a fixed front-end bundle shipped with the application, can instead be deployed as a router's static files, served without running any agent and revalidated with an `ETag`; see [HTTP routers and files](/next/invoke/making-custom-apis/http-routers).

## Cached read-only responses

Methods marked read-only can be answered from a cache without loading the agent. On a `GET` endpoint, the response carries an `ETag`, and a client that already has the current version gets `304 Not Modified`.

## Streams that survive reconnects

A method that returns a stream, mounted on an HTTP endpoint, is served using the **Durable Streams** protocol, an open HTTP protocol for resumable streams. The stream belongs to the agent, not to the HTTP connection, so a browser tab that reloads continues from the last position it read. Existing Durable Streams clients work with these endpoints.

## Login

Endpoints can require authentication. A single-page app can sign users in with the OAuth2 authorization code flow with PKCE, and Golem checks the token before any agent code runs.

<Callout type="warning">
  Authentication tells an agent who is calling; it does not decide which agents a user may reach.
  A user can put any agent's name in a URL, so a method that serves user data should read the
  authenticated caller (the principal) and check it against the application's access rules.
</Callout>

## Keeping an existing web app

You do not have to serve your front-end from Golem. An existing application, such as a Next.js app, can call agents from its server through a client library generated for its language or through the REST API, and keep its own UI and hosting.

## One agent, many entry points

The same agent can be reached from a browser, an MCP client, the CLI, a generated client library in your own application, the REST API, and other agents. Endpoints are declared in agent code, and they become reachable over HTTP or MCP only when an `httpApi` or `mcp` deployment in `golem.yaml` publishes them.
