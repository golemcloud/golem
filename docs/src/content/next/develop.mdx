# Develop an application on Golem

A Golem application contains one or more WebAssembly components, their agents and tools, and optional HTTP or MCP API deployments. The application manifest keeps these parts and their environments in one deployable definition.

## Create an application

The primary development tool is the [Golem CLI](/next/cli). List the current templates, optionally filtered by language:

```shell copy
golem templates
golem templates rust
```

Create an application by selecting a template:

```shell copy
golem new my-app --template <template-name>
cd my-app
```

In non-interactive use, provide at least one `--template`. The template determines the language and generates a component name when you do not pass `--component-name`.

Add another component from the application directory:

```shell copy
golem new . --template <template-name> --component-name my:component
```

See [Defining components](/next/develop/defining-components) and the language-specific SDK pages for implementation guidance.

## Build and deploy

<Steps>
### Build locally

Build every selected component from the application manifest:

```shell copy
golem build
```

From a component directory, manifest discovery selects that component. You can also select components explicitly with positional names, for example `golem build my:component my:other-component`.

### Review a deployment

Preview the deployment without staging or applying changes:

```shell copy
golem deploy --plan
```

Use `--full-diff` when you also want unchanged entries in the displayed deployment and environment-setup diff.

### Deploy the application

```shell copy
golem deploy
```

Deployments reconcile the application manifest as one application-level operation. Changed source is built automatically. Existing agents remain on their current component revision unless you explicitly request an update, redeployment, or reset.

</Steps>

### Choose what happens to existing agents

By default, `golem deploy` activates the new component revisions and leaves existing agents on their current revision with their current state. To change existing agents during a deployment, pass one of these mutually exclusive flags:

| Flag | Effect on existing agents | Typical use |
|------|---------------------------|-------------|
| `--update-agents auto` | Updates agents in place. Golem starts from the latest eligible periodic snapshot, or replays retained history when none is available. State is preserved. | Compatible code changes in shared or production environments |
| `--update-agents manual` | Updates agents in place through a snapshot-based migration that your code implements. State is preserved. | Breaking changes with a migration |
| `--redeploy-agents` | Deletes every agent and recreates it with the same name, environment variables, and configuration on the new revision. State is lost. | Development, when the agent list matters but state does not |
| `--reset` | Deploys, then deletes existing agents of the deployed components. Their state is lost, and agents are not recreated until invoked. The environment is retained. | Clear agent state in local development or CI |

`--reset` does not clear domains, HTTP and MCP deployments, secrets, retry policies, or plugins. The deployment still reconciles the manifest and can update these resources. Reset also permits incompatible component configuration changes and replacement of incompatible agent secrets; it is not a new environment or a reset of component revision history.

See [Deployment](/next/cli/app-manifest#build-and-deploy) for environment selection, [Updating agents](/next/develop/updating) for the update model, and the [Redeploying existing agents](/next/how-to-guides/common/golem-redeploy-agents) and [Updating running agents](/next/how-to-guides/common/golem-update-running-agents) guides.

## Expose an API

Define HTTP endpoints in agent code, then configure HTTP and MCP deployments in `golem.yaml` using `httpApi.deployments` and `mcp.deployments`. `golem deploy` deploys them alongside the application's components, so you do not need a separate manual delete-and-recreate cycle for each version.

Start with [Defining custom APIs](/next/invoke/making-custom-apis), then see the [application manifest reference](/next/app-manifest) for the deployment fields.

Direct invocation remains available when an application does not need a public endpoint. See [Invoke](/next/invoke) and [Agent communication](/next/concepts/communication).
