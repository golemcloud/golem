# Control durability guarantees

Durable agents record host interactions in the oplog. Recovery replays completed calls from their
recorded outcomes and repairs an eligible incomplete call at its own `Start`. It does not rerun a
group of completed effects. Guests cannot disable recording or change the execution cursor.

Use [SDK sagas](/next/develop/transactions) for workflows that need compensation. Use
[retry policies](/next/develop/retries) for retryable host operations. A trap is permanent;
return an error for a transient condition and use a retry schedule. Throwing after an HTTP response
does not retry that completed request.

## Remote-write safety

Golem treats remote writes as eligible for re-execution. An incomplete call can therefore be
retried even when the peer might already have applied it. External exactly-once behavior requires
the peer to enforce an idempotency key; a header alone is not a guarantee.

There is no guest idempotence-mode switch. Make writes duplicate-safe at the peer before relying
on retries or crash recovery. A lost response does not prove the write failed. Retry predicates
must not use `is-idempotent`: the host no longer supplies that property.

## Custom durable operations

Custom durable operations let SDK and library authors group host effects into one logical call
with a typed request and response. Completing the operation records the result; replay returns
that result without evaluating the body. Leaving it unfinished does not trigger a retry.
Recovery of an eligible incomplete custom call reruns its whole body, so the library must make
repeated attempts safe.

Application code should normally use the high-level SDK APIs and Golem's built-in durability instead. When writing an SDK or library, give each custom operation a stable name, a typed semantic request, and a recorded outcome. Classify it as a local or remote read or write. Use an SDK combinator to manage recording and replay rather than handling runtime resources yourself.

The examples below record a catalog revision read. The `readRevision` (or `read_revision`) adapter performs the physical read. The fixed catalog name is the request; the revision is the result. Each example calls one adapter without starting concurrent work.

```typescript
import { durable, durableAsync, FunctionType } from "@golemcloud/golem-ts-sdk"
import { z } from "zod"

const readRevisionSpec = {
  iface: "catalog-library",
  function: "read-revision",
  functionType: FunctionType.readRemote,
  requestSchema: z.string(),
  success: z.string(),
}

function catalogRevision(readRevision: (catalog: string) => string): string {
  return durable(readRevisionSpec, "public", () => readRevision("public"))
}

function catalogRevisionAsync(
  readRevision: (catalog: string) => Promise<string>
): Promise<string> {
  return durableAsync(readRevisionSpec, "public", () => readRevision("public"))
}
```

`durable` takes a synchronous body. A body that returns a promise makes `durable` throw a `TypeError`; use `durableAsync` for a body that awaits. An adapter exception or rejection leaves the operation unfinished instead of recording an error result. With an `error` schema, both functions take a body that returns a `Result` and record either variant.

`durableAsync` runs its body in the operation's own execution scope. Host calls that the body starts belong to the operation, also after an `await` and in timers, `queueMicrotask` callbacks and promise reactions that the body registers. Operations that the body starts are its children. Concurrent operations, for example inside `Promise.all`, and other work that runs while a body waits keep their own scopes. An operation finishes only after the operations that started inside it have settled, also when the body did not await them.

Limits:

- A parent stops waiting for children when they have all settled. An operation that starts after that, for example from a getter that reads the result, begins in the nearest enclosing operation that still waits, or in the invocation.
- Work that the body detaches and that runs after the operation finished does not belong to that operation. It runs in the nearest enclosing open operation, or in the invocation, and the runtime writes one report to stderr. Await or join the work that the body starts before the body returns.
- `FinalizationRegistry` callbacks and dynamic `import()` jobs run outside every custom operation.
- Each `await` inside an operation switches the scope in and out with two host calls, so a CPU-bound loop with many awaits runs slower inside an operation than outside it.
</Tabs.Tab>

```typescript
import { Effect, Schema } from "effect"
import { Durability } from "@golemcloud/effect-golem"

const catalogRevision = (
  readRevision: (catalog: string) => Effect.Effect<string, string>
) =>
  Durability.wrap({
    iface: "catalog-library",
    function: "read-revision",
    functionType: Durability.FunctionType.readRemote,
    requestSchema: Schema.String,
    success: Schema.String,
    error: Schema.String,
  }, "public", Effect.suspend(() => readRevision("public")))
```

`Durability.wrap` and `wrapInfallible` operations can run in concurrent fibers and can nest. Each fiber carries the execution scope of its operation, so Golem records the calls of a body under that operation and not under a sibling. A parent operation finishes only after its child operations close. Work that continues after its operation closes runs in the nearest open enclosing operation, or else in the agent invocation; do not let work continue after the agent method returns.

Timers in a body (`setTimeout`, `setImmediate`, `Effect.sleep`) sleep in the operation that started them. Fibers yield through Promise jobs, so wait for I/O with an effect such as `Deferred.await`, not with an `Effect.yieldNow` polling loop.
</Tabs.Tab>
<Tabs.Tab>
```rust
use golem_rust::durability::{Durability, DurableFunctionType};

fn catalog_revision(
    read_revision: impl FnOnce(&str) -> Result<String, String>,
) -> Result<String, String> {
    Durability::<String, String>::new(
        "catalog-library", "read-revision", DurableFunctionType::ReadRemote,
        &"public".to_string(),
    ).run(|| read_revision("public"))
}
```

For an async adapter, use `run_async`; its execution scope follows the body's polls. Detached tasks do not inherit that scope automatically, and no task may outlive the operation body.

The sequential-only restriction does not apply to Rust's scope integration. Use the SDK's custom durability combinators to manage each operation's execution scope.

A Rust panic is permanent. It does not retry the block or rewind completed effects.
</Tabs.Tab>

```scala
import golem.host.DurabilityApi
import golem.host.DurabilityApi.DurableFunctionType

def catalogRevision(readRevision: String => String): String =
  DurabilityApi.durable(
    "catalog-library",
    "read-revision",
    DurableFunctionType.ReadRemote,
    "public"
  )(readRevision("public"))
```

An adapter exception leaves the operation unfinished instead of recording an error result.

Use `durableAsync` for an asynchronous body. Concurrent `durableAsync` operations within one invocation are supported: each body, every `Future` callback it registers through a `golem.concurrent.GolemExecutionContext`, and every host call made from those callbacks belong to that operation, in any completion order. Ordinary host calls made outside the operation stay outside it. The body receives the scoped execution context as a context parameter, and it takes precedence over an imported one. Use `import golem.concurrent.Implicits.global` in agent code, and `GolemExecutionContext.wrap` for an execution context of your own.

```scala
import golem.concurrent.Implicits.global
import golem.host.DurabilityApi
import golem.host.DurabilityApi.DurableFunctionType
import scala.concurrent.Future

def bothRevisions(read: String => Future[String]): Future[List[String]] = {
  def revision(name: String) =
    DurabilityApi.durableAsync("catalog-library", "read-revision", DurableFunctionType.ReadRemote, name)(read(name))
  Future.sequence(List(revision("public"), revision("internal")))
}
```

Operations started in a body are nested. A parent finishes, or is dropped on failure, only after its nested operations have finished, so a nested operation that never completes keeps its parent open. A continuation that is already ready to run when the body and its nested operations finish, for example a `flatMap` on a nested operation that just completed, still runs before the parent finishes, and an operation it starts is nested too. An operation started after that point, for example by a callback that waited for a later host call, belongs to the nearest enclosing operation that has not started to finish, or to the root. `durable` is for synchronous bodies only; starting a `durableAsync` operation inside it fails.

The remaining limits:

- Callbacks run by other execution contexts, including `ExecutionContext.parasitic`, are not attributed to the operation that registered them.
- Work still running after its operation closed continues in the nearest open enclosing operation, or at the root. Host calls from work that escapes an outermost operation are not supported, because replay skips the completed body.
- Only Scala `Future` callbacks are covered. ZIO and Cats Effect fibers are not attributed to the operation that started them.
</Tabs.Tab>

```moonbit
fn catalog_revision(
  read_revision : (String) -> Result[String, String],
) -> Result[String, String] raise {
  @api.durable(
    "catalog-library", "read-revision", @api.ReadRemote, "public",
    () => read_revision("public"),
  )
}
```

For an async adapter, use `@api.durable_async`. Its execution scope follows the task that runs the body, so concurrent tasks of the same invocation, their ordinary host calls, and other custom operations are not attributed to it while it waits. Nested operations keep their parent.

A task spawned inside a body, including a stream or future producer, runs in the body's scope. Join every such task before the body returns, for example with a task group opened inside the body. A task that is still running when the body returns is cancelled, and the combinator raises `@api.DurabilityError::TaskOutlivedScope`; `@api.durable` runs a synchronous body, so any task it spawns gives this error. On success, `durable_async` waits for the stream and future producers its body started. When the body fails or is cancelled, the combinator cancels the tasks and producers of the scope and propagates the error at once. A producer that does not end at cancellation, such as a future producer that waits for a value the body never supplied, keeps the scope open until it ends; an agent invocation that returns while a scope is still open fails.
</Tabs.Tab>
<Tabs.Tab>
```go
import (
    "github.com/golemcloud/golem/sdks/go/golem"
    "github.com/golemcloud/golem/sdks/go/golem/durability"
)

func catalogRevision(
    readRevision func(string) golem.Result[string, string],
) golem.Result[string, string] {
    return durability.Run(durability.Spec{
        Interface: "catalog-library",
        Function: "read-revision",
        Type: durability.ReadRemote,
    }, "public", func() golem.Result[string, string] {
        return readRevision("public")
    })
}
```

`durability.Run` can run on several goroutines at once. Each goroutine keeps its own custom scope while a body waits, so host calls of goroutines outside the body stay outside the operation, and sibling and nested operations replay in their recorded order.

Goroutines that the body starts, directly or transitively, belong to the operation, and so do the callbacks of `time.AfterFunc` timers that the body sets. An `iter.Pull` iterator runs in the scope of the code that calls its `next` function, wherever the iterator was created. `Run` returns only after all of them have exited. A goroutine that never exits keeps the operation open, and the invocation fails without a result. Timers that the body set and that are still pending when the body returns are stopped.

A completed operation replays its result without running the body, so the rest of the program must observe the body only through its return value. Do not share variables or channels between the body and goroutines outside the operation. The runtime keeps the clock, the timers and the random state (map seeds and iteration order, `select`, `math/rand`) of each operation separate, so these do not leak out of a skipped body. Heap addresses are not separated: code after the operation must not depend on pointer values, such as the iteration order of a map keyed by pointers or `%p` output.
</Tabs.Tab>

The combinators serialize recorded outcomes, including declared error results. A completed operation replays its outcome without calling the adapter. This does not make arbitrary external side effects exactly once: recovery can repeat an unfinished body, so writes still need an external idempotency key or a transaction.

Keep requests and outcomes bounded. The request, response, operation name, and observational host calls may appear in oplog inspection, logs, and metrics. Use useful schemas and names, but redact credentials and personal data.

The custom-operation restrictions do not apply to ordinary built-in durable HTTP and RPC APIs.

## Nonresumable handles

A live connection is not durable state. Nonresumable handles report typed loss after
reconstruction. Handle the loss by explicitly opening and initializing a new session. Do not
silently resend pending traffic: loss does not prove that an earlier write never reached the peer.
See [WebSockets](/next/develop/websocket) for the supported reconstruction policies.

## Commit oplog

`oplog-commit` waits for replication before execution continues. It is a replication barrier,
not a transaction commit for external services, and it does not undo any effect.
