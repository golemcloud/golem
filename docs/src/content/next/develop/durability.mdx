# Control durability guarantees

Golem provides a set of functions components can call to control details of the durable execution engine.

### General concepts

The high-level SDKs let applications control idempotence, define atomic regions, commit the oplog, and change retry policies (discussed in [the next page](/next/develop/retries)).

All these features are regional - they can be changed for a section of the code within a single exported function.

    </Tabs.Tab>
    <Tabs.Tab>

    </Tabs.Tab>

### Custom durable operations

Applications normally rely on Golem's built-in durability and should not call the low-level `golem:durability@1.6.0` interface. It is intended for SDK and library authors who need to turn an otherwise raw operation into one logical durable call.

**TypeScript, Effect, Scala, MoonBit, and Go: sequential execution only.** In these SDKs, a custom operation's execution scope remains installed while its body waits. Do not run unrelated guest work concurrently with it, including ordinary host calls or another custom operation. A sibling's effects can be attributed to the wrong operation, causing incorrect replay or invocation failure. The SDKs do not reliably detect this misuse.

Sequential and properly nested custom operations remain supported. An asynchronous body can await host operations when no unrelated guest work runs during those waits. For example, a library can perform a sequence of remote calls and persist one typed result. Complete one custom operation before starting the next; await each nested operation before continuing its parent.

Do not leave detached promises, fibers, futures, tasks, goroutines, or callbacks running after the body exits. This applies to failure and cancellation as well as success. Stop and join outstanding work before closing the operation. A fail-fast combinator such as `Promise.all` does not join surviving siblings on rejection, and joining at the end does not make concurrent custom scopes supported.

| SDK | Custom operation restriction |
| --- | --- |
| TypeScript | Use `durable` sequentially; do not overlap it with other promises or callbacks. |
| Effect | Use `Durability.wrap` and `wrapInfallible` sequentially; do not overlap them with other fibers or concurrent effects. |
| Scala | Use `DurabilityApi.durable` and `durableAsync` sequentially; do not overlap them with other futures or callbacks. |
| MoonBit | Use `@api.durable` and `durable_async` sequentially; do not overlap them with other tasks. |
| Go | Use `durability.Run` sequentially; its blocking body can yield to other goroutines, so a synchronous-looking call is not a concurrency safeguard. |

These restrictions concern custom durability in the five SDKs above, not ordinary built-in durable HTTP/RPC APIs or the Rust scope integration described below.

A custom durable operation has a replay-stable UUID, a semantic request, and one typed response. The executor allocates the UUID synchronously when the operation begins. The UUID is independent of the request value, so a generator with no input is distinct from another concurrent call of the same generator.

1. `begin-custom-durable-invocation` takes the function name, typed request, and function type. It returns `live(live-invocation)` for a new or incomplete operation, or `replayed(recorded-response)` for an operation that already completed.
2. On the live path, keep the returned resource alive and install its execution scope while performing the operation's host effects. Begin installs the scope on the current guest task. Host calls initiated in the installed scope are recorded as replay-inert observational entries owned by the custom operation. Holding the resource alone does not install its scope.
3. Finish consumes the live resource and records the operation's complete success or failure result. On replay, decode and return the recorded response without executing the operation body.

Golem derives the UUID from the top-level idempotency key, the parent custom invocation when nested, and a deterministic ordinal in that logical parent's namespace. Child operations do not shift later root identities when a completed parent is skipped during replay. The function metadata and request are recorded and validated independently.

The live invocation is an affine resource: it can be finished only once. Dropping it without finishing removes observational ownership but does not write a matching `End` entry. If recovery later replays the incomplete custom operation, its whole body runs again.

Dropping the resource does not trigger a retry. A deterministic trap outside an atomic region fails the agent without retry; inside an atomic region, the region is retried according to the applicable retry policy. When recovery replays an incomplete custom operation, it runs the **whole custom operation**, not individual effects inside it. Library authors must therefore choose an appropriate function type and make repeated attempts safe, for example with an external idempotency key or transactional API.

Requests, responses, operation names, and observational host calls can be visible to oplog search, logs, metrics, and other observability tooling. Record useful names and schemas, but redact secrets and avoid putting unnecessary or unbounded payloads into observable values.

Use the SDK combinator for this lifecycle instead of managing the affine resource directly: `golem_rust::durability::Durability::run*` in Rust, `durable` in TypeScript, `Durability.wrap`/`wrapInfallible` in Effect TypeScript, `DurabilityApi.durable`/`durableAsync` in Scala, `@api.durable`/`durable_async` in MoonBit, or `durability.Run` in Go. Each combinator starts the invocation before evaluating the body, skips the body on replay, finishes after the complete live body returns, and drops any live resource left unfinished.

In Rust, `Durability::new` only prepares the request. Synchronous runners begin when called; async runners begin on their first poll, including call observation for logs and metrics. An async runner that is never polled opens no invocation. Code between construction and execution is outside that custom operation. Async runners install their scope while polling or destroying the body and restore the actual caller's scope afterwards. Concurrent Rust futures can therefore run sibling custom operations without falsely nesting them. Borrowed and non-`Send` futures remain supported.

Nested custom operations must finish or be dropped before their parent finishes. Keep nested work inside the body and await it there; detached `spawn_local` work does not automatically acquire its parent's scope. Restoring a context snapshot does not make escaped live children safe.

The low-level `exchange-custom-invocation-context` operation lets a guest runtime capture, install, and restore a resident execution context without yielding or writing to the oplog. A snapshot cannot be installed in another invocation or after any of its custom scopes have closed. It does not keep those scopes alive. The Rust SDK uses this mechanism around execution and destruction. TypeScript, Effect, Scala, MoonBit, and Go combinators do not yet propagate scopes across concurrent continuations. Their sequential and properly nested use remains unchanged; concurrent custom operations in those SDKs are not fixed by the new host mechanism or generated bindings.

In Effect TypeScript, `Durability.wrap` records both successes and typed failures described by its error schema. Defects, interruption, and response-encoding failures leave the live invocation unfinished. `Durability.wrapInfallible` accepts an Effect with no typed error channel.

### Idempotence mode

Golem assumes that HTTP requests are idempotent by default. This means that in case of a failure, if the system cannot determine whether the request successfully reached the target or not, it will be retried.

<Tabs items={["TypeScript", "Effect TypeScript", "Rust", "Scala", "MoonBit", "Go"]} storageKey="nextra-tabs-language-sdk">
    <Tabs.Tab>
        This behavior can be changed using the `withIdempotenceMode` function:

        ```typescript
        import {withIdempotenceMode} from "@golemcloud/golem-ts-sdk"

        const result: string = withIdempotenceMode(false, () => {
          // this closure runs with idempotence mode disabled
          return "hello"
        })
        ```
    </Tabs.Tab>
    <Tabs.Tab>
        Use `Durability.withIdempotenceMode` to scope the setting to an Effect:

        ```typescript
        import { Effect } from "effect"
        import { Durability } from "@golemcloud/effect-golem"

        const result = Durability.withIdempotenceMode(
          false,
          Effect.succeed("hello"),
        )
        ```
    </Tabs.Tab>
    <Tabs.Tab>
        This behavior can be changed using the `with_idempotence_mode` function:

        ```rust
        use golem_rust::with_idempotence_mode;

        let result: &str = with_idempotence_mode(false, || {
          // this block runs with idempotence mode disabled
          "hello"
        });
        ```
    </Tabs.Tab>
    <Tabs.Tab>
        This behavior can be changed using the `Guards.withIdempotenceMode` function:

        ```scala
        import golem.Guards

        import scala.concurrent.Future

        val result: Future[String] =
          Guards.withIdempotenceMode(false) {
            // this block runs with idempotence mode disabled
            Future.successful("hello")
          }
        ```
    </Tabs.Tab>
    <Tabs.Tab>
        Assuming the `golemcloud/golem_sdk/api` package is imported as `@api`, use the `with_idempotence_mode` function:

        ```moonbit
        let result : String = @api.with_idempotence_mode(false, fn() {
          // this callback runs with idempotence mode disabled
          "hello"
        })
        ```
    </Tabs.Tab>
    <Tabs.Tab>
        This behavior can be changed using the `durability.WithIdempotenceMode` function, which returns a function restoring the previous mode:

        ```go
        import "github.com/golemcloud/golem/sdks/go/golem/durability"

        result := func() string {
            defer durability.WithIdempotenceMode(false)()
            // this function runs with idempotence mode disabled
            return "hello"
        }()
        ```
    </Tabs.Tab>
</Tabs>

With disabled idempotence mode, in case Golem cannot determine if the request was sent or not, it won't retry it, but the agent will fail.

### Atomic regions

By default, side effects are persisted and retried one by one. It is possible to group them together into atomic regions, in which case the execution is retried for some reason (the agent failed or interrupted within the region), all the side effects will be reexecuted.

<Tabs items={["TypeScript", "Effect TypeScript", "Rust", "Scala", "MoonBit", "Go"]} storageKey="nextra-tabs-language-sdk">
    <Tabs.Tab>
        The `golem-ts-sdk` library exports the `atomically` function for using atomic regions:

        ```typescript
        import {atomically} from "@golemcloud/golem-ts-sdk"

        const result: [string, string] = atomically<[string, string]>(() => {
          const firstResult: string = firstSideEffect()
          const secondResult: string = secondSideEffect(firstResult)
          return [firstResult, secondResult]
        })
        ```
    </Tabs.Tab>
    <Tabs.Tab>
        `Durability.atomically` runs an Effect in an atomic region:

        ```typescript
        import { Effect } from "effect"
        import { Durability } from "@golemcloud/effect-golem"

        const result = Durability.atomically(
          Effect.gen(function* () {
            const first = yield* firstSideEffect
            const second = yield* secondSideEffect(first)
            return [first, second] as const
          }),
        )
        ```
    </Tabs.Tab>
    <Tabs.Tab>
        The `golem_rust` crate exports the `atomically` function for using atomic regions:

        ```rust
        use golem_rust::atomically;

        let result = atomically(|| {
            let first_result = first_side_effect();
            let second_result = second_side_effect(&first_result);
            (first_result, second_result)
        });
        ```
    </Tabs.Tab>
    <Tabs.Tab>
        The Scala SDK exposes `Guards.atomically` for using atomic regions:

        ```scala
        import golem.Guards

        import scala.concurrent.Future

        val result: Future[(String, String)] =
          Guards.atomically {
            val firstResult = firstSideEffect()
            val secondResult = secondSideEffect(firstResult)
            Future.successful((firstResult, secondResult))
          }
        ```
    </Tabs.Tab>
    <Tabs.Tab>
        Assuming the `golemcloud/golem_sdk/api` package is imported as `@api`, use the `with_atomic_operation` function:

        ```moonbit
        let result : (String, String) = @api.with_atomic_operation(fn() {
          let first_result : String = first_side_effect()
          let second_result : String = second_side_effect(first_result)
          (first_result, second_result)
        })
        ```
    </Tabs.Tab>
    <Tabs.Tab>
        The `durability` package exports the `Atomically` function for using atomic regions. Its callback returns nothing, so results are captured in outer variables:

        ```go
        import "github.com/golemcloud/golem/sdks/go/golem/durability"

        var firstResult, secondResult string
        durability.Atomically(func() {
            firstResult = firstSideEffect()
            secondResult = secondSideEffect(firstResult)
        })
        ```

        A panic in the callback traps the component at once, even where something above would recover it, so the region stays open and runs again on retry.
    </Tabs.Tab>

</Tabs>
