# Publishing packages

Give the package a name and an exact version in the root `golem.yaml`:

```yaml
package:
  name: my-package
  version: 1.0.0
```

Use a SemVer version without build metadata. The name and version are part of
the digest-covered package config. Repack any archive made before the package
config included this identity.

Build your application before you pack it. The package commands use the built
WebAssembly components and the declarations for the selected manifest environment
and preset. They do not deploy the application or log in to a server.

```shell
golem build
golem package pack --output my-package.tar
golem publish --dry-run
```

`golem package pack` writes an OCI image layout in a tar archive and prints its
SHA-256 manifest digest. The default filename is `golem-package.tar`.
`golem publish --dry-run` validates the same package and prints the same digest
without writing an archive or contacting a server.

Neither command includes the publisher's HTTP API or MCP deployments in the
package. Both report the omitted exports by kind and domain name across the
manifest's environments. In JSON and YAML output, `omittedExports` contains
entries with `kind` (`http-api` or `mcp`) and `name` (the resolved domain).

Initial files must resolve
inside the application root. Download any initial file with an HTTP or HTTPS
source and declare it as a local file before packing. A typed `File` default is
a path relative to the manifest that supplies it and must resolve inside the
application root. Packing embeds its contents. Ordinary string defaults stay
literal, even if they look like paths. To package a directory, point to a
dedicated input directory, not the application root. Keep build outputs and the
package archive outside that directory. File defaults are supported for
component and agent config, not tool or middleware provisions.

**Everything in a package is visible to anyone with `read` access.** This includes
the WebAssembly, initial files, `File` contents, extracted metadata, config defaults, environment
values, plugin parameters, and initial cards. Environment templates are stored
as written, including variable names; packing does not substitute their values.
Anyone you give the tar file to can also read its contents. Do not put
credentials in any of these inputs. Package defaults cannot name a secret or use
a `$config` reference, even inside a record or list.

## Install a file package

From the application that will use the package, run `golem install ./my-package.tar`.
Install verifies the archive without running its components. It records the file
source, exact version, and digest in `packages:` in the root `golem.yaml` and
in `golem.lock`. Commit both files. Put the archive inside the application to
record a portable path, and make the archive available on other machines that
need to build it.

Build uses a verified archive from the per-user cache or reads the source on a
cache miss. It unpacks under `golem-temp` and uses the publisher's metadata
instead of running the installed components. Build and deploy do not change
`golem.lock`. If a pin is missing or differs, run `golem install` with the
intended archive to repair it.

Deploying an installed package does not expose any of the publisher's HTTP
routes or MCP endpoints by default. To expose an installed agent, declare the
HTTP API or MCP deployment in your own `golem.yaml` and deploy the application.

To select tools from an archive, add declarations under `tools:` after
`golem install`. Reference the same package entry for each tool. The declaration
key is the local name used in bindings and calls:

```yaml
tools:
  local-echo:
    package: my-package
    tool: echo
  local-search:
    package: my-package
    tool: search
```

If a package contains only one tool, you can omit `tool:`. If you do not declare
any tools for a package, its tools keep their published names. Otherwise only the
tools you declare are registered. Local names must be unique, and selecting tools
does not change the archive pin in `golem.lock`.

### Copy an embedded file default

Do not edit files in `golem-temp`. To make an editable copy of a packaged `File`
default, use the archive's `index.json` to find its manifest digest, then the
manifest's `config.digest` to find its config blob. Each digest `sha256:<hex>`
names an archive entry `blobs/sha256/<hex>`. In the config blob, find the
`fileDefaults` entry for the field and take its `digest`. For a regular file,
copy that blob into your application without extracting the archive in place:

```shell
mkdir -p config
tar -xOf my-package.tar 'blobs/sha256/<file-default-hex>' > config/my-default.txt
```

Replace `<file-default-hex>` with the hexadecimal part of the file's digest.
Edit `config/my-default.txt`, not the blob or the unpacked file. This creates
only a local copy: it does not change the installed default or make the copied
file visible to a deployed guest.

## Work on a package locally

Point to the package directory instead of an archive in the consuming
application's root `golem.yaml`:

```yaml
packages:
  my-package:
    path: ../my-package
```

The directory must contain a `golem.yaml` with a `package:` identity that matches
the entry name. Relative paths start at the consuming application's root.
`golem build` uses the current source and builds its components as local code.
Edit the files in that directory and rebuild; you do not need to pack or install
the package after each edit. A development path has no entry in `golem.lock` and
cannot be included in a published package.

Registry publishing is not available through these commands.
