# User-Defined Snapshotting

Golem recovers agent state by **replaying the oplog** — the log of all operations performed by the agent. For long-running or CPU-heavy agents, this replay can become slow. Golem 1.5 introduces **user-defined snapshotting**, allowing agents to opt in to periodic snapshots so that recovery only needs to replay entries recorded _after_ the last snapshot.

Snapshotting also enables **manual agent updates** between incompatible versions — see [Updating Agents](/next/develop/updating) for details.

<Callout type="info">
    Automatic snapshotting is optional. Without it, recovery replays from the last successful manual-update snapshot, if one exists; otherwise it replays the full oplog.
</Callout>

## Default snapshotting implementation

Each language SDK can generate JSON saving and loading when the complete agent state has an explicit JSON-deserialization contract. Automatic loading is not generated for arbitrary state: use custom snapshotting when your SDK cannot deserialize the complete state.

<Tabs items={["TypeScript", "Effect TypeScript", "Rust", "Scala", "MoonBit"]} storageKey="nextra-tabs-language-sdk">
    <Tabs.Tab>
        Provide a state schema in the snapshotting configuration and **do not** provide a custom `snapshot: { save, load }` block. The SDK serializes and restores the schema-defined state as JSON:

        ```typescript
        snapshotting: {
            state: z.object({ value: z.number() }),
            policy: { everyNInvocations: 1 },
        }
        ```

        A bare enabled policy without `state` requires a custom `save`/`load` pair.
    </Tabs.Tab>
    <Tabs.Tab>
        Declare the saved value with `Snapshot.define(...)` and use a matching implementation strategy such as `Snapshot.ref()`:

        ```typescript
        snapshotting: Snapshot.define({
          schema: Schema.Struct({ value: Schema.Number }),
          policy: Snapshot.policy.everyN(1),
        })

        // In .implement({ ... }):
        snapshot: Snapshot.ref<{ value: number }>()
        ```
    </Tabs.Tab>
    <Tabs.Tab>
        If your agent struct implements `Serialize` and `DeserializeOwned` (from [serde](https://serde.rs/)), **do not** override the `save_snapshot` and `load_snapshot` methods. The SDK will use a default JSON-based implementation. Ordinary owned structs commonly satisfy these bounds by deriving `Serialize` and `Deserialize`.
    </Tabs.Tab>
    <Tabs.Tab>
        Mix `Snapshotted[S]` into the implementation and provide a `Schema[S]` (from [zio-blocks-schema](https://github.com/zio/zio-blocks)). The SDK handles JSON, while a companion `loadSnapshot(state, context)` factory constructs the complete implementation instance.
    </Tabs.Tab>
    <Tabs.Tab>
        If your agent struct derives `ToJson` and `@json.FromJson`, the SDK auto-generates JSON saving and a restoration factory.
    </Tabs.Tab>
</Tabs>

## Custom snapshotting

You can implement custom saving and restoration to control exactly how agent state is serialized. Saving runs on the live instance. Loading is a separate factory that returns the complete state or instance; the SDK never runs the normal agent initialization path first and then hands that instance to the loader. The following example shows a counter agent that saves its count as raw bytes:

<Tabs items={["TypeScript", "Effect TypeScript", "Rust", "Scala", "MoonBit"]} storageKey="nextra-tabs-language-sdk">
    <Tabs.Tab>
        Provide a `snapshot: { save, load }` block on `.implement(...)`. `save()` has the agent state as `this`. `load(bytes, context)` has no `this` and returns a complete fresh state object:

        ```typescript
        import { z } from 'zod';
        import { defineAgent, method } from '@golemcloud/golem-ts-sdk';

        export const Counter = defineAgent({
            name: 'Counter',
            id: { name: z.string() },
            snapshotting: { everyNInvocations: 1 },
            methods: {
                increment: method({ input: {}, returns: z.number() }),
            },
        });

        export const CounterImpl = Counter.implement({
            init: () => ({ value: 0 }),
            methods: {
                increment() {
                    this.value += 1;
                    return this.value;
                },
            },
            snapshot: {
                save() {
                    const snapshot = new Uint8Array(8);
                    new DataView(snapshot.buffer).setFloat64(0, this.value);
                    return snapshot;
                },
                load(bytes, _context) {
                    const value = new DataView(
                        bytes.buffer,
                        bytes.byteOffset,
                        bytes.byteLength,
                    ).getFloat64(0);
                    return { value };
                },
            },
        });
        ```
    </Tabs.Tab>
    <Tabs.Tab>
        Select binary snapshots on the definition and provide `save` and `restore` effects on the implementation. Restoration constructs fresh state and does not run `init` first:

        ```typescript
        import { Effect, Ref } from "effect"
        import { Snapshot } from "@golemcloud/effect-golem"

        // In defineAgent({ ... }):
        snapshotting: Snapshot.custom({
          policy: Snapshot.policy.everyN(1),
        })

        // In .implement({ ... }):
        snapshot: {
          save: (state) =>
            Ref.get(state).pipe(
              Effect.map((value) => {
                const bytes = new Uint8Array(8)
                new DataView(bytes.buffer).setFloat64(0, value)
                return bytes
              }),
            ),
          restore: (bytes, _context) =>
            Ref.make(
              new DataView(bytes.buffer, bytes.byteOffset, bytes.byteLength)
                .getFloat64(0),
            ),
        }
        ```
    </Tabs.Tab>
    <Tabs.Tab>
        Define instance `save_snapshot` and an associated `load_snapshot` factory. The factory returns `Self`; it does not receive `&mut self`:

        ```rust
        async fn save_snapshot(&self) -> Result<Vec<u8>, String> {
            Ok(self.value.to_le_bytes().to_vec())
        }

        async fn load_snapshot(
            bytes: Vec<u8>,
            _context: golem_rust::agentic::SnapshotRestoreContext,
        ) -> Result<Self, String> {
            let arr: [u8; 4] = bytes
                .try_into()
                .map_err(|_| "Invalid snapshot".to_string())?;
            Ok(Self {
                value: u32::from_le_bytes(arr),
            })
        }
        ```
    </Tabs.Tab>
    <Tabs.Tab>
        Define `saveSnapshot()` on the implementation and `loadSnapshot(...)` on its companion object:

        ```scala
        final class CounterImpl(private val name: String) extends Counter {
          private var value: Int = 0

          def saveSnapshot(): Future[Array[Byte]] =
            Future.successful {
              val buffer = java.nio.ByteBuffer.allocate(4)
              buffer.putInt(value)
              buffer.array()
            }
        }

        object CounterImpl {
          def loadSnapshot(
            bytes: Array[Byte],
            context: SnapshotRestoreContext
          ): Future[CounterImpl] = Future.successful {
            val instance = new CounterImpl(context.identity[String](0))
            instance.value = java.nio.ByteBuffer.wrap(bytes).getInt()
            instance
          }
        }
        ```
    </Tabs.Tab>
    <Tabs.Tab>
        Implement the saving-only `@agents.Snapshottable` trait and define a separate static `load_snapshot` factory:

        ```moonbit
        pub impl @agents.Snapshottable for Counter with save_snapshot(self) {
          let arr: Array[Byte] = []
          for i = 7; i >= 0; i = i - 1 {
            arr.push(((self.value >> (i * 8)).to_int() & 0xff).to_byte())
          }
          Bytes::from_array(arr)
        }

        pub fn Counter::load_snapshot(
          bytes: Bytes,
          context: @agents.SnapshotRestoreContext,
        ) -> Result[Counter, String] {
          if bytes.length() != 8 {
            return Err("Expected an 8-byte snapshot")
          }
          let mut value: UInt64 = 0
          for i = 0; i < 8; i = i + 1 {
            value = value | (bytes[i].to_uint64() << ((7 - i) * 8))
          }
          let name: String = context.identity(0) catch {
            error => return Err(error.to_string())
          }
          Ok({ name, value })
        }
        ```
    </Tabs.Tab>
</Tabs>

## How snapshot restoration runs

Snapshot loading is a specially supported SDK lifecycle operation, not an agent method. The SDKs keep it separate from normal initialization and install the returned state or instance only after restoration succeeds. Restore context exposes the agent identity and restored principal, plus the phantom ID and fresh configuration where applicable.

Golem runs snapshot loading in read-only mode and writes nothing from it to the oplog. Decoding, local computation, fresh randomness, configuration access, and other permitted reads can be used to construct the restored value. Durable host calls classified as writes, and outgoing HTTP or agent RPC calls, are rejected before they take effect. This restriction is not a general filesystem write sandbox: local filesystem writes are not blocked by it.

If loading fails, partial state is discarded:

- A manual update fails and the agent remains on its previous component version.
- If an automatic snapshot is rejected by its loader, or loading or subsequent replay fails deterministically, Golem rejects only that snapshot record and recreates the component. The next start uses the usable automatic snapshot before the rejected one, if there is one. When no usable automatic snapshot is left, Golem replays from the last successful manual-update snapshot, or from the beginning if none exists. Transient failures and resource-limit failures can instead propagate or cause recovery to retry.
- Failure to load the baseline snapshot from an already completed manual update cannot fall back to pre-update history.

## Configuring snapshot-based recovery

To enable snapshotting, add a `snapshotting` option to your agent definition:

<Tabs items={["TypeScript", "Effect TypeScript", "Rust", "Scala", "MoonBit"]} storageKey="nextra-tabs-language-sdk">
    <Tabs.Tab>
        Pass the `snapshotting` option to `defineAgent(...)`:

        ```typescript
        export const Counter = defineAgent({
            name: 'Counter',
            id: { name: z.string() },
            snapshotting: {
                state: z.object({ value: z.number() }),
                policy: { periodicSeconds: 5 },
            },
            methods: {
                increment: method({ input: {}, returns: z.number() }),
            },
        });
        ```
    </Tabs.Tab>
    <Tabs.Tab>
        Pass a `Snapshot` definition to `snapshotting`:

        ```typescript
        snapshotting: Snapshot.define({
          schema: Schema.Struct({ value: Schema.Number }),
          policy: Snapshot.policy.periodic("5 seconds"),
        })
        ```
    </Tabs.Tab>
    <Tabs.Tab>
        ```rust
        #[agent_definition(snapshotting = "periodic(5s)")]
        ```
    </Tabs.Tab>
    <Tabs.Tab>
        ```scala
        @agentDefinition(snapshotting = "periodic(5 seconds)")
        ```
    </Tabs.Tab>
    <Tabs.Tab>
        ```moonbit
        #derive.agent(snapshotting="every_n(5)")
        ```
    </Tabs.Tab>
</Tabs>

The available policy forms are listed below. Exact spelling and policy support vary by SDK, as shown in the examples above.

| Option | Description |
|---|---|
| `disabled` | Automatic snapshot creation is disabled. Recovery still uses the last successful manual-update snapshot, if one exists. |
| `enabled` | Uses the server-side default snapshotting configuration, which may be disabled. |
| `every(N)` | Takes a snapshot every **N** successful invocations. |
| `periodic(duration)` | Schedules snapshots at safe invocation boundaries after each **duration** interval (e.g. `5s`, `1m`). |

## Agent files and snapshots

An application snapshot holds only the bytes that your snapshot code returns. Golem does not write file changes to the oplog. Without help, a start from a snapshot record loses every file that the agent wrote before the record, because the replay does not run that code again. The same happens to the files of an agent after a manual update.

A **filesystem snapshot** fixes this. It is a copy of the agent's [filesystem](/next/develop/agent-filesystem) that Golem keeps in blob storage next to the application snapshot. Golem makes filesystem snapshots only on executors whose operator enabled them. See [Availability](#availability).

### Restore points

The application snapshot and the filesystem snapshot of one snapshot record form one restore point. Golem uses a restore point only when both parts are there:

- When the filesystem snapshot is missing, is not confirmed yet, or does not restore, Golem uses an older restore point or a full replay of the oplog.
- When the application snapshot does not load, Golem does the same. See [How snapshot restoration runs](#how-snapshot-restoration-runs).
- For a manual update, the update fails, and the agent stays on its current revision.

A snapshot record without a filesystem snapshot name is also a valid restore point on an executor with filesystem snapshots. It means that the agent's files were exactly the initial files of the component revision. A start from it puts the initial files in place.

### When Golem captures the files

Golem captures the files at the same boundary where it takes the application snapshot. No invocation runs at that moment. The order is:

1. Your snapshot code runs and returns the application snapshot.
2. Golem stops new file calls of the agent, waits for the calls in progress, and copies the agent's files on the executor's disk. The copy shares the data blocks of the files, so it is fast and the agent waits only for it.
3. Golem writes the snapshot record into the oplog. The record holds the name of the filesystem snapshot.
4. The agent continues with its next invocation. Golem uploads the copy to blob storage in the background.
5. When the upload is complete, Golem writes a second oplog entry that confirms the name.

The capture keeps the agent's files, directories, symbolic links, hard links and modification times. Golem leaves out an untouched read-only initial file, because the component revision already has its content. Golem uploads nothing when the files are exactly the initial files of the component revision, or when nothing changed the files since the last confirmed filesystem snapshot. In the second case the new record uses the name of that snapshot and is confirmed at once.

Ephemeral agents get no filesystem snapshot. Golem never restores an ephemeral agent, so their snapshot records have no filesystem snapshot name.

`golem agent oplog <agent_id>` shows the name on each `SNAPSHOT` entry as `filesystem:`, and a `SNAPSHOT CONFIRMED` entry for each confirmed upload.

### When a snapshot becomes usable

A snapshot record with a filesystem snapshot name becomes usable only when its confirmation entry follows it in the oplog. A record without a name is usable at once.

At most one upload runs for each agent. While it runs, Golem skips the next automatic snapshot of the agent: your snapshot code does not run, and Golem writes no record. There is one exception. When an upload failed and waits to try again, the next automatic snapshot replaces it. The record of the replaced upload never becomes usable. Golem also skips an automatic snapshot when the free space of the executor's volume is low.

If the agent stops while its upload runs, the stop does not wait for the upload. A later start of the agent on the same executor waits for the upload, for at most a limit that the operator sets, and then checks the store. A start on any executor confirms the snapshot itself when the store holds the whole snapshot. An upload that still runs when the agent moves to another executor is lost for that start.

### What the agent sees after a restart

At a start, Golem selects the newest usable automatic snapshot record of the current component revision. Before your snapshot loading code runs, Golem downloads the filesystem snapshot of that record and puts the files in place. Your loading code can therefore read the files. Then Golem replays the oplog entries after the record.

When the newest record is not confirmed yet, Golem uses the usable record before it. Golem restores the files of that older record, loads its application snapshot, and replays all the oplog entries after it. The replay includes the invocations after the unconfirmed record, so the agent gets the same state and the same files as before the restart. The only cost is a longer replay. Golem also uses the older record when the newest confirmed filesystem snapshot does not restore. A start uses at most these two automatic snapshot records. When neither is usable, Golem uses the last manual-update snapshot, or replays the full oplog.

After a restore, the files are the files that the agent had at the capture. This is also what a full replay of the oplog rebuilds. Hard links come back as hard links.

### Manual updates

A manual update also captures the files. The update waits until the upload of the filesystem snapshot is complete, and only then writes its update record. If an automatic snapshot upload of the agent runs at that moment, the update waits for the upload that runs now, but not for later retries of it. The update waits for at most a limit that the operator sets, 60 seconds by default. When the upload still runs after this limit, the update fails.

At the start in the target revision, Golem restores the files and then applies the initial files of the target revision. The files that the agent wrote in the old revision are kept. If the target revision changes the declaration of an initial file at a path where the agent wrote or changed the file, the update fails. The error names the path, and the agent stays on its current revision with its files.

### When a snapshot fails

| Failure                                          | Automatic snapshot                                                                                                                               | Manual update                                                    |
| ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------- |
| Your snapshot code fails                         | Golem writes no snapshot record and restarts the agent. The agent replays its oplog from its last restore point, so each failed save costs a restart and a replay. | The update fails, and the agent stays on its current revision.   |
| The capture of the files fails or waits too long | Golem writes no snapshot record. The agent continues, and the next snapshot boundary tries again.                                                | The update fails, and the agent stays on its current revision.   |
| The upload fails after its retries               | The snapshot record stays without a confirmation. A start uses an older restore point.                                                          | The update fails, and the agent stays on its current revision.   |
| The filesystem snapshot does not restore         | The start uses the usable record before it, the last manual-update snapshot, or a full replay.                                                  | The start of the agent fails with a visible cause.               |

### Code that leaves a stream write unflushed

Golem can capture the files only when no file call of the agent is in progress. A write to a WASI output stream of a file stays in progress until the code flushes or polls the stream. If an invocation returns while such a write is still in progress, the capture waits for at most a limit that the operator sets, 5 seconds by default. Then it gives up:

- For an automatic snapshot, Golem writes no snapshot record, and the agent continues. The next snapshot boundary tries again.
- For a manual update, the update fails.

To keep your agent snapshottable, flush each output stream before the invocation returns.

### Cold-start cost

A restore downloads the whole filesystem snapshot before the agent's code runs. A large tree of files makes the start of the agent slower, in proportion to the size of the tree. The executor also limits how many restores run at the same time. A start that has no free restore slot waits for one.

### Delete, revert and fork

- **Delete.** When you delete an agent, Golem deletes all its filesystem snapshots from blob storage in the background. An agent that you create again with the same id starts with no filesystem snapshots.
- **Revert.** When you revert an agent, Golem deletes the filesystem snapshots of the snapshot records in the reverted part of the oplog. It keeps a filesystem snapshot that a remaining record uses. A start after the revert uses the remaining snapshot records.
- **Fork.** When you fork an agent, Golem copies the filesystem snapshots of the source agent to the new agent before the new agent exists. When the new agent would start from a manual-update snapshot whose filesystem snapshot is not in the store, Golem refuses the fork. The error names the oplog index of the fork. This also happens on an executor without filesystem snapshots.

### Availability

Filesystem snapshots are disabled by default. Only an executor with managed XFS storage can enable them. See [Filesystem Snapshots](/next/operate/filesystem_snapshots) for the operator setup.

On an executor without filesystem snapshots, Golem keeps the earlier behaviour:

- Snapshot records have no filesystem snapshot name, and Golem does not save the agent's files.
- After a start from a snapshot record, the files that the agent wrote before the record do not exist.
- After a manual update, the files of the old revision do not exist. Your snapshot code must save the file contents in the application snapshot if the agent needs them.

### SQLite databases in TypeScript agents

Typed state snapshotting in the TypeScript SDK handles each top-level `DatabaseSync` field (from `node:sqlite`) of the agent:

- An **in-memory** or **temporary** database is saved in the application snapshot with its contents.
- A **file-backed** database is not saved in the application snapshot. The snapshot holds only the location of the file. The filesystem snapshot restores the file, and the load opens the database again at that location.

A typed snapshot with a file-backed database relies on filesystem snapshots. An executor without filesystem snapshots keeps the earlier behaviour, in which the files that the agent wrote before a snapshot are not restored. On such an executor, use an in-memory database, or custom `save` and `load` functions.

These cases make the save fail:

- A database with an open transaction, also a file-backed one. Commit or roll back before the invocation ends.
- A field that holds a `StatementSync`, a `Session` or a `SQLTagStore`.

A failed save has the effect in [When a snapshot fails](#when-a-snapshot-fails): for an automatic snapshot, Golem restarts the agent, which replays its oplog; for a manual update, the update fails.

After a load from an automatic snapshot, the replay of the later oplog entries must read the database as the live agent did. This holds only while the database fits in SQLite's page cache and the live agent had read every page of it. When it does not hold, the start from that snapshot can fail, and Golem uses an older snapshot or a full replay. The state of the agent stays correct, but the start takes longer.

The [TypeScript custom snapshot guide](/next/how-to-guides/ts/golem-custom-snapshot-ts#sqlite-databases) gives the full rules and limits.

## Observability

When using the default (JSON-based) snapshotting implementation, snapshot entries recorded in the oplog contain the serialized JSON state of the agent. This makes it easy to inspect agent state at any snapshot point for debugging purposes.

<Callout type="info">
    Snapshotting is also used when [updating agents](/next/develop/updating) across incompatible versions, allowing Golem to capture the agent's state before applying the update.
</Callout>
