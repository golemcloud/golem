# User-Defined Snapshotting

Golem recovers agent state by **replaying the oplog** — the log of all operations performed by the agent. For long-running or CPU-heavy agents, this replay can become slow. Golem 1.5 introduces **user-defined snapshotting**, allowing agents to opt in to periodic snapshots so that recovery only needs to replay entries recorded _after_ the last snapshot.

Snapshotting also enables **manual agent updates** between incompatible versions — see [Updating Agents](/next/develop/updating) for details.

<Callout type="info">
    Automatic snapshotting is optional. Without it, recovery replays from the last successful manual-update snapshot, if one exists; otherwise it replays the full oplog.
</Callout>

## Default snapshotting implementation

Each language SDK can generate JSON saving and loading when the complete agent state has an explicit JSON-deserialization contract. Automatic loading is not generated for arbitrary state: use custom snapshotting when your SDK cannot deserialize the complete state.

<Tabs items={["TypeScript", "Effect TypeScript", "Rust", "Scala", "MoonBit"]} storageKey="nextra-tabs-language-sdk">
    <Tabs.Tab>
        Provide a state schema in the snapshotting configuration and **do not** provide a custom `snapshot: { save, load }` block. The SDK serializes and restores the schema-defined state as JSON:

        ```typescript
        snapshotting: {
            state: z.object({ value: z.number() }),
            policy: { everyNInvocations: 1 },
        }
        ```

        A bare enabled policy without `state` requires a custom `save`/`load` pair.
    </Tabs.Tab>
    <Tabs.Tab>
        Declare the saved value with `Snapshot.define(...)` and use a matching implementation strategy such as `Snapshot.ref()`:

        ```typescript
        snapshotting: Snapshot.define({
          schema: Schema.Struct({ value: Schema.Number }),
          policy: Snapshot.policy.everyN(1),
        })

        // In .implement({ ... }):
        snapshot: Snapshot.ref<{ value: number }>()
        ```
    </Tabs.Tab>
    <Tabs.Tab>
        If your agent struct implements `Serialize` and `DeserializeOwned` (from [serde](https://serde.rs/)), **do not** override the `save_snapshot` and `load_snapshot` methods. The SDK will use a default JSON-based implementation. Ordinary owned structs commonly satisfy these bounds by deriving `Serialize` and `Deserialize`.
    </Tabs.Tab>
    <Tabs.Tab>
        Mix `Snapshotted[S]` into the implementation and provide a `Schema[S]` (from [zio-blocks-schema](https://github.com/zio/zio-blocks)). The SDK handles JSON, while a companion `loadSnapshot(state, context)` factory constructs the complete implementation instance.
    </Tabs.Tab>
    <Tabs.Tab>
        If your agent struct derives `ToJson` and `@json.FromJson`, the SDK auto-generates JSON saving and a restoration factory.
    </Tabs.Tab>
</Tabs>

## Custom snapshotting

You can implement custom saving and restoration to control exactly how agent state is serialized. Saving runs on the live instance. Loading is a separate factory that returns the complete state or instance; the SDK never runs the normal agent initialization path first and then hands that instance to the loader. The following example shows a counter agent that saves its count as raw bytes:

<Tabs items={["TypeScript", "Effect TypeScript", "Rust", "Scala", "MoonBit"]} storageKey="nextra-tabs-language-sdk">
    <Tabs.Tab>
        Provide a `snapshot: { save, load }` block on `.implement(...)`. `save()` has the agent state as `this`. `load(bytes, context)` has no `this` and returns a complete fresh state object:

        ```typescript
        import { z } from 'zod';
        import { defineAgent, method } from '@golemcloud/golem-ts-sdk';

        export const Counter = defineAgent({
            name: 'Counter',
            id: { name: z.string() },
            snapshotting: { everyNInvocations: 1 },
            methods: {
                increment: method({ input: {}, returns: z.number() }),
            },
        });

        export const CounterImpl = Counter.implement({
            init: () => ({ value: 0 }),
            methods: {
                increment() {
                    this.value += 1;
                    return this.value;
                },
            },
            snapshot: {
                save() {
                    const snapshot = new Uint8Array(8);
                    new DataView(snapshot.buffer).setFloat64(0, this.value);
                    return snapshot;
                },
                load(bytes, _context) {
                    const value = new DataView(
                        bytes.buffer,
                        bytes.byteOffset,
                        bytes.byteLength,
                    ).getFloat64(0);
                    return { value };
                },
            },
        });
        ```
    </Tabs.Tab>
    <Tabs.Tab>
        Select binary snapshots on the definition and provide `save` and `restore` effects on the implementation. Restoration constructs fresh state and does not run `init` first:

        ```typescript
        import { Effect, Ref } from "effect"
        import { Snapshot } from "@golemcloud/effect-golem"

        // In defineAgent({ ... }):
        snapshotting: Snapshot.custom({
          policy: Snapshot.policy.everyN(1),
        })

        // In .implement({ ... }):
        snapshot: {
          save: (state) =>
            Ref.get(state).pipe(
              Effect.map((value) => {
                const bytes = new Uint8Array(8)
                new DataView(bytes.buffer).setFloat64(0, value)
                return bytes
              }),
            ),
          restore: (bytes, _context) =>
            Ref.make(
              new DataView(bytes.buffer, bytes.byteOffset, bytes.byteLength)
                .getFloat64(0),
            ),
        }
        ```
    </Tabs.Tab>
    <Tabs.Tab>
        Define instance `save_snapshot` and an associated `load_snapshot` factory. The factory returns `Self`; it does not receive `&mut self`:

        ```rust
        async fn save_snapshot(&self) -> Result<Vec<u8>, String> {
            Ok(self.value.to_le_bytes().to_vec())
        }

        async fn load_snapshot(
            bytes: Vec<u8>,
            _context: golem_rust::agentic::SnapshotRestoreContext,
        ) -> Result<Self, String> {
            let arr: [u8; 4] = bytes
                .try_into()
                .map_err(|_| "Invalid snapshot".to_string())?;
            Ok(Self {
                value: u32::from_le_bytes(arr),
            })
        }
        ```
    </Tabs.Tab>
    <Tabs.Tab>
        Define `saveSnapshot()` on the implementation and `loadSnapshot(...)` on its companion object:

        ```scala
        final class CounterImpl(private val name: String) extends Counter {
          private var value: Int = 0

          def saveSnapshot(): Future[Array[Byte]] =
            Future.successful {
              val buffer = java.nio.ByteBuffer.allocate(4)
              buffer.putInt(value)
              buffer.array()
            }
        }

        object CounterImpl {
          def loadSnapshot(
            bytes: Array[Byte],
            context: SnapshotRestoreContext
          ): Future[CounterImpl] = Future.successful {
            val instance = new CounterImpl(context.identity[String](0))
            instance.value = java.nio.ByteBuffer.wrap(bytes).getInt()
            instance
          }
        }
        ```
    </Tabs.Tab>
    <Tabs.Tab>
        Implement the saving-only `@agents.Snapshottable` trait and define a separate static `load_snapshot` factory:

        ```moonbit
        pub impl @agents.Snapshottable for Counter with save_snapshot(self) {
          let arr: Array[Byte] = []
          for i = 7; i >= 0; i = i - 1 {
            arr.push(((self.value >> (i * 8)).to_int() & 0xff).to_byte())
          }
          Bytes::from_array(arr)
        }

        pub fn Counter::load_snapshot(
          bytes: Bytes,
          context: @agents.SnapshotRestoreContext,
        ) -> Result[Counter, String] {
          if bytes.length() != 8 {
            return Err("Expected an 8-byte snapshot")
          }
          let mut value: UInt64 = 0
          for i = 0; i < 8; i = i + 1 {
            value = value | (bytes[i].to_uint64() << ((7 - i) * 8))
          }
          let name: String = context.identity(0) catch {
            error => return Err(error.to_string())
          }
          Ok({ name, value })
        }
        ```
    </Tabs.Tab>
</Tabs>

## Multipart snapshots: JSON state and named bytes

Use explicit multipart snapshots when the live instance contains binary resources that should not be serialized into JSON. Save a small schema-backed state projection separately from a dynamic map of named `{bytes, contentType}` parts. This is an additional mode: the simpler JSON, byte-only, and existing SQLite snapshot modes remain available.

These examples save a revision counter and an in-memory binary index. The loaders construct fresh live state; ordinary initialization is skipped.

<Tabs items={["TypeScript", "Effect TypeScript", "Rust", "Scala", "MoonBit"]} storageKey="nextra-tabs-language-sdk">
    <Tabs.Tab>
        Select `multipart.state` in the definition. Both `save` and `load` are required, and may be async. The live state returned by `init` is independent of the saved schema.

        ```typescript
        import { Snapshot } from '@golemcloud/golem-ts-sdk';

        // In defineAgent({ ... }):
        snapshotting: {
          multipart: { state: z.object({ revision: z.number() }) },
          policy: { everyNInvocations: 10 },
        }

        // In .implement({ ... }), with live { revision, index }:
        snapshot: {
          async save() {
            return {
              state: { revision: this.revision },
              parts: new Map([
                ['index', { bytes: this.index, contentType: 'application/octet-stream' }],
              ]),
            };
          },
          async load(saved, _context) {
            return {
              revision: saved.state.revision,
              index: Snapshot.requirePart(saved.parts, 'index', 'application/octet-stream'),
            };
          },
        }
        ```

        Standard Schema validates the input on save, but the SDK persists that input JSON, not a transformed validation result. On load, the schema validates stored JSON and the loader receives its output type. There is no reverse encoding. Do not combine `state` and `multipart` configuration. Explicit multipart does not automatically discover SQLite databases and rejects managed `db:` parts.
    </Tabs.Tab>
    <Tabs.Tab>
        `Snapshot.multipart` requires an explicit strategy. Effect Schema encodes the saved state and decodes it before restoration.

        ```typescript
        // In defineAgent({ ... }):
        snapshotting: Snapshot.multipart({
          schema: Schema.Struct({ revision: Schema.Number }),
          policy: Snapshot.policy.everyN(10),
        })

        // In .implement({ ... }), with a Ref of { revision, index }:
        snapshot: {
          save: (ref) => Ref.get(ref).pipe(Effect.map((live) => ({
            state: { revision: live.revision },
            parts: new Map([
              ['index', { bytes: live.index, contentType: 'application/octet-stream' }],
            ]),
          }))),
          restore: (saved, _context) => Effect.gen(function* () {
            const index = yield* Snapshot.requirePart(saved.parts, 'index', 'application/octet-stream')
            return yield* Ref.make({ revision: saved.state.revision, index })
          }),
        }
        ```

        To compose managed SQLite images, add `databases: ["main"] as const` to `Snapshot.multipart` and expose `databases: live => ({ main: live.database })` on the strategy. Before user restoration, the SDK validates the complete declared database part set and content types. Your restore strategy constructs database handles, then the SDK hydrates their images and warms schema caches **before** constructing method handlers. Do not query restored database contents inside `restore`: hydration has not happened yet. Existing autocommit and attached-schema restrictions still apply.
    </Tabs.Tab>
    <Tabs.Tab>
        Define both async hooks inside the `#[agent_implementation]` block. The live implementation does not need Serde; only the saved projection does.

        ```rust
        use golem_rust::agentic::{MultipartSnapshot, SnapshotPart, SnapshotRestoreContext};

        #[derive(golem_rust::serde::Serialize, golem_rust::serde::Deserialize)]
        struct SavedState { revision: u32 }

        async fn save_snapshot_parts(&self) -> Result<MultipartSnapshot, String> {
            MultipartSnapshot::from_state(
                &SavedState { revision: self.revision },
                std::collections::BTreeMap::from([(
                    "index".into(),
                    SnapshotPart { bytes: self.index.clone(), content_type: "application/octet-stream".into() },
                )]),
            )
        }

        async fn load_snapshot_parts(
            snapshot: MultipartSnapshot,
            _context: SnapshotRestoreContext,
        ) -> Result<Self, String> {
            let saved: SavedState = snapshot.decode_state()?;
            let index = snapshot.require_part("index", "application/octet-stream")?.to_vec();
            Ok(Self { revision: saved.revision, index })
        }
        ```

        Keep the normal snapshot policy annotation. An incomplete hook pair, or combining explicit byte-only and multipart hooks, is a compile error.
    </Tabs.Tab>
    <Tabs.Tab>
        Add the instance saver and companion loader without a new mixin. `Schema` is needed for the saved projection, not the live instance.

        ```scala
        import golem.runtime.{MultipartSnapshot, SnapshotPart, SnapshotRestoreContext}
        import zio.blocks.schema.Schema
        import scala.concurrent.Future

        final case class SavedState(revision: Int) derives Schema

        // On IndexImpl:
        def saveSnapshotParts(): Future[MultipartSnapshot] = Future.fromTry(
          MultipartSnapshot.fromState(SavedState(revision), Map(
            "index" -> SnapshotPart(index.clone(), "application/octet-stream")
          )).toTry
        )

        // On companion object IndexImpl, with a constructor accepting saved fields:
        def loadSnapshotParts(snapshot: MultipartSnapshot, context: SnapshotRestoreContext): Future[IndexImpl] =
          Future.fromTry((for {
            saved <- snapshot.decodeState[SavedState]
            bytes <- snapshot.requirePart("index", "application/octet-stream")
          } yield new IndexImpl(context.identity[String](0), saved.revision, bytes)).toTry)
        ```

        Keep the normal policy annotation and registration. Incomplete or conflicting explicit hooks, including multipart combined with `Snapshotted[S]`, are compile errors.
    </Tabs.Tab>
    <Tabs.Tab>
        Implement the async saving trait and a separate static async loader. The generator suppresses automatic JSON hooks for this explicit pair; the existing synchronous `Snapshottable` trait is unchanged.

        ```moonbit
        priv struct SavedState { revision : Int } derive(ToJson, FromJson)

        impl @agents.MultipartSnapshottable for Index with fn save_snapshot_parts(self) {
          Ok(@agents.MultipartSnapshot::from_state(SavedState::{revision: self.revision}, {
            "index": { bytes: self.index, content_type: "application/octet-stream" },
          }))
        }

        pub async fn Index::load_snapshot_parts(
          snapshot : @agents.MultipartSnapshot,
          context : @agents.SnapshotRestoreContext,
        ) -> Result[Index, String] {
          let saved : SavedState = match snapshot.decode_state() {
            Ok(saved) => saved
            Err(error) => return Err(error)
          }
          let index = match snapshot.require_part("index", "application/octet-stream") {
            Ok(index) => index
            Err(error) => return Err(error)
          }
          let name : String = context.identity(0)
          Ok({ name, revision: saved.revision, index })
        }
        ```

        Keep `#derive.agent` and the normal snapshot policy. Merely deriving JSON traits on the live instance does not conflict with the explicit multipart pair.
    </Tabs.Tab>
</Tabs>

### Part and envelope rules

- Names are case-sensitive and match `[A-Za-z0-9_][A-Za-z0-9_.-]*`. Logical names `state` and `__proto__` are valid. Parts have no automatic resource semantics; applications decide what they mean and whether to accept extra parts.
- Content types must be bare ASCII MIME type/subtype strings, such as `application/octet-stream`. They are normalized to lowercase; parameters such as `; charset=utf-8` are rejected. `requirePart` checks both presence and content type, returning the SDK's normal snapshot error on failure.
- Multipart is emitted even when there are no binary parts. Binary-only applications use JSON `null` state. Empty bytes and trailing CR, LF, or CRLF are preserved exactly.
- The SDK owns the principal envelope. On the wire, one `state` part contains UTF-8 JSON `{version:1, principal, state}`, user names become `part:<name>`, and managed SQLite images use `db:<name>`. Do not construct these prefixes or envelope metadata yourself.
- The SDK validates framing, metadata, names, duplicate structural fields, and supported namespaces before invoking user restoration. Changing snapshot modes does not enable fallback parsing or historical-format migration.

Snapshots are whole-buffer operations. Copies of state, part bytes, encoded payloads, and restored resources can amplify peak memory usage. The host's 64 KiB inline/blob-spill setting is a storage threshold, **not** a maximum snapshot size. Save and load hooks are unpersisted lifecycle operations and may be retried; async hooks do not make external effects exactly-once.

## How snapshot restoration runs

Snapshot loading is a specially supported SDK lifecycle operation, not an agent method. The SDKs keep it separate from normal initialization and install the returned state or instance only after restoration succeeds. Restore context exposes the agent identity and restored principal, plus the phantom ID and fresh configuration where applicable.

Golem runs snapshot loading in read-only mode and writes nothing from it to the oplog. Decoding, local computation, fresh randomness, configuration access, and other permitted reads can be used to construct the restored value. Durable host calls classified as writes, and outgoing HTTP or agent RPC calls, are rejected before they take effect. This restriction is not a general filesystem write sandbox: local filesystem writes are not blocked by it.

If loading fails, partial state is discarded:

- A manual update fails and the agent remains on its previous component version.
- If an automatic snapshot is rejected by its loader, or loading or subsequent replay fails deterministically, Golem recreates the component and replays from the last successful manual-update snapshot—or from the beginning if none exists. It does not try an older automatic snapshot. Transient failures and resource-limit failures can instead propagate or cause recovery to retry.
- Failure to load the baseline snapshot from an already completed manual update cannot fall back to pre-update history.

## Configuring snapshot-based recovery

To enable snapshotting, add a `snapshotting` option to your agent definition:

<Tabs items={["TypeScript", "Effect TypeScript", "Rust", "Scala", "MoonBit"]} storageKey="nextra-tabs-language-sdk">
    <Tabs.Tab>
        Pass the `snapshotting` option to `defineAgent(...)`:

        ```typescript
        export const Counter = defineAgent({
            name: 'Counter',
            id: { name: z.string() },
            snapshotting: {
                state: z.object({ value: z.number() }),
                policy: { periodicSeconds: 5 },
            },
            methods: {
                increment: method({ input: {}, returns: z.number() }),
            },
        });
        ```
    </Tabs.Tab>
    <Tabs.Tab>
        Pass a `Snapshot` definition to `snapshotting`:

        ```typescript
        snapshotting: Snapshot.define({
          schema: Schema.Struct({ value: Schema.Number }),
          policy: Snapshot.policy.periodic("5 seconds"),
        })
        ```
    </Tabs.Tab>
    <Tabs.Tab>
        ```rust
        #[agent_definition(snapshotting = "periodic(5s)")]
        ```
    </Tabs.Tab>
    <Tabs.Tab>
        ```scala
        @agentDefinition(snapshotting = "periodic(5 seconds)")
        ```
    </Tabs.Tab>
    <Tabs.Tab>
        ```moonbit
        #derive.agent(snapshotting="every_n(5)")
        ```
    </Tabs.Tab>
</Tabs>

The available policy forms are listed below. Exact spelling and policy support vary by SDK, as shown in the examples above.

| Option | Description |
|---|---|
| `disabled` | Automatic snapshot creation is disabled. Recovery still uses the last successful manual-update snapshot, if one exists. |
| `enabled` | Uses the server-side default snapshotting configuration, which may be disabled. |
| `every(N)` | Takes a snapshot every **N** successful invocations. |
| `periodic(duration)` | Schedules snapshots at safe invocation boundaries after each **duration** interval (e.g. `5s`, `1m`). |

## Observability

When using the default (JSON-based) snapshotting implementation, snapshot entries recorded in the oplog contain the serialized JSON state of the agent. This makes it easy to inspect agent state at any snapshot point for debugging purposes.

<Callout type="info">
    Snapshotting is also used when [updating agents](/next/develop/updating) across incompatible versions, allowing Golem to capture the agent's state before applying the update.
</Callout>
