Implementation atlas · September 2026

Durable Streams,
from URL to oplog.

One stream engine, several entry points. Follow the ownership boundaries between HTTP, the resident worker, durable production, consumer replay, and disposable transport.

Snapshot: durable-streams-1 · 2bc20b9b. This pins the pushed implementation at that commit; it does not describe later uncommitted cleanup.

Store

What was produced?

The producer oplog records registration, items, terminals, attachments and session changes. DurableStreamStore owns journal writes, the reconstructed index, write admission and committed publication.

Session

What did this binding read?

The consumer's oplog journals mappings and observations. StreamSession owns runtime topology, control, materialization and binding-local transport mappings.

Transport

How does it arrive now?

HTTP pages, SSE, RPC frames and live buses deliver data. They are not the only copy of a committed item or terminal.

“Producer” is a role, not a server. For an RPC A → B, A produces input streams and B consumes them; B produces output streams and A consumes them. Each worker can be both a producer and a consumer. HTTP readers do not acquire an agent-side consumer replay journal.
Lifecycle foundation is deferred. Coordination with #3797 is intentionally not part of this snapshot. The guide states the implemented slot and drain behavior without predicting the later acquisition/deletion design.

HTTP adapter worker-service

DurableStreamsHandler adapts a compiled stream-aware custom API route. It classifies collection / session / slot paths, validates session IDs and unsupported headers, then delegates to the split handler modules.

  • session.rs: generated or explicit session PUT, slot PUT, session inspection and DELETE. Builds InvocationStart from route and request data.
  • append.rs: validates POST payloads and external producer headers, resolves the input schema, dispatches an append.
  • read.rs: offsets, live mode, long-poll, conditional reads and SSE response lifetime.
  • encoding.rs: offsets, ETags, headers, JSON / bytes and SSE framing. load.rs: active-read permits and rate limits.

The worker-service WorkerService and WorkerClient authorize/resolve agents and route executor calls. They do not own stream history. Plain appends must not be transparently retried as though they carried a producer deduplication key.

Handler modules · WorkerService · WorkerClient routing / retries

Agent RPC and invocation-session adapters executor boundary

wasm_rpc opens a durable RPC call, derives its child idempotency key and constructs a caller-side StreamSession. It materializes input, invokes Rpc::invoke_and_await_streaming, and materializes the returned value and mappings. The callee accepts an ordinary invocation carrying stream mappings.

Tool-body streams use a different path. Tool and middleware stdin/stdout use in-memory attachment streams and pumps, not StreamSession or DurableStreamStore. Their entity invocation runs in its own Wasmtime Store, records in the owner's oplog and shares its replay cursor. Reconstruction re-executes the body with replayed host interactions; it does not resume stdin/stdout from durable-stream offsets.

Agent RPC inside a tool still uses durable streams. If that body calls an agent method with stream-bearing values, wasm_rpc constructs a StreamSession backed by the owner's DurableStreamStore. with_entity_parent_start_index attributes those stream records to the entity invocation. HTTP exports and agent-to-agent streaming RPC therefore share the durable stream engine; tool-body attachment streams are separate.

RPC result ≠ end of all streams. The caller records the result stripped of streams before returning the stream-bearing value to the guest. Stream draining may continue after the RPC's durable End.

The gRPC stream-slot methods are a different adapter: they dispatch HTTP-export operations to Worker. For example, ReadStreamSlot currently returns one response envelope per call; worker-service implements repeated long-poll/SSE reads around it.

Worker integration and producer slot resident owner

worker/durable_stream_slots.rs owns create_stream_session, read_stream_slot, append_to_stream_slot and control_export_stream. It resolves the session's pinned method/schema and canonical slot, distinguishes pending/value/stream/tombstoned outputs, and calls the stream engine.

Worker also accepts streaming invocations, materializes results, recovers sessions, reconciles attachments and coordinates completion with the invocation loop. It supplies the commit callback that connects producer mutations to the status actor.

The legacy slot name is not the algorithm owner: durable_stream::DurableStreamStore is the stream store; worker::durable_stream_producer::DurableStreamProducerSlot retains its older module/type name but owns only lazy store loading, replacement, response leases, retirement and shutdown. The slot shares load/retirement results and prevents a usable store from appearing after fencing.

EphemeralResponseLease counts response lifetimes. Normal archival waits for them, then fences; explicit retirement and shutdown do not wait for those leases. This retains an incarnation for readers, not a Wasmtime Store forever.

HTTP-export operations · Producer slot / response leases · Worker orchestration

durable_stream producer engine

One resident DurableStreamStore coordinates streams in one worker's oplog. It owns journal/index consistency, count/byte admission, the serial local writer, per-stream buses, retained committed events and keyed session locks.

Its operations register streams, write items and nested handles, append session records, apply external producer sequencing, finalize sessions, and maintain attachment/deletion state. “Producer” therefore includes persistence for session/control records, not just a push-only item writer.

Mutations are journal-changing operations. Their local bodies run serially and never await remote work. A root admitted operation may orchestrate remote waits outside the writer while retaining its count/byte reservation. Commit happens before live publication; poisoning rejects new work when durable effects cannot safely be treated as unapplied.

durable_session session orchestration + consumer replay

StreamSession combines the store, local oplog, durable session identity, attachment state, schemas, RPC routing and an optional consumer-journal commit interface. Its topology, control state and materialization are runtime responsibilities; pure persisted projections live in durable_stream/session_state.rs.

  • Pure projection: SessionControlMetadata and SessionTopologyMetadata fold prepared/attached/finished state, mappings, topology, cancellation intents and tombstones without owning runtime transport.
  • Materialization: transforms schema values containing streams into durable handles and guest-facing endpoints, including nested and forwarded streams.
  • Consumer replay: DurableInputEndpoint owns producer reads, journal replay/write, read ordinals and terminal completion; DurableInputProducer is the Wasmtime bridge and separately polls pending_drop.
  • Session operations: attachment/resume, input writes, output pumps, cancellation reconciliation and completion.

Cloning one StreamSession shares its mapping table and next transport ID. Calling StreamSession::new again creates an independent binding-local table, even for the same durable key. There is no global transport-ID registry; only the keyed session lock comes from the store.

This is not merely a consumer-side mirror of durable_stream. It uses the producer to persist local journal/control records and coordinates both input and output roles. Most production code still lives in mod.rs; the tests are split out.

Oplog, commit controller and projections durability boundary

DurableStreamOplogRecord batches append to the existing worker oplog. The shared primary/multilayer/forwarding implementations remain responsible for storage and ordering. Durable records use normal size-threshold payload externalization; ephemeral records stay inline for archival.

Worker::durable_stream_commit delegates to WorkerStateActor. A durability receipt can arrive before the callback's status-fold tail finishes. Stream publication requires durability; owner retirement must also drain the remaining durable/status work.

StreamSessionIndexService stores coverage-tracked session/control metadata, consumer-journal positions and producer projections. durable_stream/metadata.rs defines producer projection keys and rows. These are derived lookup structures, not a third authoritative stream journal.

Oplog contracts · Status actor / commit receipt · Session index · Producer metadata projection

Catch-up, buses, transport and value codecs delivery boundary

DurableCatchUpReader combines historical segments with committed live events and discards overlap by offset. DurableLiveStreamBus is a bounded committed-event live tail. Lag or connection loss cannot become the loss of the authoritative item.

stream_bus.rs also contains a separate live transport bus. stream_transport.rs owns disposable endpoints and source lifecycle. These must not be confused with producer durability.

stream_session.rs, despite its name, is primarily recursive stream-value encoding/decoding, schema-path validation and reference remapping—not the durable session state machine. schema_value_stream.rs bridges schema values and Store-owned values.

03 · Follow a request

These are explanatory traces, not executable simulations. Each step names the owner and the durable boundary. Use “Show full trace” to compare steps together.

Create an HTTP session

  1. 1 · HTTP route → invocation description

    The handler validates the suffix and headers, generates or validates a session ID, resolves method arguments and constructs InvocationStart. A generated collection PUT returns a session URL; the route determines which method may execute.

    Owner: handler session.rs. A URL alone is not durable acceptance.

  2. 2 · Executor → pinned session and input mappings

    The worker-service routes to the executor. Worker::create_stream_session resolves the invocation's schema and stream slots; streaming acceptance prepares session metadata and registers input handles.

    Owner: Worker slot operations and streaming invocation acceptance. Records include Prepared and input registrations.

  3. 3 · Persist acceptance → execute → materialize result

    The ordinary invocation queue commits acceptance before acknowledging it. When the invocation produces its result, durable session materialization registers output mappings and records InvocationResult. A slot may be pending before that result exists.

    Owner: materialize_result. Invocation acceptance, result availability and all-streams-finished are different milestones.

Append an HTTP input batch

  1. 1 · HTTP POST → validated append request

    The handler checks content type, JSON/byte payload, body limits and optional producer headers. The worker-service sends AppendToStreamSlot; a plain append is not automatically retried.

    Owner: append.rs. No item is durable yet.

  2. 2 · Worker → canonical input slot

    append_to_stream_slot loads the producer, checks the expected method and pinned schema, rejects tombstoned/read-only slots, validates the handle and maps the producer ID to Client.

    Owner: append_to_stream_slot. Schema and identity checks precede mutation.

  3. 3 · Admission → session lock → serial write

    append_external_input retains count/byte admission across its orchestration. Session-sensitive callers acquire the session lock before StreamWriteAdmission::submit; the serial writer never acquires that lock and never performs remote waits. The local body checks epoch/sequence, assigns item sequences, and batches producer state, items and an optional terminal.

    Owner: external_input.rs and mutation.rs. Explicit StreamWriteContext carries nested write effects; there are no mutation/effect task-local scopes.

  4. 4 · Durable body → release lock → tails → publication

    submit returns after the durable local body, not after its status-fold tail. The root admitted operation releases the session lock, joins status tails, and then waits for deferred publication. If the requesting HTTP future disappears after queue admission, the accepted operation remains owned by the store task.

    Owner: mutation.rs and publication.rs. Commit before publish; status publication is outside the session lock.

  5. 5 · Reply or retry → original offset

    The handler maps Accepted / Duplicate / fenced epoch / sequence gap / Closed into HTTP behavior. While open, a duplicate returns the original offset and highest accepted producer sequence. After closure only the original closing tuple is a producer duplicate.

    The consumer reads the same producer history whether the writer used HTTP or attached invocation transport. These have distinct external producer identities.

Read history → live SSE

  1. 1 · Choose read semantics

    read.rs validates offset/live/cursor parameters, applies load limits and conditional request rules, and invokes read_slot. HEAD inspects metadata without rendering item bodies.

    Owner: HTTP reads. HTTP cursor/ETag values are protocol presentation, not a consumer agent journal.

  2. 2 · Resolve identity → read committed data

    The worker resolves pending/value/stream/tombstoned slot state. For a stream, the producer validates the handle and reads after the requested offset. A pending result may wait for session changes up to a bounded deadline.

    Owner: read_stream_slot → read_by_handle.

  3. 3 · Catch up and follow the tail

    Producer readers use committed offsets to bridge historical storage and the bounded live bus. The gRPC read delivers a bounded result; the HTTP SSE body repeats reads and encodes batches/cursors. Its load permit is held for the response stream's lifetime.

    Owner: catch_up.rs and sse_body. SSE is not a single persistent executor bus subscription.

  4. 4 · Terminal does not skip historical items

    A closed stream can still have unread history. Historical pages are rendered before EOF; the final SSE batch signals closure only after the reader reaches the terminal boundary. Reconnect resumes from the client's offset.

    Owner: encoding.rs. The oplog remains authoritative after a response disconnects.

RPC consumer crash → replay

  1. 1 · A calls B with stable invocation identity

    wasm_rpc derives the child key from the durable RPC position (the logical counter inside atomic regions). Session identity includes B's fingerprint. A's input streams and B's output streams each live in their producer's oplog.

    Owner: caller_durable_rpc_streams. Retry attempts are not new logical invocations.

  2. 2 · Journal a consumer observation

    For A reading B's output, session mappings connect transport IDs to durable handles. DurableInputEndpoint journals item values/source offsets with consumer_read_ordinal and terminal observations before guest delivery. commit_consumer_journal makes that consumer evidence visible to peers that probe it for reconciliation.

    Owner: DurableInputEndpoint. Producer history says what exists; consumer history says what was observed.

  3. 3 · Lose the Store and connection

    A's runtime disappears. The normal worker reconstruction path creates a new Store and replays its oplog. If the RPC result was already recorded, that result is reused; if not, dispatch retries with the same child key.

    No connection state is required to survive. Completed RPC End does not imply that all output items had been consumed.

  4. 4 · Replay observations → resume by offset

    The consumer rebuilds mappings and journaled reads, then fetches after the last source offset using attached/routed segment sources. Fingerprint mismatch rejects a deleted-and-recreated producer. Completed terminal outputs can be reconstructed without reattaching a finished consumer; open agent-RPC outputs still require attachment.

    Owner: routed sources + session recovery. Exactly-once logical observation does not mean exactly-once network delivery.

Cancel a session / tombstone a slot

  1. 1 · DELETE → export control

    HTTP DELETE goes through control_export_stream, reusing attachment-control transport with a system-only, route-authorized export request. This is not worker interruption.

    Owner: control_export_stream.

  2. 2 · Persist cancellation intent

    Session cancellation records CancelRequested and intents for mapped streams. Slot deletion resolves its canonical role and records cancellation intent plus Tombstoned under the session lock shared with result materialization. A later output cannot escape an earlier cancellation by appearing after it.

    Owner: cancel_session_streams / tombstone_slot_owned. History is retained; a tombstone is not physical agent deletion.

  3. 3 · Apply locally or route remotely

    Cancellation reaches the producer, then ConsumerCancelApplied acknowledges the exact durable intent. A crash before that receipt leaves an idempotently retryable intent. Remote work is not awaited while holding the session lock.

    Pending intents participate in worker assignment recovery, even without a local prepared session. A receipt is not a guest ConsumerTerminal.

  4. 4 · Preserve outcomes and URL semantics

    Existing terminal outcomes do not change. Tombstoned slot GET/HEAD/POST/DELETE return 410 and PUT returns 409. Session cancellation is cooperative: guest code independent of streams may keep running and producing other effects.

    A new stream at that URL requires a new session; this operation does not erase oplog history.

Finalize → ephemeral archival

  1. 1 · Invocation completes → finish the session

    The invocation loop completes the ordinary invocation, then the stream protocol finalizes remaining open inputs/outputs. finish_session_owned uses one vector batch with terminal records before Finished, committed before publication.

    Owner: session.rs. Transient memory may scale with open-stream count × error-payload size.

  2. 2 · Normal ephemeral archival waits for responses

    The producer slot waits for response leases to drain, atomically marks itself retired and poisons its producer. A stalled response can postpone normal archival indefinitely; there is no lease timeout. Ephemeral agents remain fail-stop, not restartable computations.

    Owner: wait_for_responses_and_fence. This is not a “keep the Store alive” rule.

  3. 3 · Drain pending work → archive → remove resident owner

    The current worker cleanup path stops execution, drains store/lifecycle/forwarding work, commits and stops status writers before archival. It then forgets the forwarding wrapper and removes the cached owner. Physical deletion retains a separate maintenance/removal sequence.

    Owner: archive_ephemeral_oplog and owner retirement. Coordination with #3797 remains deferred; this page makes no claim about its eventual lifecycle shape.

04 · Inside durable_stream/

The decomposition splits responsibilities across files while DurableStreamStore deliberately owns the journal/index/write/publication invariant. StreamSession is the separate binding runtime.

mod.rs · State, construction, shared contracts

Defines the producer, index/state types, errors and committed event types. Loads/reconstructs the producer and exposes StreamSegmentSource, AttachedStreamSegmentSource, StreamAttachmentControl. Holds shared fields used by child modules and re-exports routed adapters.

Source
index.rs · Apply and validate durable records

Folds oplog records into producer state: stream registrations, sequences, sessions, attachments and terminals. Enforces identity and history consistency. Index application is reconstruction of committed facts, not a second durable source.

Source
metadata.rs · Indexed projection of producer state

Defines projection keys/rows and record-to-key dependencies, backed by the worker metadata store. Supports selective loading instead of rebuilding all producer history for every lookup. Collaborates with StreamSessionIndexService.

Source
mutation.rs · Admission, serialization and cancellation safety

Owns data/lifecycle count-and-byte admission, the serial local writer, health/fencing and commit callback handling. StreamWriteAdmission spans remote orchestration; StreamWriteContext explicitly carries nested effects. Local submit awaits durability only, while the root joins status tails and publication after session-lock release.

Source
publication.rs · Committed events → live readers

Owns bounded retention, bus creation, ordered publication, terminal dispatch and publication repair. Terminals can retain an oplog offset and be read on dispatch rather than keeping a large terminal payload indefinitely. Durable commit precedes this layer.

Source
registration.rs · Stream identity and output registration

Registers streams by stable coordinates, validates schema/reference relationships and constructs output registrations. Root and nested stream identity must survive retries; registration is more than allocation of an in-memory transport ID.

Source
items.rs · Data writes, handles and nested values

Reads by handle, writes item batches, materializes stream-bearing values and resolves nested handles. Applies committed write batches to the producer index. Combines value/schema concerns with durable sequence and offset bookkeeping.

Source
external_input.rs · External writer sequencing

Validates external producer epochs/sequences, deduplicates appends, handles closed streams and atomically stores producer state with items/terminals. HTTP Client and invocation transport Attached are distinct identities; producer-local sequence is not the global item sequence.

Source
session.rs · Session writes, locks and finalization

Persists session records, provides keyed per-session locks, prepares sessions and finishes them. Finalization produces an ordinary atomic vector batch. Pure record folding is in sibling session_state.rs, owned by the store and consumed by the runtime.

Source
session_state.rs · Pure control and topology projections

SessionControlMetadata and SessionTopologyMetadata fold persisted journal facts through a coverage boundary. They contain no runtime transport or global binding registry.

Source
terminals.rs · End, cancel and terminal replay

Terminals are end or cancel records that close a stream. This module implements guest/protocol terminal handling, cancellation of open streams and source cancellation. It replays known terminals instead of creating competing ones; protocol finalization fences later guest-authored terminal attempts.

Source
catch_up.rs · Segments, cursor validation, live handoff

Validates cursors and reads durable segments. Implements source traits and DurableCatchUpReader for history/live delivery with overlap elimination by offset.

Source
routing.rs · Local / remote source and control adapters

RoutedAttachedStreamSegmentSource and RoutedStreamAttachmentControl delegate segment reads and attachment controls to the owning producer via local or RPC paths. They adapt locality rather than define a new stream protocol.

Source
probe.rs · Ask for consumer journal status

A probe asks the consumer journal for durable status used during attachment/deletion reconciliation. Peer visibility depends on commit_consumer_journal; socket connectivity is not consumer evidence.

Source
attachment.rs · Dependency lifecycle and cleanup

Appends attachment state, implements attachment control, reconciles leases and cascades deletion using consumer evidence. Durable intent/receipt records make interrupted cleanup retryable. Attachment lease expiry is distinct from the no-timeout ephemeral response lease.

Source
tests.rs · Engine contracts and shared fixtures

Exercises records, mutation cancellation, ordering, sessions, offsets, terminals and attachment behavior. Exposes helpers used by other executor test modules. Metadata projection tests also live in metadata.rs.

06 · Boundaries a refactor must preserve

Mutation ≠ delivery

The single queue serializes mutation bodies. Slow commit tails, remote cancellation and live fanout are completion work. Blocking the queue on a remote call back into the same producer can deadlock.

Receipt ≠ fully drained

A durability receipt permits committed index/publication progress. Status-fold callback work can still be running. Retirement must drain that work before storage cleanup.

Session lock ≠ owner lifetime

The session lock orders materialization/control on one session. Producer admission bounds work; ActivityGate tracks durable activity; the Worker slot fences lifetime. None is interchangeable with the others.

  • Admission: data and lifecycle work have separate count/byte lanes. A channel alone does not reproduce these limits. Oversized finalization reserves capped admission, not a hard allocation bound.
  • Cancellation: dropping a caller does not abandon an accepted mutation mid-commit. Physical worker deletion, session cancellation and slot tombstoning are three different operations.
  • History/live handoff: committed offsets and the publication boundary prevent gaps or duplicates; a new abstraction must preserve the handoff, not merely expose Stream<Item>.
  • Owner retirement: close admission, settle active durable work and reject unsafe new work. Response leases protect normal ephemeral archival only. They are not a persisted recovery mechanism.
  • Oplog singleton: the current explicit cache-forget / late-drop protection is an unsettled boundary, not proof that two mutable oplog instances may safely coexist.

07 · Implemented boundaries and optional follow-ups

The first statements below describe the approved implementation at the pinned commit. Questions are deliberately marked optional and do not imply planned work.

A · Session state is split by responsibility implemented

Implemented: pure persisted SessionControlMetadata/SessionTopologyMetadata live in durable_stream/session_state.rs. Runtime topology, control, materialization and binding-local mappings live in StreamSession.

Optional: smaller files inside the runtime may improve navigation, but should not recreate a second persistence owner.

B · The store owns the write invariant implemented

Implemented: DurableStreamStore owns journal/index/write admission/publication. The explicit write context and admitted root operation preserve local serialization while keeping remote waits outside the writer.

Optional: helper extraction is useful only if commit → index → publication ordering remains under one clear owner.

C · Consumer endpoint and Wasmtime bridge are separate implemented

Implemented: DurableInputEndpoint owns source reads, journal operations, ordinals and completion. DurableInputProducer adapts it to Wasmtime and independently completes guest-drop work.

Optional: further materialization decomposition must preserve binding-local mapping identity and affine stream ownership.

D · Which transport abstractions already exist?

Observation: StreamSegmentSource, AttachedStreamSegmentSource, StreamAttachmentControl, the consumer probe and journal interfaces already isolate capabilities. HTTP has protocol-specific paging, headers and tombstones; RPC has guest observations and attachment replay.

Question: can consumers depend more narrowly on those existing capabilities? A generic “stream service” that combines all of them might hide the differences instead of simplifying them.

E · Which boundaries must wait for lifecycle work?

Observation: worker acquisition, deletion completion, active-cache authority and oplog singleton lifetime overlap the pending lifecycle changes. Their current coordination is documented above but not endorsed as final.

Question: after that foundation settles, which DS-specific hooks remain necessary—producer drain, response lease, cancellation reconciliation—and which cleanup state can disappear into the worker state machine?

08 · Read the contracts through their tests

This page describes the pinned source. It does not claim that generating or browsing the walkthrough executes these Rust tests.

  1. Start with HTTP behavior: custom API integration suite and encoding tests (historic closed pages versus EOF, SSE payloads and cursors).
  2. Then producer contracts: producer tests for mutation cancellation, commit order, external sequencing and terminals; metadata projection tests.
  3. Then consumer recovery: session unit tests and RPC restart tests, including durable_streaming_output_recovers_after_executor_restart and caller_recovery_restarts_input_drain_after_rpc_result_commit.
  4. Finally lifecycle: producer-slot tests, archival / interruption tests, and oplog tests. Existing late-drop coverage does not establish the stronger singleton invariant.
