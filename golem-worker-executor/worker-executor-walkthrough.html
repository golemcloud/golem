The Golem Worker Executor, explained

An interactive walkthrough of how Golem runs WASM agents so that their progress survives the loss of the process running them: the architecture, the oplog, deterministic replay, durable host calls, exactly-once RPC, streams, tools, snapshots, lifecycle and recovery.

Describes the executor in golem-worker-executor/src as of September 2026. Collapsible sections open with a click or Enter; the interactive widgets need JavaScript, but every fact they show is also written out in plain text.

How to read this Part I gives the mental model (read it in order). Parts II–IV can be read independently once you know the vocabulary from sections 3–5. Words in italics at first use are defined in the glossary.

1What the executor is

The worker executor (golem-worker-executor/) is the process that actually runs agents. An agent is a WebAssembly component instance with a durable identity (AgentId) and an append-only history called the oplog. For a durable agent the oplog is what the agent is rebuilt from; an ephemeral agent also writes one, but only so that its status and results can be observed afterwards — it is never resumed from it. The worker service routes invocations to the executor that owns the agent's shard; the executor loads the component into a Wasmtime Store, feeds it invocations, records every nondeterministic interaction the guest has with the host, and — whenever the running instance is lost — rebuilds it by replaying that record.

Three guarantees come up in almost every later section, so they are worth stating once up front. The code is structured around them, and many non-obvious pieces of the executor exist to protect one of them.

1

Replay is deterministic by construction

The guest is a deterministic function of its guest-observable host inputs. The executor records every such input in the oplog and feeds it back on replay. If a replaying guest asks for a host call different from the one recorded next, the executor has a bug. It is never "normal nondeterminism".

2

The resident runtime is disposable

The Wasmtime Store, the worker task, sockets, channels, caches and the executor process itself may vanish at any instruction boundary. Suspend, evict, reshard, restart and crash are all recovered the same way: throw the instance away, build a new Store, replay the oplog, continue.

3

Durable RPC is exactly-once per logical callee invocation

A caller may attempt a dispatch many times (replay, transport retry, atomic-region rollback). Every attempt carries the same durable idempotency key, the target persists one invocation, and one durable result exists. Attempts are not executions.

What "durable execution" buys an application developer

  • Agent code is written as ordinary sequential code — awaiting an HTTP response, sleeping for a week, waiting for another agent — and the platform guarantees the code continues after any infrastructure failure from exactly the point it reached.
  • State lives in the agent's linear memory and filesystem, not in an external database, because memory is reconstructed from the oplog.
  • Calls between durable agents are exactly-once; a failed executor cannot cause a duplicated transfer.
  • Agents can be updated to a new component revision while keeping their history, snapshotted, reverted to an earlier point, or forked.

What it does not promise

  • Exactly-once effects on arbitrary external services. Between performing an external effect and durably recording its result there is an ambiguous crash window; Golem attaches idempotency keys and offers atomic regions, but the peer has to honour them (§15).
  • Resumption of ephemeral agents. They are deliberately fail-stop (§3).
Why the guest is deterministic The guest is a sandboxed WebAssembly component. It has no clock, no randomness, no network, no filesystem and no shared memory of its own; every interaction with the outside world is a call into one of the executor's host functions, and every host function that can return a different answer on a different day records what it returned. Given the same sequence of recorded answers, the guest computes the same sequence of requests. Determinism is therefore not a property the application developer has to maintain — it follows from the component model, and the executor's job is to make sure that the recorded answers are fed back at exactly the same points.

When an agent needs another agent that lives elsewhere, RemoteWorkerProxy forwards the call to the owning executor over gRPC. worker_enumeration lists agents by scanning oplogs (durable agents only, unless the filter asks for ephemeral modes). worker_activator wakes agents in the background (for example after a shard is assigned, to resume interrupted work).

Admission, memory, fuel & quota services/active_agents/*, linear_memory.rs, resource_limits.rs, quota.rs, workerctx/default.rs

Before a worker becomes resident it must be admitted. The AdmissionController compares the larger of measured RSS (cgroup memory.current) and the total linear memory granted to live workers against a usable ceiling; when short it evicts resident idle, then warm workers, and if that is not enough it rejects rather than over-commits. The MemoryGrant guard returns the reservation exactly once when dropped. A per-account ConcurrentAgentsScheduler hands out execution permits fairly (FIFO per account). CPU is metered with Wasmtime fuel: each Store borrows fuel batches from a shared per-account pool and only re-borrows when the batch is spent; ephemeral invocations get a bounded local overdraft (EphemeralFuelExhausted when it runs out). QuotaService leases resource limits from the shard manager with a credit model (credit_rate, max_credit) so hot paths do not call out per use. compilation_limiter bounds how many local Wasmtime compilations can run when both the component cache and the compiled artifact store miss.

How an invocation travels

  1. A client calls the worker service (HTTP or gRPC). The worker service resolves the agent's shard and forwards to the owning executor over gRPC (src/grpc/mod.rs: invoke_and_await_worker and friends).
  2. The executor's shard service confirms it owns the shard (check_worker); otherwise the request is rejected and the worker service retries with fresh assignment.
  3. The executor finds or creates the resident Worker. Creating one means loading the component, folding the agent's status from its oplog, and deciding which history the new instance must replay (snapshot baselines, pending updates).
  4. The invocation is deduplicated by idempotency key, appended as PendingAgentInvocation and committed before the caller is told "accepted".
  5. The invocation loop pops it, appends AgentInvocationStarted, runs the guest export in a Wasmtime Store, and every host call the guest makes is recorded through the durable host context.
  6. AgentInvocationFinished is appended and committed with CommitLevel::Always; only then are waiters notified and the result returned.

Durability guard and durable call sessions: two layers, not two alternatives

The two boxes on the second row of the map are easy to confuse because both are about "one durable host call". They are layered. The durability guard (DurabilityHost::begin_durable_function / end_durable_function in durability.rs) is the scope layer: it checks that a read-only invocation is not about to perform a write, tracks atomic regions, decides whether a failure may be retried inside the function, and, for non-idempotent writes, records the scope-level Start/End that says "an external effect may have begun here". A DurableCallSession (concurrent/call.rs) is the per-call state machine built on top of it: its start calls begin_durable_function, then it either runs the effect live and appends the terminal entry, or claims the recorded Start and answers from the recorded End, and finally delivers the completion to the guest with a CompletionDelivered marker. Reusing the guard inside the session is what keeps scope semantics identical for every host function, whatever style of host API it implements.

Almost every host function (random, clocks, key-value, blob store, RPC, tools, …) goes through a DurableCallSession. The guard is called directly only where a single external effect spans several host calls and therefore cannot fit into one session: the HTTP client (outgoing_handler::handle, whose response body arrives through later stream reads) and RDBMS query streams. §8 follows one call through both layers; custom durable invocations written by application code use their own Start/End pair through begin_custom_durable_invocation rather than a session.

"Exactly-once" is also not one promise. RPC between durable agents, oplog-processor delivery, stream items and stream terminals each have their own exactly-once contract with their own mechanism; §15 sets them side by side after each has been introduced.

4Durable vs. resident state

The single most useful question when reasoning about the executor is: which column does this fact live in? Anything in the right column may be rebuilt from the left column at any time. A design that needs something from the right column to survive a restart is wrong.

Rebuilding status: a fold over the oplog

"Rebuilt from the oplog" is not magic; for the agent's status record it is a plain left fold. calculate_latest_worker_status in worker/status.rs reads the entries in index order and updates one record: the status enum, the queue of pending invocations, the invocation whose result is not yet known, the map from idempotency key to result entry, the component revision, the linear-memory size, the regions to skip on replay and the retry state. Two details matter. First, the fold runs in two passes: it collects Jump and Revert regions before folding status, so entries inside a skipped region do not change the status (they were a failed attempt), while their Error entries still count toward the retry state. Second, the fold is incremental in practice: a cached record plus the entries appended since it was computed gives the same answer as recomputing from Create, which is what makes status cheap to keep current.

Append versus commit

Two persistence steps matter for every crash window. Append puts an entry into the oplog's in-memory buffer. Commit (commit_oplog_and_update_state(CommitLevel)) writes the buffer to storage and makes the entries recoverable. The buffer exists so that not every append costs a storage round trip; where an entry must be recoverable before the executor proceeds, the code commits explicitly:

  • Accepting remote work: PendingAgentInvocation is committed before the caller learns the invocation was accepted.
  • Finishing an invocation: AgentInvocationFinished is committed with CommitLevel::Always before waiters are notified.
  • Stream records are committed before they are published on the live bus.

CommitLevel::Always waits for durable storage; CommitLevel::DurableOnly only does so for durable agents (the ephemeral oplog honours the level, the primary oplog always flushes). Whenever this document says "accepted only after commit", it means the commit, not the append.

Rediscovery

Durability alone is not liveness: after a crash somebody must notice that an agent has pending work. Two mechanisms provide that. A timed wait (sleep, promise with timeout) first schedules its wake-up as a persisted scheduler action (durable_host/suspendable_wait.rs, WakeupScheduler::sleep_until). And the shard-keyed RunningWorkers index is updated synchronously whenever a worker gains or loses pending work (worker/status_flusher.rs), so an executor that takes over a shard can enumerate the agents it must revive. The status blob cache is only an asynchronously flushed baseline.

5The oplog

The oplog is an append-only sequence of typed entries per agent, indexed from OplogIndex::INITIAL (the Create entry). Entries are defined once, by the oplog_entry! macro in golem-common/src/base_model/oplog/mod.rs, which generates both the binary OplogEntry and the user-facing PublicOplogEntry.

Positional entries versus hints

Every entry kind is either positional or a hint (OplogEntry::is_hint()). Replay consumes positional entries in order: the guest's next host call must match the next positional entry. Hints are skipped by the replay cursor (skip_forward moves past them without advancing last_replayed_non_hint_index), take part in no Start/terminal pairing, and never satisfy a claim. Hints record facts about the execution — status, queueing, delivery boundaries, stream records — without being inputs to the guest.

Storage layers

Logically the oplog is one append-only sequence per agent. Physically it is spread over several storage layers that trade write latency for cost, and the MultiLayerOplogService hides the split: from the replay cursor's point of view there is only read(agent, from_index, count) over one contiguous index space.

The pieces, top to bottom:

  • Primary layer. PrimaryOplogService keeps an in-memory buffer per open oplog and writes it to indexed storage on commit: implicitly after max_operations_before_commit (128) appends, or explicitly wherever the executor needs the entries to be recoverable now (see append versus commit). Payloads above max_payload_size (64 KiB) are stored in blob storage and referenced from the entry, so a huge invocation argument does not bloat the index.
  • Archive layers. With the default configuration there are two: one CompressedOplogArchiveService (indexed_storage_layers = 2 means "primary plus one compressed layer" in indexed storage) and one BlobOplogArchiveService (blob_storage_layers = 1). On every commit the multi-layer service checks whether more than entry_count_limit (1024) entries were added since the last transfer; if so it moves the oldest prefix one layer down. Independently, a persisted ScheduledAction::ArchiveOplog fires every archive_interval (24 h) and pushes the prefix of an idle agent's oplog down a layer, provided the oplog has not grown since the action was scheduled. Archiving never changes an index: entry #17 is #17 whichever layer holds it.
  • Reads. read / read_exact ask the primary layer first and fill the remaining index range from lower layers, so a replay of a very old agent may touch all three layers for its first entries and only the primary for the recent tail.
  • Ephemeral oplogs. An ephemeral agent's EphemeralOplog buffers in memory, commits every max_operations_before_commit_ephemeral (1024) appends directly into the first archive layer, and is archived when the instance ends. It is never read back to resume the agent (§6); it exists so that what an ephemeral instance did can be inspected afterwards.

6Worker lifecycle

A Worker (worker/mod.rs) is the resident object for one agent on one executor. It receives invocations, persists them, and processes them in order through the invocation loop (worker/invocation_loop.rs::run). The loop has two levels, and understanding them is most of understanding recovery.

Agent status

The status you see in the API (AgentStatus) is folded from the oplog (worker/status.rs): given the entries, the status is a pure function. Caches and checkpoints only speed up the fold.

Ephemeral agents in the loop

An ephemeral agent goes through the same loop with two differences, and they are easy to conflate.

Within one life of the Worker, the loop still retries. An ephemeral Worker accepts exactly one method invocation in its life (its EphemeralInvocationState moves from Available to Accepted(key); a second key is rejected, the same key is accepted again). The constructor (AgentInitialization) runs first and is recorded in the ephemeral oplog like any other invocation. If the method then fails with a retriable error, the outer loop does what it always does: it drops the instance and creates a fresh Store. prepare_instance now needs the agent object to exist again before the method can be re-run, so it replays only the constructor from the oplog (resume_replay stops after the first AgentInvocationStarted for an ephemeral agent), switches to live, appends a Restart hint and runs the method again, live. That is the purpose of replaying the initialisation: it rebuilds the constructor's state for a retry of the same accepted invocation, not for accepting a new one. When the method finishes, successfully or with a terminal failure, the outcome is BreakInnerLoopAndArchiveEphemeralOplog: the Worker leaves the active set and its oplog is archived for observation.

Across lives there is no recovery. If the executor loses the Worker itself (crash, eviction, resharding) and a later request finds the agent's metadata already present, get_or_create builds a reconstructed ephemeral Worker: it can answer status queries and idempotency-key lookups from the archived oplog, but it starts in Accepted(None) and its instance "must never be started again". The invocation that was in flight is lost and the caller sees an error. This is what makes RPC to an ephemeral target at-most-once (§12).

7Invocation queue & results

The queue of pending invocations is durable: it is the set of PendingAgentInvocation hints not yet matched by an AgentInvocationStarted. The in-memory VecDeque is a cache of that.

Acceptance

enqueue_worker_invocation_with_effect (worker/mod.rs) first looks the idempotency key up (lookup_invocation_result). Anything other than LookupResult::New — Pending, Interrupted, or Complete(result) — returns the existing invocation without appending anything. Only for a new key does it append PendingAgentInvocation and commit; the caller learns "accepted" only after that commit. This ordering is what lets a caller that never heard back simply retry with the same key.

Execution and completion

The invocation loop appends AgentInvocationStarted, runs the guest export in InvocationMode::Live, and on success on_agent_invocation_success (durable_host/mod.rs) appends AgentInvocationFinished with the result and commits with CommitLevel::Always before waiters are notified. Failures go through on_invocation_failure, which decides a RetryDecision; whether a failed invocation gets a terminal entry depends on that decision, so never model a trap as "AgentInvocationFinished { Err }".

During replay the invocation runs in InvocationMode::Replay and the recomputed result is compared with the recorded one (replay_equivalent); a mismatch is an unexpected_oplog_entry determinism error, not something to paper over.

Tail work (durable_host/tail_work.rs) keeps the Store's event loop running until no spawned task is still active, so a task's positional Start/End can never land after AgentInvocationFinished. Tasks parked at guest-driven safe park points may span invocations. Hints may follow Finished: the streaming-session completion (protocol terminals, StreamSession { Finished }) is appended by invocation_loop.rs::agent_invocation_finished after the success hook.

Read-only methods

An agent method can be declared read-only in its agent-type metadata (AgentMethodSchema::read_only, with a cache policy and a flag saying whether the result depends on the calling principal). The executor treats such a method as a promise it enforces, and as an opportunity to cache:

  • Same worker, same queue. A read-only invocation is not forked onto a copy of the agent. It is a normal queued invocation on the same Worker, serialized with the mutating ones, and it appends the usual AgentInvocationStarted/Finished pair so that its result is recorded and deduplicated by idempotency key like any other.
  • Writes trap. For the duration of the call the host is in read-only strictness (enter_read_only_mode). Every durable function that is a write-type side effect (WriteLocal/WriteRemote/…: outgoing HTTP, RPC, key-value writes, custom durable invocations declared as writes) runs check_read_only_allows first and fails with AgentError::ReadOnlyViolation before anything is appended to the oplog. The violation is not retriable; the invocation fails and the agent stays consistent because the write never began.
  • Per-worker result cache. worker/read_only_cache.rs keeps results keyed by method, arguments, component revision, an epoch, and (if uses_principal) the caller. The epoch is bumped only when a mutating invocation completes successfully, so a cached value keeps serving while a mutation is merely queued, and is invalidated lazily on the first lookup after the mutation lands. On the awaiting path concurrent misses for the same key coalesce into one execution; on the fire-and-forget path each miss runs and an observer fills the cache on completion, rechecking the epoch so a populate raced by a mutation is dropped.

Because the cache is resident state (right column of §4) it disappears with the Worker and is simply rebuilt by the next calls; correctness never depends on it.

8Durable host calls & deterministic replay

Every nondeterministic host function — HTTP, key-value, blob store, RDBMS, sockets, clocks, random, RPC, promises, tools — goes through begin_durable_function / end_durable_function (durable_host/durability.rs) and, for the concurrent WASI p3 "accessor" path, a DurableCallSession (durable_host/concurrent/call.rs). The serialized p2 path (&mut self host calls) uses persist_durable_function_invocation / read_persisted_durable_function_invocation with the same Start/End shape but no delivery markers.

Four steps, four different facts

Execute

Perform the live effect. Allowed only when the durable context reports live (store_is_live / is_live()) — never because the cursor happens to be at the end of history.

Append

Start is appended eagerly when the call begins; End or Cancelled when it terminates. A trap leaves Start incomplete (abandon_for_trap); a trap never writes Cancelled.

Claim

On replay, match the host call the guest is making now against a recorded Start by identity (StartClaim: function name, owner, optional request payload). A Start that does not exist in history is a divergence error.

Observe

The guest reads the result. For accessor calls this is recorded by CompletionDelivered / CompletionDiscarded as the tail operation of the host function. Host completion time and guest observation time are different facts; only the second is a guest input.

Live path (accessor)

  1. Append Start { function_name, request, durable_function_type, parent_start_index }.
  2. Run the live action (the HTTP request, the KV read, the RPC dispatch…).
  3. Append End { start_index, response } — or Cancelled { start_index, partial } if the guest dropped the future first.
  4. Hand the result to the guest.
  5. Append CompletionDelivered { start_index } — or CompletionDiscarded if the guest dropped the completion unread.

Custom durable invocations

Application code can wrap a whole block of guest code as one logical durable operation with golem:durability/durability.begin-custom-durable-invocation (durability.rs::begin_custom_durable_invocation). The Rust SDK exposes it as Durability:

use golem_rust::durability::{Durability, DurableFunctionType};

fn charge_card(order: &Order) -> Result<Receipt, PaymentError> {
    // Names identify the operation in the oplog; the type says how it may
    // be retried (WriteRemote: a non-idempotent effect on the outside world).
    Durability::<Receipt, PaymentError>::new(
        "shop",                      // interface
        "charge-card",               // function
        DurableFunctionType::WriteRemote,
        &order.id,                   // recorded as the request
    )
    .run(|| {
        // Live: this body runs once and its Result is recorded in the End entry.
        // Replay: the body is skipped and the recorded Result is returned.
        let token = fetch_token()?;             // nested host calls are fine
        payment_gateway::charge(token, order)   // ... as are plain computations
    })
}

The wrapper appends a root Start when new is called; run executes the body in live mode and appends the root End with the serialized result (there are run_infallible and run_async variants). Nested host calls inside the body point at the root through observational_owner. On replay, if the root has an End, the recorded result is returned and the body does not run; nested entries are consumed as a replay-inert subtree. If the root is incomplete (the process died inside the body), the block goes live under its original root Start and the whole body re-runs, re-recording nested calls as new physical Starts. This is the one ordinary durable path where a completed nested effect legitimately repeats, which is why the block author owns idempotency: the body should be written so that running it twice is acceptable, or the function type should be one the executor refuses to re-execute.

9Replay cursor, claims & replay-to-live

ReplayCursor (durable_host/replay_state/cursor.rs) is the single chokepoint over recorded history: try_get_oplog_entry reads speculatively, commit_consumed_entry commits, move_replay_idx advances and emits ReplayFinished exactly once.

Claims: matching a live host call to its recorded Start

When a replaying guest makes a host call, the executor has to find which recorded Start entry belongs to it. The simplest rule, "the next positional entry", is correct only when the guest makes one host call at a time. Golem guests can have several host calls in flight at once (async tasks, concurrent futures, tool bodies running on the same oplog), and although the guest's behaviour is deterministic, the host's is not: two calls issued concurrently may have had their Start entries appended in either order during the live run, and the replaying host will not necessarily reach them in the same order. So the cursor uses claims (replay_state/claims.rs).

The rule is therefore: claim_start_matching claims the first unclaimed matching Start between the cursor and the replay target. Scanning ahead exists only to route concurrent completions to the right awaiter; it does not let the guest make different calls. The scan is also bounded by the next CompletionDelivered marker, so a call can never claim a Start that was recorded after a result the guest has not yet observed in this replay; guest-visible order is preserved exactly. When no matching Start exists in that window, replay stops with a divergence error, which is how nondeterminism in guest code or a host-function bug surfaces instead of being silently absorbed. The one exception is entries inside a region deleted by a Jump, which are never candidates.

Three facts that are not the same

  1. Cursor exhaustion — the recorded history has been consumed. An observation only.
  2. Shared primary publication — transition_phase moves Replaying → Settling → Live. ReplayState::switch_to_live with ReplayToLiveRole::PrimaryAgent runs begin_primary_settling, then finish_settling_to_live loops until every HistoricalReconstruction fence (a tool body still validating its recorded terminal) has validated, and CursorTx::finish_primary_settling publishes Live — or reports ReplayResumed when new history appeared meanwhile.
  3. Entity-local liveness — store_is_live(mode, local_live_tail, shared_live_published): the primary Store is live iff (2) has published; a ReplayingCompleted entity Store is never live; a ReplayingIncomplete or Live entity Store is live iff its own local_live_tail was set by PendingReplayToLive::finish. For ReplayToLiveRole::NonPrimary, switch_to_live skips (2): the entity Store goes live for its own invocation scope without waiting for the primary.
Replayingconsuming recorded entries; live effects refused

fn store_is_live(mode, local_live_tail, shared_live_published) -> bool {
    match mode {
        Some(ReplayingCompleted)            => false,
        Some(ReplayingIncomplete | Live)    => local_live_tail,

    }
}

Consequences. A host function must not perform a live effect because "the cursor is at the end"; it must observe is_live from the durable context. A markerless End is delivered once the cursor drains (await_natural_tail_end) with a live-armed delivery token (CompletionDelivery::prepare_delivery), which makes "crash after End, before delivery" safe without re-executing.

Resetting a cursor is not recreating an instance. Component metadata, revision and plugin context come from instance creation in the outer loop. When history or provenance changes, go through the outer loop.

WASI p3 Accessor host calls run concurrently inside one Store; p2 &mut self calls are serialized (concurrent/mod.rs). The runtime property this relies on holds even with bare Wasmtime and no oplog: the order in which a guest initiates concurrent host calls is stable across re-executions, while the order in which the host completes them is not, and the guest observes exactly the completion order. Recording the completion order as CompletionDelivered markers is what turns the second, nondeterministic order into a replayable one.

Cursor operations and recorded-marker waits remain active; durable Start/End work must finish before AgentInvocationFinished.

  • Pick the DurableFunctionType for re-execution safety, not for what the peer is. A non-idempotent remote write must be WriteRemote with idempotence off, or batched/transactional, so it is neither retried inline nor re-executed on incomplete replay.
  • If the function has a natural idempotency handle (HTTP idempotency-key, keyed writes), make it WriteRemote so the cheap inline path applies while assume_idempotence is on.
  • Attach RetryProperties so named policies can distinguish, for example, HTTP status classes.
  • Expect both shapes in the oplog: an inline retry that succeeds leaves Error hints under the same retry_from and a single Start/End; a fallback to trap leaves no extra inline hints, and the worker is reconstructed.

12Exactly-once RPC & atomic regions

Agent-to-agent RPC (durable_host/wasm_rpc/mod.rs) is a WriteRemote durable call on the caller whose result is a durable invocation on the target. Exactly-once is a property of the target's logical invocation, not of caller attempts, packets, or replay spans.

The key is the identity

  1. The caller appends Start { rpc/invoke-and-await, request }; its index begin_index is the call identity.
  2. derive_idempotency_key(begin_index) yields IdempotencyKey::derived(current_key, current_idempotency_key_oplog_index(begin_index)). Inside an atomic region the index is the outermost region's logical counter, not the physical index (see below).
  3. Caller state the target may depend on is committed before the first dispatch.
  4. If execution is needed, the target persists PendingAgentInvocation { key } — durable acceptance — then eventually AgentInvocationFinished. Any same-key arrival attaches to that one invocation. A settled read-only cache hit or coalesced follower instead returns the shared result and intentionally persists no separate invocation, result, or alias; only the executing miss owner uses normal durable admission.
  5. Caller replay of a completed call returns the recorded End. Replay of an incomplete call re-dispatches with the same key (InvocationFreshnessDisposition::MayExist, the default) — allowed because RPC is WriteRemote and assume_idempotence defaults to true. With set-idempotence-mode(false) the incomplete remote write fails instead.

RPC preparation does not acquire target execution capacity. For an execution-needing call, the target durably enqueues the acceptance prefix before reporting acceptance, and caller cancellation cannot tear that prefix apart.

Pending RPCs can yield the resident Store

A pending durable RPC registers a suspendable wait when the operation starts. After rpc_suspend_after (default 30s), its await checks the same voluntary-sleep predicate as other suspendable waits. If outgoing HTTP transmission or other live work defers yielding, it retries eligibility after wait_suspend_check_interval (default 10s). Once eligible, it first persists a scheduler wakeup rpc_resume_after later (default 5s); mixed waits select the earliest wakeup. The worker then suspends and returns through ordinary reconstruction with the same logical RPC key.

Scheduling, not recoveryThis proactive yield is never a gate on explicit interruption or arbitrary Store loss. It introduces no new recovery mechanism, RPC deadline, Wasmtime change, phase query, overcommit, or immediate restart.

Atomic regions keep the key across rollback

Ephemeral targets are deliberately fail-stop: a same-key retry never re-executes accepted incomplete work, but completion is not guaranteed because there is no durability to resume from; a retry that finds the target gone gets INACTIVE_EPHEMERAL_AGENT_ERROR. Distinct calls get distinct final identities.
  • Self-call. An agent calling itself is rejected: "RPC calls to the same agent are not supported".
  • Body → owner. A synchronous call from an entity body back into its blocked owner must pass OwnerLane::ensure_synchronous_owner_call; otherwise it is rejected with WouldDeadlock instead of hanging. Asynchronous owner calls are allowed.

13Streaming invocations

A streaming RPC is an ordinary durable RPC whose method signature carries input or output streams (remote_method_uses_streams). Live streams require invoke-and-await; a fire-and-forget streaming call is rejected with RpcError::ProtocolError. The target is pinned by streaming_target_fingerprint: AgentFingerprint is minted once at agent creation and stable across restarts, so a deleted-and-recreated agent with the same AgentId is a different producer.

Identity survives atomic rollback. Both streaming entry points reserve the outermost atomic region's logical counter once per call, during live execution and replay, and reuse the resulting key for the persisted request and dispatch. Outside atomic regions they use the exact physical Start index to distinguish concurrent calls. The target's session descriptor excludes retry tracing and sorts environment entries while retaining execution-relevant configuration; the first accepted invocation keeps its tracing context. A new caller attempt is not a new logical provider invocation.

Two durable journals, one optimisation

  • Producer journal (DurableStreamProducer::{register, write_items, end, cancel_open}, durable_host/durable_stream.rs). Each StreamItemsRecordV1 carries first_sequence, per-item StreamOffsetV1 { oplog index, sub_index } and producer_fingerprint.
  • Consumer StreamSession journal (StreamSessionRecordV1): caller attempts, attach/detach, mappings, topology, ConsumerItemValue { source_offset, consumer_read_ordinal }, cancel intent, terminals, the invocation result, and Finished.
  • All stream entries are hints in the oplog-entry sense: they take part in no Start/terminal pairing and never satisfy a claim. "Hint" does not mean "not replayed" — see below.

Why item order is still deterministic on replay

If stream records are hints, what guarantees that a consumer that performs a side effect per received item performs them in the same order on replay? Two things, working together.

  1. The consumer journals every item before the guest sees it. When a live consumer pulls the next item, the session appends a ConsumerItemValue { source_offset, consumer_read_ordinal, value } record to its own oplog and commits it before handing the value to the guest. On replay the session does not touch the producer or the bus for those items: it reads its own ConsumerItemValue records back in consumer_read_ordinal order and hands them to the guest one by one. So the replaying guest receives the same values in the same order, with the same batch boundaries. Only items beyond the journal, the ones the guest never saw, are fetched from the producer after the Store goes live.
  2. The side effects are ordinary durable calls. Whatever the guest does with an item, such as an RPC, a key-value write or an HTTP request, is a positional durable call with its own Start/End and, if concurrent, its own CompletionDelivered marker. Because the guest is deterministic (§1) and receives identical inputs in identical order, it issues those calls in the same order, and the cursor and claims of §9 pair each one with its recorded entry.

In other words, the item stream is treated like any other recorded input to the guest, journaled on the consumer side, while the guest's outputs keep the positional machinery. The two do not need to be woven into one Start/End sequence for the interleaving to be reproduced, which is why a change to the stream protocol cannot desynchronise Start/End pairing. Byte streams (HTTP response bodies, TCP sockets) take the other route: DurableDemandStream records a batched parent and one durable child Start/End per demanded chunk, so there the items are positional entries.

Exactly-once item delivery is by offset, not by connection

A restarted consumer first replays its own journal in consumer_read_ordinal order, then reads producer oplog segments after the last source_offset (read_segment / RoutedAttachedStreamSegmentSource in durable_session.rs); a live subscription samples the bus high-water under the publication lock and discards overlap by offset. A restarted producer replays its items from its oplog and resumes writing after the last committed sequence. Producer identity is checked at every boundary: validate_forwarded_mapping requires the session key, consumer and producer fingerprint to match, and producer-side record application rejects records naming another producer incarnation as CorruptHistory.

Randomness is allowed where it is recorded before it is observed: caller_attempt_id calls AttemptId::fresh() only when no CallerAttempt record exists, appends and commits it, and every later run reads the persisted value.

RPC result versus stream draining

On the synchronous streaming path the caller completes the durable call with the result stripped of streams (strip_streams) and only then returns the stream-bearing value to the guest. The caller's RPC End can therefore already be recorded while items are still flowing. Three crash windows follow:

  1. Setup done, RPC result not yet recorded — replay finds an incomplete Start and re-dispatches with the same key; the target attaches to the same invocation.
  2. RPC result recorded, streams partially consumed — replay returns the recorded result; the consumer session resumes by offset.
  3. Invocation finished, session cleanup pending — agent_invocation_finished runs complete_durable_streaming_session after the success hook, appending protocol terminals and StreamSession { Finished } as hints after AgentInvocationFinished.

Terminals are guest-authored (StreamEnd with the guest's result, StreamCancel with GuestDrop/Cancelled) or protocol-authored. The ambiguous window, precisely

For a WriteRemote call to a non-Golem peer the ambiguous window is after the request left the executor and before End was appended. With idempotence mode on, recovery re-sends under the same Start (same derived key). If the peer ignores the key, it sees two writes. The guest's choices are:

  • Keep idempotence mode on and make the peer honour idempotency-key (or use a naturally idempotent operation such as PUT-by-id).
  • Call set-idempotence-mode(false) around the write: the incomplete call is then not re-executed on recovery; the invocation fails instead, and the guest decides.
  • Wrap a group of writes in an atomic region so a failure re-runs the whole group with stable keys.

Four exactly-once contracts that must not be conflated

1. RPC exactly-once

One logical target invocation per key. Owner: caller's Start + target's durable queue.

2. Oplog-processor delivery

One delivery per batch. Owner: batch key + confirmed_up_to/sending_up_to checkpoints.

3. Stream-item exactly-once

Each StreamOffsetV1 consumed once per consumer session. Owner: durable_stream.rs / durable_session.rs.

4. Exactly-once finalisation

One terminal per stream; protocol terminals fence guest terminals.

A change that satisfies one of these does not imply the others.

16Oplog processor delivery

Oplog-processor plugins receive an agent's oplog entries as they are committed. Delivery is exactly-once per batch (services/oplog/plugin.rs), using the same two ingredients as RPC: a deterministic key and a durable checkpoint.

  • Key. oplog_processor_idempotency_key hashes source agent, plugin grant id and the batch's first/last index into a UUIDv5. Two forwarders that both see the same batch derive the same key.
  • Checkpoints. Per plugin, confirmed_up_to and sending_up_to live in AgentStatusRecord.oplog_processor_checkpoints, so a reconstructed forwarder knows exactly which entries still need delivery. The OplogProcessorCheckpoint hint (plugin_grant_id, target_agent_id, confirmed_up_to, sending_up_to, last_batch_start) records checkpoint advances in the source oplog.
  • Retry never widens the batch. If sending_up_to > confirmed_up_to when the forwarder wakes up, it re-sends exactly confirmed_up_to+1 ..= sending_up_to — the same range, hence the same key. Only when the previous batch is confirmed does a new batch extend to the committed tail. A range consisting only of checkpoint entries is skipped by advancing both cursors.
  • Target. The processor is itself a durable agent, so the "exactly-once" is ultimately the ordinary RPC contract of §12 applied to a deterministically keyed batch.

17Snapshots & updates

Replaying a long oplog from INITIAL every time an agent is reconstructed would be slow, and a component update needs a way to carry state across code that no longer replays identically. Both use snapshots: guest-provided serialisations of the agent's state.

A third execution mode

Snapshot save/load runs guest code in snapshotting mode: it neither appends nor consumes durable-call oplog entries (DurableCallSession created with persisted: false; durability_is_suppressed is exactly snapshotting_mode). A snapshot load is therefore not a fast-forwarded replay — the loaded state replaces skipped history from a revision-scoped baseline.

Which history does the new instance replay?

Decided at Worker construction (worker/mod.rs, component_version_for_replay):

  1. The last manual-update snapshot (a SnapshotBased update) is the baseline; if none, OplogIndex::INITIAL.
  2. A revision-matching automatic snapshot overrides it and skips INITIAL+1 ..= snapshot_idx — but only while no update is pending and the resident snapshot_recovery_disabled flag is unset.
  3. The component revision to instantiate comes from the same decision. A cursor cannot change it; only the outer loop can.

Two update flavours

UpdateDescription::Automatic

PendingUpdate { target revision r2 } (hint) is appended, the worker is unloaded and reconstructed. Because an update is pending, automatic snapshots are ignored; the new instance is created for r2. prepare_instance runs try_load_snapshot on the baseline, then resume_replay replays the remaining old history against the r2 component. Success appends SuccessfulUpdate during that replay.

If replay fails while the update is pending, on_worker_update_failed appends FailedUpdate and returns RetryDecision::Immediate: the outer loop rebuilds on the old revision, automatic snapshot eligible again.

UpdateDescription::SnapshotBased

The save hook ran on the old revision and its payload was recorded before unload. prepare_instance requires the store to be live already and finalize_pending_snapshot_update loads the payload into r2. No old history is replayed against the new code.

Use this when the new revision cannot replay the old oplog deterministically (changed host-call sequence, changed data model).

With no update pending, prepare_instance calls try_load_snapshot; if the load fails, the resident Worker's snapshot_recovery_disabled flag is set and the worker retries immediately with a full replay. The old oplog is untouched by snapshotting mode, so this fallback is always available.

When may a snapshot be taken?

Automatic snapshots are taken only at a safe boundary. SnapshotBoundaryConditions::blocker reports the first blocking condition in precedence order; a request at an unsafe boundary is rejected with that reason and never partially taken.

Marker
CompletionDelivered / CompletionDiscarded: records when (or whether) the guest observed a completion.
Oplog
The append-only, indexed journal of an agent's history; the only durable state.
Positional entry
An oplog entry that replay must match in order.
Replay
Re-running the guest from a baseline while feeding it recorded host results instead of performing effects.
Resident state
Anything held in executor memory: Store, instance, caches, queues. Disposable by definition.
Snapshot
A guest-serialised state used as a replay baseline (automatic) or to carry state across incompatible revisions (snapshot-based update).
Store
A Wasmtime store holding one instance and its host context; one per resident incarnation of an agent (plus one per active entity body).
Terminal
The entry that completes a Start: End or Cancelled.
Worker
The executor's resident object for one agent: queue, status cache, invocation loop.
