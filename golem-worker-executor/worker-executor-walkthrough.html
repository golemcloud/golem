The Golem Worker Executor, explained

An interactive walkthrough of how Golem runs WASM agents so that their progress survives the loss of the process running them: the architecture, the oplog, deterministic replay, durable host calls, exactly-once RPC, streams, tools, snapshots, lifecycle and recovery.

Describes the executor in golem-worker-executor/src as of September 2026. Collapsible sections open with a click or Enter; the interactive widgets need JavaScript, but every fact they show is also written out in plain text.

How to read this Part I gives the mental model (read it in order). Parts II–IV can be read independently once you know the vocabulary from sections 3–5. Words in italics at first use are defined in the glossary.

1What the executor is

The worker executor (golem-worker-executor/) is the process that actually runs agents. An agent is a WebAssembly component instance with a durable identity (AgentId) and an append-only history called the oplog. For a durable agent the oplog is what the agent is rebuilt from; an ephemeral agent also writes one, but only so that its status and results can be observed afterwards — it is never resumed from it. The worker service routes invocations to the executor that owns the agent's shard; the executor loads the component into a Wasmtime Store, feeds it invocations, records every nondeterministic interaction the guest has with the host, and — whenever the running instance is lost — rebuilds it by replaying that record.

Three guarantees come up in almost every later section, so they are worth stating once up front. The code is structured around them, and many non-obvious pieces of the executor exist to protect one of them.

1

Replay is deterministic by construction

The guest is a deterministic function of its guest-observable host inputs. The executor records every such input in the oplog and feeds it back on replay. If a replaying guest asks for a host call different from the one recorded next, the executor has a bug. It is never "normal nondeterminism".

2

The resident runtime is disposable

The Wasmtime Store, the worker task, sockets, channels, caches and the executor process itself may vanish at any instruction boundary. Suspend, evict, restart and crash are all recovered the same way, by the same executor: throw the instance away, build a new Store, replay the oplog, continue. Losing the shard is different: every oplog write asserts this executor's shard epoch inside the storage transaction, and once another executor holds it, the next write is refused rather than accepted. That refusal gives up the agent (InterruptKind::ShardLost) — stopped here with nothing more written, dropped from this executor, never restarted in place — and it is the shard's new owner, not this executor, that builds the Store and replays (§18).

3

Durable RPC is exactly-once per logical callee invocation

A caller may attempt a dispatch many times (replay, transport retry, incomplete-call repair). Every attempt carries the same durable idempotency key derived from its own Start, the target persists one invocation, and one durable result exists. Attempts are not executions.

What "durable execution" buys an application developer

  • Agent code is written as ordinary sequential code — awaiting an HTTP response, sleeping for a week, waiting for another agent — and the platform guarantees the code continues after any infrastructure failure from exactly the point it reached.
  • State lives in the agent's linear memory and filesystem, not in an external database, because memory is reconstructed from the oplog.
  • Calls between durable agents are exactly-once; a failed executor cannot cause a duplicated transfer.
  • Agents can be updated to a new component revision while keeping their history, snapshotted, reverted to an earlier point, or forked.

What it does not promise

  • Exactly-once effects on arbitrary external services. Between performing an external effect and durably recording its result there is an ambiguous crash window; Golem attaches idempotency keys, but the peer has to honour them (§15).
  • Resumption of ephemeral agents. They are deliberately fail-stop (§3).
Why the guest is deterministic The guest is a sandboxed WebAssembly component. It has no clock, no randomness, no network, no filesystem and no shared memory of its own; every interaction with the outside world is a call into one of the executor's host functions, and every host function that can return a different answer on a different day records what it returned. Given the same sequence of recorded answers, the guest computes the same sequence of requests. Determinism is therefore not a property the application developer has to maintain — it follows from the component model, and the executor's job is to make sure that the recorded answers are fed back at exactly the same points.

The rest of the crate: what surrounds the durable core

The component map above is the part of the executor that makes progress durable. It is embedded in a larger process that has to be placed in a cluster, admit work without running out of memory, load code, expose host interfaces and talk to storage. The cards below group the remaining modules under golem-worker-executor/src; each later section refers back to them when needed.

Observation: connect_worker (live log/event stream), get_oplog, search_oplog, get_workers_metadata, get_running_workers_metadata, get_agent_metadata, get_agent_wallet, get_file_contents, get_file_system_node. Streams: read_durable_stream_segment, control_durable_stream_attachment. Placement & scaling services/{shard,shard_manager,worker_proxy,worker_enumeration,worker_activator}.rs

Every agent id hashes to a shard; the shard manager assigns shards to executors and each executor's ShardService accepts or refuses work by shard (check_worker). The single-binary golem uses ShardManagerServiceSingleShard. When an agent needs another agent that lives elsewhere, RemoteWorkerProxy forwards the call to the owning executor over gRPC. worker_enumeration lists agents by scanning oplogs (durable agents only, unless the filter asks for ephemeral modes). worker_activator wakes agents in the background (for example after a shard is assigned, to resume interrupted work).

Admission, memory, fuel & quota services/active_agents/*, linear_memory.rs, resource_limits.rs, quota.rs, workerctx/default.rs

Before a worker becomes resident it must be admitted. The AdmissionController compares the larger of measured RSS (cgroup memory.current) and the total linear memory granted to live workers against a usable ceiling; when short it evicts resident idle, then warm workers, and if that is not enough it rejects rather than over-commits. The MemoryGrant guard returns the reservation exactly once when dropped. A per-account ConcurrentAgentsScheduler hands out execution permits fairly (FIFO per account). When compute metering is enabled, each Store borrows Wasmtime fuel batches from the shared account entry and re-borrows when the batch is spent. Production hard-limit execution has no local ephemeral overdraft: exhausted compute fails an ephemeral invocation with EphemeralFuelExhausted. Monthly memory and matching storage caps use the same admission and epoch path, described under monthly policy. QuotaService leases resource limits from the shard manager with a credit model (credit_rate, max_credit) so hot paths do not call out per use. compilation_limiter bounds how many local Wasmtime compilations can run when both the component cache and the compiled artifact store miss.

Code & files services/{component,file_loader,agent_types,environment_state,registry_event_subscriber}.rs, services/agent_filesystem/*, sandbox_filesystem/*, storage_volume/*, host_directories/*

Executor startup opens and validates one storage_volume::FilesystemVolume before creating host directories or sandbox provisioning. The volume owns the shared root descriptors and any exclusive root lock, native cloning, XFS quota operations and project reservations, and capacity observations. sandbox_filesystem creates and deletes isolated trees on that volume and owns confined paths, handles, seeding and copying contents out. Root capabilities provide confinement; project quotas provide accounting and limits. filesystem_pressure observes the volume directly without accessing a sandbox. Queued work retains the descriptors and locks it needs even if its caller stops waiting.

Executor startup creates .scratch and .initial-files through services/agent_filesystem/executor_directories/mod.rs, outside the per-agent sandbox lifecycle. The generic host_directories module uses standard filesystem operations and has no XFS or sandbox-provisioning dependency. AgentFilesystems::track_shutdown joins invocation loops and snapshot-store shutdown before removing these directories. The file loader refuses new loads and drains entered downloads and outstanding source leases before its cache is removed. Shutdown closes admission without holding a lock across filesystem work. New source loads return retryable Unavailable while existing leases drain. Both release() and shutdown_and_wait_for_invocation_loops() wait for tracked cleanup before a replacement can start. If invocation drainage fails, both host directories and their temporary parent stay on disk instead of being removed by Drop. Production drainage and cleanup share the existing shutdown grace. Without explicit shutdown, dropping the last cache lease after the loader can run synchronous directory cleanup on the caller's thread.

On SIGTERM, the existing InvocationLoops watcher closes construction admission, fences oplogs and cancels worker tasks as soon as the shutdown token trips. gRPC stays open until the tracked shutdown wait ends and the server join set stops, so requests can be refused in that interval. wait_for_exit() actively stops worker roots and joins cleanup. Concurrent callers serialize this drain and can retry after failure. EpochTicker owns its thread from creation, so an early failure in snapshot binding or service construction stops and joins it. Failed bootstrap cancels only this executor's token and waits at most SHUTDOWN_GRACE for tracked cleanup. It does not abort tasks in the caller's join set. Cleanup can outlive the returned error if the grace expires. Cancelling the bootstrap future instead relies on the Drop fallback.

The test helper shutdown_and_wait_for_invocation_loops() keeps its invocation timeout separate from the later cleanup grace. Only a successful return proves both completed. It does not drop the service graph. A replacement over the same root must also wait for that graph to release its root lock.

OperationContext shares construction, formatting and cause access for an operation, optional path and typed failure. It owns no cleanup policy. The domain marks rollback failures as cleanup failures and retains both diagnostics when an operation and its cleanup fail. Preflight stale-probe removal is primary work, not cleanup. If a probe and its later removal both fail, the actual removal error supplies the cleanup classification. Task errors keep BlockingTaskError, have no I/O kind, and remain terminal. Any failed rollback deletion sets cleanup_failed so worker startup retains its cleanup obligation.

CleanupFailure<E> shares diagnostic-chain bookkeeping while each domain chooses classification. The type parameter keeps each original error's type, and conversion consumes and maps the chain. Bootstrap failure and process termination share Shutdown::cancel_and_wait_for_tracked; ownership of the server join set stays with the caller.

component downloads component bytes and precompiled artifacts from the registry and caches them; engines are built through the shared golem_common::wasmtime_config so precompiled artifacts stay loadable. file_loader fetches content-addressed initial files. Each agent gets its own filesystem (§6). services/agent_filesystem holds its lifecycle: the start, the baseline, the initial-file rule, the read-only checks and the storage errors. sandbox_filesystem owns each isolated tree and its confined operations. storage_volume owns the shared storage and its XFS or APFS implementation. Production uses XFS with project quotas, ManagedXfs, or XFS with reflink and without project quotas, ReflinkXfs. Local development uses plain directories, Temporary or Directory, or Apfs on macOS. Apfs adds file clones and volume free-space checks to a root that the executor creates as Directory does. The sandbox has the operations of each call, and two tree operations. seed puts host files into a sandbox. copy_contents takes sandbox files out to a host directory. Both make copy-on-write copies on XFS or Apfs, and byte copies on other storage. Each storage mode states how it accounts for the files of each agent. ReflinkXfs and Apfs state AgentAccounting::Unaccounted. resolve_storage_limits accepts unlimited policy on these modes but rejects finite Registry limits instead of silently dropping enforcement. Neither mode reports per-agent usage. The executor refuses to start with resource_usage_metering.filesystem = true on either mode through check_filesystem_metering, because filesystem metering reads the project quota of each agent. Pressure monitoring is in filesystem_pressure/mod.rs. WASI filesystem p2 and p3 expose the filesystem to the guest. environment_state caches deployments, secrets, retry policies and which tools an agent may reach. registry_event_subscriber invalidates those caches when the registry changes.

Filesystem snapshots services/agent_filesystem_snapshots/*, filesystem_snapshot/*, worker/filesystem_snapshots.rs

AgentFilesystemSnapshots connects the snapshot records of an agent to the snapshot store: admission, names, the upload in the background, the confirmation, retention, restores, the copy of a fork, and the deletes of a delete, a revert and an unpublished fork stage. StoreCalls is the only owner of the store. The store (FilesystemSnapshotStore) keeps the snapshots of each agent incarnation in blob storage, in the restic format through rustic; nothing outside filesystem_snapshot/ knows rustic. worker/filesystem_snapshots.rs holds the plans of the worker: the record of a snapshot, the baseline of a start, and who can confirm. The service is off unless the configuration sets filesystem_snapshots to Enabled on storage that makes copy-on-write copies. Production uses ManagedXfs or ReflinkXfs. Local development and tests on macOS use Apfs. Project quotas are not required for snapshots. See §17.

Cross-agent plumbing services/{rpc,promise,scheduler,worker_event,events,stream_session_index,card,card_interest,direct_invocation_auth,agent_webhooks}.rs

rpc implements the agent-to-agent invocation path (local worker or remote proxy). promise creates, polls and completes durable promises that external parties can fulfil; scheduler persists timed actions (wake a sleeping agent, complete a promise, invoke, archive an oplog) so a timer set before a crash still fires after it. worker_event is the per-worker log/event stream behind connect_worker. card / card_interest implement permission cards (check, derive, revoke, ancestors) and direct_invocation_auth authorizes local RPC by principal. agent_webhooks delivers agent-defined webhooks.

Storage backends src/storage/{indexed,keyvalue,scheduler}/*

The oplog service, key-value service, scheduler and status flusher are written against three small storage traits. Implementations: in-memory (tests), SQLite and multi-SQLite (single binary, local runs), PostgreSQL and Redis. Every indexed storage fences oplog writes on the shard epoch inside the write itself — a Lua script on Redis, SELECT … FOR UPDATE on PostgreSQL, the single-connection write pool on SQLite — through trait methods with no default (set_key_epoch, delete_with_epoch, delete_empty_with_epoch, and the expected_epoch of append / append_many / drop_prefix), so a backend cannot leave the fence out. The primary oplog and every compressed archive level go through them, including the archive transfer's appends and trims. Blob storage has no conditional write, so the blob archive layer lists its chunks in a manifest in indexed storage, fenced the same way: a chunk no manifest lists is never read. Executors that share shards need storage they can all reach, which means PostgreSQL or Redis; a SQLite file is written by one process. Decorators exist for retrying, namespace routing and fault injection (used by the tests that simulate storage failure). Indexed storage also offers scan_stable, a key walk that does not skip keys when the caller deletes the ones it was handed, which is what the oplog sweep pages with. Blob storage for oplog archive layers and snapshots is provided by golem-service-base.

Multi-SQLite removes a per-agent database when a successful delete or prefix trim leaves its entire index empty; primary presence markers, other keys and staged entries prevent removal. Ordinary operations share a per-file lease, while reclamation excludes operations and waits for both current and previously evicted pools to close. The existing LRU and idle cache eviction policies remain in use. Writer epochs transfer durably to epochs.db before removal and back before a later append, so draining a file does not lose its fence. Empty epoch snapshots are temporary handoff markers, removed only after the database and its sidecars have been unlinked; nonempty snapshots retain fencing authority. Missing-file reads and scans do not recreate databases; filename scan markers and file-count pagination remain valid after removal. Admitted writes and cold initialization finish even if their callers cancel their waits; warm reads avoid an extra task. Completed operation errors evict their pool generation, and reopening waits for its retirement instead of permanently disabling reclamation. Uncertain initialization, epoch-authority transfer or retirement, or cancellation of an admitted warm read, disables physical reclamation for that file until process restart. This does not itself reject operations against an authoritative live database, but recreation from an authoritative epoch snapshot may require process restart.

Live filesystem inspection: metadata first, one pinned generation

get_file_contents serves the existing CLI and REST file-read operation with a metadata-first stream instead of a full-file buffer. Live HTTP filesystem bindings reuse this operation; static initial files come directly from blob storage. Its Rust API receives one CanonicalFilePath, and gRPC carries that canonical absolute path as the string file_path. The HTTP layer owns exposure-root selection, root/suffix composition, decoded-segment checks and trailing-directory intent. The executor validates the raw absolute path without URI decoding; it does no route interpretation, Range parsing or validator generation. Inspection itself invokes no guest method and is not a durable stream.

  1. Activate normally. Concurrent first reads share agent creation. The constructor must complete before inspecting files; its reserved idempotency key identifies it at the head of the pending queue. Inspection invokes no exported method, but initialization and replay may execute guest code. There is no separate read admission limit or executor read deadline.
  2. Inspect current state fairly. Reads and listings enter the existing resident command deque. After active execution and its streams finish, one inspection can bypass queued work; the next yields to a pending update or invocation. Alternating turns prevents continuous reads from starving ordinary work without draining the invocation backlog or recording an oplog position. Control commands retain their priority. Abandoned resident requests are pruned at scheduler and lifecycle boundaries; durable invocations are never pruned when callers disconnect.
  3. Open under exclusive ownership. The invocation loop acquires the exclusive OwnerLane, walks descriptors without following any symlink, opens only a regular file, and captures metadata from that descriptor. Absent and forbidden targets remain distinct; there is no listing or implicit index file.
  4. Stream under the same guard. A metadata head reports total u64 size, selected offset/length or unsatisfiable selection, and optional modification time. Full, bounded, open-ended, suffix and metadata-only selections share one implementation. Chunks are at most 64 KiB through a capacity-one channel; whole-file length never sizes an allocation.
  5. Release after production. The descriptor, generation and lane remain held until every selected byte has been copied into the bounded response. They are then released without waiting for consumer-observed EOF. Producer failures are published before channel close, so a terminal error never appears as EOF. The worker service owns the transport stream directly and never retries after the head.
Exposure policy is not lifecycle revision. A read uses the agent's normal current revision at the exact canonical path supplied by its caller. Updates, revert and unload cannot splice another generation into an active response. Later reads reconstruct normally and inspect that same path in the new generation; a missing file never selects another path. A queued read survives ordinary Suspend and waits for normal resume; it does not force a fuel, quota or scheduled-wait bypass.

Owners: worker/mod.rs, worker/invocation_loop.rs, services/agent_filesystem/lifecycle/{inspection,inspection_stream}/mod.rs. Real runtime coverage: tests/filesystem_inspection.rs.

How an invocation travels

  1. A client calls the worker service (HTTP or gRPC). The worker service resolves the agent's shard and forwards to the owning executor over gRPC (src/grpc/mod.rs: invoke_and_await_worker and friends).
  2. The executor's shard service confirms it owns the shard (check_worker); otherwise the request is rejected and the worker service retries with fresh assignment.
  3. The executor finds or creates the resident Worker. Creating one means loading the component, folding the agent's status from its oplog, and deciding which history the new instance must replay (snapshot baselines, pending updates).
  4. The invocation is deduplicated by idempotency key, appended as PendingAgentInvocation and committed before the caller is told "accepted".
  5. The invocation loop pops it, appends AgentInvocationStarted, runs the guest export in a Wasmtime Store, and every host call the guest makes is recorded through the durable host context.
  6. AgentInvocationFinished is appended, then completion waits for the state actor's commit receipt before notifying waiters. Durable agents use Always (storage first); ephemeral agents use Deferred (ordered writer handoff).

Durability guard and durable call sessions: two layers, not two alternatives

The durability guard (durability.rs) checks read-only invocation restrictions and evaluates retry policy. A DurableCallSession (concurrent/call.rs) owns one call: it appends or claims Start, runs or repairs the effect, records its terminal result and delivers it with a CompletionDelivered marker. Incomplete repair completes the existing Start; it does not discard neighboring history.

Nesting is recorded only in Start.parent_start_index, not in the function type or a generic implicit scope. There are no extra generic scope Start/End records. DurableDemandStream retains its actual parent call session, and RDBMS retains its explicit transaction protocol. §8 distinguishes call lineage from protocol recovery ownership. Custom durable invocations use their own Start/End pair through begin_custom_durable_invocation.

"Exactly-once" is also not one promise. RPC between durable agents, oplog-processor delivery, stream items and stream terminals each have their own exactly-once contract with their own mechanism; §15 sets them side by side after each has been introduced.

4Durable vs. resident state

Append versus commit

Two persistence steps matter for every crash window. Append puts an entry into the oplog's in-memory buffer. A storage commit makes entries recoverable. The buffer exists so that not every append costs a storage round trip; where an entry must be recoverable before the executor proceeds, the code commits explicitly:

  • Accepting remote work: PendingAgentInvocation is committed before the caller learns the invocation was accepted.
  • Finishing an invocation: after appending AgentInvocationFinished, durable completion waits for Always storage; ephemeral completion waits only for a Deferred ordered writer handoff before notifying waiters.
  • Stream records are committed before they are published on the live bus.

CommitLevel::Always waits for durable storage. Deferred still waits for durable oplogs, but on an ephemeral oplog returns after ordered handoff to its bounded asynchronous writer; queue backpressure may still wait. DurableOnly waits only for durable agents and remains a no-op for ephemeral agents. Explicit protocol barriers and acceptance keep their existing storage guarantees: completion's use of Deferred is not a global weakening.

A commit can be refused instead of written. Every append and commit asserts this executor's shard epoch inside the storage transaction, and a storage that has recorded a newer epoch — another executor now owns the shard — returns OplogError::Fenced (StreamStoreError::Fenced for durable-stream session records) instead of writing anything. commit_oplog_and_update_state, commit_oplog_before_status_update and add_and_commit_oplog return that refusal rather than swallowing it, so the three guarantees above hold either way: a refused PendingAgentInvocation commit is not acknowledged as accepted, a refused AgentInvocationFinished commit is not published to waiters, and a refused side-effect Start is not treated as durable. The first refusal latches — every later add on that oplog is refused too, without a second storage round trip — and the agent is given up (§18) instead of retrying the write or restarting in place.

worker/state_actor.rs::commit_and_update_state samples the appended oplog tip before its explicit commit and discards receipt entries already folded into the published status. Threshold auto-flushes in both primary and ephemeral oplogs, and replica waits, can commit outside the status actor; therefore an empty commit receipt does not prove that no new entries committed. After such a commit the primary oplog calls its auto-commit listener, which queues one coalesced FoldAutoCommits status job. The job commits nothing and folds the entries that CommitLevel::ReportOnly returns, so status.oplog_idx follows the committed index during a long invocation; an append below the threshold stays invisible in the status until a commit. The primary oplog keeps its latest auto-commit batches in memory until that report, which normally follows at once, up to oplog.max_retained_auto_commit_batches; beyond it the report reads the oldest unreported entries back from storage. Ephemeral oplogs call no listener: ephemeral agents fold at the explicit commit that ends each invocation. Because the status follows the oplog, each status-cache write catches up the stream-session index and the invocation-result index over only the entries since the previous write, instead of over a whole long invocation at once. Ephemeral threshold flushes hand batches to a bounded async writer, while read snapshots include handed-off entries plus the buffered tail after the persisted writer watermark. The status path retains at most 32 batch receipts; if that cap creates a gap, exceptional catch-up forces storage after the completion acknowledgment, then reads the missing range. Otherwise a non-contiguous receipt makes the actor reuse status::try_fold_status_from to read committed storage in bounded chunks, hydrate external StreamSession payloads and publish once. Completion itself does not await that fold. When the fold needs archived history that does not read, the status stays detached: the invocation loop chooses its next work only from a repaired status, so the owner rebuilds it first, and a rebuild that fails again sends the agent to infrastructure recovery, or stops it with OplogFailed when the history does not read for good. That stop does not fail the invocation whose completion was already published: the result cache keeps the keys of committed completions that the status has not folded yet, even after it evicts their payloads. A freshness-sensitive status read queued on the actor waits behind it; the persistent status cache remains asynchronous. Admission and authority jobs still await their full folds, and the RunningWorkers recovery index remains synchronously updated by the actor. The unchanged synchronous Create write preserves an ephemeral agent's identity before execution; after executor loss, that identity reconstructs an observation-only owner, never a fresh execution.

Status rebuilds classify retained StreamSession payload reads through OplogServiceOps::download_payload. A backend failure gives RecoveryRequired; the agent can recover when storage answers again. A missing reference or undecodable payload gives OplogFailed for that agent only, with the entry index and cause. Neither stops the executor. Reverted payloads do not participate in the rebuild. Regions that invalidate even the empty status baseline are corrupt history, not an absent worker. An absent worker at the established status actor's fixed nonempty horizon remains a fail-stop invariant violation.

Rediscovery

Durability alone is not liveness: after a crash somebody must notice that an agent has pending work. Two mechanisms provide that. Before automatic suspension, a timed wake is persisted as a scheduler action (worker/suspension.rs::RuntimeStore::drive, WakeupScheduler::sleep_until). And the shard-keyed RunningWorkers index is updated synchronously whenever a worker gains or loses pending work (worker/status_flusher.rs), so an executor that takes over a shard can enumerate the agents it must revive. Each member includes the AgentFingerprint from its Create entry: recovery admits only that exact incarnation, and stale cleanup removes only that exact member, after it requests the delete of that incarnation's filesystem snapshots (delete_all_snapshots). A member is stale when its agent has no oplog or its oplog belongs to another incarnation; a removal that fails leaves the member, and the next scan requests the delete again. The status blob cache is only an asynchronously flushed baseline.

5The oplog

The oplog is an append-only sequence of typed entries per agent, indexed from OplogIndex::INITIAL (the Create entry). Entries are defined once, by the oplog_entry! macro in golem-common/src/base_model/oplog/mod.rs, which generates both the binary OplogEntry and the user-facing PublicOplogEntry.

Storage layers

Logically the oplog is one append-only sequence per agent. Physically it is spread over several storage layers that trade write latency for cost, and the MultiLayerOplogService hides the split: from the replay cursor's point of view there is only read(agent, from_index, count) over one contiguous index space.

The pieces, top to bottom:

  • Primary layer. PrimaryOplogService keeps an in-memory buffer per open oplog and writes it to indexed storage on commit: implicitly after max_operations_before_commit (128) appends, or explicitly wherever the executor needs the entries to be recoverable now (see append versus commit). An automatic commit makes entries durable but does not bypass status accounting: the primary retains the committed-but-unreported range and returns it with the next explicit commit so that commit's caller can deliver every entry to the status reducer. Payloads above max_payload_size (64 KiB) are stored in blob storage and referenced from the entry, so a huge invocation argument does not bloat the index.
  • Archive layers. With the default configuration there are two: one CompressedOplogArchiveService (indexed_storage_layers = 2 means "primary plus one compressed layer" in indexed storage) and one BlobOplogArchiveService (blob_storage_layers = 1). On every commit the multi-layer service checks whether more than entry_count_limit (1024) entries were added since the last transfer; if so it moves the oldest prefix one layer down. Independently, a persisted ScheduledAction::ArchiveOplog fires every archive_interval (24 h) and pushes the prefix of an idle agent's oplog down a layer; commits after it was scheduled do not discard that maintenance retry. Every transfer appends and verifies the destination before dropping its source. A storage failure therefore leaves the source intact, is logged as a failed maintenance attempt without failing the agent, and lets threshold, scheduled or sweep maintenance retry with per-agent backoff instead of aborting the executor; a read required for replay or recovery never pretends history is absent. A chunk that does not decode, a failed storage read of an archive level or a gap gives UnreadableOplog. When the storage of the archive level did not answer after its retries (an indexed storage Transient or Indeterminate error, or a blob error that BlobFailure calls transient or refused), the failure is temporary: it reaches the start and the invocation as RecoveryRequired, which they retry with backoff, and shard-assignment recovery fails the assignment so that it is retried. Any other read failure reaches the start as WorkerExecutorError::OplogFailed and fails that agent only: it does not run, its status is Failed with the agent id, the archive layer and the decode or storage error, and its oplog is left as it is for inspection. Shard-assignment recovery skips such an agent and recovers the others; the executor process stays up. The same holds for an archive level whose last index or owning-epoch record fails when the oplog is opened, and for a stream session index rebuilt over an unreadable oplog. An invocation session attachment records a failed session terminal only for a violation of the session protocol (end_attachment_on_failure in grpc/invocation_session/mod.rs): when an output or request read of the session history meets storage that did not answer, including a stream payload download, the attachment ends without a terminal frame and the client reattaches from its durable cursors once the storage answers again; a fence or an oplog that failed for good goes out as its worker error and records nothing, so the session result stays with the history. When the writer of an ephemeral oplog cannot store a batch in the first archive layer, it latches the failure like a fence: the agent stops, and entries already acknowledged with Deferred can be missing from its archived history, which is only for observation. A transferred prefix may be removed from primary only through the last entry already reported to the status reducer. Archiving never changes an index: entry #17 is #17 whichever layer holds it. The transfer is fenced on the shard epoch: opening the oplog records the owner's epoch on each compressed level, and a transfer still running on an executor that has lost the shard is refused at its next append or trim, stops before verifying or trimming anything, and latches the oplog's fence. A refusal is not a storage failure: it is never retried, since the oplog belongs to the shard's new owner.
  • Reads. read / read_exact ask the primary layer first and fill the remaining index range from lower layers, so a replay of a very old agent may touch all three layers for its first entries and only the primary for the recent tail.
  • Ephemeral oplogs. An ephemeral agent's EphemeralOplog buffers in memory, commits every max_operations_before_commit_ephemeral (1024) appends directly into the first archive layer, and is archived when the instance ends. It is never read back to resume the agent (§6); it exists so that what an ephemeral instance did can be inspected afterwards. Its writes assert the shard epoch it was opened at, like the transfer's, so an executor that has lost the shard gets OplogError::Fenced from its next commit. An instance cut off by a crash leaves its entries in that first layer, and while oplog.sweep.enabled is set, ephemeral agents register no ArchiveOplog action to move them: instead OplogSweeper (services/oplog_sweep.rs) periodically walks the layer's keys for the shards this executor owns and archives every oplog whose last index has not moved since an earlier pass and whose agent is not resident, within a per-tick scan and archive budget. Like the scheduled action it archives through Worker::archive_oplog, but it waits for each transfer while holding the agent's oplog lifecycle guard.

6Worker lifecycle

A Worker (worker/mod.rs) is the resident object for one agent on one executor. It receives invocations, persists them, and processes them in order through the invocation loop (worker/invocation_loop.rs::run). The loop has two levels, and understanding them is most of understanding recovery.

Control operations acquire that resident object through an existing-only path: a cold persisted worker may be hydrated, but an absent agent is never created as a side effect of interrupt, delete, resume, update, revert, or plugin changes. Deletion is then owned by the acquired Worker. Concurrent callers share one retained attempt result; after a failed attempt, the next delete resumes at its first unfinished cleanup stage. Successful cleanup retires active-worker and open-oplog cache entries only when they still belong to the deleted generation, so stale worker references cannot affect a replacement that reuses the same AgentId. Right after the oplog delete, WorkerService::remove calls a closure that requests delete_all_snapshots for the filesystem snapshots of the deleting incarnation; a fenced delete requests nothing, and the store's delete_all waits for the store work of the incarnation that began before it. A delete of delete_all that got no answer can still land after it answered, so nothing writes a scope after a delete of all its snapshots; each incarnation and each fork stage has its own fingerprint, so nothing needs to. Retention and the cleanup of a revert and a fork are in §17.

The bounded unload result and final cleanup completion are separate facts. An unload timeout permanently fails that deletion attempt, while module-owned cleanup continues. A later explicit delete joins the retained completion, or retries a failed filesystem deletion through the owning filesystem generation. Durable storage and cache authority remain fenced until verified cleanup succeeds; old attempt handles retain their original error. Cleanup with no verifiable owning-component repair remains a failure: successful filesystem deletion cannot erase an unverified metering settlement, including ObserverLost during startup rollback.

For a resident owner, retained module-owned unload follows primary runtime destruction → filesystem drain → final metering and scheduler-permit release → current OwnerToolOperations registry empty → filesystem deletion → successful unload. wait_owner_settled observes registry settlement, not a join of every supervisor. Entity Store destruction and lane drainage remain separate, necessary barriers. begin_generation still rejects active operations rather than clearing them. EntityFence::drain must not wait for the registry: its caller can hold an operation and would wait on itself. The existing unload deadline observer can report CleanupFailed while retained final cleanup keeps waiting; an early metering error can also report before the registry wait. Neither error permits successful reconstruction. Startup cleanup without a resident owner skips this registry barrier.

ensure_existing_with_fingerprint resolves identity and metadata, not execution readiness. A resolved Worker remains reachable by public Delete after failed unload so the same filesystem generation can repair disposal. Startup and readiness still reject retained cleanup failure. The permission test uses a real FIFO contender: after deletion fails, it acquires capacity while the failed runtime root still exists. Restore permissions, delete and require actual root removal. Returned capacity is not successful filesystem cleanup or a count of all acquisitions.

Create, open, archival, fork-source reads, and deletion share the logical oplog's exclusive cold lifecycle guard. Fork reads persisted source history without constructing an absent source. The complete hidden stage is published atomically into an absent target under its lifecycle guard. Source and target guards are never held together, and publication releases the target guard before resuming the child. Cancellation or failure may leave an unreachable hidden stage; cleanup removes that stage's index and its filesystem snapshots, and never target payloads or canonical state. Archival runs through the existing worker owner. Individual stream items, oplog reads, and replay steps do not acquire this lifecycle lock.

Oplog::stop_and_wait joins work belonging to the actual open oplog generation, including older worker shells removed from the active cache. It cancels transport roots and joins their descendants without waiting for client IO. Invocation loops are joined, not cancelled: their final commits, state destruction, and panic cleanup must finish. Already-spawned metadata loads and attachment queries finish independently so a suspended Store cannot retain their locks: registration occurs once per spawned task, never on cached no-spawn queries; attachment queries may spawn every time. Worker-state actors register once at construction and drain lifecycle jobs, status jobs, and the status flusher, including on ordinary worker drop. Final retirement also joins oplog actors, payload uploads, archive transfers, and monitors. Errors are reported only after all owned work finishes. Deletion records that completion separately so an explicit retry can remove storage without reusing a retained stop error; the original attempt keeps its error. A later cold acquisition reloads persisted state instead of inheriting a stopped generation's error.

On executor shutdown, the active-agent cache task removes cached workers regardless of their TTL. Each worker owns the service graph that owns the cache, so task cancellation alone cannot release the graph or its storage pools. This removes cache references only: it records no interruption and deletes no persisted agent. In-process replacement still waits for the old executor's invocation loops and oplog generations to drain.

External metadata observation uses a fallible FIFO status read that repairs a detached projection before returning it. Unreadable history returns its cause rather than a stale status; once history reads again, the next observation reconstructs the status without starting the worker. Cleanup keeps its non-repairing FIFO read so an unreadable oplog cannot prevent runtime teardown. If the actor has stopped, the lookup takes the cold oplog lifecycle guard, verifies retirement, joins writer completion, and reconstructs from persisted metadata and the oplog. A failed deletion can therefore leave a cached but stopped worker observable until removal is retried. Missing storage means absence; failed reconstruction means an error, never a stale cached status or permission to restart work.

Monthly admission and recovery

Registry resolves monthly compute, memory, durable storage and ephemeral storage independently. The existing refresh path updates the shared AtomicResourceEntry and rejects stale policy revisions. worker/invocation_loop.rs checks the latest cached capacity before creating an instance, resuming replay and running an invocation. Reconstruction uses those same gates; an exhausted applicable cap cannot be bypassed by resume or queued work.

Context::ensure_fuel, the FuelManagement implementation in workerctx/default.rs, calls ensure_monthly_resource_capacity to check compute when enabled, then memory and the agent's matching storage class. The existing Wasmtime epoch callback in worker/instance/mod.rs and pre-call check in worker/invocation.rs share this decision. Compute and memory apply account-wide. Durable storage exhaustion affects durable agents only; ephemeral storage exhaustion affects ephemeral agents only. Durable exhaustion requests suspension and unload with RetryDecision::TryStop. Ephemeral exhaustion fails without retry, using EphemeralFuelExhausted for compute or EphemeralCannotSuspend for memory/storage. Enforcement infrastructure failure is distinct from exhausted capacity.

After a UTC month reset, a grant or plan increase above usage, or application of an allowOverage revision, subsequent demand can pass admission and reconstruct. Mode revisions reach running agents through refresh within five minutes. Idle refresh eligibility reserves one batch interval for the next scheduled tick. Usage attributed to an applied allowOverage revision remains eligible for excess billing until hardLimit applies. Registry currently allocates the included amount in revision order, not exact cross-executor accrual order during overlapping refreshes. That MVP limitation is tracked in GOL-848.

Memory and storage exports retain measured hard-limit overshoot rather than clipping it to remaining capacity. Fractional byte-time remains exact across settlements and policy/month cutovers. Overshoot totals are diagnostics, not another capacity debit. Fuel keeps the existing prepaid/refund meter, including the remaining reservation's borrow revision and month. Failed Registry delivery can lose captured usage; ambiguous additive updates are not blindly resent. Delivery and customer-credit safety are tracked in GOL-847.

Disabled meters disable the corresponding monthly accounting, caps, overage and billing. Filesystem metering controls both separate storage dimensions. Per-agent memory enforcement and managed-XFS quotas remain independent; unmanaged storage has no finite per-agent storage limit.

The single-binary configuration rejects enabled per-agent storage policy without managed XFS, even when filesystem billing is off. Split-service executors reject finite Registry limits on unaccounted storage before filesystem creation. A live limit update uses the same resolver and the existing seal/unload owner on failure. Unlimited policy remains valid. Registry's finite policy is a deployment requirement; an unsupported backend cannot omit enforcement and continue as unlimited.

Registry limit requests carry the deployment's existing meter flags. Disabled runtime dimensions skip usage reads and allowance calculations. All-off reads still resolve per-agent limits without creating monthly billing revisions or baselines. Aggregate display does not create runtime billing state.

Delivery acknowledgement and monthly-policy availability are separate facts. A usage update can commit even when the subsequent Registry policy read fails. The reply acknowledges that delivery and marks enforcement unavailable. The account entry retains its applied policy instead of installing the fallback's mode, period or capacity. Admission, guest checks and the existing monitor report infrastructure failure, not quota exhaustion. Guest-entry, post-instantiation and epoch checks share resource_capacity_error. Only typed resource exhaustion becomes durable suspension; infrastructure errors retain their AgentError and retry-policy classification. The latest observed policy revision remains a floor against stale replies. The next existing batch tick refreshes an unavailable entry; a valid reply restores admission without resending acknowledged usage. All-off entries have no monthly availability gate.

A live invocation still holds allocated linear memory and filesystem stock while waiting for host I/O. Those live allocations accrue byte-time during permit-held waits even when no Wasm executes. The memory meter measures allocated linear-memory bytes, not the configured maximum. The parked guest itself burns no fuel.

Reconstruction keeps physical admission, the concurrent-agent permit, allocation observations, per-agent limits and cleanup ownership. Cold initialization is shared, but not published early

The active-agent cache reserves one unresolved Worker. An executor-owned attempt prepares its metadata-dependent data privately; dropping the initiating request does not cancel that attempt. Only successful local construction publishes the resolved data and changes the lifecycle to Unloaded. If preparation fails, attempt-owned actors and persistence work finish before the worker returns to Unresolved. Current waiters receive the same error; a later explicit request can retry on that same worker. Persisted data is never deleted as rollback: the retry reloads any committed Create and pending initialization, preserving that incarnation and its original initialization context.

Remote stream topology recovery runs after local publication, followed by finished-session recovery in the same reconciler pass. Attachment control can acquire another cold worker, including one on a different executor that refers back to this worker; awaiting that round trip inside both constructors would deadlock. Publication therefore means local readiness, not completed remote topology recovery. Prepared consumer topology does not authorize stream reads, and failed topology recovery postpones finished-session recovery. The reconciler folds only through the committed in-memory status tip. The deletion gate remains applied.

Healthy attachments do not need a polling timer. Once recovery has no unfinished work, the resident task parks on committed stream-state notifications, even with active attachments. First producer load wakes a worker with no prior stream history. Session records and stream terminals wake recovery after their commit callbacks publish worker status; ordinary producer items do not. A forwarded input's terminal therefore wakes deferred session completion. Only failed or unfinished recovery arms a retry deadline.

Stale attachment bookkeeping is lazy. Deletion reconciles before deciding which source-history dependencies remain. A read can repair a producer left Prepared by a lost activation RPC, but only after checking the exact committed Active consumer topology; healthy reads stay read-only. Resident notifications are disposable: cold acquisition reconstructs from committed history, and idle stale records may remain until demand. This does not add an atomic storage outbox or a global cleanup sweep.

Each reconciler uses a child of the executor shutdown token, so graph shutdown stops new recovery passes and wakes parked reconcilers. Explicit owner retirement, revert, and deletion cancel and join the in-flight pass; TTL cache retirement does not itself cancel or join the reconciler.

Each start builds the agent filesystem

Every start of an agent instance builds a new agent filesystem before it makes the Store and the instance. The lifecycle in services/agent_filesystem/lifecycle moves the filesystem through typed stages. Before the baseline is in place, the filesystem accepts no call of the guest. Replay access opens after the baseline and ends at finish_replay:

  1. Worker::decide_start selects the baseline record (§17), and StartFilesystem::load_and_plan plans it with filesystem_snapshots::plan_start and loads its restore, before the filesystem exists.
  2. create_fresh_with_pressure_recovery makes an empty generation (Created), and the start binds its resource usage metering (Reconstructing). When the bind fails, the start deletes the Created filesystem (delete_created).
  3. prepare_initial_files checks the declarations of the replay revision and loads their content into the .initial-files cache.
  4. materialize_baseline puts the baseline in place and then enables replay access.
  5. prepare_instance replays. The filesystem calls of the guest during replay change the tree as they did live.
  6. Only Ok(None) from preparation continues to finish_replay, which ends replay access. Then finish_reconstruction checks the usage against the limits and makes the filesystem Resident.

Ok(Some(decision)) aborts preparation, even when the decision is RetryDecision::None. PreparedAgent::finish seals the reconstructing filesystem without draining it and returns the runtime to the common teardown and retry tail. It does not activate or publish a resident generation. The unload continuation drops the Store before it drains the sealed filesystem, closes the execution window, releases the permit, and deletes the filesystem. This order matters: a P2 output stream can retain a pending FilesystemCall after interruption cancels its borrowed readiness future. Draining replay with that Store alive would wait for a call that only Store destruction can detach. The common tail preserves the original retry decision, later interrupts, ephemeral fail-stop rules, and cleanup failures.

After the metering bind, a failure releases the filesystem context, worker context or Store that owns open nodes before it awaits filesystem cleanup. Cleanup seals the filesystem (abort_reconstruction) and drains those nodes; retaining an open node across that wait would deadlock. Then the start does one of these:

  • It fails.
  • It starts again, after it skips a record or appends FailedUpdate (see below).
  • It suspends the agent, when the agent quota is exhausted (reconstruction_startup_error).
  • On a lost shard, it stops and writes nothing.

When the baseline fails, worker/start_outcome.rs::decide decides what the start does, from the baseline role and the update at the head of the queue (§17). A filesystem snapshot of an automatic record that does not restore makes the start skip that record and start again. A transient error fails the start as an ordinary reconstruction error, and a later start tries again. For a pending manual or snapshot-assisted update, the other classes fail the update, and the start begins again on the source revision: UPDATE_SNAPSHOT_UNAVAILABLE for Lost (an assisted update also rejects its record), UPDATE_SNAPSHOT_RESTORE_FAILED for Fixed and DiskFull. For an authoritative baseline of a successful update they fail the start with a visible cause. A conflict of the initial-file rule at the start of a pending manual update appends FailedUpdate with the message of the conflict, and the start begins again on the current revision; on a lost shard the start writes nothing, and when the write of FailedUpdate fails, the start ends with that error. On an executor with filesystem snapshots disabled, the selection takes a candidate automatic record only when the record names no filesystem snapshot, and otherwise the authoritative baseline or a full replay. A pending update whose record names a filesystem snapshot fails the update there with UPDATE_RESTORE_NEEDS_FILESYSTEM_SNAPSHOTS; an authoritative baseline that names one fails the start with a visible cause.

One initial-file rule for every install

One rule decides the declared files at each install: the baseline of a start, an automatic update, a manual update after a restore, and entity provisioning. initial_files::plan decides the changes, and initial_files::install makes them with seed and the sandbox calls: first the unlinks, then the removals of directories with the deepest directory first, then the seeds. The rule reads the tree and two sets of declarations: the old declarations before the install, and the new declarations after it. The record of the installed read-only files (below) only saves a read of their content.

At a path where the old and the new declarations are equal, the install changes nothing, also when the agent changed the file. At every other path, the install expects what the old declarations left there: the initial file where they declare the path, and nothing where they do not. The initial file of a declaration is a regular file with the declared content and, for a read-only declaration, without write permission. The rule does not ask who put the file there.

A conflict names the path and what is at it, in one of three forms (InitialFileConflict): "the agent filesystem holds another object at {path}", "the agent filesystem holds a file above {path}", or "the agent filesystem no longer holds the initial file at {path}", each followed by ", so the initial files of the agent cannot be installed". An install that can find a conflict first reads, through observe, each path whose declaration changes and each directory at a path that only the new declarations have. The install loads every source before its first change. So the install itself changes nothing at a conflict. The agent stays runnable:

  • An automatic update fails in prepare_instance: on_worker_update_failed appends FailedUpdate, and the start returns RetryDecision::Immediate and begins again on the old revision.
  • A pending manual update records FailedUpdate, and the start begins again on the current revision. The restore before the rule has already changed the tree of that start, and the start seals it for cleanup. On a lost shard the start writes nothing. When the write of FailedUpdate fails, the start ends with that error.
  • Entity provisioning fails the entity invocation with the message of the conflict. The generation of the running agent stays valid.

A failure while the install changes the tree invalidates the generation. A failure to load a source does not. Two different declarations at one path, for example an entity-provisioned file and an initial file of the revision, are refused before the plan with a verification error, which is not an InitialFileConflict (validate_compatible).

The lifecycle records the file identity of each read-only file that an install puts in place, and a file without write permission that keeps that identity counts as the initial file without a read of its content (InstalledFile).

Read-only initial files and permission errors

P2 and P3 preserve the capabilities that the guest requests. A directory needs MUTATE_DIRECTORY for namespace changes; file WRITE does not grant it. Mutable child opens, including create and truncate, cannot exceed the parent directory's capability. An open with neither data capability grants no read or write access. Missing directory mutation gives read-only, not a live policy denial. Opening a directory with READ | MUTATE_DIRECTORY needs Read/List policy, not Write. Each later namespace operation still checks its own Write or Delete policy; a policy denial gives not-permitted. Reconstruction uses the same descriptor rules.

A policy decision has a track in the oplog. Every protected P2 or P3 filesystem import records its permission decision in a normal durable call, allowed or denied, and replay returns the recorded decision without a policy check. Most imports record a filesystem::permissions::check call before their effect, with the verbs and the guest paths in its request and Ok or the denial reason in its response. stat and stat-at check inside their own durable call and record a denial as their not-permitted result. P3 write-via-stream and append-via-stream record the decision in their admission call. The check runs after the claim resolves as new work and before the call writes its Start. A denied check records the denial in its Start, so the recovery of an incomplete denied check completes it with the same denied result and the protected effect does not run. An incomplete Start without a denial was allowed, so its repair completes it as allowed without a new check. P2 TCP start-connect and UDP explicit-address operations record their decisions in sockets::tcp::permissions::check-connect and sockets::udp::permissions::check calls; a recorded denial returns access-denied without the protected operation.

Authorize new calls, not Stores. A new call can reach the replay tail before live publication, while a historical retained Start can be claimed after publication. Accessor initiation resolves the call first, performs the guarded live transition when needed, then authorizes through AccessPermissionCheck before appending its immutable Start. Completed replay and allowed incomplete repair keep the recorded decision. HTTP quota admission follows authorization in the owned request builder, still before Start; denied calls and historical claims do not consume quota, and quota failures retain their typed traps.

A read-only initial file refuses a change to its contents or its times. A truncation or a time change gives the guest not-permitted. An open of the file for write, an open that can set its times, and an open with a create or truncate disposition give not-permitted too (open_requires_mutable_target), so no descriptor can write the file. A write through a descriptor that is open for read fails as it does for any file that is open for read. The agent can still delete the file, rename it, hard link it, and move a directory above it. The check reads the write permission of the file itself (authorize_writable_target), so it follows the file after a rename, a hard link or a move of a directory above it. The lifecycle installs read-only files without write permission, a restore keeps the permissions, and WASI cannot change them.

On a Unix platform, executor bootstrap clears the owner write bit (0o200) of the process umask before the agent filesystem service starts, and keeps the other bits (lib.rs::start_active_agents). So each file that an agent makes has write permission for its owner, and only an install or a restore makes a file without it. On Windows an agent cannot set the read-only attribute.

A storage error of one call of the agent either fails only that call or invalidates the generation. For a change, decide_effect decides from the cause of the error (classify_failure) and from what the call knows about its effect. A read uses invalidates_generation through classify_query_error, with no retry. A flush uses neither. The sandbox tags a capability escape refusal as SandboxEscape. P2 and P3 return access, or EACCES, for that refusal and keep the generation valid. Other permission errors are terminal. If cleanup did not fail, a recheck can establish a guest-policy refusal when a failed writable open finds a read-only regular file, or a hard link fails with PermissionDenied or AlreadyExists and finds a directory at the source without following the final symlink. The hard-link recheck holds the namespace edit lease through classification. A terminal failure of that recheck invalidates the generation through classify_query_error. A missing source, a non-directory source or a nonterminal recheck failure leaves the original link error in control. These rechecks use the current object; they do not prove which object caused the native denial. A terminal storage failure means that the storage of the agent is broken.

Agent status

The status you see in the API (AgentStatus) is folded from the oplog (worker/status.rs): given the entries, the status is a pure function. Caches and checkpoints only speed up the fold.

Every derived per-agent cache—live status, clean checkpoint, invocation-result index and durable-stream projection—is physically scoped by the current Create.instance_id (AgentFingerprint). A reader first resolves the authoritative Create entry; the flat mode cache is only a hint about which durable or ephemeral oplog namespace to probe first. Consequently a delayed writer from a deleted incarnation can update only its old namespace and cannot splice fields into a newly created incarnation. Cache namespaces expire after a long renewable TTL and can always be reconstructed from the oplog. Metadata compare-and-mutate operations publish multi-field updates atomically and restart reconstruction if another publisher or cache loss changes the baseline.

Errors also carry a machine-readable kind. Invocation means an application invocation failed; Recovery means instance startup or replay failed. Infrastructure recovery errors do not consume the agent's semantic retry policy: metadata stays Retrying without a limit, and invoke, resume, scheduler activation, or shard reassignment triggers the next attempt instead of an executor retaining the instance for a scheduled retry. Invalid components, exports, snapshot baselines, replay divergence, an oplog that failed (OplogFailed), and other permanent failures are terminal. An authoritative manual-update snapshot that cannot be loaded is terminal even when the immediate cause is a payload download failure, because recovery has no compatible replay fallback. Structured metadata reports Failed with last_error_kind: Recovery; the human CLI table calls that state Unavailable. A queued update still starts the worker but does not cosmetically change terminal durable health until recovery succeeds. The error is committed before the resident worker unloads, so get/list and invocation admission agree after restart or reassignment. Once a later startup fully completes prepare_instance, it appends RecoverySucceeded only if such a failure is still unresolved; normal suspend/recovery remains marker-free.

Ephemeral agents in the loop

An ephemeral agent goes through the same loop with two differences, and they are easy to conflate.

Response leases delay normal archival until the response and its stream readers finish, without keeping the Store loaded. Shared gRPC owner lookup acquires this lease before reading session metadata or accepting work. If archival has already fenced the cached owner, lookup waits for archival and cache removal, then resolves an observation-only owner from storage. Failed or aborted archival rejects the request; it never permits reads through the old poisoned producer. Explicit interruption, deletion, and executor shutdown do not wait for response leases.

Normal archival and explicit interruption share Worker::quiesce_for_owner_retirement under the owner-cleanup lock: stop execution, drain stream retirement and lifecycle/forwarding work, commit, then stop status writers. Only explicit interruption records a pending terminal interrupt. Archival moves the oplog before removing the cached worker. The open oplog generation and its forwarding wrapper may be reused by the next worker, so ordinary retirement does not close their task admission or forwarding. Deletion claims ownership under the same lock, drains the resident producer, and runs stream maintenance on a private producer. Failed maintenance is drained before retry; deletion closes the oplog generation permanently. Producer-targeted attachment controls arriving while the producer is recovering or being deleted are answered as unavailable and retried by the caller; a producer that no longer exists answers not-found, which consumer-side finalization treats as already done.

An ephemeral agent never reconstructs in process once its Store has run. An ephemeral Worker accepts exactly one method invocation in its life (its EphemeralInvocationState moves from Available to Accepted(key); a second key is rejected, the same key looks up the accepted invocation). The constructor (AgentInitialization) runs first and is recorded in the ephemeral oplog like any other invocation. In on_invocation_failure, a trap that would restart the constructor or method becomes a terminal failure: the executor stores the failure and notifies the caller instead of creating a fresh Store. Any other restart-type decision (Immediate, Delayed, or ReacquirePermits) that reaches the outer loop becomes a terminal interruption plus archive. This guard does not replace an outcome already published to the caller. An active Suspend becomes a terminal EphemeralCannotSuspend failure after interrupt acknowledgement and monthly-exhaustion conversion. A lowered memory limit or failed monthly monitor therefore cannot leave a method suffix for constructor-only replay. Monthly capacity exhaustion retains its specific monthly error, and a monthly-policy outage keeps its Monthly enforcement unavailable reason. Ordinary ephemeral agents keep idle and pre-method suspension as TryStop; an ephemeral external-tool owner also treats TryStop as terminal. This preserves at-most-once execution of the accepted method. Constructor-only replay in replay remains for restarts before the accepted invocation ran; it does not permit a started method to run again. When the method finishes, successfully or with a terminal failure, the outcome is BreakInnerLoopAndArchiveEphemeralOplog: the Worker leaves the active set and its oplog is archived for observation. Startup retries before a Store exists remain unchanged.

Across lives there is no recovery. If the executor loses the Worker itself (crash, eviction, resharding) and a later request finds the agent's metadata already present, get_or_create builds a reconstructed ephemeral Worker: it can answer status queries and idempotency-key lookups from the archived oplog, but it starts in Accepted(None) and its instance "must never be started again". The invocation that was in flight is lost and the caller sees an error. This is what makes RPC to an ephemeral target at-most-once (§12).

7Invocation queue & results

The queue of pending invocations is durable: it is the set of PendingAgentInvocation hints not yet matched by an AgentInvocationStarted. The in-memory VecDeque is a cache of that.

Acceptance

enqueue_worker_invocation_with_effect (worker/mod.rs) first looks the idempotency key up (lookup_invocation_result). Anything other than LookupResult::New — Pending, Interrupted, or Complete(result) — returns the existing invocation without appending anything. Only for a new key does it append PendingAgentInvocation and commit; the caller learns "accepted" only after that commit. This ordering is what lets a caller that never heard back simply retry with the same key.

Payload reference and start authority

The live loop hydrates an ordinary invocation from the committed Pending entry into an executor-local HydratedInvocation. AgentInvocationStarted reuses that exact payload reference, including cached serialized bytes, without a second serialization or upload. Lowering transforms a separate invocation clone; the retained original payload stays unchanged. When the Pending entry or its payload does not hydrate, the loop records a recovery failure: a storage that did not answer sends the agent to delayed infrastructure recovery with the invocation still pending, and an entry or payload that does not decode stops the agent with OplogFailed, which also fails the pending waiters.

Only the payload is reused. The start hook checks current authority and records the executing context and current wallet pin, not the Pending context or pins. It still commits Started with CommitLevel::Always before guest execution, and a refused shard-epoch fence still stops execution. ManualUpdate takes its separate snapshot path and never passes its Pending payload to the normal start hook.

A fork rehomes both references into the target owner. Archive and revert do not individually delete a referenced payload blob, so retaining both entries does not shorten the payload lifetime.

Native external tools share the invocation queue

AgentInvocation::ExternalTool carries a tool name, command path, typed input and pinned activation, rather than pretending to be a guest method. Admission fences the existing owner's fingerprint and selects the activation using its oplog-folded component revision. The accepted payload pins that deployment's binding: same-key retries attach before resolving current deployment state, and an update queued ahead of the tool does not replace the accepted binding.

REST, CLI and native sessions target either the exact existing real owner or a component-backed ephemeral virtual owner; they do not create a named real owner as a side effect. Typed input and structured success/custom-error results use materialized scalar schemas only. They cannot contain recursive typed streams: optional byte stdin and byte stdout are the only stream attachments.

MCP is a native-session adapter that always creates a fresh ephemeral owner on the export's explicit policy-owning component. Authentication selects the compiled deployment before dispatch and grants only Invoke on that exact owner. An expected deployment revision fences the activation before queueing, including accepted-key and scheduling paths: stale listings cannot select historical bindings or execute against a newer schema. The MCP adapter drains stdout concurrently with stdin and buffers at most 16 MiB per direction.

The shared invocation driver installs the principal and scope, runs invoke_external_tool as a registered NativeToolTask, settles child/tail work and commits the result before notifying waiters. Registering host work keeps pending I/O visible to Wasmtime's concurrent driver. Completed replay uses the activation pinned at acceptance, reconstructs entity filesystem state and reuses recorded external effects; it does not simply return a cached tool result. Tool errors also invalidate read-only method caches because a tool can mutate state before returning an error.

Virtual tool owners instantiate the component, not an agent

A virtual owner is tied to an actual deployed component and uses its component-level tool bindings, configuration, environment, files, plugins and permission card. Creation derives a reserved owner name from the invocation's idempotency key and persists OwnerKind::EphemeralExternalTool. Normal agent creation cannot claim this namespace.

The primary runtime has an ordinary Store and Instance of the deployed component, with normal executable loading, linear-memory and compiled-module charges, filesystem preparation and concurrent-agent admission. Component/core initializers run, but no agent type or constructor parameters are selected and no AgentInitialization is queued. Ephemeral preparation replays initialization only for a resolved typed agent owner, not merely because the component exports agent schemas. The accepted external-tool invocation starts once through the live queue after preparation.

These owners follow ordinary ephemeral one-shot, fail-stop semantics, including loss of the Store during core initialization. Concurrent same-key requests share one accepted invocation; recovery decisions close the owner instead of creating a replacement instance. After executor loss, completed results can be observed without starting a Store, but accepted incomplete execution never restarts. Completion uses ordinary ephemeral unloading and result retention; there is no virtual-owner recovery journal or cleanup scheduler. Guest-only operations such as update, snapshot execution and revert are unsupported.

Execution and completion

The invocation loop appends AgentInvocationStarted, runs the guest export in InvocationMode::Live, and on success on_agent_invocation_success (durable_host/mod.rs) appends AgentInvocationFinished with the result. It then waits for the state actor's commit receipt before notifying waiters: durable agents use CommitLevel::Always, which awaits storage; ephemeral agents use CommitLevel::Deferred, which awaits ordered writer handoff but neither storage nor the queued status fold. Failures go through on_invocation_failure, which decides a RetryDecision; whether a failed invocation gets a terminal entry depends on that decision, so never model a trap as "AgentInvocationFinished { Err }".

During replay the invocation runs in InvocationMode::Replay and the recomputed result is compared with the recorded one (replay_equivalent); a mismatch is an unexpected_oplog_entry determinism error, not something to paper over.

Tail work (durable_host/tail_work.rs) keeps the Store's event loop running until no spawned task is still active, so a task's positional Start/End can never land after AgentInvocationFinished. Tasks parked at guest-driven safe park points may span invocations. Hints may follow Finished: the streaming-session completion (protocol terminals, StreamSession { Finished }) is appended by invocation_loop.rs::agent_invocation_finished after the success hook.

P3 HTTP request cleanup. A Store-owned leak guard is armed before send Start admission, because the guest can drop the send while its replay claim waits at the cursor gate. The guard fences owned cursor operations, then deletes and drains the request. This releases pending guest body/trailer writes without re-issuing the request or closing an implicit durable scope. Replay consumption and live execution disarm the guard when they take request ownership (durable_host/p3/http/{send,replay}.rs).

Read-only methods

An agent method can be declared read-only in its agent-type metadata (AgentMethodSchema::read_only, with a cache policy and a flag saying whether the result depends on the calling principal). The executor treats such a method as a promise it enforces, and as an opportunity to cache:

  • Same worker, same queue. A read-only invocation is not forked onto a copy of the agent. It is a normal queued invocation on the same Worker, serialized with the mutating ones, and it appends the usual AgentInvocationStarted/Finished pair so that its result is recorded and deduplicated by idempotency key like any other.
  • Writes trap. For the duration of the call the host is in read-only strictness (enter_read_only_mode). Every durable function that is a write-type side effect (WriteLocal/WriteRemote/…: outgoing HTTP, RPC, key-value writes, custom durable invocations declared as writes) runs check_read_only_allows first and fails with AgentError::ReadOnlyViolation before anything is appended to the oplog. The violation is not retriable; the invocation fails and the agent stays consistent because the write never began.
  • Per-worker result cache. worker/read_only_cache.rs keeps results keyed by method, arguments, component revision, an epoch, and (if uses_principal) the caller. The epoch is bumped only when a mutating invocation completes successfully, so a cached value keeps serving while a mutation is merely queued, and is invalidated lazily on the first lookup after the mutation lands. On the awaiting path concurrent misses for the same key coalesce into one execution; on the fire-and-forget path each miss runs and an observer fills the cache on completion, rechecking the epoch so a populate raced by a mutation is dropped.

Because the cache is resident state (right column of §4) it disappears with the Worker and is simply rebuilt by the next calls; correctness never depends on it.

8Durable host calls & deterministic replay

Every nondeterministic host function — HTTP, key-value, blob store, RDBMS, sockets, clocks, random, RPC, promises, tools — goes through begin_durable_function / end_durable_function (durable_host/durability.rs) and, for the concurrent WASI p3 "accessor" path, a DurableCallSession (durable_host/concurrent/call.rs). The serialized p2 path (&mut self host calls) uses persist_durable_function_invocation / read_persisted_durable_function_invocation with the same Start/End shape but no delivery markers.

Deterministic initial-file metadata is the narrow filesystem exception. A p2 or p3 stat/stat-at of the exact path of a read-only component or pinned entity-activation initial file still queries the reconstructed sandbox, but clears access and modification timestamps and omits the durable Start/End pair. Type, size and link count still reflect the exact local object; removing the volatile times makes that result reconstructible. Mutable paths and aliases use the ordinary ReadLocal durable path. An unexpected failure after a path is classified as immutable traps the invocation so a retry cannot choose a different oplog shape. Successful fast-path calls remain visible in host-call metrics.

Resolve before preparing live work

Two-step callers use DurableCallSession::begin (returning BegunCall) → BegunCall::resolve → ResolvedCall::Live or ResolvedCall::Replay. Only the Live branch performs live-only authorization and request preparation before start_live; BegunCall::is_live() is private so callers cannot choose prematurely. The Replay branch consumes the recorded result or repairs an admitted incomplete call without re-authorizing. Resolution can finish the guarded replay-tail transition and refresh authority capture. Snapshot calls remain unpersisted: resolving one as Live does not publish Store liveness or lift snapshot restrictions.

Accessor and direct (Store-holding) calls build the same BegunCall (DurableCallSession::new_begun) and resolve it through one BegunCall::resolve_against_history. It claims the recorded Start, or continues live at the replay tail. When the replay target grew while the transition was settling (BeginReplayToLive::ReplayResumed), it claims again, so the call replays the Start the grown target covers. Both paths append the live Start through append_start. A call whose request or identity depends on its own Start index (RPC keys, schedule IDs, runtime card IDs, transfer IDs) builds the request in the start_live_at_index callback; there is no separate begin index.

Four steps, four different facts

Execute

Perform the live effect. Allowed only when the durable context reports live (store_is_live / is_live()) — never because the cursor happens to be at the end of history.

Append

Start is appended eagerly when the call begins; End or Cancelled when it terminates. A trap leaves Start incomplete (abandon_for_trap); a trap never writes Cancelled.

Claim

On replay, match the host call the guest is making now against a recorded Start by identity (StartClaim: invocation id, function name, kind, owner). A Start that does not exist in history is a divergence error.

Observe

The guest reads the result. For accessor calls this is recorded by CompletionDelivered / CompletionDiscarded as the tail operation of the host function. Host completion time and guest observation time are different facts; only the second is a guest input.

Live path (guest-facing accessor)

  1. Append Start { function_name, request, durable_function_type, parent_start_index }.
  2. Run the live action (the HTTP request, the KV read, the RPC dispatch…).
  3. Append End { start_index, response } — or Cancelled { start_index, partial } if the guest dropped the future first.
  4. Hand the result to the guest.
  5. Append CompletionDelivered { start_index } — or CompletionDiscarded if the guest dropped the completion unread.

Host-internal results have no guest boundary

A live oplog snapshot can stop after the outer wait's Start or the internal clock's Start, before the clock End is visible. The sleep test waits for that recorded input before checking its original deadline. It still rejects duplicate calls and malformed completed history. The regression checks read-only prefixes of real history without changing clock recording or replay.

DurableCallSession::invoke_host_internal_access records and validates Start/End, then returns the recorded result directly to the host. It creates no guest-terminal observer, delivery token, delivery/discard marker, or markerless replay-tail gate. A Store-holding reader must never wait for progress whose only producer needs that Store's event loop.

P3 monotonic-clock::wait-for records the outer wait's Start first and owns its internal now read as a child. Replay resolves the outer wait before the child: a cancelled outer wait parks without issuing the child; an incomplete outer wait owns cancellation cleanup before reconstructing the deadline from recorded now + duration. A completed outer wait requires a recorded completed child. Cancelling after the child's End settles the outer wait without an internal delivery marker. Only the outer wait has a real guest-delivery boundary.

P3 timers always return STARTED before successful guest delivery, including zero-duration and expired waits. Live execution and replay both yield before completing the timer. wait-for derives its deadline before that yield, so the duration does not restart. Without this boundary, an inline live timer can record its delivery before a direct P2 call, while replay enters that Store-holding call before delivering the timer. The direct call then blocks the very guest boundary it awaits.

Native stream reads have a guest boundary

Native guest reads append one existing ConsumerItemValue or ConsumerTerminal when Wasmtime's per-read observer confirms consumption at a waitable delivery or callback. After source/cursor readiness, InputObservationDelivery::prepare waits for the consuming Store's fresh blocked wait. It shares the one-event-per-block gate with timers and accessor completions, live and replay alike. Host-side takes do not gate. The observer synchronously reserves the oplog position; owned work then commits and indexes the record under producer admission. That position is the guest boundary. Replay retains the reconstructed value there until the observer releases the cursor. Stream entries remain hints and satisfy no claim, but guest observations reserve their positions. No extra Start, End or delivery marker is recorded.

Retained calls still constrain guest delivery. Reaching the observation's physical position is not enough: the cursor may have passed calls the guest has not reached. Every earlier retained Start in the consuming invocation's root namespace must be claimed, including host-internal descendants that share the import's invocation id, or adopted as replay-inert by a cancelled parent's claim. Reserving an import's ordinal is not enough: live host-internal calls run eagerly before the guest can observe the read. The waiter releases the cursor transaction and advance gate while blocked; retained claims and ready host results remain accessible under a delivery barrier.

The consuming invocation's anchor selects the retained Starts that constrain its read; Starts with another anchor do not block it. This prerequisite applies to native guest items and terminals, including tool attachments and client-tool stdin. Host projections and ordinary CompletionDelivered boundaries keep their existing rules.

A crash after host take but before guest consumption leaves no consumer record; restart re-reads the durable source by offset. Packed byte records cover only the consumed bytes, and later reads record the remainder. Nested reader identities resolve from the parent's assigned journal index before indexing or forwarding. Host projections keep take-time batching and ordinary hint skipping; a consumer discriminant distinguishes them from guest reads because the source binding alone does not identify the consuming operation. Destroying the Store abandons its observers without inventing guest cancellation. Zero-capacity readiness reads consume no item and record nothing.

A covered observation skips its own commit. Each observation's owned write calls DurableStreamStore::commit_through with its reserved index. A commit always flushes the whole oplog buffer, so when the owner's published status already covers that index, an earlier commit made the record durable and the status task folded it; the write returns its receipt without a commit. Only an attached status of a durable agent counts: an ephemeral agent's weaker commit levels fold without storage, and a detached status is not a fold, so those writes always commit. The receipt therefore still means durable and folded. The skip writes nothing, so it cannot hide a fence; the next append or commit still reports it. The read itself also stays off the oplog actor, which runs commits inline: only a re-observation reads the current oplog index, and an upload at or below max_payload_size stays inline without an actor request. Without these rules each read waited behind the previous read's commit and each commit flushed about one entry.

Cancelling a read is not dropping its source. A zero-progress native read cancellation keeps the producer's pending receive and prepared observation for the next read. Dropping the readable end cancels unread source input through the existing cleanup path. The receive keeps its original runtime activity binding; a later transfer remains unclassified, conservatively preventing automatic suspension while it waits. Removing the original activity's classification must not prevent a ready receive from returning unless the owner actually stopped. Store loss discards resident state and reconstructs from recorded consumer observations and source offsets; it does not record a cancellation.

Each consumer record fixes one guest observation boundary. Reconstruction preserves that input and its nested reader identities; local recovery does not delete and replace the boundary.

Cancellation replay limit. Native reads do not reconstruct whether canonical cancellation returned inline or blocked. If cancellation cannot retain a recorded guest delivery, replay fails with UnexpectedOplogEntry and poisons the shared cursor instead of discarding the value or waiting forever. The runtime keeps the canonical cancellation policy and does not force always-blocked returns.

Durable-source reads without a runtime observer

The keyed durable-source test observer, weak registry and capture field are removed. The plain first-read branch calls await_first_durable_source with the actual reader future and a borrowed guard. Native readiness wins a plain-branch ready tie. The suspension match stays in the caller, with classified waits unchanged. The outer receive owns its live-call permit through selected packed reads, consumer-journal commit and nested mapping work.

Receive-body tests prove actual first Pending, unchanged ordinal, typed interruption and entered-versus-never-polled Drop. They distinguish source errors, real End and missing-terminal failure. The full ExternalInlineInput case covers a source that cannot suspend, an ignored suspension wait and mandatory journal completion after selection. These checks add no reader polls or wakes and do not change guest cancellation or replay.

The native frontend case preserves an accepted session through a monthly memory stop and ordinary same-key continuation. Accepted and a monthly timer poll do not prove source Pending or Running status. Before exhaustion, test-only capture observes the existing agent/key-qualified wait_for_invocation_result span, after the remaining ingress startup calls. No production span or hook is added. After physical cleanup, exact monthly and owner causes must match before input or policy restoration. The first packed bytes then produce exact output and one successful result without changing the stopped raw prefix. Positive account-level memory usage can include constructor usage; it is not per-read attribution. The exact read and raw-delivery boundaries remain separate body proofs.

HTTP frame delivery is reader observation

P3 HTTP response bodies use an actual P3HttpClientConsumeBody parent call and durable child calls, not consumer-journal records or an implicit wrapper. The parent and children are WriteRemote; each child names the parent through parent_start_index and requires the protocol owner's explicit repair authorization. A data frame's first positive guest consumption, or ordinary EOF consumption, settles the child's CompletionDelivered through Wasmtime's per-read observer. Installing a producer buffer is too early: another timer can reach the guest before the body read, and replay must preserve that ordering.

The producer fills at most the guest read's capacity and keeps the frame's suffix. Later reads drain that suffix without another durable child. A fresh frame demand initially parks, while a buffered suffix is available inline on both live and replay paths. Custom durable invocations

Application code can wrap a whole block of guest code as one logical durable operation with golem:durability/durability.begin-custom-durable-invocation (durability.rs::begin_custom_durable_invocation). The Rust SDK exposes it as Durability:

use golem_rust::durability::{Durability, DurableFunctionType};

fn charge_card(order: &Order) -> Result<Receipt, PaymentError> {
    // Names identify the operation in the oplog; the type says how it may
    // be retried (WriteRemote: a non-idempotent effect on the outside world).
    Durability::<Receipt, PaymentError>::new(
        "shop",                      // interface
        "charge-card",               // function
        DurableFunctionType::WriteRemote,
        &order.id,                   // recorded as the request
    )
    .run(|| {
        // Live: this body runs once and its Result is recorded in the End entry.
        // Replay: the body is skipped and the recorded Result is returned.
        let token = fetch_token()?;             // nested host calls are fine
        payment_gateway::charge(token, order)   // ... as are plain computations
    })
}

The wrapper prepares the request in new and appends a root Start when run begins; run executes the body in live mode and appends the root End with the serialized result (there are run_infallible and run_async variants). Host calls observed inside the body identify the custom result owner through observational_owner; this is distinct from parent/child nesting in parent_start_index. On replay, if the root has an End, the recorded result is returned and the body does not run; observed entries are consumed as a replay-inert subtree. If the root is incomplete (the process died inside the body), the block goes live under its original root Start and the whole body re-runs, re-recording observed calls as new physical Starts. Completed observed effects can therefore repeat. The block author owns idempotency: make repeated attempts safe. None of the four function types makes this block atomic or prevents its incomplete-call repair.

9Replay cursor, claims & replay-to-live

ReplayCursor (durable_host/replay_state/cursor.rs) is the single chokepoint over recorded history: try_get_oplog_entry reads speculatively, commit_consumed_entry commits, move_replay_idx advances and emits ReplayFinished exactly once.

Claims: matching a live host call to its recorded Start

When a replaying guest makes a host call, the executor has to find which recorded Start entry belongs to it. The simplest rule, "the next positional entry", is correct only when the guest makes one host call at a time. Golem guests can have several host calls in flight at once (async tasks, concurrent futures, tool bodies running on the same oplog), and although the guest's behaviour is deterministic, the host's is not: two calls issued concurrently may have had their Start entries appended in either order during the live run, and the replaying host will not necessarily reach them in the same order. So the cursor uses claims (replay_state/claims.rs).

Cursor exhaustion does not erase call identity. Resolving one call can drain the cursor to its target while retaining another call's Start and terminal. Before returning ReplayEnded or StoreAlreadyLive, a missing claim rejects an unclaimed Start with the same invocation id but a different function, type, parent, or observational owner. The original claim can still take that retained Start. A genuinely absent sibling id can still use ordinary crash-prefix repair.

RPC target identity is checked separately. Connection reconstruction compares the requested remote agent with the recorded constructor request before restoring the client. A matching function and invocation id cannot substitute a different target. An automatic snapshot that changes either identity is rejected; full replay must preserve the original target effects.

claim_start_matching claims the first unclaimed matching Start between the cursor and replay target, bounded by the next delivery marker. Operator-reverted entries are not candidates. Scanning routes concurrent completions; it does not authorize different guest calls. A missing match is divergence only after any active entity body enclosing the head can consume its history. head_owner and nearest_active_body derive that ownership from claimed and retained parent chains without reading the oplog. A claim waits for another active enclosing body to progress or settle, but not for itself or a parent appended after the replay target.

A crash prefix can contain one concurrent call's Start but not its sibling's: invocation ids follow guest call order, while Starts follow host scheduling order. A missing claim therefore lets CursorTx::decide_missing_start retain sibling Starts with invocation ids, their same-id protocol children, and records of retained custom invocations. It waits for retained entity bodies and drains registered awaiters' terminals. At the replay target the call continues through the ordinary replay-to-live transition; a delivery boundary or active body waits; any other entry is divergence. A Start with the claiming call's own invocation id is divergence before the cursor moves. Any retained Start that nobody claims is reported at the end of the invocation.

The identity of a recorded call is its invocation id. Two concurrent calls of one host function reach their claims in an order that depends on host scheduling, so without it one could take the other's record. The id (DurableInvocationId) is the oplog index of the current agent, entity or parent custom invocation and the next ordinal under that index. A guest import reserves its id (GuestImportNumbering) at its first durable call, while it is still the guest's newest import; a later reservation is refused, so a host function that awaits before its first durable call reserves at entry (reserve_invocation_id_before_await). Imports that make no durable call, such as polls, take no ordinal. The Store's call hook decides the anchor on CallingHost: imports inside a custom invocation body are numbered under that invocation's Start. A task that an import spawns must receive the import's id explicitly; a durable call from an unidentified activity fails, and a host task that no guest import issued records no id. A direct call takes the id of the running import. Explicit protocol children, host-internal children, and records the host adds for a call carry the id of the call they belong to; a tool invocation carries the id of the import that dispatched it. Every Start carries the id in Start.invocation_id, and the claim requires it together with the function name and the kind. Parentage is recorded separately in parent_start_index. Calls observed by a custom invocation record no id: replay never claims them.

Custom execution scopes: lifetime is not attribution

A live custom invocation stays registered while suspended, but its resource lifetime does not determine which operation owns a host effect. Attribution follows the context installed on the current guest task. Synchronous begin_custom_durable_invocation installs its scope; asynchronous admission returns a resource without changing the caller's context. Its synchronous enter method installs the captured execution scope. The synchronous exchange_custom_invocation_context captures without changing the context for None, or consumes and installs a snapshot for Some, returning the actual previous context. An empty snapshot clears attribution. Snapshots are resident-only: they write no oplog entries, keep no scopes alive, and cannot cross invocation anchors or restore any closed scope, including an ancestor.

The Rust SDK prepares the request in Durability::new and begins and observes an async operation on its first poll. Around each body and finish poll, response conversion, and destruction, it installs the operation's saved context, saves the outgoing context, and restores the actual caller. Sibling futures therefore remain siblings even when the first one suspends before the second begins. Body resources are destroyed before finish; cancelled descendants and undelivered results are destroyed before their enclosing live resource. Closing a suspended resource absent from the current stack leaves the caller's stack unchanged. Finish checks active children and decodes the response before persistence. An async scope remains registered until the guest drops its owned resource, including after persistence but before result delivery.

Completion order is an ordinary guest input. The async combinators await begin-custom-durable-invocation-async and finish-async rather than blocking sibling guest futures. A live finish borrows the resource and hands its accepted End append and commit to an owned task. The existing CompletionDelivery token retains that receipt across cancellation: a guest drop appends CompletionDiscarded only after successful persistence, while Store teardown drains the task and leaves the End markerless. Completed replay releases the recorded bytes at AtMarker or AtReplayTail, without running the body or replaying its internal entries. This preserves outward completion order, not body polling: a completed sibling cannot return early and change a later root call's ordinal while another sibling remains incomplete. The guest retains the live resource until finish completes or is cancelled.

Structured ownership is required. Nested operations must finish or be dropped before the parent finishes. Detached spawn_local work does not automatically acquire the scope; snapshots do not make escaped children safe. Other SDK bindings expose the mechanism, but their concurrent continuations do not yet install the proper custom scope automatically. This is a Rust execution fix, not a platform-wide concurrency guarantee.

Suspension uses the existing Worker path, not custom-scope lifetime. The custom-promise composition tests observe automatic suspension and physical Store/permit release before public promise completion reconstructs the sibling scopes. Separate monthly-memory cases hold either accepted custom End receipt at the oplog dependency, selected by its original Start rather than function-name observation order. The pending finish retains its owner through the quota stop; teardown leaves its completed End markerless and its sibling incomplete. Both completion orders preserve the original Starts, later root ordinal, exact terminals and full committed prefix. Closed-window settlement remains unchanged. Promise values prove continuation, not external mutation deduplication; upstream HTTP tests retain their separate effect counters. These cases do not establish every meter or ephemeral custom-operation failure.

Entry ownership: retained Starts and attributed positional reads

Claims are not the only readers that drive the cursor. Positional retry-policy reads, a direct call awaiting its own End, or a sibling's terminal drain all move the head forward. Kind and owner are validated before consumption:

  • An unclaimed durable-call Start is neither consumed nor waited on. Its owner may be a concurrent host task that needs the very Store the reader holds — an entity body waiting for admission, an accessor task behind a Store-holding direct call — so parking on it would deadlock replay, and consuming it as a marker would steal the owner's claim. The cursor commits past it and retains it (CursorState::retained_starts, in oplog order, with its terminal once the cursor reaches that too). The owner's later claim checks retained Starts before the head (claim_retained_start); this ordering is required because a CompletionDelivered marker at the head may belong to a retained Start, and a claim that stopped at the marker first would block forever.
  • Retaining is not consuming. A retained Start and the terminal attached to it are committed through commit_retained_entry, which leaves last_replayed_non_hint_index untouched; publish_claimed_position publishes them only when the owner claims the Start. A durable call that derives its retry point from that index therefore sees the same value the live run saw as the oplog tip before its own Start was appended, not a position advanced by entries nobody has consumed. Replay events follow the same rule: a CardDerived or CardInstalled hint trailing a retained Start or its terminal is a side effect of that call, looked up by its owner when it replays the terminal (pending_card_derivation); publishing it while the Start is merely retained would let an intervening authority boundary apply it first. Events recorded during a retained commit are therefore deferred on the RetainedStart (deferred_events) and published (publish_deferred_events) when the Start leaves the retained map — claimed, adopted into a custom subtree, folded into the abandoned tolerance, or released at the live invocation end.
  • Local repair retains history. An incomplete call completes its original Start. Nonresumable resources report typed loss instead of abandoning a suffix.
  • Positional reads are attributed per Store. Entity bodies share the owner's cursor, so get_oplog_entry(scope) accepts only entries whose OplogEntry::entity_attribution() matches the reading Store: the primary agent consumes entries with no entity parent, an entity body only entries recorded under its own invocation Start. A reader that finds another Store's entry at the head parks only while that Store can still consume it (the primary while the cursor replays; an entity body whose Start is claimed, retained or scan-ahead claimed). Anything else is dead history nobody will reconstruct, and check_parked_positional_read reports it as divergence instead of hanging. The invocation-boundary reader never waits on another Store.
  • Nothing retained is silently forgotten. A settled entity body that returned without claiming one of its retained descendants is a structural divergence (ensure_body_claimed_retained_descendants). Retained Starts that reach the invocation boundary fold into the abandoned-record tolerance (only can_drain kinds are retained at all). When a live primary invocation finishes, retained Starts closed by a recorded End/Cancelled are released with a warning; an unclosed one is a divergence error (release_retained_starts_at_live_invocation_end), so AgentInvocationFinished is never appended after an open Start.
  • Admission after the live transition still claims first. While unclaimed retained Starts exist, a call that arrives after the primary published live may still be their replayed owner. Durable-call admission therefore uses durable_call_is_live(), which is is_live() plus "no unclaimed retained Starts" (entity Stores in Live mode are exempt); such calls go through claim_start_for_store and append a fresh Start only once replay reports none remains. The primary runtime treats a cursor that became live between its liveness check and the claim as ReplayEnded, not divergence. Custom (guest manual) durability follows the same per-Store admission: begin_custom_durable_invocation claims through claim_custom_start_for_store and continues to live with the Store's own ReplayToLiveRole (Primary only for the primary agent runtime), so a completed-replay entity body can neither settle the primary fence nor fall through to fresh execution. Positional readers, authorization and snapshot decisions keep using is_live(), which describes the Store's position rather than a call's admission.
  • Quotas are charged by quota class. Per-call quotas are charged before Start admission, so refusal leaves no call record. durable_call_is_fresh(QuotaClass) exempts a replay owner only when its class still has an unclaimed retained Start. Other classes do not suppress charges. HTTP covers P3 HTTP, MCP and external durable streams; RPC covers Golem invokes.

A retained Start remains claimable only by its identity-validated owner. See replay_state/tests.rs for retained-start and delivery-marker coverage, and tests/tool_streaming.rs for body admission and overlapping reconstruction.

10Concurrency & guest completion delivery

Accessor host calls run concurrently inside one Store; direct &mut self calls retain the Store while awaiting (concurrent/mod.rs). Concurrent completions may finish in any host order, but the guest observes them in exactly one order per run, and that order is recorded by the CompletionDelivered markers. On replay, ReplayDeliveryBarrier transfers the cursor gate so each completion is released at its recorded boundary. supersede_prior_completion_delivery hard-errors if an observer is still armed: delivery must be the tail operation of a host function.

Recorded async events reach the guest only at a blocked wait, one event per block, live and replay alike. Native stream items and terminals (including producer cancellation), timers, accessor completions and tool results share RuntimeStore::await_guest_blocked in the consuming Store; an entity body uses its own Store. The outer driver promotes a fresh DriverBlocked observation only after returning Pending. Delivery consumes an unconsumed edge, including one published before the delivery became ready, not the current blocked level: waking a waiter invalidates the level. Non-blocking waitable polls and yields admit no recorded async events. A busy guest must ask through recorded synchronous host calls. Host-side takes and direct non-accessor host returns do not gate. Native guest write completions remain uninstrumented. Every bash script has a time limit and makes a recorded wait-for(0) every 1024 yields, allowing stop requests and time limits to arrive without charging a durable call for every yield.

The delivery gate blocks advancement, not retained claims. A synchronous host call may need a Start that the cursor already retained while another completion owns the gate. with_claim_tx enqueues one gate waiter before inspecting retained state; on a miss, it keeps that queue position and rechecks on progress. RetainedClaims uses history the physical reader has already passed: it adopts the recorded identity, installs its resolver, and publishes its claimed position in last_replayed_non_hint_index under the state mutex. It cannot advance the physical reader or publish live. Advancing the reader requires a gate-owning CursorTx. Resolution prefers a ready gate and finishes the ordinary drain; if the gate remains held, an already-routed result may return to its host continuation. This is readiness, not guest observation: delivery still waits for the exact recorded marker. The marker-consuming owned task constructs the RAII barrier before returning, so dropping an unobserved task result latches failure and releases the gate without acknowledging delivery.

Cancelling an awaiter does not cancel its owned cursor operation. The surviving task keeps the receiver and HistoricalReconstruction guard until its drain or receiver arbitration completes. Settling the guard in the cancelled caller would admit a replacement generation while the old operation still runs. A cursor-operation fence alone does not prove reconstruction has settled; generation replacement also requires the reconstruction fences to settle.

Clock reads need no live wallet refresh. P2 wall-clock reads and monotonic now retain exclusive bindings so they work during synchronous core initialization. Fresh clock/random value reads in the primary Store skip wallet synchronization: an accessor holding card_event_boundary_lock may need the Store to finish, so waiting for it from an exclusive clock would deadlock. The coordinator uses an explicit allowlist, not ReadLocal. Replay, retained recorded Starts, snapshotting and entity Stores keep the ordinary boundary; an automatic-update latch prevents exemption until success is committed. Clock-only execution does not guarantee card-transfer progress, and replay-transition/cleanup lock contention remains outside this exemption.

WebSocket operations release the Store while waiting. Connect/send/close use accessor bindings even when the guest calls synchronously. Their boundary-lock waits and authority synchronization run outside Store windows. Drop only removes local state and does not await boundary work.

Per-handle reconstruction races: the websocket reconnect gate

A replayed golem:websocket/client handle cannot serve replacement live I/O until its connect-time reconstruction policy permits it, and concurrent accessor calls can reach that point at the same time. connect on replay therefore installs a per-handle reconnect gate — WebSocketConnectionEntry::Replay(Arc<Mutex<()>>) — and every send/receive/receive-with-timeout/close on that handle goes through ensure_websocket_connection_live_access in durable_host/websocket/client.rs.

Automatic reconstruction. The following handshake path applies to reconnect-automatically, the default when the third optional WIT connect(url, headers, reconstruction-policy) parameter is absent.

The helper takes the gate — racing the wait against the interrupt signal, so a reconnecting peer never blocks suspension — then re-reads the entry while still holding it (classify_reconnect_entry). Only a call that still sees its own gate in the entry proceeds: it takes one pool permit, runs the handshake, and publishes Live in a single store window re-verified against the current entry. A queued peer re-reads the entry instead of independently reconnecting: a Live entry published by the leader means it uses that entry and takes no permit, and a Terminal entry fails with the recorded error. The handle's calls borrow the resource, so the guest cannot drop the handle while one of its calls queues on the gate, and a fresh table after reconstruction discards the queued call — a call holding the gate can only ever see its own replay incarnation in the entry, so a different incarnation is the InconsistentReplayGate invariant violation, never a reconnect. A failed handshake publishes its terminal through the same re-verified window (mark_websocket_reconnect_failure_terminal): it only terminally closes the handle when the entry still carries the same replay incarnation the failed attempt gated on, so a replayed response that terminally closed the handle, or a concurrent call's live publication, owns the entry's outcome and is never superseded. Without the gate, two accessors can each snapshot Replay, each take a pool permit, and the leader's published Live connection then retains the only permit while the follower waits on the pool forever — the gate bounds reconnection to one in-flight attempt per handle, with no change to pool capacity or timeouts, and an unpublished live connection is dropped, releasing its permit.

12Exactly-once RPC & call repair

Agent-to-agent RPC (durable_host/rpc/mod.rs) is a WriteRemote durable call on the caller whose result is a durable invocation on the target. Exactly-once is a property of the target's logical invocation, not of caller attempts, packets, or replay spans.

RpcTargetAdmission::{Recorded, LiveOnly} separates admission from call resolution. Deferred durable activation records or replays its own decision (Recorded). Non-deferred targets return LiveOnly(PermissionTarget); their asynchronous permission check runs inside ResolvedCall::Live, after resolution, preserving operator authorization and decision telemetry. Denials use persist_*_denial_from_begun to record on the already-begun call instead of beginning another. Recorded calls, including incomplete repairs, retain admission without re-authorizing.

The key is the identity

  1. The caller appends Start { rpc/invoke-and-await, request }; its own index start_index is the call identity. Live builds the request in the start_live_at_index callback, so the request can embed that index; replay reads it from the claimed Start.
  2. IdempotencyKeyPosition::derive(start_index) derives the key from the caller invocation key and this call's own physical Start index. Repair retains that identity.
  3. Caller state the target may depend on is committed before the first dispatch.
  4. If execution is needed, the target persists PendingAgentInvocation { key } — durable acceptance — then eventually AgentInvocationFinished. Any same-key arrival attaches to that one invocation. A settled read-only cache hit or coalesced follower instead returns the shared result and intentionally persists no separate invocation, result, or alias; only the executing miss owner uses normal durable admission.
  5. Caller replay returns a completed call's recorded End. An incomplete WriteRemote re-dispatches with the same key (InvocationFreshnessDisposition::MayExist) and completes the original Start.

RPC preparation does not acquire target execution capacity. For an execution-needing call, the target durably enqueues the acceptance prefix before reporting acceptance, and caller cancellation cannot tear that prefix apart.

One owner decides automatic suspension

OwnerExecution shares one OwnerSuspension across primary, entity and native participants. A current runtime blocked witness is necessary, not sufficient: every admitted participant must be accounted for, with no active outer poll or unknown non-root work. Preparation and borrowed synchronous RPC veto automatic suspension; raw sync RPC does not auto-suspend. Root return or an early stream result is not idleness.

Classify owned waits

Owned async RPC activities register at dispatch, including unconsumed results. They become eligible after rpc_suspend_after (default 30s). Owned timers supply deadlines; promises supply activation evidence. Every remaining activity must also permit yielding.

Keep the boundary narrow

P2 timer-only poll/block uses owned dispatch without retaining the Store borrow; duplicates keep their indices. Other pollables and ready are not generally adapted. Durable reads retain their future and bind to the exact runtime transfer. Local external inline input and its descendants veto suspension; eligible agent-hosted, invocation-output and attached downstream waits use a durable timed recheck. Active journaling, publication and settlement still block suspension.

Persist, then revalidate

RuntimeStore::drive checks after wait_suspend_grace and retries after wait_suspend_check_interval (default 10s). It persists the earliest timed wake (RPC: rpc_resume_after, default 5s), then revalidates the same activity revision and eligibility. Readiness, admission or runtime wake invalidates stale evidence.

Sources: worker/{instance,suspension}.rs (OwnerSuspension::eligible, RuntimeStore::drive), durable_host/{io/poll,suspendable_wait}.rs, durable_host/rpc/mod.rs and durable_host/durable_session/mod.rs. Borrowed wait_for_ready only observes readiness and interruption; it does not elect suspension.

Scheduling, not recoveryRuntime observations supply facts, not authority. Timestamped Suspend, explicit interruption/retirement precedence, wake activation and ordinary discard/replay reconstruction remain unchanged, with the same logical RPC key. There is no new cleanup barrier, lifecycle protocol, RPC deadline, overcommit or immediate restart.

RPC span recovery

An admitted RPC records its invocation span as structured metadata on the ordinary call: Start(span_started = S) → End(span_finished = S), or Cancelled(span_finished = S). The request identity claims the Start; span ids, timestamps and trace context never participate in matching. After that claim, the host restores the recorded opening and applies the terminal transition at the same guest-observation boundary as live execution. The generic replay cursor neither interprets spans nor consumes a span-specific tail.

Record the executing parent. Before any guest code runs, AgentInvocationStarted records the actual invocation stack, including the invocation span added by the loop. This also applies to oplog-processor callbacks: the oplog writer receives that stack explicitly, rather than generating a fresh context from the invocation payload. If a callback's HTTP or RPC span has parent S1, reconstruction must restore S1 before replaying the child opening; recording an unrelated root would make that parent lookup fail.

  • Crash after Start: restore SpanStarted, then repair the incomplete RPC under the original key if its function type permits re-execution.
  • Crash after End: reuse the recorded result without dispatching again and apply its embedded SpanFinished; there is no later positional span record.
  • Cancellation: the existing Cancelled owner carries the close. Resource destruction after closure cannot export it again.

A local synchronous denial remains spanless and records the denial in its Start. Recovery of that incomplete denied call writes the same denied response without dispatching it. Asynchronous validation or activation rejection uses its existing short durable operation with both opening and failed/denied close embedded. Resource and guest-created spans may outlive their opening call. An explicit finish and attribute mutation use short ordinary durable operations whose terminals carry the close or applied updates rather than keeping the original call open. Dropping an RPC client or an unfinished guest span is not a durable call: a garbage-collected guest, or one restored from a snapshot, releases handles at points that differ between runs. The live drop appends a SpanClosed hint for the recorded opening; replay only finishes the span in memory and claims nothing.

13Streaming invocations

A streaming RPC is an ordinary durable RPC whose method signature carries input or output streams (remote_method_uses_streams). Live streams require invoke-and-await; a fire-and-forget streaming call is rejected with RpcError::ProtocolError. The target is pinned by streaming_target_fingerprint: AgentFingerprint is minted once at agent creation and stable across restarts, so a deleted-and-recreated agent with the same AgentId is a different producer.

Identity survives repair and ownership changes. Streaming calls use their exact physical Start index to distinguish concurrent calls. Repair reuses that index and key. The persisted request retains the original streaming origin. The target descriptor excludes retry tracing and canonicalizes environment ordering while retaining execution-relevant configuration; the first accepted invocation keeps its tracing context.

Tool attachments are ordinary schema-value streams. Public tool arguments and structured results remain fully materialized scalar values. Internal envelopes carry { arguments, stdin: option<stream<u8>> } and { outcome, stdout: option<stream<u8>> }. Stdin uses recursive input reconstruction; only the tool boundary adapts its consumer to WIT. An Output mapping committed in Prepared starts generic stdout pumping before stdin EOF or result readiness. After body execution and draining join, materialize_result binds the same existing handle at its result-leaf coordinate. The shared byte drain validates historical bytes and terminals without writing or republishing them, independent of batching, then appends only the live suffix. Ordinary methods still register outputs when returning; requested output declarations remain part of retry identity.

Two durable journals, one optimisation

  • Producer journal. Registration defines LocalStreamId(registration_oplog_index); later owner records use that local ID. Bindings are explicitly Local or Foreign, and a received handle stays foreign even when it names this same owner.
  • Consumer journal. Each value or terminal stores bytes/terminal, consumer_read_ordinal, source_offset, and LocalStreamReaderId { introducing_oplog_index, binding_slot }. Nested registrations and their enclosing item batch are atomic.
  • All stream entries are hints in the oplog-entry sense: they take part in no Start/terminal pairing and never satisfy a claim. "Hint" does not mean "not replayed" — see below.

Current ownership boundary. Persisted stream references are owner-relative. Local means “registered in this oplog” and is qualified into a runtime handle only when materialized; Foreign preserves the complete received handle. DurableStreamStore remains the per-worker journal/index store and owns serialized mutation, commit, and post-commit publication. The binding-local StreamSession owns its readers and mappings. This removes any need for replay-time source discovery: reconstruction projects the owner's complete local journal.

Nested transport IDs follow the journal. Independent session runtimes share the session lock, but not their mapping tables or ID counters. Guest nested-output drains recover committed mappings under that lock before allocating transport IDs, so a guest drain cannot reuse an ID already allocated by an output observer.

Why item order is still deterministic on replay

If stream records are hints, what guarantees that a consumer that performs a side effect per received item performs them in the same order on replay? Two things, working together.

  1. The consumer journals every item before the guest sees it. The record contains the bytes, source offset, ordinal and the reader's introducing entry/binding slot. Replay reads only the owner's oplog: no producer RPC, authorization, or attachment is allowed. Only after the Store is live may the unread suffix be fetched after the last journaled offset.
  2. The side effects are ordinary durable calls. Whatever the guest does with an item, such as an RPC, a key-value write or an HTTP request, is a positional durable call with its own Start/End and, if concurrent, its own CompletionDelivered marker. Because the guest is deterministic (§1) and receives identical inputs in identical order, it issues those calls in the same order, and the cursor and claims of §9 pair each one with its recorded entry.

In other words, the item stream is treated like any other recorded input to the guest, journaled on the consumer side, while the guest's outputs keep the positional machinery. The two do not need to be woven into one Start/End sequence for the interleaving to be reproduced, which is why a change to the stream protocol cannot desynchronise Start/End pairing. Byte streams (HTTP response bodies, TCP sockets) take the other route: DurableDemandStream owns its actual parent call session and records one durable child Start/End per demanded chunk, linked through parent_start_index. Those items are positional entries; no generic implicit wrapper is added.

Exactly-once item delivery is by offset, not by connection

A restarted consumer resolves each reader from its owner's binding table, replays journaled observations in ordinal order, and only in the live suffix contacts the source after the last source_offset. A restarted producer resumes from its own committed sequence. Complete foreign handles retain the producer fingerprint, so a recreated producer is still rejected.

DurableInputEndpoint owns source reads, journal replay, packed-byte buffering and read ordinals. It commits each observation before delivery. If still unread, it can instead be forwarded directly as the original Foreign handle—without an intermediary attachment or read. Once read, forwarding is rejected.

Randomness is allowed where it is recorded before it is observed: caller_attempt_id calls AttemptId::fresh() only when no CallerAttempt record exists, appends and commits it, and every later run reads the persisted value.

RPC result versus stream draining

Acceptance is one durable batch. The target commits Prepared, PendingAgentInvocation, Attached, and foreign-input TopologyPrepared intents together, after validating the descriptor and referenced handles. It then prepares and activates remote attachments. A crash after the commit preserves the original invocation, principal, and input bindings; startup recovers those attachments before guest reconstruction. A retry cannot replace the winning invocation in this window.

A caller fork joins the same remote invocation. If A calls B and F retains A's RPC Start, both callers keep the same remote key and original logical streaming origin. B keeps its first accepted input bindings. Unread foreign inputs can be forwarded directly; replay itself performs no remote attachment or authorization.

Joining does not take over A's connection. Remote RPC marks F's acceptance as joined_origin_observer, without attachment credentials. F receives B's persisted Result and Finished and reads the returned stream handles by offset, outside this invocation transport. A result already published is delivered before any later failure; a failure before the result does not wait for B's guest to finish. Disconnecting F or sending invalid controls cannot detach or finalize A's attachment. A lost observer response retries the same Start, not ResumeAttach.

Dropping F's reader leaves A's source running. B's existing Prepared record identifies the first accepted physical caller. Only that caller's reader cancellation terminates B's RPC output. Other consumers, including downstream agents receiving a forwarded output, finalize only their own attachment. B checks the producer's registered input/output role, including nested streams, rather than the receiving mapping's role. Ordinary input cancellation and fresh RPCs made by F retain their existing behavior. A ConsumerFinalized tombstone also covers a missing attachment: recovery can finish an inherited cancellation intent without cancelling B or allowing a delayed same-epoch attachment to activate.

Staging keeps partial copies invisible. A standalone primary actor writes a hidden oplog without populating visible caches, archives or session indexes. Publication moves the complete committed stage into an absent primary key atomically. That key survives archival, even when empty, until agent deletion; a later fork cannot overwrite an archived worker. SQL stores key existence separately from oplog entries. Before publication, the fork copies the filesystem snapshots of the source into the repository of the stage (ForkCopy, Copied::publish, the StagePublication that publish_staged requires); the copy catches up with the source in rounds, each round copying its packs before its index files. A fork whose baseline, the record of the last successful snapshot-based or snapshot-assisted update in the copied prefix, names a filesystem snapshot that the stage does not hold is refused after the reconciliation, unless a parallel attempt published the target; with filesystem snapshots disabled the copy copies nothing, so such a fork is refused that way too. Losing-stage cleanup removes its hidden index and the filesystem snapshots of the stage, preserving payloads owned by the final target.

A lost fork response does not create another child. The committed stage contains the exact prefix, its ForkCut marker and any synthetic guest result. The marker binds source generation, cut and request kind. The recorded Start anchors a guest fork's derived key and cut; repair resumes the same child. Fresh calls and independent phantom siblings get different children.

A cut replaces cached state, not just the live connection. Session-control and topology-recovery caches reload the authoritative session index when a committed cut appears in their suffix. A repeated Start reports the retained session's current epoch, even after a resume or revert, without reactivating bindings owned by another attempt. Remote RPC follows revoked acceptance with Resume, or Takeover if still attached. It permits one switch back to Resume if the old transport detached in between. Existing authority checks remain in force. Ambiguous transport loss repeats the same attempt; other definitive rejections stop it.

A fork drains its own output. Reverting the original callee preserves its attachment gate. Forking changes the callee fingerprint: the child materializes its output into its own oplog without waiting for the original consumer to attach. It inherits neither attachment authority nor active source topology.

On the synchronous streaming path the caller completes the durable call with the result stripped of streams (strip_streams) and only then returns the stream-bearing value to the guest. The caller's RPC End can therefore already be recorded while items are still flowing. Three crash windows follow:

  1. Setup done, RPC result not yet recorded — replay finds an incomplete Start and re-dispatches with the same key; the target attaches to the same invocation.
  2. RPC result recorded, streams partially consumed — replay returns the recorded result; the consumer session resumes by offset.
  3. Invocation finished, session cleanup pending — agent_invocation_finished runs complete_durable_streaming_session after the success hook, appending protocol terminals and StreamSession { Finished } as hints after AgentInvocationFinished.

Keep polling during cleanup. Output materialization settles positional tail work before invocation completion. Session completion then runs inside the Store event loop, both live and after replay reaches live. An unfinished host stream operation can retain a producer or session lock across a pending poll; awaiting cleanup outside that event loop can deadlock and leave the next invocation queued even though the oplog reports Idle.

A returned result does not suspend execution. The primary stays ExecutionStatus::Running while owned output streams drain and invocation/session completion runs. materialize_streaming_result publishes the early result and classifies producer and settlement traps just like guest-export traps. An interrupt can therefore stop a producer that keeps computing without another stream write; it remains an interruption, not a runtime error or retry. The outer live invocation or replay boundary marks execution Suspended only after that work ends. Snapshot calls retain their own settled suspension boundary.

Subsequent submits reuse admission rather than acquiring another reservation. Producer-index and control-metadata guards must be dropped before submitting or calling a peer.

Live delivery waits until the operation releases its session lock. Normal publication retains admission until delivery; lifecycle admission is released before the caller waits for terminal delivery, so stalled readers cannot consume all cancellation capacity. Caller disconnection does not cancel admitted work. Durable activity covers local writes through status publication, not remote waits between writes. Retirement can cancel a peer wait and reject the next submit; committed records remain the recovery source.

A JSON batch has one item record per value, committed atomically. Typed producer identities distinguish HTTP clients from the attached WebSocket. The WebSocket counts only its own items, continuously across reconnections; under the producer index guard, each write receives a global stream sequence and persists its transport-sequence-to-offset mapping with the data. HTTP appends can therefore interleave without changing WebSocket sequence numbers. Nested stream coordinates remain global, and retries validate the original payload and topology.

When HTTP closes an input, fresh WebSocket frames already in flight are discarded without failing the invocation. The producer head's last offset identifies whether the WebSocket itself wrote the terminal: items after its own End remain protocol errors. This distinction survives reconstruction.

An open-stream producer retry returns the original batch offset and the highest accepted sequence. After closure, only the original closing producer tuple is a successful duplicate; other tuples get a closed-stream conflict. Producer-less empty close retries remain idempotent. The gateway never transparently retries a plain append: callers need producer headers to retry an ambiguous result safely.

HTTP cancellation closes streams, not agent execution

DELETE /invocations/{session} commits CancelRequested and stream cancellation intents through the shared ControlDurableStreamAttachment RPC. It preserves readable history and existing terminal outcomes. Pending outputs read as cancelled immediately; later output materialization commits cancellation with registration and the result, rather than starting new drains.

This is cooperative cancellation. Independent agent code can continue computing, changing state, performing I/O, and returning. It does not interrupt the worker or roll back effects. Replay reconstructs historical drains and guest observations unchanged.

DELETE /invocations/{session}/streams/{slot} instead commits a cancellation intent and a Tombstoned record atomically, under the same session lock used for result materialization. The deleted URL returns 410 for GET, HEAD, POST, and repeated DELETE; PUT returns 409. Session DELETE itself returns 204 on both first and repeated calls. Oplog history remains; recreating a deleted stream requires a new session.

Crash windows for cancellation

  1. Intent committed, producer not yet cancelled: recovery retries the cancellation. Pending intents keep even idle workers discoverable through the assignment recovery index.
  2. Producer cancelled, acknowledgment not recorded: recovery may retry, but exactly-once terminal handling preserves the original terminal.
  3. ConsumerCancelApplied committed: the exact intent is acknowledged and no longer needs recovery. This receipt does not claim that the guest observed a ConsumerTerminal; those are different facts.

Structural tool authorization

Authorization uses the effective tool definition and typed arguments in the calling component's tool namespace. Complete command paths match exactly; flags are unordered, additive requirements; positionals form an ordered prefix. Repeated options and count flags retain distinct occurrences. A positive repeated-option constraint requires a matching occurrence, not that every extra value is safe. A denial catches a matching occurrence anywhere. The CLI tail separator is not a positional value.

Value globs are anchored: * excludes slashes and ** includes them; both can match empty text. Literal invocation strings remain literal, even when they contain stars. Stream-bearing values are Opaque: positive grants need definite coverage, denials block possible matches, and no stream is read for authorization. Admission refusal replays at the original demand

The operation terminal records the refused demand separately from its result: a typed Start claim, a validated recorded-entry index, a positional request, a session input read, or an attachment or durable input disposal. Semantic writer abandonment and rejection enqueue a terminal receipt through the existing cleanup queue. Live selection happens before returning; publication follows commit. The cursor must cross the watermark, claim all retained Starts in the entity subtree, and acknowledge guest delivery before restoring the refusal. Missing evidence never permits refusal.

Disposal admission jobs belong to a separate context-owned task set, using the existing worker task ownership. They do not hold Store tail activity. Successful completion drains cleanup, joins admissions, then drains their handoffs before publishing its terminal. Primary replay consumes its historical Finished before joining at replay exit. A failed entity body aborts pending admissions without cancelling accepted terminal publications or native accepted-write reconstruction; later destructors cannot start repair in that failed context.

Cleanup failure does not skip parent closure or child settlement. Finalization drives failure election and settlement inside the Store, retaining both futures across secondary Store-task errors. Settlement waits for election, but Store tasks can still complete a terminal selection that election needs. An already committed entity terminal is published before retained-resource cleanup; its filesystem lane remains held until cleanup succeeds or owner-failure cleanup drains it. Cleanup cannot wait for its own terminal selection.

Finalization preserves the body's original failure and retry metadata over secondary cleanup errors. Shard loss remains authoritative over later cancellation and a previously selected ordinary owner failure. A typed snapshot divergence remains recognizable after the old generation's deferred admissions settle, allowing ordinary snapshot fallback.

The ambiguous window, precisely

For WriteRemote, the ambiguous window lies after dispatch and before End. Recovery re-sends under the same Start and key. If the peer ignores the key, it can see duplicate writes. Applications can:

  • Make the peer honour idempotency-key or use a naturally idempotent operation such as PUT-by-id.
  • Reconcile uncertain effects with the peer before deciding what to send next.
  • Use sagas to compensate completed steps and loop in guest code. Compensation can fail and does not prove complete rollback.

Four exactly-once contracts that must not be conflated

1. RPC exactly-once

One logical target invocation per key. Owner: caller's Start + target's durable queue.

2. Oplog-processor delivery

One delivery per batch. Owner: batch key + confirmed_up_to/sending_up_to checkpoints.

3. Stream-item exactly-once

Each StreamOffset consumed once per consumer session. Owner: durable_stream/mod.rs / durable_session.rs.

4. Exactly-once finalisation

One terminal per stream; protocol terminals fence guest terminals.

A change that satisfies one of these does not imply the others.

16Oplog processor delivery

Oplog-processor plugins receive an agent's oplog entries as they are committed. Delivery is exactly-once per batch (services/oplog/plugin.rs), using the same two ingredients as RPC: a deterministic key and a durable checkpoint.

  • Key. oplog_processor_idempotency_key hashes source agent, plugin grant id and the batch's first/last index into a UUIDv5. Two forwarders that both see the same batch derive the same key.
  • Checkpoints. Per plugin, confirmed_up_to and sending_up_to live in AgentStatusRecord.oplog_processor_checkpoints, so a reconstructed forwarder knows exactly which entries still need delivery. The OplogProcessorCheckpoint hint (plugin_grant_id, target_agent_id, confirmed_up_to, sending_up_to, last_batch_start) records checkpoint advances in the source oplog.
  • Retry never widens the batch. If sending_up_to > confirmed_up_to when the forwarder wakes up, it re-sends exactly confirmed_up_to+1 ..= sending_up_to — the same range, hence the same key. Only when the previous batch is confirmed does a new batch extend to the committed tail. A range consisting only of checkpoint entries is skipped by advancing both cursors.
  • Target. The processor is itself a durable agent, so the "exactly-once" is ultimately the ordinary RPC contract of §12 applied to a deterministically keyed batch.

17Snapshots & updates

Replaying a long oplog from INITIAL every time an agent is reconstructed would be slow, and a component update needs a way to carry state across code that no longer replays identically. Both use snapshots. A snapshot record holds a serialisation of the agent's state that the guest gives. On an executor with filesystem snapshots, the record can also name a filesystem snapshot: a copy of the agent's files in the snapshot store (below).

A third execution mode

Snapshot save/load runs guest code in snapshotting mode: it neither appends nor consumes durable-call oplog entries (DurableCallSession created with persisted: false; durability_is_suppressed is exactly snapshotting_mode). A snapshot load is therefore not a fast-forwarded replay — the loaded state replaces skipped history from a revision-scoped baseline.

Which history does the new instance replay?

Decided at Worker construction (worker/mod.rs, create_instance, with the pure worker/snapshot_selection.rs::decide_start). It reads the status and the update at the head of the queue, and gives one StartDecision:

  1. PersistStrategy: the head is a public Automatic admission without a strategy. The start appends the strategy entry and decides again (below).
  2. FailHead: the head is a snapshot-assisted update whose source does not hold any more (stale_assisted_head). The start appends its FailedUpdate and decides again.
  3. Start(StartSelection): the baseline is one SelectedBaseline. A snapshot-assisted head gives its frozen record (AssistedPending), and a SnapshotBased head gives its record (ManualPending). With no update pending, an automatic snapshot record overrides the authoritative baseline and skips INITIAL+1 ..= snapshot_idx (Periodic). The status keeps two candidates: the last record, and the newest usable record before it. A record is usable when it names no filesystem snapshot, or when a SnapshotConfirmed entry confirms its name. The start takes the first usable candidate that has the current revision, is not in the fingerprint-scoped set of rejected indexes, is not unavailable for this startup attempt, is not the selected record of a live FailedUpdate whose snapshot was lost, and does not name a filesystem snapshot when filesystem snapshots are disabled on the executor. An ephemeral agent never has an automatic snapshot record: resolve_agent_properties gives it SnapshotPolicy::Disabled, because a start from a snapshot record skips the initialization that the replay of an ephemeral agent needs, and that replay then fails. Without a record, the baseline is the authoritative snapshot of the last successful update (AssistedPromoted or ManualPromoted), else InitialFiles. A pending plain Automatic head uses that baseline, never a periodic record.
  4. The component revision to instantiate and the replay revision come from the same decision. A cursor cannot change them; only the outer loop can.

Two public update modes

Target validation and executor failures. Before loading a pending target, the worker validates its cached metadata with component_support_error. Admission uses the same support policy. An unsupported target writes FailedUpdate with UPDATE_TARGET_REFUSED and the policy's refusal reason. The current policy rejects shared linear memory with The target revision uses WebAssembly threads, which Golem does not support. The failed update preserves its attempt index and assisted details, without a snapshot fault or rejection. Admission charges the source for an unsupported target, so its advertised memory cannot park the agent before the refusal. After committing the refusal, startup releases the old memory admission and re-admits the next queued target, or reconstructs the source if no update remains. This restart does not consume the out-of-memory retry budget. A cancelled compilation task becomes Interrupted(Restart); a panicked task becomes Runtime. The target-load outcome passes these executor failures without failing the update. The worker converts the passed runtime error to RecoveryRequired, and startup retries with infrastructure backoff without consuming the invocation retry budget. Interruption keeps its exact kind; retirement and pending terminal interrupts still stop reconstruction. Ordinary parse errors and generic metadata or instantiation errors retain their existing outcomes.

UpdateDescription::Automatic

PendingUpdate { target revision r2 } (hint) is appended, the worker is unloaded and reconstructed. Because an update is pending, automatic snapshots are ignored; the new instance is created for r2. prepare_instance runs try_load_snapshot on the baseline, then replay replays the remaining old history against the r2 component. Success appends SuccessfulUpdate during that replay.

If replay fails while the update is pending, on_worker_update_failed appends FailedUpdate and returns RetryDecision::Immediate: the outer loop rebuilds on the old revision, automatic snapshot eligible again. A conflict of the initial-file rule from r1 to r2 at the end of the replay fails the update the same way. An initial file of r2 that the blob storage refuses fails the update too (below). Another filesystem error there retries the start.

The admission entry P records target r2 and is the update attempt's durable identity. When the agent is loaded at admission and its newest periodic record is not confirmed, the agent waits for the upload of that record, at most confirmation_wait, or asks the store once when no upload runs, before the restart, so the update can select that record (Worker::confirm_filesystem_snapshot_before_an_update). A Delayed retry does not wait. A stop, a revert, a retirement of the owner or a terminal interrupt ends that wait, and the wait does not count against the unload deadline of the restart. When that request reaches the head of the update queue, decide_start gives PersistStrategy, and create_instance appends a correlated pending entry with update_attempt_index: Some(P) that freezes the strategy. With no record that passes the selection below, the strategy is plain Automatic, a full replay. The status fold (worker/status/update_queue.rs) refines admission P with that entry instead of adding a second request. A failure of the load or the replay writes FailedUpdate with UPDATE_REPLAY_FAILED, also a divergence at a host call, and the agent runs on its source revision. At the update point, an initial file of the target that the blob storage refuses (an S3 4xx other than 408, 416 and 429 and without a code that asks for one more attempt, such as a 400 RequestTimeout, or PermissionDenied of the filesystem backend) writes FailedUpdate with UPDATE_BLOB_STORAGE_REFUSED; the install changed no file, so the agent runs on its source revision. A transient blob error writes nothing and retries as a recovery.

The replay for the pending update is speculative (SnapshotReplayPurpose::AutomaticUpdate): a trap while it replays recorded entries writes no invocation Error. An out-of-memory trap, in the load of the baseline or in the replay, keeps its retry (ReacquirePermits, DurableWorkerCtx::speculative_retry): the start runs again with new permits, writes no FailedUpdate, and the update stays pending. During the startup replay the status stays the one before the restart. An idle agent stays Idle, so interrupt_decision ignores an API interrupt: no Interrupted entry and no FailedUpdate are written, and the update completes without a resume. Only a Running, Suspended or Retrying status lets the interrupt through; the replay then writes no Interrupted entry, and the invocation loop records the request after the start (record_retry_interrupt_failure). A lost shard writes nothing, and the new owner runs the attempt again. The replay of a snapshot-assisted attempt and the replay after a periodic record do the same.

Internal SnapshotAssistedAutomatic strategy

The strategy selects a record S by the periodic rules, with the head-aware queue filter (QueueFilter::UnselectedAutomatic): the last usable record of the source revision R, else the previous one, only when the target is newer than R, only before every SnapshotBased update in the queue, never a rejected record, and never a named record on an executor without filesystem snapshots. S can be newer than P. When a live FailedUpdate of the same target from the same source has SnapshotFault::Incompatible, no record passes (incompatible_before), and the strategy is a full replay. The strategy entry freezes S, its filesystem snapshot name, R, and the oplog entry E that established that revision. Status reconstruction folds it as an in-place refinement of admission P, not a second request.

The attempt restores the filesystem snapshot of S (or the initial files of R for a record without a name) and loads the application snapshot of S into the target, from one StartPlan. It skips only through S and replays the surviving stopped-source suffix with the target code and R's metadata; the tail is not fixed at P. At ReplayFinished, update_state_to_new_component_revision applies the initial-file rule from R to the target at the update point, as a full replay does. Then success U is committed, after historical results and entity reconstruction validate but before target live effects continue. A mutable invocation can span Started < P < U < Finished.

U promotes S to the authoritative baseline with its name, and the fold keeps component_revision_for_replay = R. A later start from S restores the same filesystem snapshot, replays the suffix with R's metadata and applies the rule at the replayed U, the same order as the attempt. Retention keeps the name of S while U is live (names_in_use).

A failure goes through start_outcome::decide and records one FailedUpdate with the assisted details of the head, then rebuilds the healthy source: a lost filesystem snapshot or payload of S gives UPDATE_SNAPSHOT_UNAVAILABLE (SnapshotFault::Unavailable, S rejected); a load failure or a typed divergence gives UPDATE_SNAPSHOT_INCOMPATIBLE (SnapshotFault::Incompatible, S kept); a filesystem snapshot of S that does not restore on this executor gives UPDATE_SNAPSHOT_RESTORE_FAILED, also when the local disk is full, and one on an executor without filesystem snapshots gives UPDATE_RESTORE_NEEDS_FILESYSTEM_SNAPSHOTS; a stale R/E, a mode change, a trap or exit, an untyped replay error or an update-point error give a failed update without a fault (a target revision that does not exist or that the component service refuses has its own code, an initial file of the target that the blob storage refuses gives UPDATE_BLOB_STORAGE_REFUSED, and an unreachable component service or a transient blob error retries). A transient cause writes nothing and retries with the same S. After selection an attempt never tries another snapshot or switches to full target replay.

Public Manual: internal SnapshotBased

The save hook ran on the old revision and its payload was recorded before unload. prepare_instance requires the store to be live already and finalize_pending_snapshot_update loads the payload into r2. No old history is replayed against the new code.

A failure of the start writes FailedUpdate, and the agent runs on its source revision: a lost filesystem snapshot of the update gives UPDATE_SNAPSHOT_UNAVAILABLE, whose text says to request the manual update again, which takes a new snapshot; a snapshot that does not restore gives UPDATE_SNAPSHOT_RESTORE_FAILED; a named snapshot on an executor without filesystem snapshots gives UPDATE_RESTORE_NEEDS_FILESYSTEM_SNAPSHOTS. The details have the form CODE: text: cause.

SuccessfulUpdate follows only a load that completed. The load reports its own result (ManualLoadResult): an error of the load, and a guest that exits during it, write FailedUpdate without a code; the cause of an exit is the agent exited during the snapshot load. An interrupted load ends the start with its interrupt and writes nothing, so the update stays pending and the next start loads the payload again; after a lost shard the new owner does.

Use this when the new revision cannot replay the old oplog deterministically (changed host-call sequence, changed data model).

Automatic snapshot assistance bounds the historical replay window to the suffix after frozen S; it does not guarantee a wall-clock update bound. Snapshot age, suffix size, compilation, payload I/O and resource admission still matter. Public --await waits for this attempt's terminal SuccessfulUpdate or FailedUpdate, including a repeated request for the same target.

Rejecting a bad automatic baseline

With no update pending, an automatic snapshot load failure — or a divergence while replaying its recorded suffix — rejects that exact record and returns RetryDecision::Immediate. The outer loop recreates the entire Store, component metadata, revision and plugin context and selects again: the other usable record, the authoritative baseline, or a full replay. This is not a cursor rewind, and it never replays history before a completed snapshot-based migration.

After preparation succeeds, and before readiness is published, prepare_instance calls Worker::settle_exclusions_after_prepare, which merges the rejected indexes into the set stored under the worker's AgentFingerprint. The set holds exact indexes, so a newer record stays selectable, and a recreated worker with the same agent id has a separate set. A snapshot payload-download failure, or a filesystem snapshot that does not restore, is treated more cautiously: the unavailable set skips the record only for the current startup attempt and is cleared after successful preparation, so a transient storage outage does not permanently reject the snapshot.

The authoritative baseline of a successful manual or snapshot-assisted update cannot be skipped. If it cannot be restored or loaded, resume ends with a terminal error that retains the underlying cause; a transient cause, and a payload download failure of a promoted snapshot-assisted baseline, retry.

Platform defaults

Filesystem snapshots run only when the configuration sets filesystem_snapshots to Enabled. The binding, decisions::binding, refuses Enabled on storage whose volume makes no copy-on-write copies. Production uses XFS with reflink, with or without project quotas. Local development and tests on macOS use Apfs. Temporary and Directory cannot enable filesystem snapshots. Standalone executors and local servers on other platforms use Disabled by default. The macOS local golem server defaults to Apfs and Enabled snapshots.

  • A disabled executor makes no capture, upload, confirmation, restore from the store, retention or store delete. An application snapshot is used only when the files of the agent can come back with it. In place of the capture, after the guest snapshot hook, the snapshot checks whether the tree holds only the initial files of the agent (baseline.rs::check_initial_files). The check stops the file calls as a capture does, applies the same rule as a capture, and makes no host directory, copy or store call. A tree holds only initial files when each declaration is a read-only initial file that is untouched and has a single name, no entity-provisioned file exists, no call set a chosen modification time, and the tree holds nothing else; a read-write initial file therefore counts as a change. A rename or hard link of any file, or a given time that the agent sets, counts as a change; a time that Golem puts back from a recorded stat does not.
  • A disabled executor writes a snapshot record without a name only while the tree holds only initial files. A start from such a record seeds the initial files, which is the tree at the record. When the files changed, or the check cannot decide, for example because a file call stays open, no periodic record is written: a restart replays from an older record without a name or from the start, and the replay rebuilds the files. A periodic snapshot that writes no record waits a period before the next one, as one that writes a record does (invocation_loop.rs::snapshot_baseline_timestamp). A save hook must not write files of the agent: a boundary that writes no record is not replayed, so such a write would not come back.
  • A snapshot-based manual update on a disabled executor needs a tree of initial files. When the files changed, the update fails as a failed update with UPDATE_NEEDS_FILESYSTEM_SNAPSHOTS; when the check fails, it fails with the details failed to check the agent filesystem for the update: <cause>, which have no code. In both cases the agent stays on its revision. With a tree of initial files it writes PendingUpdate without a name, and the start of the update seeds the initial files of the source revision, which are all read-only, and applies the initial-file rule to the target revision. A source revision without initial files gives an empty tree, and the start seeds the initial files of the target revision. A start from the initial files of the source revision counts as an install, not as a restore of saved times (RestoreTree::gives_saved_times), so the snapshots after the update still find a tree of initial files.
  • A switch from off to on: a record without a name that the disabled executor wrote holds only initial files, so a start from it seeds those files, and the replay after it writes the later files again. Filesystem snapshots begin with the first capture after the switch.
  • A switch from on to off: the selection takes a candidate automatic record only when the record names no filesystem snapshot, and otherwise the authoritative baseline or a full replay. A pending manual or snapshot-assisted update whose record has a name fails the update with UPDATE_RESTORE_NEEDS_FILESYSTEM_SNAPSHOTS, and the agent stays on its revision. An authoritative baseline with a name fails the start with a visible cause.

The parts of §6 about the start, the initial-file rule, read-only files and permission errors apply to every executor.

Local development on macOS

macOS seed synchronization

On macOS, the shared seed path for Apfs, Directory and Temporary transfers each regular file, applies its permissions and modification time, then submits it with ordinary native fsync. The directory scopes attempt the required namespace submissions before the final batch flush. The adapter observes the platform once and selects typed transfer and synchronization actions. Native effects execute those actions; an unavailable syscall returns an error rather than choosing a different action.

Each fresh macOS filesystem has one precreated, unlinked regular seed_flusher owned by NativeRoot. Seed admission pins the root and seed_flusher atomically. Every admitted batch attempts one final F_FULLFSYNC through seed_flusher. This includes empty, symlink-only and directory-only batches, and batches that fail early. seed_flusher creates no per-batch directory entry, so batch completion does not change the root's modification time or require a writable root. A pathname replacement cannot redirect the admitted descriptors. A setup or admission failure before pinning them has no admitted seed_flusher to flush.

The namespace and batch finalizers still run when an admitted batch fails. Batch completion attempts ordinary fsync on seed_flusher, ordinary fsync on the root, then F_FULLFSYNC on seed_flusher. The finalizers attempt every required submission and keep the first error. In unwind-capable builds, later required finalizers also run after a panic, and the original panic or an earlier error retains priority. Production panic-abort profiles do not run unwind cleanup.

This policy applies only to macOS seed synchronization. Native file cloning and byte copying are unchanged. Linux keeps transfer, file synchronization, then attributes, and its existing XFS volume synchronization. Explicit guest flush operations keep their existing behavior. XFS remains the supported production copy-on-write path. Initial-file installation still calls seed once per file. A seed batch does not combine separate install operations. The policy does not guarantee seed, snapshot capture, blob upload or worker recovery time.

Apfs is for local development and tests only. Production still needs Linux 5.8 or later with XFS and reflink. Apfs uses the developer's existing volume, with no special volume, disk image or privilege. At startup, the executor makes the configured root if it does not exist, then probes a file clone under it with fclonefileat. It reads the clone back and removes the probe. A failed clone prevents startup. The mode has no filesystem type check, no exclusive lock of the root and no volume identity check. Use a separate root for each executor. It logs APFS storage is for local development and tests only.

Both case-sensitive and case-insensitive APFS volumes use Conservative filename coordination, because both alias Unicode normalization forms. An entry edit waits for conflicting operations in the same parent directory; two observations can run together. macOS keeps its native filename spelling, case sensitivity and lookup behavior. Users do not need to normalize names. Startup does not read the root's case sensitivity to select coordination. The mode reads free space with fstatvfs, so startup capacity checks, capture admission and write pressure recovery apply. Volumes in one APFS container share free bytes, so byte targets are approximate. The object counts are synthetic and very large, so the object targets always pass. There are no project quotas, per-agent disk limits or filesystem metering.

On macOS, the local golem server run command defaults to Apfs at <data_dir>/agents and enables Enabled snapshots. No TOML file or environment settings are needed. The --agent-filesystem-root option changes the default root. These settings override the defaults. An existing file with invalid TOML prevents startup. To choose Directory or Temporary, also set filesystem_snapshots.type = "Disabled". The agent still needs a snapshotting policy. The snapshot store uses the executor's blob storage, which the local server keeps at <data_dir>/blobs. There is no separate snapshot destination.

Without a configured repository_key, the local server generates a 64-byte repository key and stores its 128 hex characters in <data_dir>/filesystem-snapshots.repository-key. On Unix, it creates the file with permissions 0600. Later starts use the retained repository key. A configured key takes precedence over the file. Without a configured key, a corrupt file prevents startup and is not replaced. Keep the retained repository key with the local data, because another key cannot read the existing snapshots.

With filesystem_snapshots set to Enabled, a snapshot record also carries the files of the agent. invocation_loop.rs::take_guest_snapshot calls filesystem_snapshots.rs::periodic_snapshot, which asks AgentFilesystemSnapshots for admission, runs the guest snapshot hook (snapshot_guest), captures the tree, appends the Snapshot entry with the name of the filesystem snapshot, commits, and gives the capture to an upload job. The record has no name when the tree holds only the initial files of the agent, and the worker slot (SnapshotSlot) then keeps the mark of that tree with no name. When the tree did not change since the last confirmed snapshot that a start would select now, the record reuses that name and a SnapshotConfirmed entry follows it at once; the record before it, which has its own application snapshot, becomes the fallback. When the tree did not change since a record without a name that a start would select now, the record has no name again, with no store call, no confirmation and no check of the declarations and directories. A manual update uploads its filesystem snapshot before it writes PendingUpdate (filesystem_snapshots.rs::update_snapshot). When a periodic upload of the agent runs, the update first stops the deletes that the running job makes after its save (retention_stop, a child of the job's stop); the job still ends its save and its confirmation. The update then waits until the job is gone or an admission can replace it, and asks again; another refusal fails the update. The admission and the slot takes of its upload end confirmation_wait after admit_update started, with SaveRunning or NoSlot; a run of the upload that started before then runs to its end. A terminal interrupt ends that wait, or the upload of the update, and fails the update; after a lost shard it writes nothing, and the update stays pending for the new owner. SavedUpdate::delete_older_snapshots runs after PendingUpdate commits, and keeps every name that the status uses (snapshot_selection::names_in_use: the two start candidates, the pending and the successful updates, manual and snapshot-assisted, and the authoritative snapshot-assisted baseline); retained_update_snapshots limits only the other update snapshots.

A record with a name is not usable until a SnapshotConfirmed entry confirms it, because the upload can fail or the executor can stop before it ends. Two writers can append the confirmation, and both only as the owner of the agent:

  1. The upload job, after the upload, asks the worker (Worker::confirm_as, with the pure owner_gate). One status job checks that the instance that took the snapshot still runs and that the record is still the status candidate, then appends SnapshotConfirmed. Otherwise the answer is Deferred and the snapshot stays in the store; Superseded (an update or a revert replaced the record) deletes it (delete_superseded), and Confirmed deletes the older snapshots of its kind (delete_older_snapshots). A stop never waits for an upload. A shutdown, delete_all_snapshots, a manual update and a revert (RevertHold) end the deletes of a job.
  2. The next start (Worker::confirm_filesystem_snapshot_before_start, before the start takes permits, with AgentFilesystemSnapshots::prepare_start for the wait and the store check). When the start would select the last record if it were confirmed, it waits for an upload of that record on this executor for at most confirmation_wait, then asks the store once whether the snapshot is whole, for at most the rest of confirmation_wait, or for at most store_check_limit when it did not wait. A terminal interrupt ends the wait.

A start that finds no confirmed snapshot falls back to the previous usable record and replays from there. StartFilesystem::load_and_plan then plans the baseline of the selected record with plan_start and makes its restore, and StartFilesystem::materialize applies it to the new filesystem: the filesystem snapshot of a named record, or the initial files for a record without a name. §6 describes what the restore rebuilds.

What a capture holds

A periodic capture (lifecycle/baseline.rs::capture) stops new filesystem calls and waits up to capture_wait (5 s by default) for the calls that are open. A call that is still open then makes the capture give up with Busy: the loop writes no record, and the agent continues. A manual update captures with capture_whole, which never gives Unchanged; there a failed capture, Busy included, fails the update. A guest can hold a call across an invocation boundary with a wasi:io stream write that it never polls, so the wait needs a limit.

While the calls are stopped, the capture finds one of three outcomes: Unchanged when the change counters of the generation equal the mark that the worker slot gives (the last confirmed snapshot, or the last tree of initial files, while a start would select its record now), InitialFiles when the tree is what a start from the initial files gives, and otherwise Captured. InitialFiles needs all of these: each declaration is a read-only initial file, nothing is provisioned, each declared file is the initial file with a single name and every stored path component has the declaration's exact spelling, no call set a chosen modification time, and the tree holds nothing else except the directories on the way to the files (holds_only_initial_files). A rename or hard link of any file, or a given time that the agent sets, counts as a change; a time that Golem puts back from a recorded stat does not. Only Captured copies. The copy_contents operation puts the copy into a new directory in .scratch. It makes one copy-on-write copy for each file on XFS or Apfs. With XFS project quotas, the capture adds nothing to the quota of the agent. The directory holds tree/ and the capture record, record.json.

The tree leaves out the bytes of each read-only initial or entity-provisioned file that has a single name and is still the initial file at its declared path. Every stored path component must have the declaration's exact spelling. On APFS, a normalization or case alias can still reach a file after the agent renamed the file or its parent. That file stays in the captured tree under its stored spelling, and the capture does not list its declared path as left out. Otherwise, restore would seed the alias from the tree and then try to install the declaration over it. The spelling check retains one sorted set of names per relevant parent for the stopped-call operation, not a directory descriptor. Proven byte-exact parent lookup needs no name listing for that check. The left-out file's declaration gives its content, and a restore seeds it again from the initial-file cache, so the store keeps no copy of it for each agent. Every other file is in the tree with its bytes, also a read-only file that the agent renamed, moved or linked. A file with several names is in the tree once, because the store keeps no hard links. The capture record holds the left-out paths, the hard-link groups, and the initial-file and provisioned declarations. §6 describes what a restore rebuilds, and what a snapshot does not keep.

Filesystem snapshots across delete, revert and fork

The filesystem snapshots belong to one agent incarnation: the store keys them by AgentSnapshots::agent(agent, fingerprint), and a fork target uses its stage id as its fingerprint. Ephemeral agents take none. A delete requests delete_all_snapshots for its incarnation right after the oplog delete; a recovery scan does the same for each stale RunningWorkers member before it removes it. A revert deletes the names of its dropped region that no live record outside it uses, and only after its Revert entry committed: a refused commit gives OplogFenced and deletes nothing. A fork copies the snapshots of the source into its stage before it publishes, and a stage that never publishes loses them.

Periodic retention runs only after a periodic job gets Confirmed, never after Superseded or Deferred (decisions::follow_up). The job keeps its own snapshot and the newest older periodic snapshots, up to retained_periodic_snapshots (128 by default) in all, and deletes the older ones (retention::victims). A periodic snapshot whose time is within 2 minutes of the time of the job's own snapshot, or later, is neither counted nor deleted, because another executor with another clock can have given that time. Retention never deletes the names that the status uses, whatever their age, and these names do not count either (snapshot_selection::names_in_use): the last automatic record and the newest usable record before it, and the names of the pending and successful updates and of the authoritative snapshot-assisted baseline. So the filesystem snapshot of every successful snapshot-assisted update stays while its SuccessfulUpdate is live, also after later periodic confirmations. A revert is always exact: when the snapshot of a record is gone, the start falls back to an older record or a full replay, which gives the same tree. This count limits only how far back a revert can start from a snapshot: about 20 minutes at one upload every 10 seconds.

StoreCalls is the only owner of the store. The store takes a slot of its caller's limiter for each run of a call, and holds none while it waits. A write whose try was sent and failed in a way that can still land is recorded, and the call answers only after that write has landed or can no longer land, one storage call deadline after its try. A save run ends by cancelling its run token and giving its slot back, then waits until rustic's threads release its blob files, and then waits for its late writes. An admission replaces a periodic job whose store call holds the save mark and waits for, or checks, writes that can still land; the replaced call runs on as a tail that keeps the busy count of the agent, starts no run and no write, and never confirms. A clean successful save is never replaced, and neither is a job whose call has returned. Two runs of saves of one agent never run at the same time: a save call starts a run only while it holds the save mark, and a replaced tail runs beside the next save of the agent.

The clean-up queue keeps one clean-up state for each incarnation (Names, or All, which replaces pending names), and a fixed pool of max_concurrent_uploads workers takes an agent only when its busy count is 0. A request past a bound (max_pending_deletes_per_agent names for one agent, and fixed bounds over all agents) is counted as a leaked clean-up. The bound of one agent applies only to the names of a revert: retention deletes directly, and a delete of all snapshots carries no names. A revert's names come newest first, so on a large revert the bound keeps the newest names and refuses the oldest, which count retention or the delete of the agent removes later. At the bound of the agents with pending work, a delete of all snapshots evicts the oldest waiting revert names of another agent, counted as a leaked clean-up, and is itself refused only when no names are left to evict. Retention and the delete of a superseded snapshot call the store directly, after their own job's save answered.

When may a snapshot be taken?

Automatic snapshots are taken only at a safe boundary. SnapshotBoundaryConditions::blocker reports the first blocking condition in precedence order; a request at an unsafe boundary is rejected with that reason and never partially taken. The in-flight live-call counter includes permits held by open transaction protocols; no generic active-scope stack is needed.

Revert and fork

A guest count-based revert resolves its target after durable admission classifies the call as new work, before checking permissions and writing Start. Authorization uses the resolved oplog index. The request records that index and the observed target tip; incomplete repair reuses them instead of resolving the count against newer target history. Resolution failures record their error in Start.denial and End. Recovery preserves that error even without an End; it neither resolves the target again nor dispatches the rejected revert.

Two more history operations live in the same family. golem:api/host.revert-agent appends a Revert hint and reconstructs the agent so that replay stops at an earlier point (by oplog index or by number of invocations) — the later entries remain in storage but are excluded from the fold. golem:api/host.fork copies the oplog to a new agent id up to a chosen index; the new agent replays the copied history and then continues independently.

Management self-revert is unsupported. The guest revert-agent call rejects the current owning agent, including calls from its tools or middleware. The rejection is recorded without stopping the owner. Use the external API or CLI to revert across invocations. There is no guest execution-cursor API. Calls targeting another agent are unchanged.

Internal entity ownership follows the child; historical guest observations do not. Entity-invocation requests do not persist calling_principal: live execution and replay derive it from the current owner, including every middleware and leaf invocation. Ordinary and stream-export forks therefore need no entity-request rewrite. Replay still matches entity, operation, call mode, input and descendant plan position, and validates entity-scope ownership. The separate execution principal, authority snapshot, tool inputs, recorded environment and external effects remain unchanged. Inline request bytes are preserved; authoritative external payload bytes are copied under the target without decoding or re-encoding. A second-generation fork derives its own owner without changing historical guest inputs or logical RPC origins.

A revert can cross a successful manual snapshot-based update when the cut precedes that update's PendingUpdate. The new Revert then hides both records and removes that migration baseline. Assisted updates intentionally follow automatic semantics: retaining P while deleting either a successful or failed outcome makes the same frozen request pending and retryable. Retaining U retains promoted S; deleting U removes only its promotion contribution.

Validation tracks why history is skipped. Crossing a migration can expose history of the old revision, but earlier operator-reverted regions remain unavailable. Preflight checks the restored component, retained snapshot payload, replay metadata and initial files. Fork staging copies reachable payloads and filesystem snapshots; a fork retaining assisted U reconstructs from promoted S and its files. The fork appends FailedUpdate for each open pending update in queue order, then for each unpaired manual-update invocation, so none runs in the child. Preflight does not execute full replay; later replay failure cannot undo a committed Revert.

The retained prefix determines a call's outcome. A cut after Start but before its terminal uses incomplete-call recovery with the same key. A retained accessor End without its observation marker uses AtReplayTail without repeating the effect. Reverting Start #2 → End #3 → Delivered #4 to #3 keeps the result and deletes the observation. Its replacement marker survives the next reconstruction; two visible markers remain corruption. Cuts splitting remote-transaction outcomes are rejected.

Durable stream forks are independent agents

A protocol PUT with Stream-Forked-From creates a deterministic phantom agent at {base}/forks/{fork}/invocations/{session}/streams/{slot}. The source executor pins a committed horizon and resolves the opaque cursor plus optional message/byte sub-offset. The fork copies ordinary oplog entries and appends only ForkCut. That marker clips retained stream history, resets live controls, and stores the creation receipt; it carries no handle aliases or terminal-authorship mappings.

18Interrupt, suspend, restart, evict, recover

Everything in this section is the same operation seen from different angles: discard the Store, go round the outer loop. The hints appended beforehand annotate the history for status folding and observers; none of them changes how reconstruction works.

An explicit interrupt retires the cached owner and fences replacement startup. If the worker already unloaded for OOM backoff or permit acquisition, the retiring owner commits the still-unclaimed Interrupted marker and notifies invocation waiters before removal. It does not need a new Store to do this. An interrupt already handled by the invocation loop is not recorded twice, and completed or failed invocations retain their outcome.

Automatic shard-assignment recovery leaves Interrupted workers stopped, even with queued invocations or updates. An executor restart or shard move is not a request to resume them.

A simulated crash (recover_immediately = true) requests Restart for Running, Suspended and Retrying workers; it never permanently interrupts a parked invocation. If no invocation loop remains, the existing promise, scheduler or permit wakeup starts reconstruction. The pending restart neither appends Interrupted nor fails the invocation waiter.

Environment and application deletion invalidate component metadata, environment state and agent type caches before awaiting owner retirement. New metadata lookups see deletion rather than admitting requests against a retiring cached owner.

Scheduled actions

Time-based wake-ups are durable too. ScheduledAction (services/scheduler.rs) covers CompletePromise, ArchiveOplog, Invoke and Resume; the scheduler stores them in indexed storage keyed by time and the owning executor fires them, so a sleeping agent does not need a resident timer to be woken.

19Glossary

Agent
One durable (or ephemeral) instance of an agent type, identified by AgentId; has exactly one oplog.
Call-local repair
Completes an incomplete call's original Start without deleting or repeating completed neighboring effects.
Claim
Matching the host call the guest is making during replay to a recorded Start by identity.
Commit
Processing appended oplog entries at a requested level. Always awaits storage; ephemeral Deferred awaits ordered writer handoff; DurableOnly is a no-op for ephemeral agents.
Cursor
ReplayCursor: the single reader over recorded history during replay.
Durable function type
Four effect classifications: ReadLocal, WriteLocal, ReadRemote, WriteRemote. Nesting uses only parent_start_index; explicit protocol recovery authorization is separate from the type.
Entity body
Guest code (tool sidecar, middleware) that runs in its own Store but records into the owner agent's oplog.
Ephemeral agent
An agent whose state is not recovered after instance loss; RPC to it is at-most-once.
Filesystem snapshot
A copy of an agent's files in the snapshot store. A Snapshot record can name it, and a start uses the snapshot of a Snapshot record only after SnapshotConfirmed. A snapshot-based PendingUpdate names the snapshot of a manual update, which the update uploads before it writes the record.
Fingerprint
AgentFingerprint: minted once at creation; distinguishes incarnations sharing an AgentId.
Hint
An oplog entry that annotates history and is skipped by replay's positional matching.
Idempotency key
The identity of an invocation; derived from the caller's durable position so retries and replays reuse it.
Initial file
A file that the component revision or entity provisioning declares; the initial-file rule installs it. A read-only initial file refuses changes to its contents and times.
Live
The mode in which the guest runs new code and its host calls perform real effects and append to the oplog.
Marker
CompletionDelivered / CompletionDiscarded: records when (or whether) the guest observed a completion.
Oplog
The append-only, indexed journal of an agent's history; the only durable state.
Positional entry
An oplog entry that replay must match in order.
Replay
Re-running the guest from a baseline while feeding it recorded host results instead of performing effects.
Resident state
Anything held in executor memory: Store, instance, caches, queues. Disposable by definition.
Snapshot
A guest-serialised state used as a replay baseline, promoted as the mandatory baseline by snapshot-assisted automatic success, or created fresh to carry state across revisions in a manual update. On an executor with filesystem snapshots, the record can also name a filesystem snapshot.
Store
A Wasmtime store holding one instance and its host context; one per resident incarnation of an agent (plus one per active entity body).
Terminal
The entry that completes a Start: End or Cancelled.
Worker
The executor's resident object for one agent: queue, status cache, invocation loop.
