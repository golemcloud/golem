# Later managed and special-field runtime scenarios

These are required expectations, **not executed acceptance in the static corpus**.
`v1.json` checks source-plan distinctions only. The delivering units add real
runtime tests when their prerequisites exist; no fake managed runtime is used.

| Scenario                           | Inputs and required observations                                                                                                                                                                                                                                                                                       | Delivering units                                                          |
| ---------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| Captured Shared optional absence   | Deploy `Shared<Optional<String>>` without a fill. Read absence. Create a compatible named catalog entry afterward: the same owner still reads absence, including after executor reconstruction. Deploy a new owner revision with an explicit binding and update normally: that owner can now observe the named source. | TC-27, TC-03 and each Shared SDK unit, accepted together in TC-44         |
| Bound null stays live              | Bind the optional field to a named Shared entry containing null. Change that entry to a string. After propagation, fresh reads observe the new value without recapturing the owner. Replay retains recorded results. This must differ from captured absence.                                                           | TC-03, TC-27 and each Shared SDK unit                                     |
| Inheritance and broken bindings    | Omission in a higher owner layer retains an inherited binding. An explicit unknown, wrong-kind or incompatible binding fails instead of reverting to the inherited binding or captured absence. Shared lists and direct Secrets still require bindings.                                                                | TC-27, TC-29 and each Shared SDK unit                                     |
| Identity and revision retention    | Read a named source, delete it and create a compatible same-name replacement. Fresh lookup may select the replacement after propagation; held results, replay and nested Secret IDs retain the identities/revisions already observed.                                                                                  | TC-02, TC-03, TC-04, TC-11 and their SDK consumers                        |
| File paths and retained references | Resolve a File field through the owner mount view; check denied access and reconstruction with retained references. A catalog path is not a filesystem authority.                                                                                                                                                      | TC-08 with its filesystem suppliers; TC-14 conversion acceptance          |
| Bound Tool calls                   | Reflect and invoke a configured Tool with the selected callable target and owner config. Held captures and replay retain target pins; a later fresh selection follows the applicable policy.                                                                                                                           | TC-09 with the First-class tools cutover and second-to-land pin interface |
| Ambient retry rules                | Capture the selected policy name for an ambient operation. Later failures use its current predicate/body without switching names or resetting consumed budgets; explicit held policy values remain pinned.                                                                                                             | TC-10 with recorded retry decisions and affected SDK helpers              |
| Secret/OAuth protected use         | Materialize handles without exposing plaintext; reject missing authority. A valid pending-consent OAuth definition may activate with diagnostics, but protected use sends nothing before authorization.                                                                                                                | TC-11, TC-28 and the outgoing-auth suppliers                              |
| Quota and retention                | Check actual-holder reserve/debt before zero/nonzero shortcuts. Retain state according to the selected retention contract rather than collecting history in config storage.                                                                                                                                            | TC-12, TC-13 with their actual Cards/retention suppliers                  |

TC-15 integrates actual consumer artifacts. TC-16 accepts the assembled feature;
neither static reference delivery nor these listed expectations completes it.
